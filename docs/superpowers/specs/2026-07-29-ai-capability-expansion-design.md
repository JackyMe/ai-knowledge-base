## 1. 背景与目标

`topics/android-to-fullstack.html` 现状是一份"Android 工程师 12 周转 Web 全栈"的定制手册,14 个 section,大篇幅是 Kotlin→TypeScript、Compose→React 这类一对一技术映射表,外加一套绑定具体周数的学习计划。

用户认为这一版内容和结构整体偏弱,要求**彻底重新定位**,而不是修补:

- 不再绑定"Android 工程师"这个起点身份,面向任意技术背景的读者
- "全栈"重新定义为横跨移动端(Android/iOS)、Web(前端)、后端/服务端的多维度能力,不是单指"Web 前端+后端"
- 核心不再是"学一门新语言/框架",而是"怎么用 AI 扩展自己的技术能力边界"这套方法论本身——用什么工具、怎么用、做什么、学什么,要有通用性和强指导性
- 每个环节要按「学什么 / 怎么学 / 用什么 / 怎么用」四问清晰组织,读者一眼能定位到自己需要的信息
- 端到端深度案例给两个入口,不绑死一条路径
- 延续全站"不假大空、每条结论有出处"的调性——是否核实、核实到什么程度,要在内容里如实体现

## 2. 范围决策(头脑风暴过程中已与用户确认)

| 决策点 | 结论 |
|---|---|

| "全栈"的定义 | 移动端(Android/iOS)+ Web 前端 + 后端/服务端,不只是 Web |
| 扩展方向范围 | 聚焦两条:全栈能力(主线)+ 技术型一人公司/独立开发(第二线);不展开 AI/Agent 工程化、DevOps/数据工程这两个方向,只在方法论层面提"这套方法能推广到其他方向" |

| 案例结构 | 两个端到端深度案例入口,读者按自己方向选读,内部结构一致 |
| 章节组织范式 | 每个方法论步骤、每个案例阶段,统一用「学什么 / 怎么学 / 用什么 / 怎么用」四问框架组织 |

## 4. 章节骨架(8 个 section)

### 4.1 `#mindset` 认知框架

- 为什么现在能做到边界扩展:证据是 AI 把"查文档、试错踩坑消耗的时间"压缩到接近零,但"验证产出是否正确"这一步**没有**被压缩——这才是能力扩展路上真正的新瓶颈,不是"学不会新语法"
- 边界扩展 ≠ 无限全能:诚实划出适用边界(哪些扩展 AI 能大幅提效,哪些依赖判断力和经验、AI 只能辅助不能替代)
- 常见误区两条:①以为装个 AI 工具就自动会了新技术栈;②把 AI 产出当真理,不做验证直接用
- 篇幅:短,定调用,不展开方法论细节(方法论在 4.2)

### 4.2 `#engine` 通用方法论:五步扩展引擎

全篇主干。五步:

1. **诊断差距**——先搞清楚"我已经会什么、缺什么",不要从零开始学
2. **AI 知识速通**——用 AI 做概念翻译而不是从头听课,只学阻碍你验证产出的最小概念集
3. **脚手架起步**——用 AI 搭第一个能跑起来的最小产物,建立"手感"
4. **验证闭环**——AI 产出如何验证是对的(测试、对照官方文档、真机/真实环境跑通),这是最容易被跳过但最关键的一步
5. **深化沉淀**——从"能跑"到"理解为什么",把踩过的坑和心智模型沉淀成自己的资产(笔记、模板、复用脚本)

**每一步内部必须用四个小标题组织**(不是自由行文):

- **学什么**——这一步该聚焦的知识范围,明确排除什么(避免读者学过头/学偏)
- **怎么学**——具体方法/技巧,不是"多看文档"这种空话
- **用什么**——具体工具:Claude Code / Codex / 官方文档 / 特定命令行工具等,点名到工具而不是笼统说"AI"
- **怎么用**——可直接照抄的提示词模板或操作步骤

本节还承接原 `#ai-workflow` 章节被引用的两个资产(见第 6 节交叉引用处理):

- 一份通用的"AI 协同配置模板"(相当于原 CLAUDE.md 模板,但改写为面向"学习新技术域"场景,不绑定 Android/Web 具体技术栈)
- 一套六个高频场景的提示词库(沿用原有价值,改写措辞去掉 Android 专属类比)

放在步骤②③④里作为可直接复制的产物,不单独开子节。

### 4.3 `#mapping` 跨域映射技法

独立于任何具体案例的通用技巧:如何把"我已经会的 A 域心智模型"喂给 AI,让 AI 帮你标出两类东西——"这是 A 的翻译"(概念对应,学习成本低)和"这是 A 没有的新概念"(真正要花时间学的)。这是 4.2 步骤②的具体技法展开,值得单独成节是因为它本身是一个可迁移的通用能力,不只用于第一次学习,以后每学一个新域都能重复用。

配 3-4 个**紧凑**示例,每个几行到半屏,不写成完整小节:

- Android ↔ iOS(Kotlin/Compose ↔ Swift/SwiftUI)
- 移动端 → Web 前端(复用原页面 Compose→React 素材的**精华**,大幅精简,降级为示例而非页面主体)
- Web 前端 → 后端/服务端

原 `#method` 章节的"Android 类比提问术(六式)"内容迁移到这里,泛化为通用的"跨域类比提问术",不再绑定 Android 视角。

### 4.4 `#case-studies` 端到端深度案例(两个入口)

一个 section,内部两个 `<h3>` 级深度案例,分别完整走一遍 4.2 的五步方法论,内部同样用「学什么/怎么学/用什么/怎么用」组织每一步。

**"两个入口"的具体实现**:不引入新的 UI 组件(不做 tab 切换器),延续站点现有的纯锚点跳转模式——section 开头放一小段"怎么读这一节"引导,给两个描述性锚点链接(比如"从移动端出发的案例 → 跳到案例 A""从前端出发的案例 → 跳到案例 B"),两个案例的完整内容都在页面里(顺序排列,案例 A 在前),读者可以只读一个也可以都读,不是互斥展示。

- **案例 A:移动端 → Web 全栈**——复用原页面架构层(App Router/服务端组件)、数据层(Room→Supabase/RLS)的高价值内容,改写融入五步框架,不再是独立的"架构层""数据层"章节,而是案例叙事的一部分
- **案例 B:前端/客户端 → 后端与服务端工程**——新写,填补原页面完全没有的"独立后端视角"(API 设计、服务端语言选型、部署与运维基础),同样走五步框架

两个案例不要求同等篇幅——按内容成熟度自然分配,但结构骨架(五步 × 四问)必须一致,保证读者读完任一案例都对方法论有完整体感。

### 4.5 `#indie` 技术型一人公司 / 独立开发

原 `#business` 章节内容(选题五问、收款现实问题、MRR 里程碑表)质量已经不错,精炼保留,不推倒重写。新增一条原来没有的线:**AI 在商业化环节能帮你做什么**(加速验证选题假设、写落地页文案、搭建基础客服/FAQ 自动化),按四问框架组织这一新增部分。

### 4.6 `#learning-system` AI 辅助学习系统

原 `#method` 章节的"三层学习法"与"20 题自测清单"精炼保留,但**去掉对具体技术栈的绑定**(原 20 题是 Android→Web 专属题目),重新定位为"怎么用 AI 帮自己出题、查漏补缺"的通用方法——包括怎么让 AI 根据你当前的学习阶段生成针对性自测题,而不是提供一份固定的题库。

### 4.7 `#pitfalls` 陷阱与心法

原 `#pitfalls` 章节("转型陷阱手册")精炼保留可迁移的部分(多数人卡住不是技术问题这条洞察有价值),新增 AI 时代特有的坑:

- 过度依赖 AI 导致验证环节被跳过(呼应 4.2 步骤④的重要性)
- 把 AI 的自信语气当成正确性证明
- 学习速通变成"从没独立解决过一个真实问题"

### 4.8 `#resources` 资源库

沿用原有 S/A/B 评级体系与表格样式,内容按新定位调整(去掉纯 Android/Next.js 专属资源,替换或补充跨平台学习资源、AI 辅助学习相关资源)。

## 5. 明确不做的事

- 不新增第 9 个 section 存放"AI/Agent 工程化"或"DevOps/数据工程"扩展方向的完整内容——按用户决策,这两个方向只在方法论层面提及"这套方法能推广过去",不深入展开,避免范围失控
- 不保留原页面固定的"12 周"时间盒、周计划表、按周分配的学习包时长估算——这些与"通用"定位冲突
- 不做旧 URL 到新 URL 的重定向(站点无此类基础设施)
- 案例 A、B 不要求逐字对称的篇幅或格式,允许根据内容自然成熟度有差异,但五步框架结构必须一致
