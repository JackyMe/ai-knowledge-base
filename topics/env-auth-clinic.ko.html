방법론 01

5계층 진단법 + 원클릭 진단 스크립트

유일한 진단 원칙: 하위 계층부터 상위 계층으로 순차 확인하고, 한 층의 확인이 끝난 뒤 다음 층으로 넘어갈 것.

L1
바이너리 계층 —— 실제로 실행되는 프로그램은 무엇인가?

which -a claude / which -a codex로 PATH 내 중복 바이너리 확인; claude --version 확인.

L2
환경 변수 계층 —— 동작을 가로채는 변수가 있는가?

env | grep -iE 'anthropic|claude|codex|openai|proxy' 실행. 의도치 않은 ANTHROPIC_API_KEY 확인.

L3
자격 증명 계층 —— 현재 어느 계정으로 인증되어 있는가?

Claude Code 세션 내 /status 실행; Codex는 codex login status 확인.

L4
설정 계층 —— 어떤 계층의 설정이 적용 중인가?

Claude Code: claude doctor 및 /config; Codex: /debug-config 확인.

L5
네트워크 계층 —— API 서버와 정상 통신 가능한가?

curl -sI https://api.anthropic.com 또는 curl -sI https://api.openai.com 연결성 테스트.

원클릭 진단 스크립트 (읽기 전용)

#!/bin/bash
# ai-env-check.sh —— Claude Code / Codex 환경 원클릭 자가진단 (읽기 전용)
# 사용법: bash ai-env-check.sh
echo "═══ L1 바이너리 계층 ═══"
for c in claude codex; do
  if command -v "$c" >/dev/null 2>&1; then
    which -a "$c"; "$c" --version 2>/dev/null | head -1
  else echo "(미설치 또는 PATH에 없음: $c)"; fi
done

echo; echo "═══ L2 환경 변수 계층 ═══"
env | grep -iE 'anthropic|claude|codex|openai|https?_proxy|no_proxy' || echo "(깨끗함: 관련 환경 변수 없음)"

echo; echo "═══ L3/L4 설정 및 디렉토리 ═══"
[ -d ~/.claude ] && echo "Claude Home: ~/.claude (존재함)"
[ -d ~/.codex ] && echo "Codex Home: ~/.codex (존재함)"
echo "═══ 진단 완료 ═══"

자격 증명 우선순위 (높은 순서대로)

Claude Code 03

Claude Code · settings.json 완전 해설: 최소 실행 구성부터 전체 설정 딕셔너리까지

앞 장에서는 "누구의 자격 증명이 유효한가(우선순위)"를 다루었습니다. 이번 장에서는 이 모든 것을 영구적으로 기록하는 파일인 settings.json의 전체 설정 키, 최소 실행 구성, 완전한 예시, 그리고 서드파티 및 계정을 결합하는 구체적인 설정 방법을 다룹니다.

1. 파일 위치 및 덮어쓰기 우선순위

계층파일 위치영향 범위팀 공유
Enterprise 관리서버 배포 / managed-settings.json조직 또는 머신의 전체 사용자가능 (IT 관리 배포)
CLI 커맨드라인 플래그실행 시 --xxx 플래그현재 세션에만 적용 (일시적)불가
프로젝트 로컬.claude/settings.local.json본인 전용, 해당 저장소 한정불가 (자동 gitignore)
프로젝트 공유.claude/settings.json해당 저장소의 전체 협업자가능 (git 추적)
사용자 설정 (최하위)~/.claude/settings.json본인 전용, 전체 프로젝트 공통불가

우선순위는 위 표의 위에서 아래 순서입니다. 즉, Enterprise 관리가 항상 최우선되며, CLI 플래그, 프로젝트 로컬, 프로젝트 공유, 사용자 설정 순으로 적용됩니다. 설정이 반영되지 않는 원인의 90%는 상위 계층에서의 오버라이드 때문입니다. /status의 "Setting sources" 행에서 실제로 로드된 설정을 확인할 수 있으며, claude doctor로 잘못된 필드를 진단할 수 있습니다.

2. 최소 실행 구성

Claude Code는 settings.json이 없어도 정상 작동합니다. 파일이 전혀 없어도 기본값으로 로그인하여 사용할 수 있습니다. 팀을 위한 스타터 템플릿으로 명시적으로 선언할 경우, 다음만으로도 충분합니다:

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json"
}

schema 선언은 런타임 동작에는 영향을 주지 않지만, VS Code나 Cursor에서 편집할 때 자동완성과 유효성 검사를 활성화합니다. 실용적이면서 매우 간결한 스타터 구성 예시:

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}

실전 사례 분석: 증상에서 근본 원인까지

실제 현장에서 가장 자주 발생하는 4가지 고빈도 시나리오를 통해 5계층 진단법의 실제 적용 흐름을 확인해 봅니다. 이 4가지 구조를 이해하면 대부분의 "원인 불명의 오류"를 스스로 해결할 수 있습니다 — 특히 에러 메시지 텍스트와 실제 근본 원인이 얼마나 동떨어져 있는지에 주목하세요.

사례 1 · "Max 회원인데 조직이 비활성화되었다는 오류가 발생합니다"

현장 상황동료에게 인수인계받은 PC에 Claude Code를 새로 설치하고 유료 구독 계정으로 정상 로그인했으나, 프롬프트를 입력하자마자 API Error: 400 "This organization has been disabled" 오류가 발생함. 프로그램을 두 차례 재설치했으나 전혀 개선되지 않음.
진단 과정L1 정상 (단일 설치, 최신 버전); L2에서 원인 발견 — env | grep -i anthropic을 실행하자 ANTHROPIC_API_KEY=sk-ant-…가 검출됨. 확인 결과 ~/.zshrc 파일 내에 이전 사용자가 남겨둔 API 키였으며, 해당 키의 Console 조직은 이미 폐기된 상태였음.
조치 단계변수를 unset 처리하고 rc 파일에서 export 구문 삭제 → 터미널 재시작 → /status에서 Login method가 구독 계정으로 복귀했음을 확인. 소요 시간 3분, 재설치는 전혀 불필요했음.
교훈에러 메시지는 '조직'을 말했고 사용자는 '구독'을 의심했으나, 진짜 원인은 '환경 변수'에 있었습니다 — 에러 메시지는 결과 현상만을 기술할 뿐 근본 원인이 아닙니다. 이것이 L2 문제를 해결할 때 재설치(L1 조치)가 영원히 먹히지 않는 이유입니다.

사례 2 · "VS Code 확장에서만 Invalid API key가 뜨고 터미널은 멀쩡합니다"

현장 상황터미널의 claude는 완벽히 정상 작동하지만, VS Code 확장 프로그램에서는 Invalid API key · Please run /login 팝업이 반복해서 뜨고, 로그인에 성공해도 화면이 검은색으로 멈춤 (anthropics/claude-code#12204에 기록된 전형적 사례).
진단 과정L3 자격 증명 계층 문제로 보이지만 근본 원인은 L2: 머신에 3개의 서로 다른 자격 증명 소스가 동시에 공존하고 있었음 (OAuth 로그인, 수동 설정 API 키, Shell 환경 변수). 터미널이 rc 파일에서 로드한 환경과 VS Code가 GUI로 실행되며 상속받은 환경이 서로 달랐으며, 두 프로세스가 서로 다른 자격 증명을 로드하여 한쪽은 유효하고 한쪽은 무효화됨.
조치 단계자격 증명 소스를 단일화: 모든 ANTHROPIC_* 환경 변수와 수동 API 키를 정리 → CLI와 확장 프로그램 양쪽에서 클린 재로그인 → 양쪽의 /status에서 동일한 구독 계정이 인식되는지 확인.
교훈"터미널은 정상인데 IDE만 이상하다"는 현상은 십중팔구 두 프로세스가 바라보는 환경 변수의 불일치 때문입니다. 자격 증명이 혼재되어 있으면 어떤 프로세스가 어떤 키를 쥐게 될지 예측할 수 없습니다 — 자격 증명 소스는 반드시 단 하나로 단일화하세요.

사례 3 · "아침에 일어나 맥북을 열었더니 모든 세션이 일제히 재로그인을 요구합니다"

현장 상황전날 밤 3개의 병렬 Claude Code 세션을 열어둔 채 노트북을 닫고 취침. 다음 날 아침 절전 모드에서 복귀하자 3개 세션이 일제히 로그인 화면을 띄웠고, 하나를 다시 로그인하면 다른 세션이 튕기는 현상이 반복됨.
진단 과정L2/L3는 깨끗했고, 직관과 달리 L1 버전 계층이 원인이었음: 공식 changelog를 확인한 결과 v2.1.211 이전에 알려진 버그가 있었음 — 절전 복귀 시 여러 세션이 동일 토큰에 대해 동시에 갱신을 시도하며 서로의 인증을 무효화시키는 레이스 컨디션 발생.
조치 단계v2.1.211 이상으로 업데이트 (갱신 로직이 단일 프로세스 조율 방식으로 개선됨), 1회 재로그인한 뒤 완전히 재발하지 않음.
교훈전체적이고 비정상적인 시점에 발생하는 문제는 개인 설정을 의심하기 전에 도구 버전과 릴리스 노트를 확인하세요. 공식 개발팀이 이미 패치한 버그는 로컬 환경을 아무리 조사해도 원인을 찾을 수 없습니다.

사례 4 · "Codex가 CI에서 일주일간 잘 돌다가 갑자기 전체 파이프라인에서 401 에러를 냅니다"

현장 상황ChatGPT 구독 플랜으로 CI를 구성: 로컬의 auth.json을 CI Secret에 등록하고 작업 실행마다 복원하여 사용. 일주일 후 모든 파이프라인에서 일제히 401 오류가 발생하기 시작했고, 로컬에서 파일을 다시 복사해 넣으면 며칠간 정상 작동하다가 다시 깨지는 악순환 반복.
진단 과정L3 자격 증명 계층의 특성: Codex 토큰은 약 8일간 미사용 시 stale 상태가 됩니다. 작업 실행 중 자동 갱신되어 auth.json에 새로 쓰여졌음에도 불구하고, CI 파이프라인이 매 실행 시 Secret의 '최초의 오래된 파일'로 덮어쓰며 복원했기 때문에 자동 갱신 결과가 버려지고 갱신 체인이 끊겨 만료됨.
조치 단계공식 권장 CI 패턴으로 순환 루프 구축: 복원 → 실행 → 갱신된 auth.json을 Secret에 다시 저장; 병렬 작업 간 동일 자격 증명을 공유하지 않도록 격리. 자체 호스팅 러너의 경우 영구 볼륨에 CODEX_HOME을 마운트하여 완전 자동화.
교훈자격 증명은 정적 설정 파일이 아니라 생명주기(상태)를 갖는 동적 개체입니다. "N일 주기로 주기적으로 고장 나는" 문제는 만료되는 리소스의 갱신 체인이 끊어지지 않았는지 확인하세요.
