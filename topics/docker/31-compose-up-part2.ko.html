제31레슨: 실전 배틀(하): 마이크로서비스 3계층(Web + Cache + DB) 완벽 오케스트레이션

이전 레슨에서 우리는 Docker Compose를 이용해 Web과 Redis를 멋지게 연동했습니다. 하지만 현실의 엔터프라이즈 서비스에는 가장 핵심적인 요소가 빠져 있습니다. 바로 관계형 데이터베이스(RDBMS)입니다!

오늘 우리는 마이크로서비스의 완성형 퍼즐을 맞춥니다: PostgreSQL 데이터베이스를 추가하여 클래식한 Web 프론트/API + Redis 캐시 + PostgreSQL 영속화 DB 3계층 아키텍처를 Compose 하나로 완벽하게 엮어보겠습니다.

1. 전체 아키텍처 토폴로지 맵

실제 코드를 작성하기 전에 구축할 전체 시스템의 서비스 토폴로지를 확인해 봅니다:

보안 아키텍처 핵심 요약 외부 인터넷 사용자는 오직 Web 서비스(8080)만 접근할 수 있습니다. Redis와 PostgreSQL은 포트를 호스트 외부에 노출하지 않고, Docker Compose가 생성한 내부 가상 네트워크 안에 완전히 은닉되어 Web 서비스만 통신할 수 있습니다. 또한 데이터 손실을 방지하기 위해 PostgreSQL에 영속 볼륨 pgdata를 마운트합니다.

2. 3계층 통합: 완성된 docker-compose.yml

프로젝트 디렉토리에 작성할 최종 Compose 파일입니다:

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      redis:
        condition: service_started
      db:
        condition: service_healthy
    environment:
      - DB_HOST=db
      - DB_USER=myuser
      - DB_PASS=mypassword
      - REDIS_HOST=redis

  redis:
    image: redis:alpine
    restart: always

  db:
    image: postgres:14-alpine
    restart: always
    environment:
      - POSTGRES_USER=myuser
      - POSTGRES_PASSWORD=mypassword
      - POSTGRES_DB=myapp_db
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser"]
      interval: 5s
      timeout: 5s
      retries: 5

# 최상위 레벨 볼륨 선언
volumes:
  pgdata:
🔍 핵심 문법과 설계 테크닉 분석
  1. 최상위 volumes 선언: 영속 네임드 볼륨 pgdata를 정의하고, db 서비스에 마운트하여 컨테이너가 재생성되어도 DB 데이터가 완벽히 보존됩니다.
  2. 환경 변수 주입 (environment): web 서비스에 DB_HOST=db와 REDIS_HOST=redis를 주입하여 서비스 이름을 DNS 도메인으로 사용합니다.
  3. 궁극의 depends_on + healthcheck (Wait-for-it 패턴): DB 컨테이너가 뜬 직후에는 PostgreSQL 초기화가 진행 중이라 연결이 거부될 수 있습니다. db에 pg_isready 헬스체크를 설정하고, web에 condition: service_healthy를 주어 DB가 실제 쿼리를 받을 수 있는 Healthy 상태가 될 때까지 Web 시작을 대기시키는 가장 완벽하고 우아한 기동 순서 제어를 구현했습니다.

3. 실전 기동과 상태 검사

서비스를 실행하고 상태를 점검해 봅니다:

# 백그라운드로 전체 서비스 기동
$ docker compose up -d

# 프로세스 상태 확인
$ docker compose ps

출력 결과 예시:

NAME                IMAGE                  COMMAND                  SERVICE   CREATED          STATUS                    PORTS
myapp-db-1          postgres:14-alpine     "docker-entrypoint.s…"   db        2 minutes ago    Up 2 minutes (healthy)    5432/tcp
myapp-redis-1       redis:alpine           "docker-entrypoint.s…"   redis     2 minutes ago    Up 2 minutes              6379/tcp
myapp-web-1         myapp-web              "node index.js"          web       2 minutes ago    Up 2 minutes              0.0.0.0:8080->80/tcp

STATUS 열에 데이터베이스가 명확하게 (healthy)로 표시된 것을 볼 수 있습니다.

또한 docker compose exec db psql -U myuser -d myapp_db 명령어로 컨테이너 내부에 즉시 진입하여 SQL 쿼리를 실행해 볼 수 있습니다.

4. 환경별 오버라이드: docker-compose.override.yml

개발 환경과 프로덕션 환경에서 설정을 다르게 유지하고 싶다면 파일을 여러 개 복사할 필요 없이 docker-compose.override.yml을 활용합니다. Compose는 실행 시 기본 파일과 override 파일을 자동으로 병합합니다:

# docker-compose.override.yml (로컬 개발용 설정)
services:
  web:
    volumes:
      - .:/app              # 로컬 코드를 바인드 마운트하여 핫 리로딩 활성화
    environment:
      - NODE_ENV=development
⚠️
데이터 삭제 주의 경고 일반적인 docker compose down은 컨테이너와 네트워크만 삭제하고 볼륨 데이터는 안전하게 보존합니다. 하지만 -v 옵션을 붙인 docker compose down -v를 실행하면 마운트된 네임드 볼륨까지 영구 삭제되어 데이터베이스 내용이 완전히 소실되므로 프로덕션에서는 절대 함부로 사용해서는 안 됩니다!
🚨 트러블슈팅 응급실
Q1: Web 시작 시 "Connection refused" 오류가 발생하며 데이터베이스 연결에 실패합니다.
A: 가장 흔한 시작 타이밍 이슈입니다! 단순 depends_on은 프로세스 기동만 기다리므로 PostgreSQL 초기화 중에 Web이 요청을 보낸 것입니다. 위의 예제처럼 healthcheck와 condition: service_healthy를 반드시 함께 설정하세요.
Q2: 데이터 볼륨 권한 거부(Permission denied)가 발생합니다.
A: PostgreSQL은 내부에서 postgres 비특권 계정으로 실행됩니다. Docker Named Volume을 사용할 때는 Docker가 권한을 자동으로 맞춰주지만, 호스트 폴더를 바인드 마운트한 경우 호스트 폴더 소유권을 chown -R 999:999 등으로 적절히 변경해 주어야 합니다.

프로의 팁 (Pro Tip): docker-compose.yml 안에 DB 비밀번호를 평문으로 하드코딩해 두는 것은 Git에 커밋될 위험이 있어 매우 위험합니다. 다음 레슨에서는 비밀번호와 시크릿 키를 안전하게 보호하는 .env 파일 관리 기법을 배웁니다.
