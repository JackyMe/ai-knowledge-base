13. 资源枷锁：防 OOM 宕机

💥 一场由 Java 引起的惨案

有一次，小明负责维护一台 16GB 内存的服务器，上面跑了几个简单的 Node.js 前端，以及一个刚刚上线的外包 Java 爬虫系统。

下午三点，服务器突然报警，接着 SSH 彻底连不上了！小明只能去云控制台强制重启服务器。重启后一看监控，那个 Java 爬虫系统发生了严重的内存泄漏，像一个黑洞一样吞噬了所有的 16GB 内存。Linux 系统的内存防线崩溃，连维持基础通信的 SSH 服务都被操作系统无情杀死了。

“明明把它装在 Docker 容器里了，怎么还能把宿主机搞死？”小明百思不得其解。

一、揭开容器“资源无限”的假象

新手常常有一个误区，以为容器就是虚拟机，资源是天然隔离的。错！

默认情况下，Docker 容器对资源的索取是没有任何限制的！只要宿主机有 100 个 CPU 核心，1TB 的内存，一个失控的容器程序就能把它们全部吃光。这就是为什么在生产环境中，给容器加“资源枷锁”是第一铁律。

Docker 是通过 Linux 内核的 Cgroups (Control Groups) 技术来限制资源的。我们可以精准地控制每个容器能用多少内存，多少 CPU。

二、戴上枷锁：限制内存 (Memory Limits)

防 OOM (Out Of Memory) 宕机最关键的就是限制内存。使用 -m 或 --memory 参数：

# 限制这个 Java 容器最多只能使用 512MB 内存
docker run -d --name java-app -m 512m my-java-image

你可以使用 m (兆字节) 或者 g (吉字节) 作为单位。

🧠
Swap 的隐形陷阱

如果你只设置了 -m 512m，Docker 实际上会默认给这个容器分配 512MB 的物理内存，外加 512MB 的 Swap（虚拟内存）！这意味着它其实能用 1GB！
如果你想让限制极其严格，一点 Swap 都不给它用，你需要同时设置 --memory-swap 等于物理内存大小：
--memory 512m --memory-swap 512m

超限了会怎样？

如果容器里的程序不断吃内存，达到了你设置的 512MB 上限，会发生什么？
宿主机的 Linux 内核会毫不留情地触发 OOM Killer，直接一刀把这个容器内的进程砍死！
这时候你去看 docker ps -a，会发现这个容器退出了，状态码是可怕的 Exited (137)。只要看到 137，100% 就是因为 OOM 被杀了。

可以用下面这条命令一秒确诊是不是被 OOM 杀死的：

docker inspect --format='{{.State.OOMKilled}}' java-app
# 如果输出 true，那就是被制裁了。

三、戴上枷锁：限制 CPU (CPU Limits)

CPU 的限制通常有两种思路：绝对限制和相对权重。

1. 绝对限制 (--cpus)

这是最直观的限制方式，明确告诉容器最多能用几个核：

# 无论宿主机有多少个核，这个容器最多只能用 1.5 个核的算力
docker run -d --name math-app --cpus="1.5" my-image

2. 相对权重 (--cpu-shares)

这是一种更弹性的玩法。默认每个容器的 shares 值是 1024。如果你有 A 和 B 两个容器，你给 A 设置了 2048，B 保持默认。当系统 CPU 闲置时，大家随便用；但当 CPU 100% 满载，大家抢占资源时，A 能分到的算力将是 B 的两倍！

docker run -d --name priority-app --cpu-shares 2048 my-image
pie title CPU 满载抢占时的资源分配 (--cpu-shares) "App A (权重 2048)" : 66.6 "App B (权重 1024)" : 33.3

四、实时查看限制效果

限制加好了，怎么看有没有生效？祭出 docker stats 命令。你会发现，LIMIT 这一列不再是宿主机的总内存，而是你设置的上限了！

CONTAINER ID   NAME       CPU %     MEM USAGE / LIMIT     MEM %
a1b2c3d4e5f6   java-app   0.12%     120MiB / 512MiB       23.4%
🚑 踩坑自救室
Q1: 我的 Java 程序加了 Docker 内存限制后，疯狂崩溃 (Exit 137)！
A: Java 虚拟机 (JVM) 有自己管理内存的机制 (Heap Size)。在老版本的 JDK 8 中，JVM 不知道自己身处容器中，它会读取宿主机的总内存来计算默认 Heap 大小，结果远远超出了 Docker 的限制，直接被杀。解决方案是：给 Java 启动参数加上 -XX:MaxRAMPercentage=75.0，让 JVM 根据容器限制按比例分配合理内存，或者升级到 JDK 11+（已原生适配 Docker）。
🚀
Pro-tip / 老鸟技巧：如何评估合理的 Limit 值？

千万不要一开始就凭感觉瞎设限制！标准的姿势是：
1. 先不设限制，让程序在测试环境裸奔，跑满压测。
2. 观察 docker stats 的峰值数据。
3. 在峰值的基础上上浮 20%~30%，作为最后的 Limit 值。
（如果是 Node.js/Python 这种单线程模型，CPU 设 1 就够；如果是多线程或 Go 程序，根据并发量放大 CPU）。
