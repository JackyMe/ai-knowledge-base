Lesson 23: Ultimate Lifesaver: Docker Volumes

In our last lesson, we learned that containers are ephemeral creatures—one careless docker rm and your database vanishes into the void. Today, we'll discover Docker's built-in vault: Data Volumes.

A Volume is a dedicated storage area managed completely by Docker on the host filesystem. Think of a container like a rental apartment: you can cancel your lease and move out at any time (deleting the container), but you keep your valuable jewels (database data) in an external bank safe deposit box (Volume). No matter how many apartments you switch between, as long as you have the key to the vault, your data remains 100% safe and intact.

Everyday Operations: Volume CRUD

Let's first learn how to manage these storage vaults independently.

# 1. Create a named volume: my-data
docker volume create my-data

# 2. List all existing volumes on the host
docker volume ls
# DRIVER    VOLUME NAME
# local     my-data

# 3. Inspect details: find where this volume lives on host disk
docker volume inspect my-data
# Output contains: "Mountpoint": "/var/lib/docker/volumes/my-data/_data"
# That is the real physical directory path on your host!

Hands-on Rescue Mission: Guaranteeing MySQL Immortality

Let's use a real MySQL database container to demonstrate how Volumes safeguard data across container destructions.

🛡️ Walkthrough: The Immortal Database

Step 1: Start MySQL attached to our Volume
We use the -v flag to mount the my-data volume into MySQL's internal default data storage path: /var/lib/mysql.

docker run -d --name db-test -e MYSQL_ROOT_PASSWORD=123456 -v my-data:/var/lib/mysql mysql:8.0

Step 2: Write some database records
Enter the container, connect to MySQL, and create a new database.

docker exec -it db-test bash
root@xxxx:/# mysql -u root -p123456
mysql> CREATE DATABASE test_save_me;
mysql> exit
root@xxxx:/# exit

Step 3: Simulate catastrophic destruction
A junior dev accidentally forces the deletion of the container!

docker rm -f db-test

Step 4: Rebirth from the ashes
Don't panic! Because our my-data volume still exists on the host, we simply start a brand new container mounting the same volume:

docker run -d --name db-new -e MYSQL_ROOT_PASSWORD=123456 -v my-data:/var/lib/mysql mysql:8.0

Log in and inspect—the test_save_me database is sitting right there, completely unharmed! That's the power of Docker Volumes.

Anonymous Volumes vs. Named Volumes

You may sometimes encounter VOLUME /data inside a Dockerfile or run -v /data (with no volume name specified before a colon). This creates an Anonymous Volume with an auto-generated hash string (e.g. b9f8e21...).

Recommendation: In production, always use Named Volumes. Anonymous volumes easily become unidentifiable orphaned clutter on your disks.

💡
Pro-Tip: Read-Only Volume Mounts When you want a container to read configuration or data files without any permission to modify them, append :ro (Read-Only) to the mount target.
For example: docker run -v my-config:/app/config:ro nginx
Any write attempt from inside the container will immediately trigger a Permission Denied error.
🚑 Pitfall Rescue Room
Q: Error "volume my-data is in use" when trying to delete a volume?
A: As long as any container (even a stopped container) references the volume, Docker refuses deletion to protect your data. Run docker ps -a to identify and remove (docker rm) the referencing containers first, then delete the volume with docker volume rm my-data.
Q: My disk is filling up with random orphaned hash volumes. How do I clean them?
A: Run docker volume prune. This is a cleanup command that purges all volumes **currently not attached to any container**. Make sure all your critical data volumes are actively mounted before running this!
