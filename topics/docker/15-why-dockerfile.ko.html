15. 수동 환경 설정과 작별하기

😭 "제 컴퓨터에서는 잘 되는데요?"

개발자 김 대리는 꼬박 3일에 걸쳐 복잡한 라이브러리와 환경변수를 설정하고 로컬에서 프로젝트 빌드를 성공시켰습니다. 그러나 신규 입사한 동료에게 코드를 전달하자, 의존성 충돌과 환경 차이로 인해 온종일 에러를 뿜어내며 실행되지 않았습니다.

김 대리는 "귀신이 곡할 노릇이네, 내 컴퓨터에서는 완벽하게 돌아가는데!"라며 답답해했습니다.

문제를 해결하고자 김 대리는 Docker를 도입했습니다. 빈 Ubuntu 컨테이너를 띄우고 들어가서 수동으로 apt-get 패키지를 깔고 라이브러리를 설치한 뒤, docker commit으로 수 기가바이트짜리 대형 이미지를 만들어 동료에게 전달했습니다. 동료 컴퓨터에서도 즉시 실행되었습니다!

하지만 한 달 뒤 Node.js 런타임 버전을 업그레이드해야 하는 상황이 오자, 김 대리는 아무런 주석도 기록도 없는 그 거대한 '블랙박스 이미지' 앞에서 멘붕에 빠졌습니다: "내가 그때 이 컨테이너 안에 도대체 무슨 명령어를 쳤었더라...?"

1. 수동 조작의 한계와 안티패턴 (docker commit의 함정)

컨테이너 내부에 직접 들어가 수동으로 명령을 실행하고 docker commit으로 이미지를 굽는 방식은 Docker 생태계의 절대적인 안티패턴(Anti-pattern)입니다. 이 방식으로 만들어진 이미지는 내부 히스토리를 알 수 없는 블랙박스가 되어 다음과 같은 치명적인 문제를 낳습니다:

  • 추적 불가 (Untrackable): 어떤 패키지가 어떤 버전으로 설치되었는지 문서화되지 않습니다.
  • 재현 불가 (Irreproducible): 기본 환경을 다시 구축하거나 업그레이드할 때 똑같은 이미지를 다시 만들 수 없습니다.
  • 버전 제어 불가: Git에 올려서 변경사항(Diff)을 코드 리뷰할 수 없습니다.

이 문제를 근본적으로 해결하기 위해 탄생한 것이 바로 Dockerfile입니다.

2. 코드형 인프라 (Infrastructure as Code, IaC)의 혁신

Dockerfile은 확장자가 없는 순수 텍스트 파일(Dockerfile)입니다. 이미지 빌드 과정을 한 줄 한 줄 선언해 둔 '이미지 제작 레시피'입니다.

Docker 엔진은 이 레시피를 전달받아 지치지 않는 요리사처럼 정확하고 일관되게 이미지를 자동으로 구워냅니다. 이를 통해 소프트웨어 공학의 정수인 IaC(Infrastructure as Code)를 완벽하게 실현할 수 있습니다:

  • 가독성 및 투명성: 환경 구축의 모든 과정이 코드로 명확히 기록됩니다.
  • Git 버전 관리: 소스 코드와 함께 Git 저장소에 커밋되어, 코드 브랜치와 인프라 환경이 완벽히 동기화됩니다.
  • 100% 멱등성(재현성): 전 세계 누구라도 동일한 Dockerfile을 빌드하면 100% 동일한 실행 환경이 보장됩니다.
  • 레이어 캐싱(Layer Caching): 명령어 단위로 빌드 결과를 캐싱하여 코드 한 줄 수정 시 수 초 만에 초고속 재빌드가 가능합니다.

3. 수동 작업 vs Dockerfile 비교 (Python 웹 애플리케이션)

❌ 구시대 수동 조작 (Blackbox)

# 1. 베이스 이미지 다운로드
docker pull python:3.9-slim

# 2. 임시 컨테이너 접속
docker run -it python:3.9-slim bash

# 3. 셸 안에서 수동 입력
mkdir /app
cd /app
# 호스트에서 코드를 수동 복사
pip install -r requirements.txt
python app.py

# 4. 종료 후 이미지 수동 커밋
docker commit <container-id> my-app

✅ 현대 표준 (Dockerfile)

# Dockerfile 이라는 이름의 파일 작성

FROM python:3.9-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]

4. 레시피를 이미지로 변환하기: docker build

Dockerfile 작성을 마친 후, 해당 파일이 위치한 디렉터리에서 단 한 줄의 명령어로 이미지를 빌드합니다.

# -t : 생성될 이미지 이름과 태그 지정
# 마지막 . : 현재 디렉터리를 빌드 컨텍스트로 전달
docker build -t my-python-app:v1 .

🚑 트러블슈팅 구조대
Q: 빌드할 때 COPY 명령에서 "no such file or directory" 에러가 발생합니다. 절대 경로를 적었는데 왜 못 찾나요?
A: 빌드 명령어 마지막에 붙는 .은 빌드 컨텍스트(Build Context)를 의미합니다. Docker Client는 이 디렉터리 하위의 파일들만 묶어서 백엔드 Docker 데몬에 전달합니다. 따라서 COPY /Users/apple/Desktop/file.txt /app처럼 컨텍스트 디렉터리 바깥에 있는 절대 경로는 보안 및 격리 원칙상 절대 참조할 수 없습니다. 복사할 파일은 반드시 Dockerfile이 위치한 프로젝트 폴더 내부에 있어야 합니다.
🚀
보안 팁: 불필요한 대용량 파일 및 민감 정보 전송 방지 docker build .를 실행하면 현재 디렉터리의 모든 파일이 데몬으로 전송됩니다. 만약 디렉터리 안에 .git 폴더, 수백 MB의 node_modules, 비밀번호가 적힌 .env 파일이 있다면 빌드 속도가 느려질 뿐만 아니라 보안상 치명적인 이미지 유출 사고로 이어질 수 있습니다.
