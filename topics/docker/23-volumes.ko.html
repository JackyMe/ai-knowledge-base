제23레슨: 궁극의 데이터 보호: 볼륨(Volumes)

이전 레슨에서 우리는 컨테이너가 "단명"하는 존재이며, 부주의하게 docker rm을 실행하면 데이터가 허공으로 날아가 버린다는 것을 배웠습니다. 오늘은 Docker 세계의 든든한 "금고"——데이터 볼륨(Volumes)을 배웁니다.

데이터 볼륨은 Docker 엔진이 직접 관리하는 호스트 머신의 특별한 독립 스토리지 공간입니다. 비유하자면 컨테이너는 언제든 계약이 만료되어 비워줄 수 있는 "월세방"이고, 볼륨은 Docker가 관리하는 "잠금장치가 달린 지하 전용 창고"입니다. 당신이 월세방을 몇 번이나 옮기거나 철거하더라도, 지하 창고의 열쇠만 잘 쥐고 있다면 소중한 보물(데이터베이스 데이터)은 영원히 안전하게 보존됩니다.

일상적인 볼륨 관리 명령어 (생성·조회·검사·삭제)

먼저 이 "지하 창고"들을 단독으로 관리하는 기본 명령어를 살펴보겠습니다.

# 1. 생성: my-data라는 이름의 볼륨 생성
docker volume create my-data

# 2. 목록 확인: 현재 시스템에 존재하는 볼륨 목록 조회
docker volume ls
# DRIVER    VOLUME NAME
# local     my-data

# 3. 상세 정보 확인: 볼륨이 호스트 실제 디스크 어디에 위치하는지 검사
docker volume inspect my-data
# 출력 내용 중 "Mountpoint": "/var/lib/docker/volumes/my-data/_data"
# 이것이 호스트 머신 상의 실제 물리 저장 경로입니다!

실전 데이터 수호전: MySQL 데이터 영생시키기

실제 MySQL 데이터베이스 컨테이너를 통해 볼륨이 데이터를 어떻게 완벽히 지켜내는지 실습해 봅니다.

🛡️ 실습 시나리오: MySQL 데이터의 불사신 생명력

1단계: 볼륨을 장착한 MySQL 컨테이너 실행
-v 옵션을 사용하여 방금 만든 my-data 볼륨을 MySQL의 기본 데이터 저장 경로인 /var/lib/mysql에 마운트합니다.

docker run -d --name db-test -e MYSQL_ROOT_PASSWORD=123456 -v my-data:/var/lib/mysql mysql:8.0

2단계: 데이터베이스 생성 및 데이터 저장
컨테이너 내부에 접속하여 MySQL에 새로운 데이터베이스를 만듭니다.

docker exec -it db-test bash
root@xxxx:/# mysql -u root -p123456
mysql> CREATE DATABASE test_save_me;
mysql> exit
root@xxxx:/# exit

3단계: 가차 없는 컨테이너 삭제
운영자의 실수로 컨테이너가 강제 삭제되었다고 가정합니다!

docker rm -f db-test

4단계: 불사조처럼 부활한 데이터
당황할 필요가 없습니다. my-data 볼륨이 온전히 살아있기 때문입니다. 새로운 MySQL 컨테이너를 실행하면서 동일한 my-data 볼륨을 같은 경로에 마운트합니다:

docker run -d --name db-new -e MYSQL_ROOT_PASSWORD=123456 -v my-data:/var/lib/mysql mysql:8.0

새 컨테이너에 접속해 보면 우리가 만들었던 test_save_me 데이터베이스가 마법처럼 온전히 보존되어 있는 것을 확인할 수 있습니다! 이것이 바로 Volume의 강력한 힘입니다.

익명 볼륨(Anonymous) vs 네임드 볼륨(Named)

간혹 Dockerfile 안에 VOLUME /data가 적혀 있거나, 실행 시 -v /data(콜론 앞 대상이 없음)처럼 실행하는 경우가 있습니다. 이것이 바로 익명 볼륨입니다. Docker가 무작위 해시 문자열(예: b9f8e...)로 이름을 자동 생성하여 마운트합니다.

권장사항: 프로덕션 환경에서는 반드시 명확한 의미가 있는 네임드 볼륨(Named Volume)만 사용하세요. 익명 볼륨은 컨테이너 삭제 후 주인을 잃은 디스크 쓰레기로 방치되기 쉽습니다.

💡
프로의 팁 (Pro Tip): 읽기 전용(:ro) 마운트 컨테이너가 설정 파일 등을 읽기만 하고 절대 수정하지 못하게 강제하고 싶다면 마운트 경로 뒤에 :ro(Read-Only) 플래그를 붙이세요.
예시: docker run -v my-config:/app/config:ro nginx
이렇게 하면 컨테이너 내부에서 파일을 수정하려 할 때 즉시 Permission Denied 에러가 발생하여 설정 오염을 방지합니다.
🚨 트러블슈팅 응급실
Q1: "volume my-data is in use" 에러가 발생하면서 볼륨이 삭제되지 않습니다.
A: 해당 볼륨을 참조하고 있는 컨테이너(정지된 컨테이너 포함)가 하나라도 존재하면 Docker는 데이터 보호를 위해 볼륨 삭제를 차단합니다. docker ps -a로 참조 중인 컨테이너를 찾아 docker rm으로 먼저 삭제한 뒤 docker volume rm my-data를 실행하세요.
Q2: 디스크 용량이 부족한데 사용하지 않는 익명 볼륨들을 한 번에 청소하려면 어떻게 하나요?
A: docker volume prune 명령어를 실행하세요. 이 명령어는 **현재 어떤 컨테이너에서도 사용되지 않는 모든 볼륨**을 일괄 삭제합니다. 실행 전 반드시 필요한 볼륨이 컨테이너에 연결되어 있는지 재확인하세요.

볼륨을 마스터하면 어떤 데이터베이스도 영구적인 생명력을 얻게 됩니다. 하지만 개발 중 코드를 자주 수정해야 할 때 매번 볼륨으로 복사하는 것은 비효율적입니다. 다음 레슨에서는 개발 생산성을 극대화하는 신기술——바인드 마운트(Bind Mounts)를 알아보겠습니다.
