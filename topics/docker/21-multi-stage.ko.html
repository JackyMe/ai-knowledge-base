제21레슨: 궁극의 경량화: 멀티 스테이지 빌드

당신이 멋진 전원주택을 짓는다고 상상해 보세요. 전통적인 건축 방식에 비유하자면, 집을 다 지은 뒤 벽돌, 시멘트, 레미콘 트럭, 비계 파이프, 심지어 인부들의 침대까지 완성된 거실에 그대로 둔 채 집주인에게 열쇠를 넘기는 것과 같습니다. 집주인이 문을 열었더니 거실 한가운데 레미콘 트럭이 주차되어 있는 꼴입니다!

상상만 해도 황당하죠? 하지만 Docker 세계에서 수많은 초보 개발자들이 실제로 이런 실수를 저지릅니다. 컴파일러, 테스트 도구, 소스코드 전체를 최종 배포 이미지에 몽땅 담아버리는 것입니다. 고작 15MB짜리 Go 컴파일 바이너리 하나를 실행하기 위해 Docker 이미지 용량이 800MB를 훌쩍 넘는 이유가 바로 여기에 있습니다.

왜 이미지가 이렇게 거대해질까요?

안 좋은 작성 예시를 살펴보겠습니다. Go 언어로 간단한 웹 서버를 작성한 뒤 다음과 같이 Dockerfile을 작성했습니다:

# 안 좋은 예시: 단일 스테이지 빌드
FROM golang:1.20
WORKDIR /app
COPY . .
RUN go build -o myapp main.go
CMD ["./myapp"]

빌드를 완료하고 이미지 용량을 확인하면 깜짝 놀라게 됩니다:

docker images | grep myapp
myapp       latest      a1b2c3d4e5f6   About a minute ago   850MB

왜 이렇게 클까요? golang:1.20 베이스 이미지 자체가 완전한 Linux OS 환경, Go 컴파일러, 표준 라이브러리, 개발 도구 세트를 전부 포함하고 있기 때문입니다. 하지만 실제로 실행에 필요한 것은 컴파일된 단일 바이너리 파일뿐이며, 무거운 컴파일러 도구들은 런타임에 전혀 필요하지 않습니다.

멀티 스테이지 빌드: 필요한 결과물만 챙기기

멀티 스테이지 빌드(Multi-stage Build)는 건축 과정과 완성된 건물을 분리하는 기술입니다. 1단계(공사 현장 Builder)에서 코드를 컴파일하고, 2단계(입주 단계 Production)에서는 컴파일된 바이너리 실행 파일만 가져오고 나머지 도구는 모두 버립니다.

flowchart LR
    subgraph S1 ["1단계: 건축 현장 Builder"]
        A["베이스 이미지 golang:1.20"] --> B["소스코드 복사"]
        B --> C["go build 실행"]
        C -.-> D{"바이너리 실행파일 생성"}
    end
    
    subgraph S2 ["2단계: 인테리어 완료 Production"]
        E["초경량 베이스 alpine"] --> F["1단계에서 바이너리만 복사"]
        D ==> F
        F --> G["최종 이미지: 단 20MB!"]
    end

실전 사례: Go 언어 프로젝트의 궁극의 다이어트

멀티 스테이지 빌드를 적용하여 Dockerfile을 리팩토링해 보겠습니다:

🛠️ 실습 단계: 멀티 스테이지 Dockerfile 작성
# 1단계: 빌드 환경 (builder로 명명)
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
# alpine 호환을 위해 CGO 비활성화 및 정적 링크 컴파일
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp main.go

# 2단계: 프로덕션 런타임 환경 (초경량 alpine 이미지 사용)
FROM alpine:latest
WORKDIR /root/
# builder 단계에서 생성된 바이너리 결과물만 복사
COPY --from=builder /app/myapp .
# 실행 권한 부여
RUN chmod +x myapp

CMD ["./myapp"]

AS builder와 COPY --from=builder라는 두 가지 핵심 문법에 주목하세요. AS는 1단계에 별칭을 부여하고, --from은 마치 차원 이동 포털처럼 1단계의 빌드 결과물만 2단계로 쏙 가져옵니다.

다시 빌드한 뒤 이미지 크기를 비교해 보겠습니다:

docker build -t myapp:slim .
docker images | grep myapp
myapp       slim        b2c3d4e5f6g7   About a minute ago   22.4MB
myapp       latest      a1b2c3d4e5f6   10 minutes ago       850MB

850MB에서 22MB로 무려 38배나 용량이 줄어들었습니다! 디스크 공간을 절약할 뿐만 아니라 쿠버네티스나 클라우드 배포 시 이미지 풀(Pull) 시간이 획기적으로 단축되어 스케일아웃 속도가 비약적으로 빨라집니다.

Java 프로젝트도 날씬하게: Maven + JRE 조합

Go뿐만 아니라 무거운 Java 애플리케이션 역시 멀티 스테이지 빌드가 필수적입니다. 빌드 시에는 Maven이나 Gradle이 필요하지만, 런타임에는 가벼운 JRE 환경만 있으면 충분합니다.

# 1단계: Maven으로 jar 빌드
FROM maven:3.8.6-openjdk-11 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# 2단계: 경량 JRE 런타임으로 실행
FROM eclipse-temurin:11-jre-alpine
WORKDIR /app
COPY --from=build /app/target/myapp.jar .
CMD ["java", "-jar", "myapp.jar"]
💡
프로의 팁 (Pro Tip): scratch를 활용한 극한의 0바이트 베이스 Go나 Rust처럼 완전한 정적 링크 바이너리를 컴파일할 수 있는 언어는 2단계 베이스 이미지로 FROM scratch를 사용할 수 있습니다. scratch는 Docker의 내장된 완전한 빈(0바이트) 가상 베이스입니다. 운영체제 파일조차 없이 오직 단일 바이너리만 포함되므로 보안성과 크기 모두 극대화됩니다. 단, 쉘(sh/bash)이 없으므로 컨테이너 내부 진입 디버깅은 제한됩니다.
🚨 트러블슈팅 응급실
Q1: 컨테이너 실행 시 "/bin/sh: ./myapp: not found" 에러가 납니다. COPY는 분명히 성공했는데요?
A: 99%는 1단계에서 컴파일된 바이너리가 glibc 동적 라이브러리에 의존하고 있는데, 2단계의 alpine 이미지는 musl libc를 사용하기 때문입니다. 해결법: Go 컴파일 시 CGO_ENABLED=0 플래그를 추가하여 정적 바이너리로 빌드하거나, 2단계 베이스 이미지를 alpine 대신 debian:buster-slim 등으로 변경하세요.
Q2: 멀티 스테이지 빌드 속도가 너무 느리고 매번 의존성을 처음부터 다시 다운로드합니다.
A: 제19레슨에서 배운 레이어 캐시를 적용하세요. 1단계에서 go.mod와 go.sum(또는 Java의 pom.xml)을 먼저 COPY하고 의존성 다운로드 명령을 먼저 실행한 후 실제 소스코드를 COPY해야 의존성 변경이 없을 때 즉시 캐시를 타게 됩니다.

멀티 스테이지 빌드는 Dockerfile 작성의 진정한 실력을 가르는 분수령입니다. 이를 완벽히 마스터하면 군더더기 없는 초경량 고성능 이미지를 손쉽게 제작할 수 있습니다.
