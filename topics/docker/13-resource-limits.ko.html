13. 리소스 제한: OOM 서버 다운 방지

💥 실제 장애 사례: 메모리 누수로 서버 전체 먹통

16GB 메모리를 장착한 단일 호스트 서버에 Node.js 프론트엔드 컨테이너와 새로 개발한 Java 크롤러 컨테이너를 함께 올려 운영하고 있었습니다.

어느 날 오후, 서버로부터 긴급 알림이 오더니 SSH 원격 접속마저 완전히 끊어졌습니다. 클라우드 관리 콘솔에 들어가 강제 재부팅 후 확인해 보니, Java 애플리케이션에서 발생한 심각한 메모리 누수로 인해 서버의 16GB RAM 전체가 고갈되었습니다. 결국 Linux 커널의 핵심 통신 데몬(sshd 등)까지 강제 종료되면서 서버 전체가 다운된 것이었습니다.

"컨테이너로 격리해서 돌렸는데, 왜 호스트 OS 전체가 뻗어버렸을까?"

1. "컨테이너는 자원이 자동 격리된다"는 착각

초심자들은 컨테이너가 가상머신(VM)처럼 물리 자원을 미리 분할받아 격리되어 동작한다고 생각하지만 이는 심각한 오해입니다.

기본 설정 상태의 Docker 컨테이너는 호스트의 모든 자원(CPU, RAM)을 무제한으로 사용할 수 있습니다. 호스트 서버가 128코어에 512GB RAM을 갖고 있다면, 제어되지 않은 단 하나의 불량 컨테이너가 전체 자원을 독점하여 호스트 시스템을 파괴할 수 있습니다. 따라서 프로덕션 환경에서 리소스 상한선(Limit)을 설정하는 것은 필수 철칙입니다.

Docker는 Linux 커널의 Cgroups (Control Groups) 서브시스템을 통해 정밀하게 하드웨어 자원을 제한합니다.

2. 메모리 제한 (Memory Limits): OOM 방어

서버 메모리 고갈(Out Of Memory)을 막기 위해 -m 또는 --memory 옵션을 사용합니다.

# Java 컨테이너의 최대 메모리 사용량을 512MB로 엄격히 제한
docker run -d --name java-app -m 512m my-java-image

단위로는 m (메가바이트) 또는 g (기가바이트)를 지정할 수 있습니다.

🧠
스왑(Swap) 메모리의 숨겨진 함정

만약 -m 512m만 단독으로 지정하면, Docker는 기본적으로 512MB의 물리 메모리 외에 추가로 512MB의 Swap 가상 메모리를 컨테이너에 허용합니다 (총 1GB 사용 가능).
Swap 메모리 사용을 원천 차단하고 엄격하게 512MB로 고정하고 싶다면 --memory-swap을 물리 메모리 상한과 동일하게 설정해야 합니다:
--memory 512m --memory-swap 512m

메모리 제한을 초과하면 어떻게 되는가? (Exit 137의 비밀)

컨테이너 내부 프로세스가 지정된 512MB 메모리 한계치를 넘어서면, Linux 커널의 OOM Killer가 작동하여 해당 프로세스를 즉시 사살합니다.
이때 docker ps -a를 확인하면 컨테이너가 Exited (137) 종료 코드로 멈춰 있는 것을 볼 수 있습니다. (128 + SIGKILL 9 = 137이며, 137 코드는 99% 확률로 OOM 강제 종료를 의미합니다).

다음 명령어로 OOM Killer에 의해 종료되었는지 즉시 판별할 수 있습니다:

docker inspect --format='{{.State.OOMKilled}}' java-app
# 출력값이 true 라면 메모리 초과로 강제 종료된 것입니다.

3. CPU 사용량 제한 (CPU Limits)

CPU 제한은 크게 절대 수치 제한과 상대적 가중치 배분의 두 가지 방식을 지원합니다.

1. 절대 코어 할당 (--cpus)

가장 명확하고 직관적인 방식입니다. 호스트 머신의 전체 코어 수와 무관하게 컨테이너가 사용할 수 있는 최대 CPU 코어 환산량을 지정합니다.

# 호스트 코어 수와 관계없이 최대 1.5개의 CPU 연산량만 허용
docker run -d --name math-app --cpus="1.5" my-image

2. 상대적 가중치 배분 (--cpu-shares)

기본값은 1024입니다. CPU가 유휴 상태일 때는 자유롭게 쓰다가, 시스템 CPU 부하가 100%에 도달하여 컨테이너 간에 자원 쟁탈전이 벌어질 때 가중치 비율에 따라 연산력을 분배합니다.

docker run -d --name priority-app --cpu-shares 2048 my-image
pie title CPU 100% 포화 시 자원 배분 비율 (--cpu-shares)
    "핵심 서비스 컨테이너 (shares 2048)" : 66.6
    "일반 백그라운드 작업 (shares 1024)" : 33.3

4. 실시간 리소스 제한 모니터링: docker stats

제한 정책이 정상적으로 적용되었는지 확인하려면 docker stats 명령어를 실행합니다. LIMIT 컬럼에 호스트 전체 사양이 아닌 우리가 지정한 512MiB 한계치가 표시되는 것을 볼 수 있습니다.

CONTAINER ID   NAME       CPU %     MEM USAGE / LIMIT     MEM %
a1b2c3d4e5f6   java-app   0.12%     120MiB / 512MiB       23.4%
🚑 트러블슈팅 구조대
Q: Java/Spring Boot 컨테이너에 메모리 제한을 걸었더니 시작하자마자 Exit 137로 계속 죽습니다.
A: 과거 버전의 JDK 8(8u131 이전)은 자신이 Docker 컨테이너 안에 있는지 인식하지 못하고 호스트의 전체 물리 메모리를 기준으로 JVM Heap 크기를 산정하여 Docker 한계치를 즉시 초과하기 때문입니다. 해결법: Java 실행 옵션에 -XX:MaxRAMPercentage=75.0을 추가하여 컨테이너 할당량에 맞춰 Heap을 자동 조절하도록 하거나 최신 JDK 17/21로 업그레이드하세요.
🚀
실무 팁: 최적의 리소스 상한선(Limit) 산정 공식 처음부터 무작정 임의의 값을 지정하지 마세요. 모범 프랙티스는 다음과 같습니다:
1. 스테이징 환경에서 리소스 제한 없이 컨테이너를 실행하고 최대 피크 부하 테스트(부하 테스트 툴 활용)를 진행합니다.
2. docker stats를 통해 관측된 최대 메모리 및 CPU 피크 수치를 측정합니다.
3. 측정된 피크 값에 20%~30%의 버퍼 마진을 더한 수치를 프로덕션 배포 시의 최종 Limit 값으로 확정합니다.
