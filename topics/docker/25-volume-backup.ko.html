제25레슨: 금고 이사: 데이터 백업 및 복원

이제 여러분의 데이터베이스는 Volume으로 안전하게 보호되고 있습니다. 하지만 만약 팀장님이 "이번 주말에 클라우드 서버 약정이 만료되니 데이터베이스 전체를 새로운 서버로 마이그레이션해라"라고 지시한다면 어떻게 해야 할까요?

잠시 막막해질 수 있습니다. Volume은 호스트 내부의 Docker 전용 시스템 디렉토리(/var/lib/docker/volumes/...)에 저장되어 있어 일반 파일처럼 단순 복사하기 어렵기 때문입니다. 이때 Docker 세계에서 가장 클래식하고 우아한 "도우미 컨테이너(Helper Container) 전술"을 사용합니다.

그림으로 이해하는 도우미 컨테이너 전술

핵심 원리는 간단합니다: 복잡한 시스템 내부 디렉토리를 직접 건드리지 않고, 임시 도우미 컨테이너를 하나 실행합니다. 백업할 Volume과 호스트의 현재 디렉토리를 동시에 마운트한 뒤, 이 도우미 컨테이너가 내부에서 tar 압축을 수행하여 압축 파일을 호스트로 던져주게 만드는 것입니다.

flowchart TD
    subgraph Host ["호스트 머신 Host"]
        A["백업 대상 데이터 볼륨: db-data"]
        B["호스트 현재 디렉토리 $(pwd)"]
        F("최종 산출물: backup.tar.gz")
    end
    
    subgraph Helper ["도우미 컨테이너 Ubuntu (임시 실행 후 즉시 소멸)"]
        C["마운트 경로 /volume-data"]
        D["마운트 경로 /backup"]
        E(("tar 압축 명령어 실행"))
    end
    
    A -.->|볼륨 마운트| C
    B -.->|바인드 마운트| D
    
    C -->|데이터 읽기| E
    E -->|압축 아카이브 작성| D
    D ===> F

실전 1: 데이터 볼륨 백업 (Backup)

MySQL 데이터가 저장된 db-data라는 볼륨이 있다고 가정하고, 이를 현재 디렉토리에 backup.tar.gz로 압축 백업해 보겠습니다.

tar 예제는 쓰기가 중지된 볼륨용입니다. 실행 중인 DB는 전용 일관성 백업을 사용하고 버전 호환성과 새 빈 볼륨 복원을 검증하세요.

docker run --rm \
  -v db-data:/volume-data \
  -v "$(pwd):/backup" \
  ubuntu \
  tar cvzf /backup/backup.tar.gz -C /volume-data .

명령어 한 줄 완벽 해부:

  • --rm: 작업 완료 즉시 임시 도우미 컨테이너를 자동 파기하여 흔적을 남기지 않음.
  • -v db-data:/volume-data: 백업할 소중한 볼륨을 컨테이너의 /volume-data로 마운트.
  • -v "$(pwd):/backup": 호스트의 현재 폴더를 컨테이너의 /backup으로 연결하여 결과물 수령 준비.
  • tar cvzf ... -C /volume-data .: /volume-data 디렉토리 내부로 이동(-C)한 후 모든 내용(.)을 압축하여 /backup/backup.tar.gz에 저장. 호스트와 연결되어 있으므로 호스트 현재 폴더에 압축 파일이 즉시 생성됩니다!

서버 간 파일 전송

생성된 압축 파일을 scp 명령어로 새로운 대상 서버로 안전하게 전송합니다:

scp backup.tar.gz root@new-server-ip:/root/

실전 2: 새 서버에서 데이터 복원 (Restore)

이제 새로운 서버에 도착했습니다. 먼저 빈 데이터 볼륨을 생성하고, 동일한 "도우미 컨테이너"를 소환하여 압축을 풀어 넣습니다.

🔄 데이터 복원 3단계

1. 새로운 빈 볼륨 생성:

docker volume create new-db-data

2. 도우미 컨테이너를 통한 압축 해제 (명령어가 -xvzf로 변경됨):

docker run --rm \
  -v new-db-data:/volume-data \
  -v "$(pwd):/backup" \
  ubuntu \
  tar xvzf /backup/backup.tar.gz -C /volume-data

3. 복원된 데이터 볼륨을 연결하여 새 데이터베이스 시작:

docker run -d --name my-mysql -v new-db-data:/var/lib/mysql mysql:8.0
💡
프로의 팁 (Pro Tip): 데이터베이스 전용 논리 백업 tar를 이용한 파일 시스템 수준 볼륨 백업은 매우 범용적이지만, MySQL이나 PostgreSQL 같은 관계형 데이터베이스의 경우 데이터베이스 전용 논리 백업 도구(예: mysqldump)를 활용하는 것이 더욱 안전합니다.
예시: docker exec my-mysql mysqldump -uroot -p123456 my_db > backup.sql
이 방식은 DB 실행 중에도 안전한 핫 백업이 가능하며, 파일 시스템 락 문제를 방지하고 서로 다른 DB 버전 간 마이그레이션에도 호환성이 뛰어납니다.
🚨 트러블슈팅 응급실
Q1: tar 압축을 풀었더니 내부에 불필요한 /volume-data 폴더 계층이 하나 더 생겼습니다.
A: tar 명령어가 잘못 작성되었습니다! 반드시 -C /volume-data . 옵션(마지막의 마침표 포함)을 지정해야 합니다. -C는 먼저 해당 디렉토리로 이동한 뒤 현재 디렉토리(.)의 내용을 묶으라는 의미이므로 상위 경로가 포함되지 않습니다.
Q2: 복원 시 권한 거부(Permission denied) 에러가 발생합니다.
A: 데이터베이스 파일 등은 특정 UID(예: mysql 사용자의 999) 소유권이 필요합니다. root 사용자로 압축 해제 시 보통 권한이 보존되지만, 소유권 문제가 발생할 경우 tar 명령어에 --numeric-owner 옵션을 부여하여 권한 숫자를 정확히 유지하세요.

축하합니다! 이로써 여러분은 Docker의 데이터 수명 주기 전체를 완벽하게 정복하셨습니다: 단명하는 컨테이너, 영속적인 Volume, 로컬 개발을 위한 Bind Mount, 그리고 자유자재의 데이터 백업과 이관까지. 다음 챕터부터는 Docker에서 가장 매력적이고 핵심적인 분야인 컨테이너 네트워크(Network)의 세계로 들어갑니다.
