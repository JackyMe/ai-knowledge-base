제26레슨: 네트워크 탐구: Bridge vs Host

처음 Docker를 접할 때 컨테이너는 마치 외부 세상과 단절된 고립된 무인도처럼 느껴집니다. 하지만 실제 프로덕션 애플리케이션은 절대 혼자 존재할 수 없습니다. 웹 서버는 데이터베이스에 연결되어야 하고, 프론트엔드는 백엔드 API를 호출해야 하며, 전체 시스템은 외부 브라우저의 접속을 받아들여야 합니다.

오늘 우리는 Docker가 어떻게 컨테이너들을 서로 연결하고, 외부 호스트 네트워크에 안전하게 노출하는지 그 원리를 완벽하게 파헤쳐 봅니다.

1. 전체 아키텍처 조망: Docker 네트워크 구조

본격적인 명령어를 입력하기 전에 Docker 네트워크의 전체 아키텍처를 살펴보겠습니다. Docker 엔진은 내부에 "가상 스위치(Virtual Switch)"를 두고 컨테이너들을 효율적으로 연결합니다.

flowchart TD
    Internet((인터넷 Internet)) <--> HostPort["호스트 포트: 8080"]
    HostPort <--> DockerEngine{"Docker 엔진 (NAT 포워딩)"}
    
    subgraph HostOS ["호스트 OS (Host OS)"]
        DockerEngine <--> Bridge["브리지 네트워크 (docker0) 172.17.0.0/16"]
        Bridge <--> C1["컨테이너 1: Web (172.17.0.2)"]
        Bridge <--> C2["컨테이너 2: DB (172.17.0.3)"]
        
        HostNet["호스트 네트워크 (Host Network)"] <--> C3["컨테이너 3: 고성능 앱 (호스트 IP 직접 사용)"]
    end

2. Docker의 기본 네트워크 드라이버

docker network ls 명령어로 현재 환경에 생성되어 있는 네트워크 목록을 확인할 수 있습니다:

docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
1f1621cb3483   bridge    bridge    local
8cc0547ba5ef   host      host      local
0a7a40b3abf2   none      null      local

Docker 설치 시 기본으로 주어지는 대표적인 3가지 네트워크 모드를 살펴봅니다:

1. Bridge (브리지 모드) - 가장 기본적인 표준 모드

네트워크를 명시하지 않고 컨테이너를 실행하면(예: docker run nginx) Docker는 컨테이너를 기본 bridge 네트워크에 자동으로 연결합니다.

  • 동작 원리: Docker는 호스트 상에 docker0이라는 가상 브리지를 생성합니다. 이 네트워크에 접속하는 모든 컨테이너는 동일한 서브넷 대역(보통 172.17.0.0/16)의 독립된 사설 IP를 할당받습니다.
  • 상호 통신: 동일 브리지 상의 컨테이너들은 서로 사설 IP로 PING 통신이 가능하지만, 컨테이너 이름으로는 통신할 수 없습니다 (기본 bridge는 내장 DNS 조회를 지원하지 않는다는 치명적 한계가 있습니다).

inspect 명령어로 브리지의 상세 네트워크 정보를 조회할 수 있습니다:

docker network inspect bridge
[
    {
        "Name": "bridge",
        "Driver": "bridge",
        "IPAM": {
            "Config": [
                {
                    "Subnet": "172.17.0.0/16",
                    "Gateway": "172.17.0.1"
                }
            ]
        }
    }
]
2. Host (호스트 모드) - 극한의 네트워크 성능 추구

실행 시 --network host를 지정하면 컨테이너는 가상 네트워크 격리를 거치지 않고 호스트 머신의 네트워크 스택을 직접 공유합니다. 컨테이너 자체의 사설 IP가 없으며, 컨테이너 내부 프로그램이 80 포트를 열면 호스트의 80 포트가 직접 열립니다.

  • 장점: NAT 변환 레이어가 없으므로 패킷 지연이 거의 없는 압도적인 네트워크 처리 성능을 발휘합니다.
  • 단점: 포트 충돌 위험! Host 모드로 Nginx를 2개 띄우려 하면 두 번째 컨테이너는 "포트가 이미 사용 중"이라며 실행 실패합니다.
3. None (무네트워크 모드) - 완벽한 보안 격리

--network none을 주면 컨테이너에 루프백(lo) 외에 어떤 네트워크 인터페이스도 할당되지 않습니다.

활용 사례: 외부와의 통신이 절대 발생해서는 안 되는 오프라인 보안 연산 작업(예: 난수 암호키 생성 후 볼륨에만 저장)에 적합합니다.

💡
프로의 팁: Macvlan 모드 컨테이너를 가상 스위치가 아닌 공유기/스위치 상의 독립된 물리 컴퓨터처럼 작동하게 하여 독자적인 MAC 주소와 공유기 대역 IP(예: 192.168.1.x)를 부여하고 싶다면 macvlan 드라이버를 사용합니다. 소프트웨어 라우터나 특수 네트워크 모니터링 장비 운영 시 주로 사용됩니다.

3. 포트 매핑 (Port Mapping): 컨테이너 외부 공개

Bridge 모드의 컨테이너는 기본적으로 사설망에 격리되어 있어 호스트 외부에서 직접 접근할 수 없습니다. 외부 트래픽을 컨테이너로 유입시키려면 반드시 포트 매핑(Port Mapping)을 설정해야 합니다.

핵심 문법: -p [호스트IP]:[호스트포트]:[컨테이너내부포트]

  • -p 8080:80: 호스트의 모든 네트워크 인터페이스의 8080 포트를 컨테이너의 80 포트로 포워딩.
  • -p 127.0.0.1:8080:80: 매우 강력한 보안 팁! 오직 호스트 로컬 루프백(localhost) 접속만 허용하여 외부 인터넷에서의 무단 접근을 원천 차단.
  • -P (대문자): Dockerfile의 EXPOSE에 명시된 포트들을 호스트의 임의의 사용 가능한 고위 포트(보통 32768~61000)로 자동 매핑.

4. 사용자 정의 브리지 네트워크 (User-defined Bridge)

기본 bridge 네트워크는 **컨테이너 이름 기반의 DNS 해석을 지원하지 않는다**는 결정적 단점이 있습니다. 이 때문에 데이터베이스 연결 시 언제 바뀔지 모르는 172.17.x.x IP를 하드코딩해야 하는 불편이 생깁니다.

따라서 실무에서는 기본 bridge 대신 항상 사용자 정의 네트워크를 직접 생성하여 사용합니다:

# 사용자 정의 브리지 네트워크 생성
docker network create my-net

컨테이너 실행 시 네트워크를 지정합니다:

docker run -d --name db1 --network my-net mysql:8.0

이 사용자 정의 네트워크 안에서는 Docker 내장 DNS 서버가 활성화되어 ping db1이나 소스코드 연결 문자열에 mysql://db1:3306처럼 컨테이너 이름을 도메인 이름처럼 자유롭게 사용할 수 있습니다!

5. 컨테이너의 실제 사설 IP 확인하기

트러블슈팅 중 컨테이너에 할당된 사설 IP를 직접 확인하고 싶을 때는 inspect와 grep을 조합하여 간단히 확인할 수 있습니다:

docker inspect my-nginx | grep "IPAddress"
            "IPAddress": "172.17.0.2",
🚨 트러블슈팅 응급실
Q1: "Bind for 0.0.0.0:8080 failed: port is already allocated" 오류가 발생합니다.
A: 호스트 머신의 8080 포트가 다른 프로그램(또는 다른 컨테이너)에 의해 이미 점유된 상태입니다. 호스트 포트를 -p 8081:8080처럼 비어 있는 다른 포트로 변경하세요.
Q2: 컨테이너 내부에서 외부 인터넷(예: google.com)으로 통신이 안 됩니다.
A: 1. 호스트 자체의 인터넷 연결 또는 DNS 설정 문제일 수 있습니다. 2. 호스트 리눅스의 IP 패킷 포워딩이 비활성화되어 있을 수 있습니다. 호스트에서 sysctl net.ipv4.ip_forward=1 설정을 확인하세요. 또는 docker run --dns 8.8.8.8 옵션으로 공용 DNS를 지정해 보세요.
