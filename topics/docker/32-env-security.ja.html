第32レッスン：城壁の防御：.env による機密情報・パスワードの保護

セキュリティにおける悪夢のようなシナリオを想像してみてください：

金曜日の夜、docker-compose.yml に POSTGRES_PASSWORD=my_super_secret_pwd_123 と平文でパスワードを書いたまま、うっかり公開の GitHub リポジトリへ git push してしまいました。3時間後、自動スキャンボットに検知され、データベースに不正侵入されデータが全消去されて身代金要求メッセージが残されていました...

「機密パスワードや API キーをコードリポジトリに平文コミットしては絶対にならない！」 本章では、このセキュリティリスクを鉄壁に防ぐ .env ファイルの活用法を学びます。

1. .env ファイルの仕組みと基本構造

.env はシンプルなキーバリュー（Key-Value）形式のテキストファイルです。docker-compose.yml と同じディレクトリで docker compose up を実行すると、Compose は自動的に .env ファイルから環境変数を読み込んで置換します。

docker-compose.yml を変数参照形式にリファクタリングします：

# docker-compose.yml の一部
services:
  db:
    image: postgres:14-alpine
    environment:
      - POSTGRES_USER=${DB_USER}
      - POSTGRES_PASSWORD=${DB_PASS}
      - POSTGRES_DB=${DB_NAME:-default_db} # デフォルト値付き構文

同階層に .env ファイルを作成して実値を定義します：

# .env ファイルの内容（非公開）
DB_USER=admin
DB_PASS=S3cr3t!2024
DB_NAME=myapp_prod
💡
Compose における便利な変数展開パターン
  • ${VAR}: 通常の変数展開。未定義の場合は空文字。
  • ${VAR:-default}: VAR が未設定または空の場合に default を代入。
  • ${VAR:?err_msg}: 必須チェック！ VAR が未設定の場合、Compose はエラーメッセージ err_msg を出力して起動を中止。パスワードの設定忘れを確実に防止します。

2. 最重要ステップ：.gitignore への追加

変数を別ファイルに切り出しても、その .env を Git にコミットしてしまっては意味がありません。

プロジェクトルートの .gitignore に必ず以下を記述してください：

# .gitignore
.env

では、他の開発メンバーは何の環境変数が必要かどうやって把握すればよいでしょうか？

業界の標準的な作法は、.env.example テンプレートを作成して Git で管理することです：

# .env.example (Git で共有するダミー値テンプレート)
DB_USER=root
DB_PASS=your_password_here
DB_NAME=test_db

新規メンバーは cp .env.example .env を実行し、自分専用のローカルパスワードを入力するだけでセットアップが完了します。

3. 複数環境（開発・ステージング・本番）の切り替え

環境ごとに変数を切り替えたい場合、.env.dev や .env.prod などの専用ファイルを作成します。

起動時に --env-file オプションで対象ファイルを明示指定します：

# 本番環境ファイルを使って起動
$ docker compose --env-file .env.prod up -d
⚔️ 環境変数の優先順位（高い順）

同一変数が複数箇所で定義されている場合、以下の順序でオーバーライドされます：

  1. 最高優先度： CLI 実行時のインライン変数（例: DB_PASS=123 docker compose up）
  2. 第2位： docker-compose.yml の environment: で直書きされた値
  3. 第3位： 読み込まれた .env ファイル内の定義値
  4. 最低優先度： Dockerfile 内の ENV 命令で設定されたデフォルト値

4. 動作検証：正しく値が渡っているか確認する

起動後、コンテナ内部に正しく環境変数が注入されたか確認するコマンドです：

# 稼働中の特定サービスコンテナ内の環境変数を確認
$ docker compose exec db env | grep POSTGRES

# コンテナの詳細メタデータから確認
$ docker inspect myapp-db-1 -f "{{.Config.Env}}"
🚨 トラブルシューティング救急室
Q1: パスワードに $ や # が含まれており、構文エラーになります。
A: .env 内の $ は変数参照とみなされる場合があります。値をシングルクォートで囲む（DB_PASS='my$pwd'）か、$$ とエスケープしてください。また、行頭の # はコメント扱いとなるため注意が必要です。
Q2: .env ファイルの値を変更したのに、コンテナに反映されません。
A: docker compose restart では環境変数は再読み込みされません。必ず docker compose up -d を実行してください。Compose が環境変数の差分を検知し、自動的にコンテナを再作成（Recreate）して反映させます。

プロの知恵 (Pro-tip)： Kubernetes や Docker Swarm を用いる大規模本番環境では、.env よりさらに堅牢な Docker Secrets やシークレット管理サービス（AWS Secrets Manager、HashiCorp Vault 等）を利用し、メモリ上のみで一時ファイルとしてマウントする運用が標準的です。
