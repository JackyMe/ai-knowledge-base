27. 容器相亲记：告别 IP，用名字呼唤你

上节课我们提到，如果你还在用写死 IP 的方式让 Web 容器连接数据库容器，那你一定会遇到“连环翻车”惨案。今天，我们就来演绎一下小明的惨痛经历，并用 Docker 自定义网络来一次完美救赎。

一、小明的灾难日：硬编码 IP 的悲剧

小明在测试服务器上跑了一个电商网站，架构很简单：一个 Node.js 后端应用，一个 MySQL 数据库。

他先启动了 MySQL，通过 docker inspect 查到分配的 IP 是 172.17.0.2。

然后他在代码里把数据库地址写死：const dbHost = '172.17.0.2'，打包镜像，跑起来，完美！

结果周末服务器停电重启。Docker 恢复运行时，启动顺序稍微乱了一下，恰好另一个 Nginx 容器先启动了，抢占了 172.17.0.2。随后启动的 MySQL 被分配到了 172.17.0.3。

周一早上，用户疯狂投诉系统崩溃，小明的 Node.js 应用一直在疯狂重试连接 172.17.0.2 这个 IP，结果连到 Nginx 上去了，各种报错...

🚨
核心痛点 容器的 IP 就像酒店的房号。客人（容器）每次入住（重启），前台分给他的房号（IP）可能是不同的。如果你找朋友只能靠房号，那肯定会找错人。我们需要一种机制，直接喊朋友的名字就能找到他！

二、解救之道：自定义网络与服务发现

解救小明的方案很简单：放弃默认的 bridge，创建属于自己的网络！

在自定义网络中，Docker 引擎内置了一个基于 CoreDNS 的服务发现机制。只要容器连接在同一个自定义网络下，它们就可以直接把容器名字当作域名来互相访问！

sequenceDiagram
    participant Web as Web (app-server)
    participant DNS as Docker DNS (127.0.0.11)
    participant DB as DB (mysql-server)
    
    Web->>DNS: 查询 "mysql-server" 的 IP 是多少？
    DNS-->>Web: 答复: 172.18.0.3
    Web->>DB: 带着正确的 IP 发起数据库连接

三、动手实战：红娘牵线体验

现在，我们一步步来重构小明的架构。

步骤 1：创建一个新网络
docker network create ecommerce-net

这会创建一个名为 ecommerce-net 的网络。默认也是 bridge 驱动，但它拥有魔法 DNS。

步骤 2：把数据库放进去
docker run -d --name my-database --network ecommerce-net -e MYSQL_ROOT_PASSWORD=secret mysql:8.0

注意我们用 --name my-database 给了它一个响亮的名字。

步骤 3：让应用去“相亲”

为了演示，我们不用真实的 Node 应用，而是用一个能发请求的 alpine 容器来做测试：

docker run -it --rm --network ecommerce-net alpine sh

进入终端后，我们直接 PING 数据库的名字：

/ # ping -c 3 my-database
PING my-database (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.102 ms
64 bytes from 172.18.0.2: seq=1 ttl=64 time=0.081 ms

成功啦！Docker 自动把 my-database 解析成了 172.18.0.2。以后无论重启多少次，只要名字没变，IP 随你怎么变，网络永远是通的！

四、半路杀出个程咬金：连接已有容器

“等等！”小明说，“如果我有个服务 redis-cache 已经在运行了，且没加到这个网络里，我该怎么办？难道要把它删了重跑？”

当然不需要！Docker 提供了动态连接的功能。就像插网线一样，你可以给运行中的容器再插一根网线进去：

# 将运行中的 redis-cache 容器连接到 ecommerce-net 网络
docker network connect ecommerce-net redis-cache

现在，你的应用也能通过 redis-cache 这个名字访问它了。如果要拔掉网线也很简单：

docker network disconnect ecommerce-net redis-cache
🎯
老鸟技巧：网络别名 (Network Aliases) 除了用 --name 作为 DNS 名称，你还可以用别名！比如你启了 3 个后端的容器，你给它们加上 --network-alias backend-api。
神奇的事情会发生：当你内部网络 PING backend-api 时，Docker 的 DNS 会在结果里随机返回这 3 个容器的 IP 之一。这就是极其轻量级的内部负载均衡 (Round-Robin DNS)！
⚠️ 踩坑自救室
Q: 报错 "Could not resolve host" 怎么破？
A: 99% 的可能性是：你的两个容器不在同一个网络里！用 docker inspect 容器名 查看 "Networks" 节点，确保它们都在你自定义的同一个网络里。如果一个在 bridge，一个在 my-net，它们是处于物理隔离状态的，绝对无法互通。
Q: 我可以把一个容器连到多个网络吗？
A: 完全可以！就像一台电脑插了两张网卡。你可以把 Nginx 同时接入公网网络（和外部打交道）以及内部网络（和数据库打交道），而数据库只留在内部网络。这是非常经典的安全隔离架构设计。
