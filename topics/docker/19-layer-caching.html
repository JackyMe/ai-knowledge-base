第19集：图解分层缓存魔法 (重要!)

为什么有的人敲 docker build 只要 2 秒，有的人却要 5 分钟？核心秘密就在于：有没有写好 Dockerfile，从而优雅地利用 Docker 的“分层缓存机制”。

这可能是 Docker 进阶之路上最重要的一节课。

1. 什么是镜像分层？

在第 18 集打包时，我们看到构建过程是一步步（Step 1/7）执行的。Docker 的镜像是像千层饼一样堆叠起来的。Dockerfile 里除了纯配置指令外，每一个 RUN、COPY、ADD 都会产生一层全新的“饼”。

2. 缓存失效的雪崩效应

Docker 是个大聪明，它在构建时会检查：这一层的指令有没有变？如果没变（比如 COPY 的文件没改动），它就不会重新执行，直接拿以前构建好的“那一层饼”来用（显示 CACHED）。

🚨 致命规则来了：只要某一层缓存失效（比如文件被修改了），这一层及其后面所有的层，全部都要重新执行，缓存统统作废！

3. 糟糕的写法 vs 优秀的写法

❌ 糟糕的写法：新人常犯错误
FROM node:24-alpine
WORKDIR /app
# 直接把所有代码和 package.json 一次性拷进来
COPY . .
# 然后安装依赖
RUN npm install
CMD ["node", "server.js"]

灾难后果：今天你只是稍微修改了一行 server.js 里的文案，导致 COPY . . 这一层的文件发生了变化，缓存失效。随后，下面的 RUN npm install 也跟着失效了！于是 Docker 会重新去网络上下载几十 MB 的 node_modules，耗时好几分钟！

✅ 优秀的写法：分步拷贝法
FROM node:24-alpine
WORKDIR /app
# 第一步：只拷贝包描述文件
COPY package.json .
# 第二步：安装依赖
RUN npm install
# 第三步：拷贝业务代码
COPY . .
CMD ["node", "server.js"]

爽感体验：当你修改了 server.js 时，package.json 并没有变。所以第一步 COPY 走缓存！第二步 RUN npm install 也走缓存！直到第三步 COPY . . 缓存才失效，仅仅花零点几秒把代码拷进去。构建时间从 5 分钟缩短到了 2 秒！

4. 减少层数：RUN 命令的串联艺术

我们提到过，每一条 RUN 都会增加一层。每多一层，镜像就大一点。如果你要装系统软件，请用 && 串起来，最后记得打扫卫生（清理 apt 缓存等），因为一旦到了下一层，你就算用 rm 删除了文件，镜像的整体体积也不会减小（就像 Git 的提交记录一样，东西还在历史里留着）。

# 完美的一行安装法
RUN apt-get update     && apt-get install -y vim curl net-tools     && rm -rf /var/lib/apt/lists/*
💡
老鸟技巧 (Pro-Tip)：BuildKit 与挂载缓存

对于 npm/pip/maven 这些包管理器，即使巧妙利用了分层，换台机器还是要全量下一次。Docker 的新一代构建器 BuildKit 支持高级挂载：RUN --mount=type=cache,target=/root/.npm npm install。这样下载过的包缓存会被保留在一个专门的安全区域，下次构建直接用，速度快到飞起！

🚨 踩坑自救室
Q1: 为什么我的 COPY 每次都没有命中缓存？我明明没改代码！
A: 检查你的文件属性和时间戳。Docker 判定文件是否改变，除了看内容 Hash，某些老版本或者特定情况下也会受权限/时间戳影响。更常见的原因是：你在宿主机生成了日志、或者是没配好 .dockerignore 导致无关文件的变动触发了缓存失效。
