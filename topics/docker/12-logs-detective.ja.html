12. 探偵の視点：ログ調査の極意

🕵️‍♂️ 深夜3時のクラッシュ事件

深夜3時、枕元の電話がけたたましく鳴り響きます。「決済サービスが突然落ちた！ すぐに復旧してくれ！」

目をこすりながらサーバーに SSH 接続し docker ps を打つと、あるはずの payment-service コンテナが消えています！ 慌てて docker ps -a を実行すると、Exited (1) 2 hours ago の文字が……。

コンテナはすでに停止しているため、docker exec で中に入ることはできません。このとき、あなたが頼れる唯一の手がかりは、コンテナが死に際に残した「ログ」です。

一、タイムトラベル：基本的なログの確認

コンテナの出力を確認する最も基本的なコマンドが docker logs です：

docker logs payment-service

しかし、数週間稼働し続けていたコンテナの場合、このコマンドを実行すると何万行もの過去ログが一気に画面を埋め尽くし、ターミナルが流れてしまいます。

1. 直近のログだけを確認する（--tail）

トラブル調査で最も知りたいのは、クラッシュ直前に何が起きたかです。--tail オプションで末尾のN行だけを取得します：

# 直近 50 行のログのみを表示
docker logs --tail 50 payment-service

2. 発生時刻による正確な絞り込み（--since / --until）

障害発生が深夜2時頃だと分かっている場合、時間範囲を指定してピンポイントで抽出できます：

# 過去 2 時間のログを表示
docker logs --since 2h payment-service

# ISO 8601 形式で絶対時刻を指定
docker logs --since "2023-10-01T01:50:00" --until "2023-10-01T02:10:00" payment-service

3. タイムスタンプを強制付与する（-t / --timestamps）

プログラム側のログ出力に日時刻が含まれていない場合でも、Docker デーモン側の高精度な受信時刻を付与して表示できます：

docker logs -t payment-service
# 出力例: 2023-10-01T02:05:11.123456789Z Exception in thread "main"...

二、リアルタイム監視モード：ログのストリーミング追跡（-f）

コンテナが稼働中で、API を叩きながらリアルタイムにログの流れを観察したい場合は、-f（follow）フラグを付けます。Linux の tail -f とまったく同じ挙動です：

docker logs -f --tail 20 payment-service

画面が開いたままになり、新しいリクエストが届くたびにログがリアルタイムに追記されます。終了するには Ctrl + C を押します。

三、仕組みの深層：ログは一体どこに保存されているのか？

初学者のよくある疑問：「プログラムは単に標準出力（stdout）に文字列を吐いているだけなのに、バックグラウンド実行中のログはどこに記録されているのか？」

Docker はデフォルトで json-file というロギングドライバを使用しています。コンテナ内のプロセスが stdout（標準出力） や stderr（標準エラー出力） に書き込んだデータは、すべて Docker デーモンによってインターセプトされ、ホストマシンの内部 JSON ファイルに書き込まれています。

⚠️
重大な警告：放置されたログによるディスク枯渇！

デフォルト状態の Docker は、ログファイルの自動ローテーションやサイズ制限を一切行いません！ 頻繁にアクセスログを吐く API サーバーなどを放置すると、この JSON ログファイルが数日で数十GB〜数百GBに膨れ上がり、ホストマシンのディスク容量を食い潰してサーバー全体がダウンする原因になります！

防衛策：ログローテーション設定（--log-opt）

本番用コンテナを起動する際は、必ず --log-opt でサイズ制限を設ける習慣をつけましょう：

docker run -d \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  --name safe-app my-app

この設定により、1つのログファイルが 10MB を超えるとローテーションされ、最大 3 世代までしか保持されなくなります。これで「ディスク容量枯渇」による夜間アラートに怯える必要はなくなります。

四、ログ以外の高度な診断ツール

1. メタデータの完全開帳：docker inspect

割り当てられた内部 IP アドレス、ボリュームマウントの状態、環境変数が正しく渡っているかなど、コンテナの全詳細設定を JSON 形式で確認できます：

# JSON が返るため grep や jq と組み合わせるのが便利
docker inspect my-app | grep "IPAddress"

2. リアルタイム心電図：docker stats

メモリリークや CPU の高騰が疑われるとき、Linux の top コマンドのように全コンテナのリソース消費量をリアルタイム監視できます：

docker stats

3. 外部からのプロセス点検：docker top

コンテナに侵入することなく、コンテナ内で現在動いているプロセスの一覧を確認できます：

docker top my-app
🚑 トラブル救護室
Q1: docker logs を打っても画面が完全に真っ白（何も出ない）なのはなぜ？
A: アプリケーションが標準出力（stdout / stderr）ではなく、コンテナ内部のローカルファイル（例: /var/log/app.log）にログを直接書き込んでいることが原因です。Docker は標準出力しかインターセプトできません。解決策： クラウドネイティブの原則（12-Factor App）に従いロギングライブラリの出力先を標準出力に変更するか、ボリュームマウントを使ってホスト側から直接ログファイルを参照してください。
🚀
プロの知恵：構造化 JSON ログの活用

エンタープライズのマイクロサービス環境では、プレーンテキストのログではなく 構造化 JSON ログ（Structured JSON Logging） を採用するのが業界標準です。
Docker は標準出力を Syslog、Fluentd、AWS CloudWatch、Grafana Loki などの外部ログ基盤へ直接転送（ロギングドライバの変更）できます。ログ自体が JSON 形式であれば、転送先での自動パース、検索、集計、アラート検知が極めてスムーズになります。
