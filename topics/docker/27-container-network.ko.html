제27레슨: 컨테이너 간 통신: IP 직접 입력과의 작별, 이름으로 호출하기

이전 레슨에서 설명했듯이, 만약 여러분이 웹 컨테이너에서 데이터베이스 컨테이너로 연결할 때 고정된 IP를 하드코딩하고 있다면 조만간 반드시 심각한 장애를 겪게 됩니다. 오늘은 개발자 샤오밍의 쓰라린 장애 경험을 통해 Docker 사용자 정의 네트워크를 활용한 우아한 해결책을 알아보겠습니다.

1. 샤오밍의 재난의 날: IP 하드코딩의 비극

샤오밍은 테스트 서버에서 간단한 쇼핑몰 서비스를 운영 중이었습니다: Node.js 백엔드 앱 1개와 MySQL 데이터베이스 1개로 구성된 구조입니다.

먼저 MySQL을 띄운 뒤 docker inspect로 확인했더니 172.17.0.2가 할당되었습니다.

샤오밍은 소스코드에 const dbHost = '172.17.0.2'라고 하드코딩하고 이미지를 빌드해 실행했습니다. 완벽하게 작동했습니다!

하지만 주말 동안 서버에 정전이 발생하여 재부팅되었습니다. Docker가 컨테이너들을 복구할 때 시작 순서가 살짝 바뀌어 다른 Nginx 컨테이너가 먼저 실행되면서 172.17.0.2를 선점해 버렸습니다. 뒤이어 실행된 MySQL은 172.17.0.3을 할당받았습니다.

월요일 아침, 서비스 접속 불가 장애가 터졌습니다. Node.js 백엔드는 172.17.0.2로 데이터베이스 연결을 끊임없이 시도했고, MySQL 대신 엉뚱한 Nginx에 연결되어 온갖 에러가 뿜어져 나왔습니다...

🚨
핵심 문제점 컨테이너의 IP는 호텔의 객실 번호와 같습니다. 손님(컨테이너)이 체크인(재시작)할 때마다 프런트에서 배정하는 방 번호(IP)는 매번 달라질 수 있습니다. 친구를 방 번호로만 찾으려 하면 다른 사람의 방을 두드리게 됩니다. 우리는 친구의 이름으로 직접 호출하는 방식이 필요합니다!

2. 구원의 길: 사용자 정의 네트워크와 서비스 디스커버리

해결책은 아주 간단합니다: 기본 bridge 네트워크를 버리고, 사용자 정의 전용 네트워크를 만드는 것입니다!

사용자 정의 네트워크에서는 Docker 엔진에 내장된 DNS 서비스 디스커버리(Service Discovery) 메커니즘이 활성화됩니다. 같은 네트워크에 속한 컨테이너들은 서로의 컨테이너 이름을 도메인 이름처럼 사용하여 직접 통신할 수 있습니다!

sequenceDiagram
    participant Web as Web (app-server)
    participant DNS as Docker DNS (127.0.0.11)
    participant DB as DB (mysql-server)
    
    Web->>DNS: "mysql-server"의 IP는 무엇인가요?
    DNS-->>Web: 응답: 172.18.0.3 입니다.
    Web->>DB: 조회된 올바른 IP로 데이터베이스 접속 요청

3. 실전 실습: 컨테이너 이름 기반 통신

샤오밍의 시스템 아키텍처를 안전하게 재구축해 보겠습니다.

1단계: 사용자 정의 전용 네트워크 생성
docker network create ecommerce-net

ecommerce-net이라는 이름의 네트워크가 생성되었습니다. bridge 드라이버 기반이지만 마법 같은 자동 DNS 기능을 기본 탑재하고 있습니다.

2단계: 데이터베이스 컨테이너를 해당 네트워크에 배치
docker run -d --name my-database --network ecommerce-net -e MYSQL_ROOT_PASSWORD=secret mysql:8.0

--name my-database 옵션으로 고유하고 명확한 이름을 지정했습니다.

3단계: 애플리케이션에서 이름으로 직접 호출 테스트

테스트를 위해 네트워크 도구가 포함된 가벼운 alpine 컨테이너를 동일 네트워크로 실행합니다:

docker run -it --rm --network ecommerce-net alpine sh

컨테이너 내부에서 IP 대신 데이터베이스의 이름을 직접 PING합니다:

/ # ping -c 3 my-database
PING my-database (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.102 ms
64 bytes from 172.18.0.2: seq=1 ttl=64 time=0.081 ms

통신 성공! Docker가 my-database라는 이름을 자동으로 현재 IP인 172.18.0.2로 변환해 주었습니다. 이제 컨테이너가 몇 번을 재시작하고 IP가 바뀌어도 이름만 같다면 통신이 완벽하게 유지됩니다!

4. 실행 중인 기존 컨테이너에 동적으로 네트워크 연결하기

이미 실행 중인 redis-cache 컨테이너가 있는데 새 네트워크에 포함되지 않았다면 컨테이너를 삭제하고 다시 띄워야 할까요?

그럴 필요 없습니다! Docker는 실행 중인 컨테이너에 실시간으로 랜선을 꽂듯이 네트워크를 동적 연결할 수 있습니다:

# 실행 중인 redis-cache 컨테이너를 ecommerce-net 네트워크에 추가 연결
docker network connect ecommerce-net redis-cache

이제 애플리케이션에서 redis-cache라는 이름으로 즉시 접근할 수 있습니다. 연결을 해제할 때도 간단합니다:

docker network disconnect ecommerce-net redis-cache
🎯
프로의 팁: 네트워크 별칭 (Network Aliases) --name 외에도 --network-alias로 별칭을 추가할 수 있습니다. 예를 들어 3개의 동일한 백엔드 컨테이너에 --network-alias backend-api를 부여하면, 내부에서 backend-api를 호출할 때 Docker DNS가 3개의 IP 중 하나를 랜덤으로 반환합니다. 이것이 바로 초경량 내부 라운드로빈 DNS 부하분산(Load Balancing)입니다!
🚨 트러블슈팅 응급실
Q1: "Could not resolve host: my-database" 오류가 발생합니다.
A: 99%는 두 컨테이너가 **서로 다른 네트워크**에 속해 있기 때문입니다! docker inspect [컨테이너명]으로 두 컨테이너가 동일한 사용자 정의 네트워크에 접속해 있는지 확인하세요. 기본 bridge에 있거나 서로 다른 네트워크에 있다면 완벽히 격리되어 이름 해석 및 통신이 불가능합니다.
Q2: 하나의 컨테이너를 여러 네트워크에 동시에 연결할 수 있나요?
A: 물론입니다! 컴퓨터에 랜카드를 2개 꽂는 것과 같습니다. Nginx 리버스 프록시를 외부 인터넷망과 내부 전용망에 동시에 연결하고, MySQL은 내부망에만 두는 구조는 실무에서 매우 권장되는 표준 보안 격리 아키텍처입니다.
