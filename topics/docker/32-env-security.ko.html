제32레슨: 성벽 방어: .env를 통한 비밀 정보 보호

끔찍한 악몽 시나리오 하나를 상상해 보겠습니다:

금요일 저녁, docker-compose.yml 파일을 멋지게 작성한 뒤 POSTGRES_PASSWORD=my_super_secret_pwd_123라고 적힌 비밀번호를 그대로 둔 채 GitHub 공개 저장소에 git push해 버렸습니다. 3시간 뒤, 자동화된 스캐닝 봇이 비밀번호를 탈취하여 데이터베이스에 접속한 뒤 모든 데이터를 삭제하고 비트코인 몸값 요구서를 남겼습니다...

절대로 소스코드 저장소에 평문 비밀번호와 시크릿 키를 커밋해서는 안 됩니다! 오늘 우리는 이 참사를 막아줄 가장 중요한 보안 방어벽——.env 환경 변수 분리 기법을 배웁니다.

1. .env 파일이란 무엇인가?

.env는 Key-Value 형태의 환경 변수 목록이 적힌 단순한 텍스트 파일입니다. docker-compose.yml이 위치한 디렉토리에서 docker compose up을 실행하면, Compose는 진공청소기처럼 .env 파일의 변수들을 자동으로 읽어들여 ${변수명} 자리에 주입합니다.

docker-compose.yml 파일을 안전하게 개선해 보겠습니다:

# docker-compose.yml (시크릿 변수화)
services:
  db:
    image: postgres:14-alpine
    environment:
      - POSTGRES_USER=${DB_USER}
      - POSTGRES_PASSWORD=${DB_PASS}
      - POSTGRES_DB=${DB_NAME:-default_db} # 기본값(fallback) 문법 지원

그리고 동일한 디렉토리에 .env 파일을 생성합니다:

# .env (실제 비밀 정보 파일)
DB_USER=admin
DB_PASS=S3cr3t!2024
DB_NAME=myapp_prod
💡
Compose 환경 변수 치환 문법
  • ${VAR}: 기본 치환. 변수가 설정되어 있지 않으면 빈 문자열로 처리됩니다.
  • ${VAR:-default}: 변수가 설정되지 않았거나 비어있을 경우 default 기본값을 대체 사용합니다.
  • ${VAR:?err_msg}: 필수 변수 검증. 변수가 없으면 Compose가 기동을 중단하고 err_msg 오류를 출력합니다. 필수 비밀번호 누락을 방지하는 최고의 기법입니다!

2. 가장 중요한 핵심 규칙: .gitignore 등록

아무리 .env로 분리했더라도 이 파일을 Git에 올려버리면 열쇠를 문고리에 걸어두는 것과 같습니다.

프로젝트 생성 즉시 .gitignore 파일 최상단에 .env를 등록하세요:

# .gitignore
.env

그렇다면 다른 동료 개발자는 어떤 환경 변수가 필요한지 어떻게 알 수 있을까요?

업계 표준 베스트 프랙티스는 더미(가짜) 샘플 데이터가 들어있는 .env.example 파일을 만들어 Git에 커밋하는 것입니다:

# .env.example (Git 저장소에 안전하게 커밋)
DB_USER=root
DB_PASS=your_password_here
DB_NAME=test_db

새로운 팀원은 코드를 클론한 뒤 cp .env.example .env를 실행하고 자신만의 비밀번호를 입력하기만 하면 즉시 개발을 시작할 수 있습니다.

3. 다중 환경(개발 / 스테이징 / 프로덕션) 관리

환경별로 설정이 다를 경우 .env.dev, .env.prod 등으로 분리하고 --env-file 플래그를 지정하여 실행합니다:

# 프로덕션 전용 환경 파일로 실행
$ docker compose --env-file .env.prod up -d
⚔️ 환경 변수 우선순위 계층 (Priority Ranking)

동일한 변수가 여러 곳에 선언되었을 때 Docker가 채택하는 우선순위는 다음과 같습니다:

  1. 최우선: 터미널 런타임에서 직접 전달한 셸 변수 (DB_PASS=123 docker compose up)
  2. 2순위: Compose 파일 내부 environment: 섹션에 하드코딩된 값
  3. 3순위: 지정된 .env 파일에 정의된 값
  4. 최하위: Dockerfile 내부 ENV 지시자에 명시된 기본값

4. 환경 변수 주입 검증하기

컨테이너에 실제 환경 변수가 올바르게 주입되었는지 확인하는 명령어입니다:

# 실행 중인 db 서비스 내부의 실제 환경 변수 출력
$ docker compose exec db env | grep POSTGRES

# docker inspect로 컨테이너 환경 설정 JSON 검사
$ docker inspect myapp-db-1 -f "{{.Config.Env}}"
🚨 트러블슈팅 응급실
Q1: 비밀번호 안에 $나 # 같은 특수문자가 있어서 구문 에러가 납니다.
A: .env에서 $는 변수 치환 문자로 인식될 수 있으므로 $$로 이스케이프하거나 작은따옴표 DB_PASS='my$pwd'로 감싸세요. 또한 #으로 시작하는 문장은 주석으로 처리되므로 주의하세요.
Q2: .env 파일을 수정하고 docker compose restart를 했는데 새 변수가 반영되지 않습니다.
A: docker compose restart는 기존 컨테이너 프로세스만 다시 띄울 뿐 설정을 다시 읽지 않습니다. 반드시 docker compose up -d를 실행해야 Compose가 변경된 환경 변수를 감지하고 컨테이너를 새로 재생성합니다.

프로의 팁 (Pro Tip): 대규모 쿠버네티스나 클라우드 환경에서는 .env 파일조차 보안상 디스크에 저장하지 않고, Docker Secrets 또는 AWS Secrets Manager / HashiCorp Vault와 같은 중앙 암호화 키 볼트에 연동하여 메모리 상의 임시 파일로만 마운트합니다.
