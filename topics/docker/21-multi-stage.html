21. 终极瘦身：多阶段构建

假设你现在要盖一栋别墅。传统的盖房方式是：你把砖头、水泥、搅拌机、脚手架、甚至是工人的床铺全都留在了建好的别墅里。最后交房的时候，买家一开门，发现客厅里停着一辆水泥车！

这听起来很荒唐对吧？但在 Docker 的世界里，很多新手就是这么干的。他们把编译器、测试工具、源码全都打包进了最终的镜像里。这就是为什么一个明明只有 15MB 的 Go 语言编译产物，最终的 Docker 镜像却高达 800MB。

为什么镜像会这么大？

我们来看一个反面教材。小明用 Go 写了一个简单的 Web 服务，然后写了这样一个 Dockerfile：

# 反面教材：单阶段构建
FROM golang:1.20
WORKDIR /app
COPY . .
RUN go build -o myapp main.go
CMD ["./myapp"]

构建完一看大小，小明当场晕倒：

docker images | grep myapp
myapp       latest      a1b2c3d4e5f6   About a minute ago   850MB

为什么会这么大？因为 golang:1.20 这个基础镜像本身就包含了整个 Linux 操作系统、Go 编译器、标准库等各种工具。而实际上，Go 编译出来的二进制文件是可以独立运行的，根本不需要这些乱七八糟的东西。

多阶段构建：只带走你需要的东西

多阶段构建（Multi-stage Build）就像是“卸磨杀驴”（褒义）。我们在第一个阶段（施工现场）把代码编译好，然后在第二个阶段（交房）只把编译好的二进制文件拿过来，其他工具全都丢弃。

flowchart LR
    subgraph 阶段一: 施工现场 Builder
        A[基础镜像 golang:1.20] --> B(拷贝源码)
        B --> C(运行 go build)
        C -.-> D{生成二进制文件}
    end
    
    subgraph 阶段二: 精装交房 Production
        E[超小镜像 alpine] --> F(从阶段一拷贝二进制)
        D ==> F
        F --> G[最终镜像: 仅20MB]
    end

实战案例：Go 语言项目的终极瘦身

让我们用多阶段构建来重写小明的 Dockerfile：

🛠️ 步骤 1: 编写多阶段 Dockerfile
# 第一阶段：命名为 builder
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
# 静态编译，禁用 CGO 以确保可以在 alpine 中运行
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp main.go

# 第二阶段：生产环境，使用极小的 alpine 镜像
FROM alpine:latest
WORKDIR /root/
# 从 builder 阶段拷贝编译好的产物
COPY --from=builder /app/myapp .
# 给执行权限
RUN chmod +x myapp

CMD ["./myapp"]

仔细看 AS builder 和 COPY --from=builder 这两个关键语法。AS 给第一阶段起了个名字，而 --from 则像是个跨越时空的传送门，把第一阶段的成果拿到了第二阶段。

现在我们重新构建，看看奇迹发生：

docker build -t myapp:slim .
docker images | grep myapp
myapp       slim        b2c3d4e5f6g7   About a minute ago   22.4MB
myapp       latest      a1b2c3d4e5f6   10 minutes ago       850MB

从 850MB 到 22MB，体积缩小了 38 倍！这不仅省下了硬盘空间，更重要的是大大缩短了镜像拉取（Pull）的时间，让你的服务扩容速度飞起。

Java 也能瘦身：Maven + JRE

不仅是 Go，Java 这种重量级选手也非常需要多阶段构建。很多时候你的代码里需要 Maven 或 Gradle 来打包，但运行的时候只需要一个 JRE 即可。

# 阶段一：用 Maven 打包
FROM maven:3.8.6-openjdk-11 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# 阶段二：用轻量级 JRE 运行
FROM eclipse-temurin:11-jre-alpine
WORKDIR /app
COPY --from=build /app/target/myapp.jar .
CMD ["java", "-jar", "myapp.jar"]
💡
老鸟技巧 (Pro Tip): 使用 scratch 作为终极基础 对于 Go 或 Rust 这样能编译出完全静态链接二进制文件的语言，你可以使用 FROM scratch 作为第二阶段。scratch 是 Docker 的内置空镜像，大小为 0 字节。这样你的最终镜像就只包含你的二进制文件，连操作系统都没有，安全性和体积都做到了极致。但要注意，此时你无法使用 sh 进入容器排错。
🚑 踩坑自救室
Q: 报错 "/bin/sh: ./myapp: not found"，但我明明 COPY 进去了啊？
A: 99% 的概率是因为你在第一阶段编译的二进制文件依赖了动态链接库（比如 glibc），而第二阶段的 alpine 镜像使用的是 musl libc。解决办法：在 Go 编译时加上 CGO_ENABLED=0 进行静态编译，或者第二阶段不要用 alpine，改用 debian:buster-slim 等镜像。
Q: 多阶段构建太慢了，每次都要重新下载依赖怎么办？
A: 利用我们在第 19 集中讲的“分层缓存”。在第一阶段，先 COPY go.mod 和 go.sum（或者 Java 的 pom.xml），运行一次依赖下载命令，然后再 COPY 真正的源码。这样只要依赖没变，下载依赖这一步就会被瞬间缓存。

多阶段构建是 Dockerfile 编写的分水岭。掌握了它，你的镜像就会像经过健身房特训一样，告别臃肿，只留一身精壮的肌肉。
