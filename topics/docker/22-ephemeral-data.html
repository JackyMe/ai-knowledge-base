22. 短命容器与消失的数据

这是一个真实的悲惨故事：某天深夜，新晋运维小王接到了扩容通知。他熟练地敲下 docker rm -f mysql-server 准备重启一个新的容器。三秒钟后，他突然意识到一个恐怖的事实：过去半年积累的用户数据，随着这个命令，永远地灰飞烟灭了。

这就是 Docker 新手最容易踩的天坑：不要相信容器，它们天生就是短命鬼。

理解“读写层” (Writable Layer)

在第 19 集中我们讲过，Docker 镜像是分层的，而且这些层是只读的 (Read-only)。当你运行一个容器时，Docker 会在这些只读层之上，偷偷加上一个读写层 (Writable Layer)。

你在容器里产生的所有新数据（比如下载的文件、数据库写入的记录、生成的日志），统统都存放在最顶部的这个“读写层”里。而最要命的设定是：一旦容器被删除（docker rm），这个读写层也会被连根拔起，直接销毁。

动手实验：证明数据的消失

耳听为虚，眼见为实。我们来亲自演示一下数据是如何消失的。

🧪 实验：消失的日记

1. 启动一个 Ubuntu 容器并命名为 my-ubuntu：

docker run -it --name my-ubuntu ubuntu bash

2. 在容器内部，我们创建一个文件并写点秘密：

echo "这是我一辈子的积蓄" > /root/diary.txt
cat /root/diary.txt
# 输出: 这是我一辈子的积蓄

3. 退出容器（输入 exit），然后毫不留情地删除它：

docker rm my-ubuntu

4. 重新基于同一镜像启动一个新容器：

docker run -it --name new-ubuntu ubuntu bash

5. 试着找回你的日记：

cat /root/diary.txt
# 轰隆！输出: cat: /root/diary.txt: No such file or directory

为什么 Docker 要这么绝情？

你可能会骂：“这设计也太反人类了吧！”但实际上，这正是容器架构的精髓所在，我们称之为“不可变基础设施” (Immutable Infrastructure)。

传统的服务器被当成“宠物” (Pets) 来养，生病了你要去治，里面的环境变得越来越复杂、独一无二。而容器被设计成“牛羊” (Cattle)，它们没有名字，只有编号，一旦生病了（崩溃、卡死），我们的做法不是去修复它，而是直接杀掉，重新拉起一头新的。

要做到“随时可以被替换”，容器就必须是无状态的 (Stateless)。容器本身不应该保存任何需要持久化的核心数据。

如何拯救数据？三种挂载方式

既然容器靠不住，那数据库这些必须要保存数据的应用怎么办呢？答案是把数据存到容器外面去。Docker 提供了三种主要的挂载（Mount）方式：

  • Volumes (数据卷)：由 Docker 统一管理的宿主机存储区域，最安全，最推荐。
  • Bind Mounts (绑定挂载)：直接将宿主机上的绝对路径映射到容器里，适合开发阶段。
  • tmpfs Mounts：数据只存在于宿主机内存中，用于极高安全要求或只需临时高速存储的场景。
📌
选择指南 不知道用哪种？记住这个口诀：
- 生产环境的数据库/日志：无脑选 Volumes。
- 本地写代码，想让容器实时看到你改的代码：无脑选 Bind Mounts。
- 存储敏感密码或者用完就扔的缓存：选 tmpfs。
🚑 踩坑自救室
Q: 我用 docker stop 停止了容器，数据会丢吗？
A: 不会！stop 只是让进程暂停，读写层依然完好无损。只有当你执行 docker rm 删除容器时，数据才会真的灰飞烟灭。但我们强烈建议你依然不要在读写层存重要数据，因为在 Kubernetes 等集群环境中，容器随时可能被调度器自动销毁。
