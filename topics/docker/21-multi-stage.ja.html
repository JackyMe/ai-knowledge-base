第21レッスン：究極の軽量化：マルチステージビルド

家を建てる時のことを想像してみてください。従来の建築現場では、レンガやセメントだけでなく、ミキサー車、足場、作業員の仮設ベッドまですべて完成した家の中に置き去りにしていたらどうでしょうか？入居者がドアを開けたら、リビングにコンクリートミキサー車が鎮座していたら驚愕しますよね。

荒唐無稽な話に聞こえますが、Docker の世界では多くの初心者がまさにこれと同じことをやってしまっています。コンパイラ、テストツール、ソースコード全体をそのまま最終イメージに詰め込んでしまうのです。その結果、本来わずか 15MB の Go バイナリのはずが、Docker イメージ全体で 800MB 超に膨れ上がってしまいます。

なぜイメージが巨大化してしまうのか？

典型的な失敗例を見てみましょう。小明は Go 言語でシンプルな Web サービスを開発し、次のような Dockerfile を作成しました：

# アンチパターン：単一ステージビルド
FROM golang:1.20
WORKDIR /app
COPY . .
RUN go build -o myapp main.go
CMD ["./myapp"]

ビルド完了後、サイズを確認した小明は思わず目を見張りました：

docker images | grep myapp
myapp       latest      a1b2c3d4e5f6   About a minute ago   850MB

なぜこれほど巨大なのでしょうか？それは、ベースイメージである golang:1.20 に完全な Linux OS、Go コンパイラ、標準ライブラリ、各種ビルドツール一式が含まれているからです。しかし実際の運用時には、Go が生成したスタンドアロンなバイナリファイルだけがあれば十分で、それ以外のツールは一切不要です。

マルチステージビルド：必要な成果物だけを持ち運ぶ

マルチステージビルド（Multi-stage Build）とは、「作業現場」と「完成品」を明確に切り分ける技術です。第1ステージ（ビルド現場）でコードをコンパイルし、第2ステージ（本番実行環境）にはコンパイルされたバイナリのみをコピーし、ビルドツール群はすべてその場に廃棄します。


flowchart LR
    subgraph S1 ["ステージ 1: ビルド環境 Builder"]
        A["ベースイメージ golang:1.20"] --> B["ソースコードをコピー"]
        B --> C["go build を実行"]
        C -.-> D{"バイナリファイルの生成"}
    end
    
    subgraph S2 ["ステージ 2: 本番実行環境 Production"]
        E["極小イメージ alpine"] --> F["ステージ 1 からバイナリのみコピー"]
        D ==> F
        F --> G["最終イメージ: わずか 20MB"]
    end

実践例：Go プロジェクトの究極スリム化

マルチステージビルドを使って小明の Dockerfile を書き直してみましょう：

🛠️ ステップ 1: マルチステージ Dockerfile の作成
# 第1ステージ：builder という名前を付与
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
# 静的リンクビルド：Alpine 環境で動作するよう CGO を無効化
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp main.go

# 第2ステージ：本番環境。超軽量な alpine イメージを使用
FROM alpine:latest
WORKDIR /root/
# builder ステージからコンパイル済みバイナリのみをコピー
COPY --from=builder /app/myapp .
# 実行権限を付与
RUN chmod +x myapp

CMD ["./myapp"]

ここで重要なのが AS builder と COPY --from=builder という構文です。AS で第1ステージにエイリアスを付け、--from を使うことで、前のステージの成果物だけをピンポイントで次ステージへ転送できます。

この Dockerfile で再ビルドしてサイズを比較してみましょう：

docker build -t myapp:slim .
docker images | grep myapp
myapp       slim        b2c3d4e5f6g7   About a minute ago   22.4MB
myapp       latest      a1b2c3d4e5f6   10 minutes ago       850MB

850MB から 22.4MB へと、サイズが 約 38 分の 1 に圧縮されました！ディスク容量の節約はもちろん、CI/CD パイプラインでのイメージ転送（Pull/Push）や本番サーバーでのオートスケーリング速度が飛躍的に向上します。

Java (Maven + JRE) のマルチステージビルド

Go だけでなく、Java や C#、Rust などコンパイルを要する言語でもマルチステージビルドは必須です。Java ではビルド時に Maven や Gradle、JDK が必要ですが、本番実行時には軽量な JRE（Java Runtime Environment）だけで十分です。

# ステージ 1：Maven と JDK で JAR をビルド
FROM maven:3.8.6-openjdk-11 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# ステージ 2：軽量な Alpine JRE で実行
FROM eclipse-temurin:11-jre-alpine
WORKDIR /app
COPY --from=build /app/target/myapp.jar .
CMD ["java", "-jar", "myapp.jar"]
💡
プロの知恵 (Pro Tip): scratch イメージによる極限の最小化 Go や Rust のように完全な静的リンクバイナリを生成できる場合、第2ステージで FROM scratch を指定できます。scratch は Docker 組み込みの 0 バイトの空イメージです。OS のファイルすら含まれずバイナリ単体のみとなるため、セキュリティ攻撃面を極小化しサイズも最小になります（※コンテナ内に sh などが存在しないため、docker exec での内部シェル調査はできなくなります）。
🚨 トラブルシューティング救急室
Q: コンテナ起動時に "/bin/sh: ./myapp: not found" と怒られます。COPY は成功しているはずですが？
A: 99% の原因は動的リンクライブラリ（glibc など）の不一致です。第1ステージでビルドしたバイナリが glibc を要求しているのに対し、第2ステージの Alpine は musl libc を使用しています。解決策：Go ビルド時に CGO_ENABLED=0 を付与して静的リンクにするか、第2ステージを debian:buster-slim などの glibc 系軽量イメージに変更します。
Q: マルチステージビルドを行うと、毎回依存関係のダウンロードが走って遅いです。
A: 第19レッスンで学んだ「レイヤーキャッシュ」を第1ステージにも適用しましょう。ソースコード全体をコピーする前に、まず go.mod / go.sum（または pom.xml）のみを先にコピーして依存関係をダウンロードするコマンドを実行します。依存関係に変更がない限り、ダウンロードステップはキャッシュされ高速化されます。

マルチステージビルドを使いこなせるかどうかは、実務レベルの Docker スキルにおける重要な分岐点です。無駄な贅肉を削ぎ落とし、洗練された軽量コンテナを構築しましょう。
