14. 헬스체크: 컨테이너 자가 진단

🧟 프로세스는 살았지만 응답하지 않는 "좀비" 컨테이너

Nginx를 이용해 트래픽을 중계하는 API 게이트웨이를 운영하던 중, 갑작스러운 트래픽 폭증으로 Nginx 내부 워커 커넥션 풀이 완전히 고갈되었습니다. 외부 사용자의 HTTP 요청은 모두 타임아웃되고 서비스는 완전히 마비되었습니다.

하지만 관리자가 서버에 접속해 docker ps를 실행해 보면 다음과 같이 태연하게 출력됩니다:
nginx-gateway Up 3 days

Docker 데몬은 "내부 1번 프로세스가 아직 살아있으니 컨테이너는 정상(Up) 상태"라고 판단합니다. 실제 비즈니스 로직은 완전히 먹통인데 겉보기 프로세스만 살아있는 이 현상을 가사(假死, Zombie) 상태라고 부릅니다.

1. 헬스체크(Healthcheck)가 필요한 이유

기본적으로 Docker는 컨테이너 내부의 메인 프로세스(PID 1)의 생존 여부만을 체크합니다. DB 연결 실패, 스레드 데드락, 메모리 포화 등으로 실제 요청 처리가 불가능한 상태는 감지하지 못합니다.

이 문제를 해결하기 위해 도입된 기능이 바로 Healthcheck(헬스체크)입니다. 관리자가 Docker에게 컨테이너의 '맥박을 짚는 법(진단 명령어)'을 지정해 두면, 주기적으로 프로브를 실행하여 응답 상태를 검증합니다.

2. 헬스체크 상태 전이도

헬스체크가 설정된 컨테이너는 docker ps의 STATUS 열에 다음과 같이 건강 상태가 명시됩니다.

  • Up (health: starting): 컨테이너가 막 실행되어 초기화 중이며 최초 검진을 대기 중인 상태.
  • Up (healthy): 진단 명령어 테스트 통과 (정상 응답).
  • Up (unhealthy): 연속 진단 실패 횟수가 한계치를 초과한 위험 상태.
stateDiagram-v2
    [*] --> starting : 컨테이너 구동 (초기화)
    starting --> healthy : 헬스 프로브 응답 성공
    starting --> unhealthy : 시작 유예 시간 초과 및 검진 실패
    healthy --> unhealthy : 연속 N회 검진 실패
    unhealthy --> healthy : 이후 검진에서 정상 응답 복구
    unhealthy --> Restart : 오케스트레이터 연계 시 자동 재시작

3. 실전 적용: 헬스체크 설정 문법

가장 표준적인 방법은 Dockerfile에 기술하는 것이지만, docker run 명령어 옵션으로도 즉시 지정할 수 있습니다.

실무 시나리오 1: Web API 서비스 진단 (HTTP 프로브)

Node.js 웹 서비스 내부에 /health 엔드포인트를 구현해 두고, curl을 이용해 주기적으로 HTTP 200 상태 코드를 확인합니다.

docker run -d --name web-api \
  --health-cmd="curl -f http://localhost:8080/health || exit 1" \
  --health-interval=30s \
  --health-timeout=3s \
  --health-retries=3 \
  my-node-app

옵션 세부 분석:

  • --health-cmd: 실행할 진단 명령. curl -f는 4xx/5xx 에러 시 즉시 실패 코드를 반환하며, || exit 1을 붙여 실패 시 명확한 비정상 종료 코드를 반환합니다.
  • --health-interval: 진단 주기 (30초마다 1회 실행).
  • --health-timeout: 단일 진단 타임아웃 (3초 이내에 응답이 없으면 실패 처리).
  • --health-retries: 최대 실패 허용 횟수 (3회 연속 실패 시 최종 unhealthy로 판정).

실무 시나리오 2: 데이터베이스 진단 (CLI 프로브)

HTTP 포트가 없는 데이터베이스는 자체 CLI 핑 도구를 활용합니다.

# MySQL 데이터베이스 핑 진단
docker run -d --name mysql-db \
  --health-cmd="mysqladmin ping -h localhost -uroot -p$MYSQL_ROOT_PASSWORD" \
  mysql:8.0

# Redis 캐시 서버 PONG 응답 진단
docker run -d --name redis-cache \
  --health-cmd="redis-cli ping | grep PONG" \
  redis:alpine

4. 헬스체크 이력 로그 확인: docker inspect

컨테이너가 unhealthy 상태로 빠졌을 때 구체적으로 어떤 에러가 났는지 확인하려면 다음 명령어를 실행합니다.

docker inspect --format='{{json .State.Health.Log}}' web-api

최근 5회 동안 수행된 헬스체크 실행 시각, 반환 코드, 표준 출력 에러 메시지를 JSON 형태로 상세히 확인할 수 있습니다.

🚑 트러블슈팅 구조대
Q: 무거운 Java/Spring Boot 컨테이너가 부팅도 끝나기 전에 unhealthy로 판정됩니다.
A: Spring Boot처럼 초기 부팅에 1분 이상 소요되는 애플리케이션은 시작 유예 시간(Start Period)을 반드시 부여해야 합니다. --health-start-period=60s 옵션을 추가하면 부팅 중인 첫 60초 동안 발생하는 진단 실패는 실패 횟수에 카운트되지 않습니다.
🚀
실무 팁: unhealthy 상태가 되면 컨테이너가 자동 재시작될까요?

많은 입문자가 착각하는 부분입니다. 순수 단일 Docker 데몬은 unhealthy 상태가 되더라도 컨테이너를 자동으로 재시작하지 않습니다! 단지 상태 뱃지만 '비정상'으로 표시할 뿐입니다.
자가 치유(Self-Healing: 비정상 컨테이너 자동 파기 및 신규 생성)를 구현하려면 Docker Swarm이나 Kubernetes (K8s) 같은 오케스트레이터를 연동해야 합니다. Docker Compose에서는 depends_on: { condition: service_healthy }와 연계하여 서비스 간 완벽한 순차 기동을 보장하는 핵심 기술로 활용됩니다.
