11. 破门而入：钻进容器内部

🔍 案发现场：找不到的配置文件

想象一下，你刚刚部署了一个完美的 Web 应用，满心欢喜地打开浏览器，却只看到一个冷酷的 500 错误。你查看了下初步的信息，发现程序报了一个错：FileNotFoundError: [Errno 2] No such file or directory: '/data/config.json'。

“不可能啊！”你喊道，“我明明在代码里写对了路径，而且在我的电脑上跑得好好的！”

这个时候，最直接的排错方式，就是“钻进”那个正在运行的容器里面，亲眼看看那个目录到底长什么样。就像房子漏水了，你得开门进去看看到底是哪根管子破了一样。

一、芝麻开门：docker exec 命令

在 Docker 世界里，进入一个正在运行的容器的“任意门”就是 docker exec 命令。它的全称是 execute（执行），意思是在运行的容器中执行一条命令。

docker exec -it my-web-app sh

这条命令看起来简单，但里面暗藏玄机，我们来拆解一下最核心的 -it 参数：

  • -i (interactive): 保持标准输入 (STDIN) 开启。如果没有它，你敲回车，容器根本收不到你的键盘输入。
  • -t (tty): 分配一个伪终端 (pseudo-TTY)。这让你能看到一个像模像样的命令行提示符，而不是对着黑屏幕发呆。

这两个参数几乎总是形影不离，一起使用，简写为 -it。

💡
到底用什么 Shell？

上面的命令最后我们写了 sh。为什么不是 bash？
这取决于容器的操作系统（基础镜像）。很多现代的轻量级镜像（比如基于 Alpine Linux 的镜像）为了极致缩小体积，直接把 bash 阉割掉了，只保留了最基础的 sh (或 /bin/ash)。
老鸟建议： 先尝试 bash，如果报错 executable file not found in $PATH，立刻降级换成 sh。

二、进门之后能干啥？

一旦你成功通过 sh 或 bash 进入了容器，你就会看到命令行提示符变了，比如变成了 /app #。这说明你已经“穿越”到了容器的内部世界。这里和宿主机是完全隔离的：

graph TD subgraph 宿主机 Host H_FS[Mac/Linux 文件系统 /Users, /var, /etc] end subgraph 容器内部 Container C_FS[容器独立文件系统 /app, /data, /etc] end H_FS -.-|完全隔离| C_FS

在这里，你可以像操作一台新机器一样，执行各种排查命令：

# 看看我是谁（通常是 root，但也可能是普通用户）
whoami

# 看看我在哪，目录里有啥
pwd && ls -la

# 查看那个该死的配置文件到底存不存在
cat /data/config.json

# 看看容器里跑着哪些进程
ps aux

# 查看容器的环境变量（有时候是环境变量没配对导致程序崩溃）
env

想要个工具？现场装！

如果在容器里发现缺少了排错工具（比如想测试网络，但没有 curl），不用急着去改镜像，你可以直接在里面装：

# 如果是 Debian/Ubuntu 系统的容器
apt-get update && apt-get install -y curl

# 如果是 Alpine 系统的容器
apk add --no-cache curl

三、一击脱离：One-Shot 模式

有时候你并不想“长住”在容器里，只是想看一眼某个文件就走。这时候就不需要 -it 了，直接把你想执行的命令跟在后面：

# 直接在外部查看容器内的 Nginx 配置文件
docker exec nginx-server cat /etc/nginx/nginx.conf

# 快速让容器里的应用重新加载配置（不重启容器）
docker exec nginx-server nginx -s reload

这种非交互式的用法，在写自动化脚本时非常有用。

四、乾坤大挪移：docker cp 文件拷贝

排查完问题，你可能想把宿主机的某个修复好的配置文件直接传进容器，或者把容器里的报错日志拷出来。用不着在容器里费劲地装 VIM 改代码，用 docker cp 即可：

# 1. 从宿主机拷贝到容器里：
# docker cp [本地文件] [容器名]:[容器内路径]
docker cp ./fixed-config.json my-web-app:/data/config.json

# 2. 从容器拷贝到宿主机里：
# docker cp [容器名]:[容器内路径] [本地路径]
docker cp my-web-app:/app/crash.dump ./local-folder/

五、如何优雅地退出

在容器的终端里玩够了，怎么出来呢？
很简单，直接输入 exit 回车，或者按快捷键 Ctrl + D 即可。
放心，这只是退出了你进入容器的这个 bash 进程，容器本身的核心应用还在后台欢快地跑着呢！

🚑 踩坑自救室
Q1: 报错 OCI runtime exec failed: exec failed: unable to start container process... executable file not found in $PATH: unknown
A: 翻译成大白话就是：你想执行的这个程序（通常是你写的 bash 或 sh）在容器里找不到！如前文所述，很大可能是你用了 alpine 镜像，它没有 bash。请把命令里的 bash 换成 sh 试试。如果连 sh 都没有（比如 scratch 极简镜像），那这个容器你是进不去的，只能通过查日志来排错了。
Q2: 报错 Error response from daemon: Container xxx is not running
A: 容器必须在运行状态（Up）才能被 exec 进去！如果你的容器一启动就崩溃退出了（Exited），你是进不去的。你需要排查为什么它启动失败（看下一章：查日志）。
🚀
Pro-tip / 老鸟技巧

虽然通过 docker exec 和 docker cp 直接修改容器内的文件可以快速修复线上问题，但这叫“打补丁”，是反模式的！
因为容器一旦被删除重建，你手动修改的所有东西都会灰飞烟灭。正确的做法是：利用 exec 查出问题在哪，然后在宿主机修改代码或 Dockerfile，重新打包镜像，重新部署。永远保持容器是可抛弃的 (Disposable)！
