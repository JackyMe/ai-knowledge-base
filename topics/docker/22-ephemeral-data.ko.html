제22레슨: 단명하는 컨테이너와 사라지는 데이터

실제 현장에서 발생했던 비극적인 이야기입니다: 어느 날 늦은 밤, 신입 운영 담당자가 서버 스케일아웃 작업을 진행하던 중 무심코 docker rm -f mysql-server를 실행하여 컨테이너를 새로 띄우려고 했습니다. 3초 후, 그는 소름 끼치는 사실을 깨달았습니다. 지난 반년간 쌓여온 귀중한 사용자 데이터 전체가 이 한 줄의 명령어와 함께 영원히 허공으로 증발해 버린 것입니다.

이것이 바로 Docker 입문자가 가장 빠지기 쉬운 거대한 함정입니다: 컨테이너를 맹신하지 마세요. 컨테이너는 태생적으로 언제든 소멸할 수 있는 "단명(Ephemeral)" 존재입니다.

"읽기/쓰기 레이어(Writable Layer)"의 이해

제19레슨에서 배웠듯이 Docker 이미지는 여러 겹의 레이어로 구성되며, 이 이미지 레이어들은 모두 읽기 전용(Read-only)입니다. 컨테이너를 실행하면 Docker는 이 읽기 전용 레이어들 맨 위에 몰래 얇은 읽기/쓰기 레이어(Writable Layer, 컨테이너 레이어) 하나를 추가합니다.

컨테이너 내부에서 생성되는 모든 새로운 데이터(다운로드한 파일, DB에 기록된 데이터, 로그 파일 등)는 전부 최상단의 "읽기/쓰기 레이어"에 저장됩니다. 그리고 가장 치명적인 규칙은: 컨테이너가 삭제(docker rm)되는 즉시, 이 읽기/쓰기 레이어도 뿌리째 통째로 파괴된다는 점입니다.

직접 확인하는 실험: 사라진 비밀 일기장

백문이 불여일견입니다. 데이터가 어떻게 사라지는지 직접 실험해 보겠습니다.

🧪 실험: 사라진 일기장

1. Ubuntu 컨테이너를 실행하고 이름을 my-ubuntu로 지정합니다:

docker run -it --name my-ubuntu ubuntu bash

2. 컨테이너 내부에서 파일을 하나 만들고 비밀을 적어봅니다:

echo "내 평생의 전 재산과 비밀" > /root/diary.txt
cat /root/diary.txt
# 출력 결과: 내 평생의 전 재산과 비밀

3. 컨테이너를 빠져나온 뒤(exit 입력), 가차 없이 삭제합니다:

docker rm my-ubuntu

4. 동일한 이미지로 새 컨테이너를 다시 시작합니다:

docker run -it --name new-ubuntu ubuntu bash

5. 비밀 일기장을 다시 찾아봅니다:

cat /root/diary.txt
# 에러 출력: cat: /root/diary.txt: No such file or directory

왜 Docker는 이렇게 냉정하게 설계되었을까요?

"이거 너무 위험한 설계 아닌가요?"라고 생각할 수 있습니다. 하지만 사실 이것이 바로 현대 클라우드 네이티브 컨테이너 아키텍처의 핵심인 "불변 인프라(Immutable Infrastructure)" 철학입니다.

전통적인 서버는 마치 "애완동물(Pets)"처럼 다루어졌습니다. 아프면 치료해 주어야 하고, 환경이 점점 복잡해지며 세상에 단 하나뿐인 독특한 상태가 됩니다. 반면 컨테이너는 "가축(Cattle)"처럼 다루어집니다. 이름 대신 번호만 부여되며, 문제가 생기면(크래시, 응답 없음) 고치려 애쓰지 않고 즉시 삭제하고 새로운 것을 띄웁니다.

"언제든 버리고 다시 교체할 수 있으려면" 컨테이너는 반드시 무상태(Stateless)여야 합니다. 컨테이너 자체는 영속화해야 할 핵심 데이터를 내부에 품고 있어서는 안 됩니다.

데이터를 안전하게 구출하는 세 가지 마운트 방식

컨테이너가 단명한다면, 데이터베이스처럼 데이터를 반드시 보존해야 하는 애플리케이션은 어떻게 해야 할까요? 정답은 데이터를 컨테이너 외부(호스트)에 저장하는 것입니다. Docker는 세 가지 주요 마운트(Mount) 방식을 제공합니다:

  • Volumes (데이터 볼륨): Docker가 호스트 머신에서 직접 안전하게 관리하는 전용 스토리지 영역. 가장 안전하며 프로덕션에 적극 권장됩니다.
  • Bind Mounts (바인드 마운트): 호스트의 절대 경로 디렉토리를 컨테이너 내부에 직접 연결. 로컬 개발 환경에 최적입니다.
  • tmpfs Mounts: 데이터가 호스트 머신의 메모리(RAM)에만 존재. 높은 보안이 필요하거나 일회성 초고속 임시 처리에 사용됩니다.
📌
마운트 선택 완벽 가이드 어떤 방식을 써야 할지 고민된다면 다음 공식만 기억하세요:
- 프로덕션 환경의 데이터베이스 / 핵심 로그: 무조건 Volumes 선택.
- 로컬에서 코드 수정 시 컨테이너에 즉시 실시간 반영하고 싶을 때: 무조건 Bind Mounts 선택.
- 비밀번호 등 민감 데이터나 일회성 임시 캐시: tmpfs 선택.
🚨 트러블슈팅 응급실
Q1: docker stop으로 컨테이너를 중지하면 데이터가 사라지나요?
A: 아닙니다! stop은 프로세스 실행만 일시 정지하는 것이며 읽기/쓰기 레이어는 그대로 유지됩니다. 오직 docker rm으로 컨테이너를 삭제할 때만 읽기/쓰기 레이어가 소멸합니다. 하지만 쿠버네티스나 클라우드 환경에서는 컨테이너가 예고 없이 자동 삭제/재생성될 수 있으므로, 영속화해야 할 데이터를 읽기/쓰기 레이어에 두는 것은 절대 금물입니다.

컨테이너의 "단명" 본질을 이해하셨다면, 다음 레슨에서는 컨테이너에 영구적인 생명력을 불어넣는 "궁극의 데이터 보호막"——Volumes (데이터 볼륨)을 본격적으로 학습하겠습니다.
