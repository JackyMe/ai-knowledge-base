14. Health Checks: Container Self-Diagnosis

🧟 The Suspended Animation of "Zombie" Containers

Imagine you configure an Nginx container serving as a reverse proxy gateway. One afternoon, incoming traffic surges, saturating Nginx's worker connection pool and leaving it completely incapable of accepting new HTTP requests.

Anxiously, you run docker ps, only to see:
nginx-gateway Up 3 days

Docker proudly declares: its primary process is still running, everything looks fine, Up!
Yet for real users, the website is completely unresponsive. This state—where the process is alive, but the business service is dead—is known as "hung" or "suspended animation".

1. Why Do We Need Healthcheck?

By default, Docker's sole criterion for judging whether a container is alive or dead is whether process PID 1 has terminated. It does not know if your application hit an internal deadlock, failed database handshakes, or leaked all worker threads.

To bridge this gap, Docker introduced the Healthcheck mechanism. It allows you to define custom diagnostic probes—executing periodic check commands. If the command succeeds, the container is confirmed healthy; if it fails consecutively, Docker flags it as unhealthy.

2. How It Works & State Progression

Once a container is configured with health checks, its STATUS column in docker ps includes an explicit health diagnosis:

  • Up (health: starting): The container just started, initializing or awaiting its first probe window.
  • Up (healthy): Health probe passed successfully; fully operational.
  • Up (unhealthy): Multiple consecutive probes failed; marked as critically degraded.
stateDiagram-v2 [*] --> starting : Container Starts starting --> healthy : Probe check passes starting --> unhealthy : Exceeds start-period & fails healthy --> unhealthy : N consecutive probe failures unhealthy --> healthy : Probe recovers successfully unhealthy --> Restart : If auto-healing configured (Orchestrator)

3. How to Configure Health Checks

The standard best practice is declaring health check rules inside your Dockerfile (detailed in the next chapter). However, you can also pass them directly via docker run CLI flags.

Scenario 1: Probing a Web API (HTTP Probe)

Suppose we have a Node.js web service with a dedicated /health endpoint returning HTTP 200 OK. We can instruct Docker to periodically ping this endpoint using curl:

docker run -d --name web-api \
  --health-cmd="curl -f http://localhost:8080/health || exit 1" \
  --health-interval=30s \
  --health-timeout=3s \
  --health-retries=3 \
  my-node-app

Flag Breakdown:

  • --health-cmd: The shell command to execute inside the container. curl -f returns an error code on 4xx/5xx HTTP responses, and || exit 1 guarantees a non-zero exit status to Docker on failure.
  • --health-interval: Run probe every 30 seconds (avoid setting this too short to prevent self-inflicted load).
  • --health-timeout: Maximum wait time per probe (3s); if no response, it counts as a failure.
  • --health-retries: Failure tolerance; 3 consecutive probe failures mark the container unhealthy.

Scenario 2: Probing Databases (CLI Probe)

Databases do not typically expose HTTP endpoints, so we probe them using native CLI client tools:

# Healthcheck for MySQL by pinging the database server
docker run -d --name mysql-db \
  --health-cmd="mysqladmin ping -h localhost -uroot -p$MYSQL_ROOT_PASSWORD" \
  mysql:8.0

# Healthcheck for Redis
docker run -d --name redis-cache \
  --health-cmd="redis-cli ping | grep PONG" \
  redis:alpine

4. Inspecting Healthcheck Diagnostic History

If a container becomes unhealthy, how do you diagnose why? Inspect the health log history:

docker inspect --format='{{json .State.Health.Log}}' web-api

This returns structured JSON with the exact timestamps, exit codes, and output logs of the last 5 probe executions, making debugging fast and transparent.

🚑 Pitfall Rescue Room
Q1: Why does my Java container immediately turn unhealthy before finishing its startup sequence?
A: Frameworks like Java Spring Boot can take 1~2 minutes to boot. If your interval is 10s and retries is 3, Docker marks it dead after 30 seconds. Solution: Add the --health-start-period=60s flag (grace period). During these initial 60 seconds, any failed checks are forgiven and do not count toward consecutive failure limits.
🚀
Pro Tips: Does Becoming Unhealthy Automatically Restart the Container?

This is a widespread misconception! A standalone Docker daemon will NEVER automatically restart a container just because it turns unhealthy! It merely flags the container as unhealthy in metadata.
To achieve automated self-healing and automatic restarts upon failure, you need container orchestrators like Docker Swarm or Kubernetes (K8s). Alternatively, in Docker Compose, you can use depends_on conditions (condition: service_healthy) to coordinate service dependencies. Health checks are the fundamental building blocks of modern resilient systems.
