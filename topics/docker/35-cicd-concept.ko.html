제35레슨: 에필로그: CI/CD 자동화 파이프라인과 그 너머의 세상

마지막 레슨까지 완주하신 것을 진심으로 축하합니다! 이제 여러분은 로컬 컴퓨터에서 Docker를 자유자재로 다룰 수 있게 되었습니다. 하지만 실제 배포할 때마다 서버에 SSH로 접속하여 수동으로 git pull을 받고, docker build를 돌리고, docker compose up을 쳐야 할까요?

이러한 수동 수공업 배포 방식은 반드시 휴먼 에러를 유발합니다. 진정한 엔지니어의 미덕은 자동화에 있습니다.

이것이 바로 현대 DevOps의 꽃, CI/CD (지속적 통합 / 지속적 배포)입니다.

1. CI/CD 자동화 파이프라인 전체 흐름도

현대적인 소프트웨어가 코딩부터 실서버 배포까지 어떻게 자동으로 "흘러가는지" 한눈에 조망해 봅니다:

sequenceDiagram
    participant Dev as 개발자
    participant Git as GitHub / GitLab
    participant CI as CI Runner
(빌드 서버)
    participant Reg as Docker Registry
(이미지 저장소)
    participant Prod as 운영 서버

    Dev->>Git: 1. git push 코딩 완료 후 커밋 푸시
    Git-->>CI: 2. Webhook 트리거 발생
    activate CI
    CI->>CI: 3. 자동 단위/통합 테스트 실행
    CI->>CI: 4. docker build 이미지 빌드
    CI->>Reg: 5. docker push 이미지 레지스트리 업로드
    deactivate CI
    CI-->>Prod: 6. 운영 서버에 원격 배포 통보
    activate Prod
    Prod->>Reg: 7. docker pull 최신 빌드 이미지 다운로드
    Prod->>Prod: 8. docker compose up 무중단 재기동
    deactivate Prod

2. CI (지속적 통합): 기계가 대신하는 무결성 검증

CI (Continuous Integration)의 핵심은 코드가 커밋될 때마다 클라우드 빌드 머신이 자동으로 테스트와 빌드를 수행하여 버그를 즉각 잡아내는 것입니다.

GitHub Actions를 예로 들면, .github/workflows/docker-build.yml에 다음과 같은 파이프라인 스크립트를 작성합니다:

# GitHub Actions 자동 빌드 & 푸시 워크플로우
name: CI to Docker Hub

on:
  push:
    branches: [ "main" ] # main 브랜치에 푸시될 때만 자동 실행

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: 소스코드 체크아웃
        uses: actions/checkout@v3

      - name: Docker Hub 로그인
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Docker 이미지 빌드 및 푸시
        uses: docker/build-push-action@v4
        with:
          context: .
          push: true
          # 이미지 태그 관리의 핵심!
          tags: myname/myapp:latest, myname/myapp:${{ github.sha }}
🏷️ 태그(Tag) 관리의 정석: latest와 Git 커밋 SHA의 결합

위 코드에서는 두 개의 태그를 동시에 부여했습니다: latest와 ${{ github.sha }} (Git 커밋 고유 해시값).

latest 태그는 항상 최신 빌드로 덮어씌워지기 때문에, 장애 발생 시 이전 버전으로 롤백하려고 해도 직전 latest가 어떤 소스코드 버전이었는지 추적하기 어렵습니다. 커밋 해시 태그(예: myapp:a1b2c3d)를 함께 빌드해 두면, 문제 발생 시 해당 해시 태그 이미지를 지정하여 단 1초 만에 안전하게 직전 버전으로 롤백할 수 있습니다!

3. CD (지속적 배포): 무중단 자동 업데이트

CD (Continuous Deployment)는 빌드된 이미지를 운영 서버에 자동으로 반영하는 단계입니다.

단일 서버 환경에서는 Watchtower와 같은 도구를 컨테이너로 띄워둘 수 있습니다. Watchtower는 주기적으로 Docker Hub를 감시하다가 새 이미지가 푸시되면 이를 자동으로 다운로드하고 컨테이너를 재생성해 줍니다:

# 이미지 자동 업데이트 도구 Watchtower 실행
$ docker run -d \
  --name watchtower \
  -v /var/run/docker.sock:/var/run/docker.sock \
  containrrr/watchtower

4. 더 넓은 세상: Kubernetes(K8s)의 부름

서비스가 폭발적으로 성장하여 서버가 수십 대, 수백 대로 늘어나면 단일 서버 중심의 docker-compose만으로는 감당하기 어려워집니다:

  • 특정 서버의 하드웨어가 고장 났을 때 컨테이너들을 다른 정상 서버로 자동 이주시킬 수 있는가? (Self-Healing)
  • 이벤트 트래픽 폭증 시 웹 컨테이너를 3개에서 300개로 1초 만에 자동 확장할 수 있는가? (Auto-Scaling)
  • 사용자의 접속 끊김이 단 0.1초도 발생하지 않도록 부드럽게 새 버전을 교체할 수 있는가? (Rolling Update & Zero-Downtime)

이 대규모 클러스터 오케스트레이션 문제를 완벽하게 해결한 글로벌 표준이 바로 Google이 오픈소스로 공개한 Kubernetes (쿠버네티스, K8s)입니다.

한 문장으로 요약하자면 다음과 같습니다: "Docker가 표준 규격의 안전한 컨테이너 화물을 만든다면, Kubernetes는 전 세계의 항만과 수천 척의 초대형 화물선을 총괄 지휘하는 관제 시스템입니다."

여정의 끝은 곧 새로운 시작입니다 제1레슨에서 로컬 환경 설정 때문에 밤을 지새우며 고통받던 샤오밍에서 시작하여, 35개 레슨을 거쳐 이제 여러분은 멀티 스테이지 빌드로 초경량 이미지를 깎고, 사용자 정의 가상 네트워크와 볼륨을 설계하며, Compose와 CI/CD 파이프라인으로 안전한 인프라를 오케스트레이션하는 진정한 엔지니어로 성장하셨습니다.
