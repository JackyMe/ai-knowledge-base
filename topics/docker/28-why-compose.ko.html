제28레슨: 왜 Docker Compose가 필요한가? 수백 줄 명령어 악몽과의 작별

앞선 27개의 레슨을 통해 여러분은 docker run으로 다양한 컨테이너를 실행하고, 볼륨을 마운트하고, 포트를 매핑하고, 사용자 정의 네트워크를 구성하는 고급 기술까지 완벽하게 익혔습니다. 하지만 현실의 실제 프로젝트 환경은 생각보다 훨씬 복잡합니다...

1. 길고 긴 명령어의 깊은 절망

실제 현대적인 웹 블로그 시스템을 배포한다고 가정해 보겠습니다. 프론트엔드 웹 1개, Node.js 백엔드 API 1개, Redis 캐시 1개, MySQL 데이터베이스 1개가 필요합니다. 이를 순수 docker run 명령어로 실행하려면 다음과 같은 긴 셸 스크립트를 일일이 작성해야 합니다:

# 1. 전용 네트워크 생성
docker network create blog-net

# 2. 데이터베이스 실행
docker run -d --name blog-db --network blog-net -v db-data:/var/lib/mysql -e MYSQL_ROOT_PASSWORD=123456 mysql:8

# 3. Redis 캐시 실행
docker run -d --name blog-redis --network blog-net redis:alpine

# 4. 백엔드 API 실행 (DB가 뜰 때까지 기다려야 하는 순서 고려 필요)
docker run -d --name blog-api --network blog-net -p 3000:3000 -e DB_HOST=blog-db my-backend:v1

# 5. 프론트엔드 웹 실행
docker run -d --name blog-web --network blog-net -p 80:80 my-frontend:v1

이것은 매우 비효율적이고 위험합니다. 서비스를 업데이트하거나, 서버를 이전하거나, 새로 입사한 동료에게 로컬 개발 환경을 세팅해 줄 때마다 이 복잡한 스크립트를 공유해야 합니다. 환경 변수와 시크릿 토큰이 섞인 명령줄에서 공백 하나만 오타가 나도 전체 시스템 실행이 멈춰버립니다.

2. 구원자의 등장: Docker Compose

Docker Compose는 바로 이러한 악몽을 해결하기 위해 탄생했습니다. 핵심 철학은 매우 단순합니다: 일일이 손으로 명령어를 내려 "어떻게 해라(명령형, Imperative)"라고 지시하는 대신, 내가 "원하는 시스템의 최종 상태(선언형, Declarative)"를 한 장의 청사진 문서로 작성하여 Docker에 넘기는 것입니다.

길고 복잡한 셸 스크립트 대신, 깔끔하고 우아한 단 하나의 텍스트 파일 docker-compose.yml을 작성하면 됩니다.

flowchart LR
    File["docker-compose.yml
(선언형 인프라 청사진)"] -->|"docker compose up"| Engine{"Docker 엔진"}
    Engine --> C1["Web 컨테이너"]
    Engine --> C2["API 컨테이너"]
    Engine --> C3["DB 컨테이너"]
    Engine --> Net["전용 가상 네트워크"]
    Engine --> Vol["데이터 볼륨"]

이제 해당 파일이 위치한 디렉토리에서 단 한 줄의 명령어만 입력하면 됩니다:

docker compose up -d

놀랍도록 평온해집니다. Docker Compose가 올바른 의존성 순서에 따라 네트워크를 생성하고, 볼륨을 마운트하고, 이미지를 다운로드하여 컨테이너들을 자동으로 실행합니다.

3. Docker Compose가 제공하는 3가지 핵심 가치

💎 1. 원클릭 실행/정지 (Plug-and-Play 개발 환경)

신규 입사자가 오더라도 프로젝트 저장소를 클론한 후 docker compose up -d 한 줄이면 프로덕션과 완벽히 동일한 풀스택 로컬 환경이 1분 만에 완성됩니다. 퇴근할 때는 docker compose down 한 번으로 깔끔하게 정리할 수 있습니다.

💎 2. 코드형 인프라 (Infrastructure as Code, IaC)

모든 인프라 설정(환경 변수, 볼륨 마운트, 포트 매핑 등)이 .yml 파일에 코드로 기록되므로 Git으로 완벽하게 버전 관리됩니다. 누가 어떤 포트를 바꿨는지, 어떤 환경 변수가 추가되었는지 커밋 히스토리로 명확히 추적할 수 있습니다.

💎 3. 프로젝트별 자동 격리 스코프

my-blog 디렉토리에서 compose up을 실행하면, Compose는 디렉토리명을 기반으로 my-blog_default라는 독립된 전용 네트워크를 자동 생성합니다. 동일 호스트의 다른 프로젝트와 이름이 겹쳐도 네트워크 간섭 없이 완벽히 격리됩니다.

4. 역사적 배경: docker-compose vs docker compose

📚
하이픈(-) 하나의 큰 차이

인터넷 자료를 찾다 보면 docker-compose와 docker compose 두 가지 표기를 보게 됩니다. 단순 오타가 아닙니다!

  • V1 버전: docker-compose (하이픈 있음). Python으로 작성된 별도 독립 도구로 따로 설치해야 했으며, 현재는 공식 폐기(Deprecated)되었습니다.
  • V2 버전: docker compose (하이픈 없음, 공백 서브커맨드). Go 언어로 완전 재작성되어 Docker 엔진에 기본 내장된 공식 CLI 플러그인입니다. Docker를 설치하면 기본 포함되어 있습니다!

따라서 앞으로는 하이픈을 잊고 현대적인 docker compose를 사용하세요!

🚨 트러블슈팅 응급실
Q1: compose 실행 시 "version is obsolete" 경고가 발생합니다.
A: 과거 Compose V1 시절에는 yml 파일 최상단에 version: '3.8' 같은 선언이 필수였습니다. 하지만 최신 Compose V2 사양에서는 version 필드가 공식적으로 폐기 및 무시되므로 해당 줄을 완전히 삭제하시면 깔끔하게 실행됩니다.
