第28レッスン：なぜ Docker Compose が必要なのか？コマンド長文地獄からの脱出

これまでのレッスンを通じて、あなたは docker run コマンドを駆使して様々なコンテナを自在に起動できるようになりました。ボリュームのマウント、ポートフォワーディング、カスタムネットワークの構築まで、単体コンテナの操作は完璧です。しかし、実際のエンタープライズ開発現場には、避けて通れない過酷な現実が待っています...

1. 肥大化する起動コマンドと運用の限界

一般的なモダン Web アプリケーション（Web フロントエンド、API バックエンド、Redis キャッシュ、MySQL データベース）を本番運用することを想像してください。docker run だけで構築しようとすると、次のような長大なシェルスクリプトを書く必要があります：

# 1. 独立ネットワークの作成
docker network create blog-net

# 2. データベースの起動
docker run -d --name blog-db --network blog-net -v db-data:/var/lib/mysql -e MYSQL_ROOT_PASSWORD=123456 mysql:8

# 3. キャッシュサーバーの起動
docker run -d --name blog-redis --network blog-net redis:alpine

# 4. バックエンド API の起動 (DB 起動待ち順序への配慮が必要)
docker run -d --name blog-api --network blog-net -p 3000:3000 -e DB_HOST=blog-db my-backend:v1

# 5. フロントエンド Web の起動
docker run -d --name blog-web --network blog-net -p 80:80 my-frontend:v1

これは運用上非常にストレスです。システムのバージョンアップ、サーバー移行、または新メンバーがローカルで環境構築するたびに、この長いスクリプトを手動で共有・実行しなければなりません。環境変数に秘密鍵やトークンが混ざるとコマンドはさらに長くなり、スペースを1文字打ち間違えただけでシステム全体が起動に失敗します。

2. 救世主：Docker Compose の登場

Docker Compose は、このようなマルチコンテナ運用の課題を解決するために生まれました。その中核思想は、「手続き型（命令を一歩ずつ実行する）」から「宣言型（欲しい最終状態を定義する）」へのパラダイムシフトです。

長大なシェルスクリプトを、極めて見通しの良い宣言型設定ファイル docker-compose.yml に集約します。


flowchart LR
    File["docker-compose.yml
(宣言型設定ファイル)"] -->|docker compose up| Engine{"Docker Engine"}
    Engine --> C1["Web コンテナ"]
    Engine --> C2["API コンテナ"]
    Engine --> C3["DB コンテナ"]
    Engine --> Net["専用ネットワーク"]
    Engine --> Vol["データボリューム"]

設定ファイルを配置したディレクトリで、以下のコマンドを1行実行するだけです：

docker compose up -d

これだけで、Docker Compose が依存関係と適切な順序を自動計算し、ネットワークの作成、ボリュームの割り当て、イメージの Pull/ビルド、全コンテナの起動を一撃で完結させます。

3. Docker Compose がもたらす3大価値

💎 1. ワンクリック起動・停止（プラグ＆プレイ開発）

新人エンジニアがチームに加わった際、リポジトリをクローンして docker compose up -d を叩くだけで、本番相当の完全な開発環境が数秒で立ち上がります。終業時には docker compose down を実行するだけで全リソースが一瞬でクリーンアップされます。

💎 2. Infrastructure as Code (IaC: コードとしてのインフラ)

環境変数、ポート公開、マウント設定、リソース制限などのすべてのインフラ構成が .yml ファイルとして Git でバージョン管理されます。「誰がいつポート設定を変更したか」「どの環境変数が追加されたか」がコミット履歴として完全に追跡可能です。

💎 3. プロジェクトごとの自動名前空間分離

my-blog ディレクトリで compose up を実行すると、Compose はディレクトリ名に基づき my-blog_default という独立ネットワークを自動生成します。同一マシン上で別のプロジェクトを実行しても、コンテナ名やポートが衝突しないよう適切に分離されます。

4. 歴史的経緯：docker-compose vs docker compose

📚
ハイフンの有無による決定的な違い

ネット上の技術記事を検索すると、docker-compose（ハイフンあり）と docker compose（半角スペース区切り）の2種類の表記を見かけます。これは単なる表記揺れではありません：

  • Compose V1（非推奨・サポート終了）： docker-compose（ハイフンあり）。Python 製のスタンドアロン CLI ツールとして配布されていました。現在は公式サポートが終了しています。
  • Compose V2（現行標準）： docker compose（スペース区切り）。Go 言語でゼロから再設計され、Docker CLI の組み込みサブコマンド（プラグイン）として統合されました。

現代のベストプラクティスとしては、常にハイフンなしの docker compose を使用しましょう！

🚨 トラブルシューティング救急室
Q: Compose 実行時に "version is obsolete" という警告メッセージが表示されます。
A: 従来の Compose V1 仕様では、yml の先頭行に version: '3.8' のようなバージョン宣言が必須でした。しかし最新の Compose V2 仕様（Compose Specification）では、この version 指定は廃止され非推奨となっています。yml 先頭の version: ... 行を削除すれば警告は消えます。
