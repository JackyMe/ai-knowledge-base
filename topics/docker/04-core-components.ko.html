04. 그림으로 이해하는 3대 핵심 아키텍처

많은 입문자들이 Docker 명령어를 기계적으로 외워서 실행하곤 합니다. 하지만 시스템에 장애가 발생하거나 기술 면접에서 아키텍처에 관한 질문을 받으면 금세 막히게 됩니다. Docker를 자유자재로 다루려면 고전적이면서도 강력한 "3대 핵심 아키텍처(클라이언트-데몬-레지스트리)"를 반드시 이해해야 합니다.

Docker는 전형적인 C/S (Client-Server) 아키텍처 시스템입니다

MySQL이나 Redis와 마찬가지로 Docker 역시 명령을 내리는 클라이언트(Client)와 실제 작업을 수행하는 데몬(Daemon / Server)으로 완전히 분리되어 있습니다. 우리가 터미널에서 입력하는 명령어는 단지 데몬에게 작업을 지시하는 '리모컨' 역할을 할 뿐입니다.

3대 핵심 구성 요소 상세 분석

1. 명령을 내리는 리모컨: Docker Client (클라이언트)

터미널에서 docker build, docker run을 실행할 때 호출되는 CLI 프로그램입니다. 클라이언트의 역할은 매우 명확합니다. 사용자가 입력한 명령어를 해석하여 표준 HTTP REST API 요청으로 래핑한 뒤 백그라운드의 데몬으로 전달합니다. 클라이언트 자체는 컨테이너 생성이나 이미지 빌드 등의 무거운 작업을 직접 수행하지 않습니다.

식당에 비유하자면 클라이언트는 '주문을 받는 홀 서빙 직원'입니다. 손님의 주문을 수기지에 적어 주방에 전달하는 역할을 맡습니다.

2. 모든 작업을 총괄하는 주방장: Docker Daemon (데몬)

보통 dockerd라는 이름의 프로세스로 백그라운드에서 상시 실행되는 시스템 서비스입니다. 클라이언트가 보내오는 API 요청을 리스닝하고 있다가, 이미지를 다운로드(Pull)하고, 컨테이너 프로세스를 띄우며, 가상 네트워크 브리지와 IP를 할당하고, 메모리 제한을 거는 등 모든 실제 작업을 처리합니다. 식당의 '메인 셰프'에 해당합니다.

3. 전 세계 식자재 마트: Docker Registry (이미지 레지스트리)

요리를 하려면 식재료가 필요하듯, 데몬이 컨테이너를 띄우려면 기본 '이미지(Image)'가 필요합니다. 만약 로컬 디스크에 mysql 이미지가 없다면 데몬은 인터넷 상의 대형 식자재 마트(Registry)로 달려가 이미지를 내려받습니다.

현재 전 세계에서 가장 널리 쓰이는 기본 공식 마트가 바로 Docker Hub (hub.docker.com)입니다. 전 세계 개발자와 기업들이 자신이 빌드한 이미지를 등록(Push)하고 자유롭게 공유할 수 있습니다.

🌟
실무 팁: 안전한 공식 이미지를 고르는 요령

Docker Hub에서 이미지를 검색하면 동일한 이름의 수많은 이미지가 나타납니다. 이때 반드시 확인해야 할 두 가지 배지가 있습니다.
1. Official Image (공식 이미지): 파란색 방패 마크가 붙어 있으며, 소프트웨어 공식 개발사 및 Docker 재단이 직접 검증하고 유지보수합니다.
2. Verified Publisher (인증된 게시자): 공인된 엔터프라이즈 계정이 배포하는 이미지입니다.
검증되지 않은 일반 개인 계정의 이미지는 내부에 가상화폐 채굴 스크립트나 악성코드가 포함되어 있을 수 있으므로 무분별한 다운로드를 지양해야 합니다.

실시간 동작 과정: docker run 실행 시 내부에서 일어나는 일

가장 기본적이고 대표적인 명령어 docker run -d nginx를 실행했을 때 백그라운드에서 어떤 단계가 진행되는지 단계별로 살펴보겠습니다.

docker run -d nginx
  1. Docker Client가 터미널 입력을 받아 REST API 요청으로 변환하여 로컬 Unix 소켓(/var/run/docker.sock)을 통해 Docker Daemon으로 전달합니다.
  2. Docker Daemon은 로컬 이미지 캐시 저장소를 먼저 탐색합니다: "로컬에 nginx:latest 이미지가 이미 존재하는가?"
  3. 로컬에 이미지가 없다면, Daemon은 원격 Docker Hub 레지스트리로 접속하여 Nginx의 최신 레이어 이미지들을 병렬로 다운로드(Pull)합니다.
  4. 다운로드가 완료되면 이미지를 로컬 스토리지 드라이버에 영구 보관합니다.
  5. Daemon은 다운로드된 불변의 이미지 레이어 위에 새로운 읽기/쓰기 컨테이너 레이어를 얹고, Linux 커널의 Namespaces와 Cgroups를 구성하여 격리된 프로세스 환경을 생성합니다.
  6. Daemon이 클라이언트에게 고유한 컨테이너 ID(64자리 해시값)를 응답으로 돌려주고, 컨테이너는 백그라운드(-d 플래그)에서 독립적으로 동작하기 시작합니다.
⚠️ 트러블슈팅 구조대
Q: "Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?" 에러가 발생합니다.
A: 전 세계 Docker 사용자들에게 가장 흔하게 발생하는 대표 에러입니다. 직관적으로 번역하자면 "주문 받는 직원(Client)이 주방(Daemon) 문을 두드렸는데, 주방에 아무도 출근하지 않았다!"는 의미입니다.
원인: Docker 데몬 서비스가 백그라운드에서 실행되고 있지 않습니다.
해결 방법: macOS나 Windows 사용자라면 Docker Desktop 앱을 실행해야 하며, Linux 서버라면 sudo systemctl start docker 명령어로 데몬 서비스를 시작해 주어야 합니다.
