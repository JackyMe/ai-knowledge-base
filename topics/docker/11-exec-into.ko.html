11. 내부 진입: 실행 중인 컨테이너 접속

🔍 문제 발생 상황: 찾을 수 없는 설정 파일

웹 애플리케이션을 새로 배포하고 브라우저를 열었더니 500 내부 서버 에러가 발생했습니다. 로그를 살펴보니 FileNotFoundError: [Errno 2] No such file or directory: '/data/config.json'라는 에러가 찍혀 있습니다.

"내 로컬 환경에서는 파일 경로가 정확했고 완벽하게 돌아갔는데 왜 서버 컨테이너에서는 파일을 찾을 수 없지?"

이때 가장 빠르고 확실한 원인 규명 방법은 실행 중인 컨테이너 내부로 직접 들어가서 해당 경로의 파일과 디렉터리 상태를 눈으로 확인하는 것입니다. 방 안에 누수가 생기면 직접 문을 열고 들어가 배관을 점검하는 것과 같습니다.

1. 컨테이너의 출입문: docker exec 명령어

실행 중인 컨테이너 내부로 진입하는 표준 명령어는 docker exec (execute의 약자)입니다.

docker exec -it my-web-app sh

이 명령어의 핵심 플래그인 -it의 역할을 분해해 보겠습니다.

  • -i (interactive): 컨테이너의 표준 입력(STDIN) 스트림을 계속 열어둡니다. 이 플래그가 없으면 터미널에서 키보드를 쳐도 컨테이너로 입력이 전달되지 않습니다.
  • -t (tty): 가상 터미널(pseudo-TTY)을 할당합니다. 일반 터미널처럼 컬러 프롬프트와 포맷팅된 셸 화면을 보여줍니다.

대화형 작업을 할 때는 항상 두 옵션을 합쳐 -it로 사용합니다.

💡
어떤 셸(Shell)을 지정해야 할까요? (bash vs sh)

명령어 끝에 bash 대신 sh를 지정하는 경우가 많습니다.
최근 널리 사용되는 경량 베이스 이미지(Alpine Linux 등)는 이미지 크기를 극소화하기 위해 무거운 bash를 제거하고 표준 경량 sh(또는 /bin/ash)만 탑재합니다.
실무 팁: 먼저 bash로 시도해보고, 만약 executable file not found in $PATH 에러가 발생하면 즉시 sh로 전환하세요.

2. 컨테이너 내부에서 수행할 수 있는 작업들

성공적으로 진입하면 프롬프트가 /app # 또는 root@컨테이너ID:/# 형태로 변경됩니다. 이는 호스트 OS와 격리된 컨테이너 가상 파일시스템 세계로 들어왔음을 뜻합니다.

graph TD
    subgraph 호스트 OS 머신 (Host)
        H_FS[호스트 파일시스템
/Users, /var, /etc]
    end
    
    subgraph 컨테이너 내부 샌드박스 (Container)

/app, /data, /etc]
    end

여기서 일반 Linux 시스템과 똑같이 다음과 같은 디버깅 명령어를 실행할 수 있습니다.

# 현재 접속한 사용자 계정 확인 (보통 root 또는 appuser)
whoami

# 현재 작업 디렉터리 및 파일 목록 확인
pwd && ls -la

# 에러를 유발한 설정 파일 내용 직접 열람
cat /data/config.json

# 컨테이너 내부에서 실행 중인 프로세스 목록 확인
ps aux

# 주입된 환경변수 목록 확인 (환경변수 오타 디버깅에 필수)
env

필요한 진단 도구 즉석 설치하기

네트워크 핑 테스트를 위한 curl이나 ping 명령어가 컨테이너에 없다면, 셸 안에서 패키지 매니저로 즉시 설치할 수 있습니다.

# Debian / Ubuntu 기반 컨테이너
apt-get update && apt-get install -y curl

# Alpine Linux 기반 컨테이너
apk add --no-cache curl

3. 일회성 실행 (One-Shot 모드)

대화형 셸에 계속 머무를 필요 없이 특정 명령의 출력만 확인하고 싶다면 -it 없이 단일 명령만 전달할 수 있습니다.

# 호스트 터미널에서 컨테이너 내부 Nginx 설정 파일 바로 출력
docker exec nginx-server cat /etc/nginx/nginx.conf

# 컨테이너 재시작 없이 Nginx 설정 리로드만 즉시 수행
docker exec nginx-server nginx -s reload

이 방식은 CI/CD 배포 스크립트나 모니터링 자동화 스크립트 작성 시 매우 유용합니다.

4. 파일 전송 마법: docker cp

컨테이너 내부 파일을 호스트로 꺼내오거나, 호스트에서 수정한 설정 파일을 컨테이너 내부로 밀어 넣을 때 사용합니다.

# 1. 호스트의 파일을 컨테이너 내부로 복사
# docker cp [로컬경로] [컨테이너명]:[컨테이너내부경로]
docker cp ./fixed-config.json my-web-app:/data/config.json

# 2. 컨테이너 내부의 로그/덤프 파일을 호스트로 복사
# docker cp [컨테이너명]:[컨테이너내부경로] [로컬경로]
docker cp my-web-app:/app/crash.dump ./local-folder/

5. 컨테이너 셸 빠져나오기

작업을 마치고 호스트 터미널로 돌아오려면 exit를 입력하거나 단축키 Ctrl + D를 누릅니다.
참고: 셸을 빠져나와도 여러분이 진입했던 보조 프로세스만 종료될 뿐, 컨테이너의 메인 서비스는 백그라운드에서 정상적으로 계속 실행됩니다.

🚑 트러블슈팅 구조대
Q1: "OCI runtime exec failed: ... executable file not found in $PATH: unknown" 에러 발생
A: 지정한 셸 프로그램(bash 등)이 컨테이너 내부에 설치되어 있지 않습니다. bash 대신 sh로 변경하여 다시 실행해 보세요. 만약 scratch 베이스처럼 셸이 아예 없는 초소형 이미지라면 exec로 진입할 수 없으며 로그 조회를 통해 디버깅해야 합니다.
Q2: "Error response from daemon: Container xxx is not running" 에러 발생
A: docker exec는 반드시 실행 중(Up)인 컨테이너에만 접근할 수 있습니다. 이미 종료(Exited)된 컨테이너라면 docker logs를 통해 왜 컨테이너가 시작하자마자 종료되었는지 원인을 분석해야 합니다.
🚀
실무 철칙: 일회용 컨테이너 (Disposable Container) 원칙 docker exec나 docker cp로 컨테이너 내부 파일을 직접 수정하는 것은 임급 처방일 뿐, 영구적인 해결책이 아닙니다(안티패턴).
컨테이너가 재시작되거나 새로 배포되면 내부 변경사항은 모두 유실됩니다. 정확한 워크플로는 "exec로 원인을 파악 -> 로컬 코드나 Dockerfile 수정 -> 새 이미지 빌드 및 재배포"의 순서를 따르는 것입니다.
