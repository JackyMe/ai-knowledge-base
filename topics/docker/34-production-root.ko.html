제34레슨: 프로덕션 절대 원칙: Root 권한으로 애플리케이션을 실행하지 말 것

이제 Dockerfile도 능숙하게 작성하고 Compose로 멀티 컨테이너도 띄울 줄 알게 되면서 프로덕션 배포에 자신감이 생겼을 것입니다.

잠깐 멈추세요! 실서버에 배포하기 전에 반드시 지켜야 할 가장 중요한 보안 원칙을 짚고 넘어가야 합니다.

어느 기업에서 Docker 기반의 웹 서비스를 운영 중이었습니다. 어느 날 프레임워크의 제로데이 취약점을 악용해 해커가 컨테이너 내부로 침투했습니다. 그런데 컨테이너 내부 프로세스가 Root 권한으로 실행 중이었던 탓에, 해커는 docker.sock과 컨테이너 탈출(Container Escape) 취약점을 통해 물리 호스트 머신의 최상위 Root 권한까지 탈취해 버렸습니다. 단 하루 만에 기업의 전사 시스템이 마비되었습니다.

1. 왜 기본값이 Root이며, 얼마나 위험한가?

Dockerfile에서 별도의 설정을 하지 않으면 프로그램은 기본적으로 컨테이너 내부의 최고 관리자인 root (UID 0) 계정으로 실행됩니다. 개발 단계에서는 파일 권한 문제 신경 쓸 필요가 없어 편리하지만, 보안적으로는 폭탄을 안고 있는 것과 같습니다.

컨테이너 내부의 Root는 Linux 네임스페이스로 격리되어 있을 뿐, 호스트 커널 입장에서는 본질적으로 호스트의 Root(UID 0)와 동일합니다. 취약점을 뚫고 탈출하는 순간 호스트 전체가 장악당합니다. 따라서 프로덕션 환경의 철칙은: 비즈니스 애플리케이션은 반드시 비특권 일반 사용자(Non-Root User)로 강등하여 실행해야 합니다!

2. 애플리케이션 권한 강등: USER 지시자

Dockerfile에 USER 지시자를 추가하여 일반 사용자를 생성하고 실행 권한을 전환합니다:

# 표준 비특권 계정 적용 Dockerfile
FROM node:24-alpine

# 1. 비특권 일반 사용자 그룹 및 사용자 생성
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# 2. 파일 복사 시 소유권(Owner)을 appuser로 지정
COPY --chown=appuser:appgroup package*.json ./
RUN npm install

# 3. 소스코드 복사 시에도 소유권 지정
COPY --chown=appuser:appgroup . .

# 4. 핵심 지시자: 이후의 모든 명령 및 컨테이너 런타임 실행은 appuser 권한으로 수행!
USER appuser

EXPOSE 8080
CMD ["node", "server.js"]
💡
권한 전환 검증 컨테이너를 실행한 뒤 docker exec -it <컨테이너ID> whoami를 실행했을 때 출력 결과가 appuser로 나타나면 안전하게 격리된 상태입니다!

3. 비특권 사용자 전환 시 자주 마주치는 문제와 해결책

일반 사용자로 전환하면 Permission denied 오류를 종종 마주치게 됩니다. 이는 자연스러운 과정입니다.

🔒 대표적인 권한 이슈 3가지와 해결 가이드
  1. 포트 바인딩 실패 (1024 미만 포트): Linux 커널 보안 정책상 1024 미만의 Well-known 포트(80, 443 등)는 오직 Root만 바인딩할 수 있습니다.
    해결책: 애플리케이션은 내부에서 8080, 3000 등 1024 이상의 포트를 리슨하게 하고, 외부에서 Nginx나 Docker 포트 포워딩(-p 80:8080)으로 연결합니다.
  2. 로그 디렉토리 쓰기 실패: appuser가 /var/log 등 시스템 경로에 파일을 쓸 수 없습니다.
    해결책: USER appuser로 전환하기 전의 Root 단계에서 RUN mkdir -p /var/log/app && chown appuser:appgroup /var/log/app으로 필요한 디렉토리를 미리 만들고 소유권을 부여합니다.
  3. 빌드 도구 설치 실패: npm install -g 등 전역 설치 명령어는 일반 사용자 권한에서 실패합니다.
    해결책: 모든 의존성 설치 및 빌드 명령은 반드시 USER appuser 지시자 위쪽(Root 권한 상태)에서 완료해야 합니다.

4. 철통 보안 하드닝: 엔터프라이즈 레벨 방어

금융권이나 고보안 시스템에서는 Compose 파일에 다음과 같은 추가 보안 잠금장치를 적용합니다:

# docker-compose.yml 보안 하드닝 예시
services:
  api:
    image: my-secure-api
    # 1. 루트 파일시스템을 완전한 읽기 전용(Read-Only)으로 잠금 (파일 변조 원천 차단)
    read_only: true
    # 2. 임시 파일 쓰기가 반드시 필요한 경로만 인메모리 tmpfs로 마운트
    tmpfs:
      - /tmp
    # 3. 모든 Linux 커널 특권(Capabilities) 박탈
    cap_drop:
      - ALL
    # 4. 하위 프로세스의 추가 권한 상승 차단
    security_opt:
      - no-new-privileges:true
🚨 트러블슈팅 응급실
Q1: distroless나 scratch 같은 초경량 이미지에는 adduser 명령어가 없는데 사용자를 어떻게 만드나요?
A: 1. 멀티 스테이지 빌드의 builder 단계에서 유저를 생성한 뒤 /etc/passwd를 복사해 오거나, 2. USER 1000:1000처럼 숫자 형태의 UID/GID를 직접 명시하면 셸 명령어가 없는 미니멀 이미지에서도 비특권 계정으로 즉시 동작합니다.

프로의 팁 (Pro Tip): 실무에서는 CI 파이프라인에 Trivy 또는 Docker Scout 취약점 진단 도구를 연동하여 배포 전 이미지의 보안 취약점을 자동으로 스캔하고, 심각한 결함 발견 시 자동으로 배포를 중단시키는 보안 거버넌스를 구축합니다.
