35. Finale: Automated CI/CD Pipelines

Congratulations on reaching the grand finale! You can now command Docker effortlessly on your local machine. But will you SSH into production servers, pull code manually, run docker build, and execute docker compose up every single deployment?

That manual artisan approach inevitably leads to human error: forgotten environment variables, mistagged images overwriting production, or mismatched dependency versions. The greatest virtue of a software engineer is automation—never do manually what a machine can do reliably.

This brings us to the crown jewel of DevOps: CI/CD (Continuous Integration / Continuous Deployment).

1. The Continuous Pipeline Blueprint

2. CI: Machine-Driven Automated Verification (Continuous Integration)

The essence of CI is simple: Every code push automatically triggers tests and builds to catch errors immediately.

Using GitHub Actions as an example, create .github/workflows/docker-build.yml in your repository:

# Example GitHub Actions Workflow
name: CI to Docker Hub

on:
  push:
    branches: [ "main" ] # Triggers only on push to main branch

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v6

      - name: Login to Docker Hub
        uses: docker/login-action@v4
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push image
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          # Dual tagging is critical!
          tags: myname/myapp:latest, myname/myapp:${{ github.sha }}

Docker · GitHub Actions — Example versions checked 2026-09-09; verify self-hosted runner compatibility and pin reviewed commit SHAs for production.

🏷️ The Art of Container Tagging

Notice the dual tags in the workflow above: latest and github.sha (the Git commit hash). Why both?

The latest tag continuously points to the newest build, but offers zero traceability during rollbacks. By tagging with the Git SHA (e.g. a1b2c3d), every image artifact is immutably linked to the exact source commit. If an issue occurs, rolling back to an older version requires only changing the image tag to that specific commit hash!

3. CD: Seamless Deployment (Continuous Deployment)

CD ensures newly published images are automatically deployed to target servers.

Deploy tested versions or image digests and record a rollback target. Review configuration and migrations, update in a maintenance window, then check health. Do not default to socket-mounted tools automatically replacing all containers.

4. The Road Ahead: The Calling of Kubernetes

As your systems scale from a single server to clusters of 10, 50, or 500 nodes, standalone docker compose reaches its architectural limits:

  • If a physical host suffers hardware failure, how do containers automatically migrate to healthy nodes?
  • During traffic surges (e.g. Black Friday), how do you automatically autoscale Web instances from 3 to 300 replicas, and scale back down afterward?
  • How do you execute zero-downtime rolling updates without disconnecting active users?

This is where Container Orchestration systems enter. While Docker created Swarm, the definitive industry standard is Google's open-source powerhouse: Kubernetes (K8s).

In short: Docker manufactures the standardized shipping containers, while Kubernetes orchestrates the global ports and autonomous container mega-ships.
