Lesson 21: Ultimate Slimming: Multi-Stage Builds

Imagine you are building a luxury villa. The traditional building approach leaves all the bricks, concrete, mixers, scaffolding, and even worker cots permanently inside the completed house. When the buyer unlocks the front door, there is a giant cement truck parked in the middle of the living room!

Sounds absurd, right? Yet in Docker, this is exactly what many beginners do. They package compilers, SDKs, build tools, and full source repositories directly into their final shipping image. That is why a Go binary that weighs only 15MB ends up bundled into an 800MB Docker image.

Why Are Images So Bloated?

Let's look at a classic counter-example. Xiao Ming wrote a simple Go web service with the following single-stage Dockerfile:

# Anti-pattern: Single-stage build
FROM golang:1.20
WORKDIR /app
COPY . .
RUN go build -o myapp main.go
CMD ["./myapp"]

After building the image, Xiao Ming checked the size and was stunned:

docker images | grep myapp
myapp       latest      a1b2c3d4e5f6   About a minute ago   850MB

Why is it so huge? Because the golang:1.20 base image contains a full Linux OS distribution, the entire Go toolchain, compilers, standard library headers, and various build utilities. But in reality, Go produces a standalone binary that needs none of these build-time tools at runtime.

Multi-Stage Builds: Take Only What You Need

Multi-stage builds allow us to compile code in a temporary construction stage (the builder), and then in the final production stage, copy only the compiled binary artifacts over, leaving all build tools behind.

flowchart LR
    subgraph Stage 1: Construction Site (Builder)
        A[Base image golang:1.20] --> B(Copy source code)
        B --> C(Run go build)
        C -.-> D{Generate binary}
    end
    
    subgraph Stage 2: Finished Production
        E[Tiny base image alpine] --> F(Copy binary from Stage 1)
        D ==> F
        F --> G[Final Image: Only 20MB]
    end

Hands-on Case Study: Extreme Slimming for Go

Let's rewrite Xiao Ming's Dockerfile using multi-stage builds:

🛠️ Step 1: Write the Multi-Stage Dockerfile
# Stage 1: Named 'builder'
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
# Static compilation: disable CGO to ensure portability in Alpine
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp main.go

# Stage 2: Production runtime using lightweight Alpine
FROM alpine:latest
WORKDIR /root/
# Copy only the compiled binary from the builder stage
COPY --from=builder /app/myapp .
# Ensure executable permissions
RUN chmod +x myapp

CMD ["./myapp"]

Pay close attention to the two key syntax elements: AS builder and COPY --from=builder. AS assigns a name to the construction stage, and --from acts like a portal, teleporting artifacts from the builder stage straight into the final stage.

Now re-build and watch the magic happen:

docker build -t myapp:slim .
docker images | grep myapp
myapp       slim        b2c3d4e5f6g7   About a minute ago   22.4MB
myapp       latest      a1b2c3d4e5f6   10 minutes ago       850MB

From 850MB down to 22MB—an astonishing 38x reduction! This saves massive disk storage, and more importantly, accelerates container pull and deployment speeds across CI/CD clusters.

Java Projects: Maven + JRE

Not just Go, heavyweight enterprise languages like Java benefit immensely from multi-stage builds. You need Maven or Gradle to package JARs, but you only need a lightweight JRE at runtime.

# Stage 1: Build with Maven
FROM maven:3.8.6-openjdk-11 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Run with lightweight JRE
FROM eclipse-temurin:11-jre-alpine
WORKDIR /app
COPY --from=build /app/target/myapp.jar .
CMD ["java", "-jar", "myapp.jar"]
💡
Pro-Tip: Using scratch as the Ultimate Base For languages like Go or Rust that can compile completely static, self-contained binaries, you can use FROM scratch for your second stage. scratch is Docker's zero-byte empty base image. Your final container contains nothing but your binary—no OS utilities, minimal attack surface, and unmatched lightness. Keep in mind you won't have sh inside for debugging.
🚑 Pitfall Rescue Room
Q: Why do I get "/bin/sh: ./myapp: not found" even though I copied the file?
A: 99% of the time, the binary compiled in Stage 1 relies on dynamic shared libraries (such as glibc), while Alpine in Stage 2 uses musl libc. Fix: Set CGO_ENABLED=0 during Go compilation for a fully static binary, or use debian:buster-slim instead of Alpine in Stage 2.
Q: Multi-stage builds feel slow because dependencies redownload every time?
A: Combine multi-stage builds with Layer Caching (Lesson 19). In Stage 1, copy go.mod / go.sum (or Java's pom.xml) first, run dependency downloads, and then copy the remaining source code. Unchanged dependencies will resolve instantly from cache.

Multi-stage builds are the watershed between beginner and expert Dockerfiles. Master this technique to build ultra-lean, secure, and production-ready container images.
