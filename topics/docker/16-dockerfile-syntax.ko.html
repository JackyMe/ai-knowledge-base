16. Dockerfile 핵심 문법 완전 정복

이전 레슨에서 Dockerfile의 필요성과 개념을 익혔습니다. Dockerfile은 요리 레시피와 같으며, Docker 엔진은 레시피를 오차 없이 실행하는 로봇 셰프입니다. 이번 레슨에서는 실무에서 매일 사용하는 핵심 지시어(Instruction)들을 완벽하게 마스터해 보겠습니다.

1. 5대 핵심 지시어 심층 분석

🍳 FROM: 베이스 이미지 선택 (요리의 육수 베이스)

모든 Dockerfile은 반드시 FROM으로 시작해야 합니다. 어떤 기본 OS/런타임 환경 위에서 작업을 시작할지 결정합니다.

  • 공식 이미지 사용: Docker Hub 공식 인증(Official) 이미지(예: node, python, openjdk)를 사용합니다.
  • Alpine vs Debian(slim): alpine은 약 5MB로 극도로 가볍지만 C 표준 라이브러리로 musl libc를 사용하여 C/C++ 네이티브 확장 패키지 빌드 시 호환성 이슈가 생길 수 있습니다. 일반적인 환경에서는 안정적인 debian-slim 계열이 권장됩니다.
  • 버전 태그 고정: 절대 FROM ubuntu:latest처럼 작성하지 마세요! 최신 버전 업데이트로 빌드가 불시에 깨질 수 있으므로 FROM node:18-alpine처럼 명확한 버전을 명시하세요.
# 권장되는 작성 예시
FROM node:18-alpine
📍 WORKDIR: 작업 디렉터리 설정 (도마와 조리대)

WORKDIR은 이후 실행되는 RUN, COPY, CMD 지시어의 기준 작업 경로를 지정합니다.

  • 작성하지 않으면? 기본 루트(/)에서 작업하게 되어 시스템 디렉터리와 소스코드가 뒤섞입니다.
  • 폴더가 없으면? Docker가 자동으로 디렉터리를 생성해주므로 별도로 RUN mkdir을 실행할 필요가 없습니다.
WORKDIR /app
📥 COPY vs ADD: 호스트 파일 가져오기 (식재료 반입)

호스트 머신의 파일/디렉터리를 이미지 가상 파일시스템 내부로 복사합니다.

  • COPY: 순수하게 파일과 디렉터리를 그대로 복사합니다. 실무 기본 표준.
  • ADD: 원격 URL 다운로드 및 .tar.gz 압축 파일 자동 해제 기능이 포함되어 있습니다. 예상치 못한 부작용을 방지하기 위해 공식 문서에서도 특별한 압축 해제 목적 외에는 COPY 사용을 강력 권장합니다.
COPY package.json .
COPY src/ ./src/
🔨 RUN: 빌드 시점 명령어 실행 (조리 과정)

패키지 설치, 의존성 다운로드, 소스코드 컴파일 등 이미지를 굽는(Build) 과정에서 실행되는 명령입니다.

⚠️
안티패턴 주의: 무분별한 다중 RUN 남발 금지 각 RUN 명령어는 별도의 이미지 레이어(Layer)를 생성하여 이미지 용량을 비대하게 만듭니다.
❌ 잘못된 예:
RUN apt-get update
RUN apt-get install -y vim
✅ 올바른 예: && 연산자로 묶고 임시 캐시 파일 정리까지 한 줄에서 수행
RUN apt-get update && apt-get install -y vim && rm -rf /var/lib/apt/lists/*
🚀 CMD vs ENTRYPOINT: 컨테이너 구동 명령어 (완성된 요리 제공)

docker run으로 컨테이너 인스턴스가 시작될 때 런타임에 실행될 기본 진입점 명령을 지정합니다.

  • CMD: 기본 실행 명령 및 인자 제공. docker run my-image [새명령]처럼 외부 인자가 주어지면 쉽게 덮어씌워집니다.
  • ENTRYPOINT: 컨테이너의 고정 실행 파일 지정. 외부에서 전달된 인자는 이 진입점의 파라미터로 추가 전달됩니다.
# 반드시 Exec 형태(JSON 배열 형태)로 작성할 것
CMD ["node", "app.js"]
⚙️ 기타 주요 지시어 모음
  • ENV: 런타임 환경변수 설정 (컨테이너 실행 중에도 유지됨). ENV PORT=8080
  • ARG: 빌드 타임 전용 변수 (이미지 빌드 시에만 사용되고 완성된 이미지에는 남지 않음). ARG VERSION=1.0
  • EXPOSE: 컨테이너가 리스닝할 포트 선언 문서화. EXPOSE 8080 (주의: 단순 메타데이터 안내문이며, 실제 포트 포워딩은 -p로 수행해야 합니다).
  • USER: 보안을 위해 root 권한을 버리고 일반 사용자 계정으로 전환. USER node
  • LABEL: 이미지 메타데이터(작성자, 설명 등) 등록. LABEL maintainer="admin@example.com"
  • VOLUME: 지속성 데이터가 저장될 볼륨 마운트 지점 선언.

2. 실전 프로덕션 레벨 Node.js Dockerfile 라인별 분석

실제 엔터프라이즈 환경에서 사용되는 완벽한 Node.js Dockerfile 예제입니다.

# 1. 베이스 이미지 선택: 경량화된 Alpine 기반 및 버전 명시
FROM node:18-alpine

# 2. 메타데이터 라벨 등록
LABEL maintainer="devops@company.com"

# 3. 작업 디렉터리 설정
WORKDIR /usr/src/app

# 4. 프로덕션 환경변수 설정 (성능 최적화)
ENV NODE_ENV=production

# 5. 의존성 정의 파일만 먼저 복사 (레이어 캐싱 극대화)
COPY package*.json ./

# 6. 프로덕션 의존성만 설치
RUN npm ci --only=production

# 7. 실제 소스코드 전체 복사
COPY . .

# 8. 보안 권한 강화: root 계정 탈피
USER node

# 9. 포트 선언
EXPOSE 3000

# 10. 애플리케이션 시작 명령
CMD ["node", "server.js"]
💡
실무 팁: CMD 작성 시 Exec 형식 vs Shell 형식의 결정적 차이

• Exec 형식 (강력 권장): CMD ["node", "app.js"]
Node 프로세스가 직접 컨테이너의 PID 1 메인 프로세스로 실행됩니다. 따라서 docker stop 시 SIGTERM 신호를 즉시 수신하여 안전한 종료 처리를 수행합니다.

• Shell 형식 (지양): CMD node app.js
Docker가 내부적으로 /bin/sh -c "node app.js"로 감싸서 실행하므로 sh 프로세스가 PID 1을 차지합니다. 결과적으로 Node 앱은 종료 시그널을 전달받지 못해 매번 10초 타임아웃 후 SIGKILL로 강제 종료됩니다.

🚨 트러블슈팅 구조대
Q1: 빌드 중 "returned a non-zero code: 1" 에러가 발생하며 멈춥니다.
A: RUN 지시어에서 실행한 명령어(npm install, apt-get 등)가 실패했습니다. 상단 로그를 확인하여 네트워크 장애, 패키지 이름 오타, 빌드 도구(gcc/python 등) 누락 여부를 확인하세요.
Q2: Dockerfile에 EXPOSE 80을 적었는데 브라우저에서 사이트 접속이 안 됩니다.
A: EXPOSE는 다른 개발자나 오케스트레이터를 위한 설명서(주석) 역할에 불과합니다. 실제 호스트 포트와 연결하려면 docker run -p 80:80 옵션을 반드시 주어야 합니다.
