第35レッスン：エピローグ：CI/CD 自動化パイプラインと未来への道

全 35 レッスン完走、本当におめでとうございます！ここまで学んだあなたは、ローカル環境で Docker と Compose を自在に操れる実力を身につけました。しかし、本番リリースのたびに手動でサーバーに SSH 接続し、ソースコードを Pull して、手動で docker build や docker compose up を実行する運用は危険です。

手動運用は「環境変数の設定漏れ」「タグ付けミスによるバージョンの上書き」といったヒューマンエラーの温床となります。プロフェッショナルな開発者の最大の美徳は「自動化できる手作業を徹底的に排除すること」です。

本最終章では、DevOps の中核を担う CI/CD (継続的インテグレーション / 継続的デプロイ) の全体像と、その先にある Kubernetes の世界を展望します。

1. CI/CD パイプラインの全体像

モダンなソフトウェア開発において、コードが本番サーバーへ届くまでの自動化フローです：


sequenceDiagram
    participant Dev as 開発者
    participant Git as GitHub / GitLab
    participant CI as CI Runner
(ビルドサーバー)
    participant Reg as Docker Registry
(イメージレジストリ)
    participant Prod as 本番サーバー

    Dev->>Git: 1. git push (コードのコミット)
    Git-->>CI: 2. Webhook をトリガー
    activate CI
    CI->>CI: 3. 自動単体テストを実行
    CI->>CI: 4. docker build (イメージ作成)
    CI->>Reg: 5. docker push (イメージ登録)
    deactivate CI
    CI-->>Prod: 6. サーバーへデプロイ通知
    activate Prod
    Prod->>Reg: 7. docker pull (新イメージ取得)
    Prod->>Prod: 8. docker compose up (サービス再起動)
    deactivate Prod

2. CI：人間に代わる機械による品質検証 (継続的インテグレーション)

CI (Continuous Integration) の本質は、「コミットが Push されるたびに、テストとビルドを全自動で実行し、不具合を即座に検知する」ことです。

デファクトスタンダードである GitHub Actions を用いた設定例（.github/workflows/docker-build.yml）：

# GitHub Actions サンプルワークフロー
name: CI to Docker Hub

on:
  push:
    branches: [ "main" ] # main ブランチへの Push 時にトリガー

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3

      - name: Login to Docker Hub
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v4
        with:
          context: .
          push: true
          # タグ付けのベストプラクティス！
          tags: myname/myapp:latest, myname/myapp:${{ github.sha }}
🏷️ イメージタグ管理の重要作法

上記の記述では latest と github.sha（Git コミットハッシュ値）の2つのタグを同時に付与しています。なぜでしょうか？

latest タグは常に上書きされるため、障害発生時に「どのコミットのコードでビルドされたか」が分からなくなります。Git のコミットハッシュ（例: a1b2c3d）をタグに含めることで、イメージとコードのリビジョンを 1 対 1 で厳密に紐付け、瞬時のロールバック（巻き戻し）が可能になります。

3. CD：ダウンタイムのない自動デプロイ (継続的デプロイ)

CD (Continuous Deployment) は、レジストリに登録された最新イメージを本番環境へ安全かつ自動的に反映させる仕組みです。

スタンドアロンサーバーのシンプルな構成では、Watchtower などの自動デプロイツールがよく使われます。Watchtower 自体もコンテナとして動作し、Docker レジストリを常時監視して新しいイメージが公開されると自動で Pull してコンテナをリスタートします。

# 自動更新ツール Watchtower の起動例
$ docker run -d --name watchtower -v /var/run/docker.sock:/var/run/docker.sock containrrr/watchtower

4. その先へ：Kubernetes (K8s) が拓く大規模分散の世界

サービスの規模が拡大し、サーバー台数が 10 台、100 台とスケールアウトしていくと、単一ホスト前提の docker-compose では以下のような課題に直面します：

  • 物理ノードが突然故障した場合、稼働中コンテナを別ノードへ自動でフェイルオーバー（救済移動）したい。
  • トラフィックの急増に合わせて、Web サービスを 3 台から 300 台へ数秒で自動水平スケーリング（Auto Scaling）したい。
  • ユーザーに一切の瞬断を感じさせずに新バージョンへ切り替えたい（ゼロダウンタイム・ローリングアップデート）。

これらクラスタ全体の統合管理を担うのがコンテナオーケストレーションシステムであり、その業界統一標準が Google 発の Kubernetes (K8s) です。

「Docker が国際標準規格のコンテナを作る工場であるなら、Kubernetes は全世界の港湾設備と巨大コンテナ船を統括する管制塔」といえます。
