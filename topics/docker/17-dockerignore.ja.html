17. .dockerignore 活用ガイド

ある新人エンジニアの恐怖体験：入社初日、意気揚々と docker build -t myapp . を実行してお茶を汲みに行きました。席に戻ると、ターミナルはまだ激しくスクロールしており、ステータスには Sending build context to Docker daemon 12.5GB と表示されていました。新人は愕然としました：「プロジェクトのコードはたったの 5MB しかないのに、どうして 12 ギガバイトもアップロードされているんだ！？」

調査したところ、プロジェクト配下の temp/ に大量のテスト用動画ファイルがあり、さらに 10GB に膨れ上がった node_modules が丸ごと Docker エンジンに転送されていたことが判明しました。これが、.dockerignore ファイルを作成しなかった場合の過酷な代償です。

一、ビルドコンテキスト（Build Context）とは何か？

docker build -t xxx . を実行したとき、末尾のドット . はビルドコンテキストディレクトリを指定しています。Docker は Client/Server アーキテクチャ（入力する CLI はクライアント、バックグラウンドで動くデーモンがサーバー）を採用しているため、クライアントはビルド開始前にこのディレクトリ全体をアーカイブして Docker デーモンへ転送します。

もし何も除外設定を行わないと、Docker は .git のコミット履歴やローカルのテストログ、巨大な依存パッケージキャッシュまで余すところなくデーモンへ送信してしまいます。その結果：

  1. ビルドが極端に遅くなる： ギガバイト単位のプロセス間データ転送に膨大な時間が浪費されます。
  2. イメージサイズが無駄に肥大化する： 不要なゴミファイルがイメージ内に焼き込まれてしまいます。
  3. 重大な機密情報の漏洩リスク： .env のパスワードや SSH 秘密鍵がイメージ内に誤って混入し、公開レジストリへプッシュされて世界中に晒される危険があります。

二、救世主の登場：.dockerignore

Git の .gitignore とまったく同じ役割を果たします。Dockerfile と同じディレクトリに .dockerignore という名前のファイルを作成し、除外したいファイルやディレクトリのパターンを列挙するだけです。

三、構文ルールの解説：ワイルドカードと除外解除

.dockerignore は標準的なパターンマッチング記法をサポートしています：

  • *.log：.log で終わるすべてのファイルを除外します。
  • temp?：temp1 や tempa にマッチします（? は任意の1文字にマッチ）。
  • **/*.md：全階層ディレクトリ下の Markdown ファイルを除外します。
  • !README.md：感嘆符 ! はルールの反転（ホワイトリスト指定）を表します。直前で *.md を除外していても、README.md だけは確実に保持されます。
  • # コメント：ハッシュ記号で始まる行はコメントとして無視されます。

四、劇的ビフォーアフター：効果の検証

📊
.dockerignore なしの場合： 
$ docker build -t bad-app .
Sending build context to Docker daemon  850.5MB
Step 1/5 : FROM node:18
...
(ビルド所要時間: 45 秒)
.dockerignore ありの場合： 
$ docker build -t good-app .
Sending build context to Docker daemon  2.15MB
Step 1/5 : FROM node:18
...
(ビルド所要時間: 2 秒)
💡
プロの知恵：キャッシュを無視して強制クリーンビルド

ファイルの更新が Docker に検知されず、古い中間キャッシュが使われてしまう場合があります。.dockerignore の確認に加え、--no-cache オプションを付与することで強制的にキャッシュを使わずに完全新規ビルドを実行できます：
docker build --no-cache -t myapp .

🚨 トラブル救護室
Q1: "COPY failed: file not found" とエラーが出てビルドが止まる
A: 99% の確率で、コピーしようとした必要なファイルが .dockerignore で誤って除外されています！ たとえば Dockerfile で COPY config/setting.json . と書いているのに、ignore ファイルに config/ が指定されていると、ビルドコンテキストから消失して見つからなくなります。
Q2: .env に書いた DB パスワードが漏洩してしまった！
A: COPY . . を実行した際、.env ファイルがイメージ内に焼き込まれ、そのまま Docker Hub などのレジストリへプッシュされてしまったことが原因です。イメージを取得した人は誰でもレイヤーを展開して中身を覗くことができます。ローカルの環境変数ファイルや秘密鍵は、必ず .dockerignore に追加してください！ 本番の機密情報は起動時引数（-e）やシークレット管理サービスを用いて注入するのが鉄則です。
