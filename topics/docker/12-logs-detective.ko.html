12. 탐정의 시선: 로그 추적 및 분석

🕵️‍♂️ 사건 발생: 새벽 3시의 서비스 장애

새벽 3시, 운영팀으로부터 긴급 장애 연락이 왔습니다. "결제 모듈 웹 서버가 다운되었습니다!"

서버에 접속해 docker ps를 쳐보니 payment-service 컨테이너가 목록에서 사라졌습니다. docker ps -a로 확인해 보니 상태가 Exited (1) 2 hours ago로 찍혀 있습니다.

컨테이너가 이미 죽어버렸기 때문에 docker exec로 들어갈 수도 없습니다. 이때 탐정처럼 원인을 규명할 수 있는 유일한 단서는 컨테이너가 남겨둔 마지막 '유언', 즉 로그(Logs)입니다.

1. 시간 여행: docker logs 기초 조회

컨테이너의 로그를 확인하는 가장 기본적인 명령어는 docker logs입니다.

docker logs payment-service

하지만 오래 실행된 컨테이너라면 수만 줄의 전체 로그가 폭포수처럼 쏟아져 터미널 화면을 도배하게 됩니다.

1. 마지막 N줄만 보기 (--tail)

보통 비정상 종료 직전의 마지막 로그가 가장 중요합니다. --tail 플래그로 마지막 N줄만 필터링합니다.

# 마지막 50줄의 로그만 출력
docker logs --tail 50 payment-service

2. 특정 시간 범위 필터링 (--since / --until)

장애가 발생한 시간대를 알고 있다면 시간 조건을 지정하여 검색할 수 있습니다.

# 최근 2시간 이내 발생한 로그만 조회
docker logs --since 2h payment-service

# 특정 ISO 타임스탬프 구간만 정밀 조회
docker logs --since "2024-10-01T01:50:00" --until "2024-10-01T02:10:00" payment-service

3. 로그에 시간 타임스탬프 강제 부착 (-t / --timestamps)

애플리케이션 자체 로깅 포맷에 시간 출력이 누락되어 있어도 Docker가 수집 시점의 정확한 시간을 붙여줍니다.

docker logs -t payment-service
# 출력 형식: 2024-10-01T02:05:11.123456789Z Exception in thread "main"...

2. 실시간 모니터링: -f (Follow 모드)

새로 배포한 애플리케이션의 실시간 동작이나 에러를 확인하고 싶다면 -f (follow) 플래그를 사용합니다. Linux의 tail -f와 동일합니다.

docker logs -f --tail 20 payment-service

터미널 세션이 대기 상태를 유지하며 새로운 로그 라인이 생성될 때마다 화면에 실시간으로 스트리밍됩니다. Ctrl + C를 누르면 모니터링이 종료됩니다.

3. 아키텍처 심층 분석: 로그는 어디에 저장되는가?

Docker는 기본적으로 json-file 로깅 드라이버를 사용합니다. 컨테이너 내부의 프로세스가 표준 출력(stdout) 및 표준 에러(stderr)로 내보내는 모든 텍스트를 Docker 데몬이 가로채어 호스트 머신의 숨겨진 JSON 파일(/var/lib/docker/containers/컨테이너ID/컨테이너ID-json.log)에 기록합니다.

⚠️
경고: 로그 폭탄으로 인한 서버 디스크 고갈 방지

Docker의 기본 설정은 로그 파일 크기 제한이 없습니다! 트래픽이 몰리는 서비스의 경우 며칠 만에 수십~수백 GB의 JSON 로그가 쌓여 호스트 서버 디스크가 100% 꽉 차는 대형 장애를 유발할 수 있습니다.

실무 필수 세팅: 로그 로테이션(순환) 정책 지정

프로덕션 컨테이너를 구동할 때는 항상 --log-opt를 추가하여 로그 최대 크기와 보관 파일 수를 제한해야 합니다.

docker run -d \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  --name safe-app my-app

개별 로그 파일 크기가 10MB에 도달하면 새 파일로 롤링되며, 최대 3개(총 30MB)까지만 보관하여 디스크 고갈을 원천 차단합니다.

4. 종합 진단: 3대 실무 상태 점검 도구

1. 상세 메타데이터 조회: docker inspect

컨테이너에 할당된 IP, 바인드 마운트 디렉터리, 환경변수, 헬스체크 상태 등을 JSON으로 확인합니다.

docker inspect my-app | grep "IPAddress"

2. 실시간 자원 사용량 모니터링: docker stats

Linux top 명령처럼 실행 중인 모든 컨테이너의 실시간 CPU, 메모리 사용량, 네트워크 I/O를 대시보드 형태로 출력합니다.

docker stats

3. 컨테이너 내부 프로세스 트리: docker top

컨테이너 내부에 접속하지 않고도 호스트 관점에서 컨테이너가 실행 중인 프로세스 목록(PID)을 확인합니다.

docker top my-app
🚑 트러블슈팅 구조대
Q: docker logs를 쳤는데 아무 내용도 출력되지 않습니다.
A: 애플리케이션이 로그를 표준 출력(stdout/stderr)으로 내보내지 않고, 컨테이너 내부의 파일(예: /var/log/app.log)에 직접 쓰고 있을 가능성이 높습니다. Docker는 표준 출력만 수집하므로, 프레임워크 로깅 설정을 콘솔 출력(Console Appender)으로 변경하거나 로그 파일을 볼륨으로 마운트하여 확인해야 합니다.
🚀
실무 팁: 엔터프라이즈 환경의 JSON 구조화 로그 마이크로서비스 환경에서는 로그를 단순 텍스트가 아닌 JSON 포맷의 구조화 로그로 출력하는 것이 모범 사례입니다. ELK(Elasticsearch-Logstash-Kibana), Datadog, Grafana Loki 등 중앙화 로그 시스템이 필드를 자동으로 파싱하여 장애 분석 및 모니터링 알람을 정밀하게 구축할 수 있습니다.
