31. Ultimate Battle (Part 2): Microservice Networks

In the previous lesson, we ran Web + Redis with Docker Compose. But we were still missing the most central component in modern architectures—the Database! Almost all real-world web applications rely on a persistent relational database.

Today, we assemble the complete microservices puzzle: adding PostgreSQL to forge the classic Web + Cache + Database three-tier architecture. Get ready to watch these services interact seamlessly inside their dedicated virtual network!

1. Global Topology Overview

Before writing the code, let's examine our architectural topology:

Plain English Explanation End users only have access to our Web service via published ports. Redis and PostgreSQL remain safely encapsulated within Docker Compose's internal network, accessible only by our Web application. To prevent data loss when containers restart, PostgreSQL mounts a persistent Docker volume.

2. The Complete docker-compose.yml

Here is our complete orchestration manifest:

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      redis:
        condition: service_started
      db:
        condition: service_healthy
    environment:
      - DB_HOST=db
      - DB_USER=myuser
      - DB_PASS=mypassword
      - REDIS_HOST=redis

  redis:
    image: redis:alpine
    restart: always

  db:
    image: postgres:14-alpine
    restart: always
    environment:
      - POSTGRES_USER=myuser
      - POSTGRES_PASSWORD=mypassword
      - POSTGRES_DB=myapp_db
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser"]
      interval: 5s
      timeout: 5s
      retries: 5

# Top-level volume declaration
volumes:
  pgdata:
🔍 Core Architectural Breakdown
  1. Top-Level volumes Declaration: Declares a persistent managed volume (pgdata). When assigned to db, PostgreSQL stores data in this volume so data persists across container recreations.
  2. Environment Variable Injection: In the web service, DB_HOST=db tells the application where the database is, using the service name db as the DNS hostname.
  3. The Ultimate Reliability Pattern: depends_on + healthcheck: In multi-container systems, a web app often crashes if it boots before the database finishes internal initialization. By defining a healthcheck (using pg_isready) and setting condition: service_healthy, Compose ensures Web starts only when PostgreSQL is truly ready to receive queries!

3. Deployment & Operational Verification

With our configuration ready, launch the entire stack in detached mode:

# Start the full stack in background mode
$ docker compose up -d

# Check the runtime health status of all services
$ docker compose ps

The status output confirms service health:

NAME                IMAGE                  COMMAND                  SERVICE   CREATED          STATUS                    PORTS
myapp-db-1          postgres:14-alpine     "docker-entrypoint.s…"   db        2 minutes ago    Up 2 minutes (healthy)    5432/tcp
myapp-redis-1       redis:alpine           "docker-entrypoint.s…"   redis     2 minutes ago    Up 2 minutes              6379/tcp

Notice the (healthy) indicator in the DB status column! You can also execute queries directly inside the database container with docker compose exec db psql -U myuser -d myapp_db.

4. Environment Overrides: Tailoring Local Development

What if you want hot-reloading in development without modifying production settings? You don't need duplicate compose files. Docker Compose automatically merges docker-compose.override.yml when present!

For example, in docker-compose.override.yml, you can mount your local source code for live-reload:

# docker-compose.override.yml
services:
  web:
    volumes:
      - .:/app
    environment:
      - NODE_ENV=development

When running docker compose up locally, Compose merges both files automatically.

⚠️
Caution: The Data-Loss Flag Running docker compose down removes only containers and networks. However, if you pass the -v flag (docker compose down -v), Compose deletes all associated named volumes as well! Your database data will be irrevocably deleted. Always exercise caution when using -v.
🚑 Pitfall Rescue Room
Q1: Web throws "Connection refused" when connecting to PostgreSQL at startup?
By default, basic depends_on: db only waits for the DB container process to start, not for Postgres to complete database startup. Fix: Implement healthcheck conditions with condition: service_healthy as shown above.
Q2: Volume encounters "Permission denied" errors inside Postgres?
Postgres runs internally as the non-root postgres user. Docker managed volumes handle ownership automatically. If using host bind-mounts, ensure host directories have write permissions assigned to UID 70/999 or chown accordingly.
