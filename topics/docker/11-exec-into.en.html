11. Breaking In: Stepping Inside the Container

🔍 Crime Scene: The Missing Configuration File

Imagine you just deployed a web application, opened your browser full of expectation, only to be greeted by a cold 500 Internal Server Error. Inspecting the preliminary logs reveals a fatal error: FileNotFoundError: [Errno 2] No such file or directory: '/data/config.json'.

"Impossible!" you exclaim. "I specified the exact path in my code, and it runs flawlessly on my local machine!"

In situations like this, the fastest diagnostic approach is to "step inside" that running container and inspect the directory structure directly. Just like dealing with a leaking pipe inside a house—you need to open the front door and examine the plumbing yourself.

1. Open Sesame: The docker exec Command

In the Docker ecosystem, the universal gateway into an actively running container is the docker exec command. Short for "execute", it runs an arbitrary command inside an existing container's namespace.

docker exec -it my-web-app sh

This command appears concise, but it houses critical mechanics. Let's dissect the core -it flags:

  • -i (interactive): Keeps Standard Input (STDIN) open. Without this flag, typing into your keyboard won't pipe keystrokes into the container's shell.
  • -t (tty): Allocates a pseudo-TTY terminal. This delivers a proper shell prompt with color support and line navigation, rather than a frozen, unresponsive screen.

These two flags are almost always combined into -it.

💡
Which Shell Should You Use?

In the command above, we specified sh at the end. Why not bash?
This depends on the container's underlying OS (base image). Many modern lightweight images (such as Alpine Linux-based images) omit bash entirely to minimize image size, retaining only the minimal sh (or /bin/ash).
Pro Tip: Try bash first. If it returns executable file not found in $PATH, immediately fall back to sh.

2. What Can You Do Once Inside?

Once you successfully enter the container via sh or bash, you will notice your terminal prompt changes (e.g., to /app #). This confirms you have crossed over into the container's isolated world, completely decoupled from the host system:

Inside, you can run standard Linux inspection commands just like on a remote server:

# Check current user identity (often root, but may be a non-root app user)
whoami

# Check current working directory and list files
pwd && ls -la

# Verify if the problematic config file exists
cat /data/config.json

# Inspect running processes inside the container
ps aux

# View container environment variables (often misconfigured env vars cause crashes)
env

Missing a Tool? Install It on the Fly!

If you discover that the container lacks essential troubleshooting utilities (e.g., you need to test network connectivity with curl), you don't have to rebuild the image immediately—install it temporarily:

# For Debian / Ubuntu based containers
apt-get update && apt-get install -y curl

# For Alpine Linux based containers
apk add --no-cache curl

3. Hit and Run: One-Shot Mode

Sometimes you don't need a persistent interactive shell session; you just want to inspect a file or reload a service. In such cases, omit -it and pass the command directly:

# Inspect Nginx config file directly from the host
docker exec nginx-server cat /etc/nginx/nginx.conf

# Tell Nginx inside the container to reload configuration without restarting
docker exec nginx-server nginx -s reload

This non-interactive execution pattern is especially powerful in automation scripts and CI/CD pipelines.

4. File Transfer: docker cp

After pinpointing the issue, you may want to copy a fixed configuration file into the container from your host, or extract a crash dump file out to your local machine. There's no need to install VIM inside the container—use docker cp:

# 1. Copy from host into container:
# docker cp [local_path] [container_name]:[container_path]
docker cp ./fixed-config.json my-web-app:/data/config.json

# 2. Copy from container to host:
# docker cp [container_name]:[container_path] [local_path]
docker cp my-web-app:/app/crash.dump ./local-folder/

5. How to Exit Gracefully

When you finish your debugging session inside the container terminal, how do you exit?
Simply type exit and hit Enter, or press the shortcut Ctrl + D.
Rest assured: this only terminates the temporary shell process you used to enter the container. The primary container service continues running uninterrupted in the background!

🚑 Pitfall Rescue Room
Q1: Error OCI runtime exec failed: exec failed: unable to start container process... executable file not found in $PATH: unknown
A: In plain English: the executable binary you tried to run (usually bash or sh) does not exist inside the container image! As discussed, Alpine-based images do not ship with bash. Replace bash with sh in your command. If the container lacks even sh (e.g. ultra-minimal distroless or scratch images), you cannot enter the container directly and must rely entirely on logs for debugging.
Q2: Error Error response from daemon: Container xxx is not running
A: A container must be in the active Up state to be targeted by docker exec! If your container crashed immediately upon launch (Exited), you cannot exec into it. You must investigate why it failed to boot (see Chapter 12: Inspecting Logs).
🚀
Pro Tips: Avoid Hot-Patching Containers

While modifying files directly inside a container with docker exec and docker cp offers quick emergency relief, this is an anti-pattern known as "hot-patching" or "container drift"!
The moment the container is recreated or redeployed, all your manual in-place modifications will vanish. The standard workflow is: diagnose the root cause with exec, modify your source code or Dockerfile on the host, build a new image, and redeploy. Always treat containers as disposable and immutable!
