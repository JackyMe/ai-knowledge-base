제18레슨: 실전: Web 프로젝트 이미지 빌드

아무리 많은 이론을 배워도 직접 손으로 코드를 작성해 보는 것만큼 좋은 것은 없습니다. 오늘은 아주 간단한 Node.js API를 처음부터 작성하고, 이를 Docker 이미지로 빌드하여 컨테이너로 실행한 뒤 최종적으로 Docker Hub에 푸시하는 전체 과정을 실습해 봅니다.

1. 프로젝트 파일 준비

컴퓨터에 my-web-api라는 새 폴더를 만들고, 그 안에 다음 4개의 파일을 생성합니다:

📄 1. package.json
{
  "name": "my-web-api",
  "version": "1.0.0",
  "dependencies": {
    "express": "^4.18.2"
  }
}
📄 2. server.js
const express = require('express');
const app = express();
const PORT = 3000;

app.get('/', (req, res) => {
  res.send('Hello Docker World! Version 1');
});

app.listen(PORT, () => {
  console.log(`Server is running on port ${PORT}`);
});
📄 3. .dockerignore
node_modules/
npm-debug.log
📄 4. Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package.json ./
RUN npm install --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

2. 마법의 시작: 이미지 빌드하기

터미널을 열고 my-web-api 디렉토리로 이동한 후 빌드 명령어를 실행합니다. 이미지 이름은 my-web-api, 태그는 v1으로 지정합니다.

docker build -t my-web-api:v1 .

터미널에서 한 줄씩 실행되는 출력을 볼 수 있으며, 각 줄은 Docker가 한 단계(레이어)의 명령어를 실행하고 있음을 나타냅니다:

3. 컨테이너 실행 및 테스트

이미지가 준비되었으니 컨테이너로 실행해 봅니다:

docker run -d -p 8080:3000 --name webapp my-web-api:v1

브라우저에서 http://localhost:8080에 접속하거나 터미널에서 curl 명령어로 테스트합니다:

curl http://localhost:8080
# 응답 결과: Hello Docker World! Version 1

성공적으로 실행되었습니다! 🎉

4. 버전 업데이트 및 이미지 히스토리 확인

이제 server.js를 수정하여 응답 메시지를 Hello Docker World! Version 2로 변경하고 새 버전으로 다시 빌드해 봅니다:

docker build -t my-web-api:v2 .

다음 명령어를 통해 이 이미지가 어떻게 조립되었는지 레이어별 상세 정보를 확인할 수 있습니다:

docker image history my-web-api:v2

각 레이어가 생성될 때 실행된 명령어와 차지한 디스크 용량이 목록으로 표시됩니다.

5. Docker Hub에 이미지 푸시하기

여러분의 멋진 프로젝트를 전 세계와 공유하려면 3단계만 거치면 됩니다:

  1. 로그인: docker login (Docker Hub 계정과 비밀번호 입력)
  2. 표준 태그 부여(사용자명 포함 필수): docker tag my-web-api:v2 사용자명/my-web-api:v2
  3. 푸시: docker push 사용자명/my-web-api:v2

이제 전 세계 누구나 docker run -p 8080:3000 사용자명/my-web-api:v2만 실행하면 여러분의 웹 앱을 바로 실행할 수 있습니다! 이것이 바로 Docker의 진정한 매력입니다.

💡
프로의 팁 (Pro-Tip): 이미지 태그 전략

실무 기업 환경에서는 v1, v2와 같은 모호한 태그 이름을 거의 사용하지 않습니다. 일반적으로 다음 두 가지 방식을 권장합니다:

  • Git 커밋 해시(Commit SHA) 활용: docker build -t myapp:a1b2c3d . (매우 엄격하며 어떤 소스코드에서 빌드되었는지 확실하게 추적 가능).
  • 타임스탬프 활용: docker build -t myapp:20231015-1430 . (빌드 시점을 직관적으로 파악 가능).
  • latest는 단순한 기본 관례일 뿐: 태그에 latest를 지정해도 그것이 실제로 최신 안정 버전임을 보장하지는 않습니다. 단순한 이름일 뿐이므로 예기치 않은 업데이트 문제를 방지하기 위해 프로덕션 환경에서는 latest 태그 배포를 반드시 피해야 합니다!
🚨 트러블슈팅 응급실
Q1: 빌드 중 npm install 단계에서 네트워크 타임아웃 오류가 발생하면 어떻게 하나요?
A: 컨테이너 내부에서는 호스트 머신의 프록시 설정이 자동으로 전달되지 않을 수 있습니다. RUN 명령어에서 레지스트리 미러를 임시로 지정하거나 사내 캐시 프록시를 설정하여 해결할 수 있습니다:
RUN npm config set registry https://registry.npmjs.org/ && npm install --production
