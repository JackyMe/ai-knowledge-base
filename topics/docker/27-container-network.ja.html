第27レッスン：コンテナ間通信：IP直打ちからの脱却、名前で呼ぶ世界へ

前回のレッスンで触れた通り、Web コンテナからデータベースコンテナへ接続する際に IP アドレスをハードコードしていると、予期せぬトラブルに見舞われることになります。今回は、小明が実際に遭遇した悲劇のシナリオを通じて、Docker ユーザー定義ネットワークによるエレガントな解決策を学びましょう。

1. 小明の悲劇：IP 直打ちによるシステム障害

小明はテストサーバー上でシンプルな EC サイトを構築しました。構成は Node.js バックエンドと MySQL データベースの2つのコンテナです。

まず MySQL を起動し、docker inspect で割り当てられた IP が 172.17.0.2 であることを確認しました。

次に Node.js のコード内に const dbHost = '172.17.0.2' と記述してイメージをビルドし、コンテナを起動。正常に動作し、小明は満足して帰宅しました。

ところが週末、サーバーの計画停電がありマシンが再起動しました。Docker が自動復旧する際、起動順序の前後により、たまたま別の Nginx コンテナが先に起動して 172.17.0.2 を取得してしまいました。その後起動した MySQL には 172.17.0.3 が割り当てられました。

月曜日の朝、システムは大混乱に陥りました。Node.js アプリは 172.17.0.2 へ接続を試み続け、実際には Nginx に向かって SQL を投げているため、当然ながら接続エラーを吐き出し続けたのです...

🚨
本質的な課題 コンテナの IP アドレスはホテルの「部屋番号」のようなものです。コンテナが再起動するたびに、フロント（Docker）から割り振られる部屋番号（IP）は変わる可能性があります。友人を部屋番号だけで探そうとすると、別の宿泊客の部屋をノックすることになります。必要なのは、部屋番号ではなく「友人の名前」を呼ぶだけで自動的に繋がる仕組みです！

2. 解決策：ユーザー定義ネットワークとサービスディスカバリ

解決策は極めてシンプルです。デフォルトの bridge ネットワークを使うのをやめ、独自のユーザー定義ネットワーク（User-defined Network）を作成することです。

ユーザー定義ネットワーク内では、Docker エンジン内蔵の DNS サーバー（127.0.0.11）が自動的に機能します。同一ネットワークに所属するコンテナ同士であれば、コンテナ名をホスト名（ドメイン名）として指定するだけで、自動的に最新の IP アドレスへと名前解決（サービスディスカバリ）が行われます！


sequenceDiagram
    participant Web as Web (app-server)
    participant DNS as Docker DNS (127.0.0.11)
    participant DB as DB (mysql-server)
    
    Web->>DNS: "mysql-server" の IP アドレスは？
    DNS-->>Web: 応答: 172.18.0.3
    Web->>DB: 正しい IP を使って DB 接続を確立

3. 実践演習：コンテナ間通信のハンズオン

小明のシステム構成をベストプラクティスに従って再構築してみましょう。

ステップ 1：カスタムネットワークを作成
docker network create ecommerce-net

ecommerce-net という名前のネットワークが作成されます。ドライバはデフォルトで bridge ですが、内蔵 DNS による名前解決が有効になっています。

ステップ 2：データベースコンテナを参加させる
docker run -d --name my-database --network ecommerce-net -e MYSQL_ROOT_PASSWORD=secret mysql:8.0

--name my-database でわかりやすい名前を付け、--network ecommerce-net で所属させます。

ステップ 3：名前解決のテスト

軽量な alpine コンテナを同じネットワーク内で起動し、通信テストを実施します：

docker run -it --rm --network ecommerce-net alpine sh

コンテナのシェル内で、直接コンテナ名に対して PING を送信します：

/ # ping -c 3 my-database
PING my-database (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.102 ms
64 bytes from 172.18.0.2: seq=1 ttl=64 time=0.081 ms

見事に疎通成功です！Docker 内蔵 DNS が my-database を自動で 172.18.0.2 に解決しました。今後コンテナが何回再起動して IP が変わろうと、接続先文字列に my-database を指定していれば通信が途切れることはありません。

4. 稼働中コンテナのネットワーク動的接続

「すでに稼働している既存コンテナ redis-cache を後からこのネットワークに参加させたい場合、コンテナを作り直す必要がありますか？」

作り直す必要はありません！Docker は稼働中のコンテナに対して、動的に仮想 LAN ケーブルを抜き差しするコマンドを提供しています：

# 稼働中の redis-cache コンテナを ecommerce-net に接続
docker network connect ecommerce-net redis-cache

これで、Web アプリから redis-cache というホスト名で即座にアクセス可能になります。ネットワークから切り離す場合も同様です：

docker network disconnect ecommerce-net redis-cache
🎯
プロの知恵：ネットワークエイリアス (Network Aliases) --name だけでなく、ネットワークエイリアスを付与することも可能です。例えば 3 台のバックエンドコンテナを起動し、すべてに --network-alias backend-api を設定します。
内部ネットワークから backend-api を呼び出すと、Docker DNS が 3 台の IP をラウンドロビンで返却します。手軽な内蔵ロードバランシングとして活用できます！
🚨 トラブルシューティング救急室
Q: "Could not resolve host" エラーでコンテナ名での接続に失敗します。
A: 99% の原因は、2つのコンテナが同一のユーザー定義ネットワークに所属していないことです。docker inspect [コンテナ名] で "Networks" 設定を確認してください。片方がデフォルトの bridge で、もう片方が my-net にある場合、ネットワークが分離されているため名前解決も通信もできません。
Q: 1つのコンテナを複数のネットワークに所属させることは可能ですか？
A: 完全に可能です！PC に複数の NIC（LANカード）を装着するのと同じ状態になります。例えば、Nginx を「外部公開用ネットワーク」と「社内 DB ネットワーク」の両方に接続し、DB コンテナは「社内 DB ネットワーク」にのみ所属させることで、堅牢な多層セキュリティ構成（DMZ 設計）を実現できます。
