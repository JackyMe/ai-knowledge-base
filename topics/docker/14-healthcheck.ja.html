14. ヘルスチェック：コンテナの自己診断

🧟 ゾンビコンテナの「仮死状態」

リバースプロキシとして稼働させている Nginx コンテナがあるとします。ある日の午後、突発的なアクセス集中によって Nginx のコネクションプールが枯渇し、新規の HTTP リクエストを一切受け付けなくなってしまいました。

慌てて docker ps を実行すると、画面にはこう表示されます：
nginx-gateway Up 3 days

Docker は平然と「主プロセスは元気に動いているぞ、すべて順調、Up だ！」と報告してきます。
しかし実際のユーザーから見れば、Webサイトは完全に沈黙しています。このようにプロセスは生きているが、業務サービスとしては死んでいる状態を「仮死（ハングアップ）」と呼びます。

一、なぜヘルスチェック（Healthcheck）が必要なのか？

デフォルト状態の Docker がコンテナの生死を判定する唯一の基準は、「主プロセス（PID 1）が終了したかどうか」だけです。内部でアプリがデッドロックを起こしていようが、DB との接続が切れていようが、スレッドが枯渇していようが、Docker は一切関知できません。

この盲点を解消するために導入されたのが Healthcheck（ヘルスチェック）機能です。カスタム診断コマンドを定期的に実行させ、成功すれば「健全」、連続して失敗すれば「異常」と Docker に判定させることができます。

二、動作原理と状態遷移マシン

ヘルスチェックを設定したコンテナは、docker ps の STATUS 列に明確な健全性ステータスが表示されるようになります：

  • Up (health: starting)：コンテナ起動直後。初期化中または最初の診断待機中。
  • Up (healthy)：診断コマンドが成功。正常にリクエストを処理可能な状態。
  • Up (unhealthy)：診断コマンドが規定回数連続で失敗。サービス異常と判定された状態。
stateDiagram-v2
    [*] --> starting : コンテナ起動
    starting --> healthy : 診断プローブ成功
    starting --> unhealthy : 起動猶予時間超過 & 失敗
    healthy --> unhealthy : N回連続失敗
    unhealthy --> healthy : 診断プローブが復旧成功
    unhealthy --> Restart : 自動復旧連携 (オーケストレーター)

三、ヘルスチェックの設定方法

実務でのベストプラクティスは Dockerfile 内にヘルスチェックルールを宣言することですが（第4フェーズで解説）、docker run の起動時引数として直接指定することも可能です。

シナリオ1：Web API サービスの検査（HTTP プローブ）

Node.js 製 Web アプリに /health という死活監視用エンドポイント（正常時に HTTP 200 を返す）が用意されている場合、curl を使って定期チェックさせます：

docker run -d --name web-api \
  --health-cmd="curl -f http://localhost:8080/health || exit 1" \
  --health-interval=30s \
  --health-timeout=3s \
  --health-retries=3 \
  my-node-app

パラメータ詳細解説：

  • --health-cmd：コンテナ内部で実行するチェックコマンド。curl -f は 4xx/5xx エラー時に非ゼロコードを返し、|| exit 1 で失敗時に確実に終了コード 1 を Docker に伝えます。
  • --health-interval：診断の間隔（例: 30秒ごと。負荷を考慮し短すぎない設定にします）。
  • --health-timeout：各診断のタイムアウト上限（例: 3秒以内に応答がなければ失敗とみなす）。
  • --health-retries：失敗許容回数（例: 3回連続で失敗したら unhealthy に切り替える）。

シナリオ2：データベースの検査（CLI プローブ）

DB には HTTP エンドポイントがないため、内蔵クライアント CLI を用いて ping を打ちます：

# MySQL: サーバーに応答確認 ping を送信
docker run -d --name mysql-db \
  --health-cmd="mysqladmin ping -h localhost -uroot -p$MYSQL_ROOT_PASSWORD" \
  mysql:8.0

# Redis: ping コマンドで PONG の返答を確認
docker run -d --name redis-cache \
  --health-cmd="redis-cli ping | grep PONG" \
  redis:alpine

四、ヘルスチェックの診断ログを確認する

コンテナが unhealthy に陥った際、何が原因で失敗したのかを過去ログから追跡できます：

docker inspect --format='{{json .State.Health.Log}}' web-api

直近5回分の診断実行時刻、終了コード、コマンド出力ログが構造化 JSON で出力され、トラブルシューティングが極めて容易になります。

🚑 トラブル救護室
Q1: Java アプリを起動すると、起動処理が終わる前に unhealthy に判定されてしまう
A: Java Spring Boot などの重量級フレームワークは、起動完了までに 1〜2 分かかることがあります。間隔 10 秒・リトライ 3 回だと 30 秒で異常と誤判定されてしまいます。解決策： --health-start-period=60s（起動猶予時間）を設定してください。起動開始から最初の 60 秒間に発生した失敗はカウントされず、猶予されます。
🚀
プロの知恵：unhealthy になったら自動で再起動してくれるのか？

初心者が最も抱きやすい勘違いです！ 単体の Docker デーモンは、unhealthy になったコンテナを自動で再起動することは絶対にありません！ 単にメタデータ上のフラグを unhealthy に書き換えるだけです。
真の自己修復（異常検知時の自動再作成・再起動）を実現するには、Kubernetes (K8s) や Docker Swarm などのオーケストレーターと組み合わせるか、Docker Compose の depends_on（condition: service_healthy）で起動順序を制御する必要があります。ヘルスチェックは、高可用性アーキテクチャの基礎となる最重要パーツです。
