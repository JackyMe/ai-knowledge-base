10. 컨테이너 생명주기 제어 (상태 머신)

컨테이너를 실행하는 것은 첫걸음에 불과합니다. 실제 운영 환경에서는 컨테이너를 일시 정지하거나, 정상 종료하고, 재시작하며, 수명이 다한 컨테이너를 안전하게 파기하는 등 다양한 생명주기(Lifecycle) 관리가 필수적입니다. 모든 컨테이너는 탄생에서부터 소멸에 이르기까지 명확한 상태 머신(State Machine)을 따라 움직입니다.

1. 컨테이너 생명주기 상태 전이도

명령어를 실행하기 전에 아래의 상태 전이 다이어그램을 반드시 머릿속에 기억해 두세요. Docker 프로세스 제어의 핵심 뼈대입니다.

stateDiagram-v2
    [*] --> Created: docker create (생성 단계)
    Created --> Running: docker start (실행 단계)
    [*] --> Running: docker run (생성 + 즉시 실행)
    
    Running --> Paused: docker pause (CPU 프로세스 동결)
    Paused --> Running: docker unpause (동결 해제)
    
    Running --> Stopped: docker stop (우아한 종료 SIGTERM)
    Running --> Stopped: docker kill (강제 종료 SIGKILL)
    
    Stopped --> Running: docker start (재가동)
    Running --> Running: docker restart (재부팅)
    
    Stopped --> [*]: docker rm (영구 파기 및 디스크 정리)
    Running --> [*]: docker rm -f (강제 강등 후 파기)

2. 핵심 생명주기 제어 명령어 5가지

앞서 생성한 my-web 컨테이너를 예제로 단계별 제어 명령을 실습합니다.

1. 우아한 정상 종료 (Graceful Shutdown): docker stop

docker stop my-web

동작 원리: 무작정 프로세스를 강제 종료하는 것이 아닙니다. docker stop은 컨테이너 내부의 1번 프로세스(PID 1)에 먼저 SIGTERM (종료 요청) 시그널을 전달합니다. 실행 중인 애플리케이션은 처리 중이던 클라이언트 HTTP 요청을 마무리하고 DB 커넥션을 안전하게 닫을 수 있도록 기본 10초의 유예 기간을 부여받습니다. 만약 10초가 지나도 종료되지 않으면 Docker 데몬이 SIGKILL 시그널을 보내 강제 종료하며, 상태는 Exited로 바뀝니다.

2. 즉시 강제 종료 (Kill): docker kill

docker kill my-web

stop과 달리 유예 시간 없이 즉시 SIGKILL 시그널을 보내 프로세스를 그 자리에서 사살합니다. 컨테이너 내부 프로세스가 데드락에 걸려 응답하지 않는 긴급 상황 외에는 데이터 유실 위험이 있으므로 지양해야 합니다.

3. 재기동 및 재부팅: docker start / docker restart

docker start my-web
docker restart my-web

start는 Exited(정지) 상태의 기존 컨테이너를 그대로 다시 깨울 때 사용합니다. restart는 stop 후 start를 수행하는 단축 명령으로, 설정 파일 변경 후 서비스를 재시작할 때 자주 사용됩니다.

4. 프로세스 일시 동결: docker pause / docker unpause

docker pause my-web
# 동결 해제:
docker unpause my-web

pause는 컨테이너를 중지하지 않고(네트워크 포트와 메모리 상태 유지), Linux 커널의 cgroups freezer를 이용해 CPU 스케줄링을 일시 중단시킵니다. 게임의 '일시정지' 버튼과 같으며, 호스트 서버 리소스를 순간적으로 확보하거나 디버깅 상태를 보존할 때 유용합니다.

5. 컨테이너 영구 삭제: docker rm

docker rm my-web

중요: 중지(stop)와 삭제(rm)는 완전히 다릅니다! 컨테이너를 stop해도 컨테이너가 생성한 파일, 로그, 쓰기 레이어는 호스트 디스크에 그대로 남아있습니다. rm 명령을 내려야 비로소 가상 파일시스템이 파기되고 디스크 공간이 반환됩니다. 실행 중인 컨테이너는 실수를 방지하기 위해 기본적으로 rm이 불가하며, 강제 삭제하려면 docker rm -f my-web을 사용해야 합니다.

3. 대량 일괄 정리 기법

로컬에 종료된 수십 개의 더미 컨테이너가 쌓여 있을 때 하나씩 삭제하는 것은 매우 번거롭습니다.

🧹 종료된 컨테이너 일괄 삭제 팁
# 방법 1: Shell 파이프라인 활용
docker rm $(docker ps -aq)

# 방법 2: Docker 공식 권장 전용 청소 명령어
docker container prune -f

동작 원리: docker ps -a -q는 모든 컨테이너의 ID 목록만 깔끔하게 출력합니다. 이를 $(...)로 묶어 docker rm에 넘기면 종료된 모든 컨테이너가 한 번에 청소됩니다. 최신 Docker 환경에서는 docker container prune이 가장 안전하고 직관적인 방법입니다.

🚑 트러블슈팅 구조대
Q1: 동일한 이름으로 새 컨테이너를 실행하려는데 "Conflict. The container name is already in use" 에러가 발생합니다.
A: 기존 컨테이너가 stop 상태로 남아있기 때문입니다. Docker 시스템 내에서 이름(Name)은 유일해야 하므로, docker rm [기존이름]으로 먼저 삭제한 뒤 새 컨테이너를 실행하세요.
Q2: 실행 중인 컨테이너의 이름을 변경할 수 있나요?
A: 가능합니다! docker rename [기존이름] [새이름] 명령을 사용하면 컨테이너를 중단하지 않고 즉시 이름을 변경할 수 있습니다.
🌟
실무 팁: 무중단 서비스를 위한 컨테이너 자동 재시작 정책 (Restart Policies) 운영 환경에서 서버가 불시에 재부팅되거나 프로세스가 비정상 종료되었을 때, 엔지니어가 수동으로 복구하지 않도록 자동 재시작 플래그를 지정할 수 있습니다.
• --restart=always: 컨테이너가 종료되면 어떤 이유든(수동 stop 제외) 무조건 자동 재시작하며, 호스트 OS 부팅 시에도 자동 기동됩니다.
• --restart=unless-stopped: always와 유사하지만 관리자가 명시적으로 docker stop한 경우에는 재부팅 후에도 자동으로 켜지지 않습니다 (가장 추천하는 프로덕션 옵션).
• --restart=on-failure:3: 0이 아닌 비정상 에러 코드로 죽었을 때만 최대 3회까지 재시작을 시도합니다.
