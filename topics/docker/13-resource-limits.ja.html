13. リソース制限：OOMクラッシュの防止

💥 Java が引き起こしたサーバー大崩壊

かつてある現場で、16GB メモリの本番サーバー上にいくつかの軽量な Node.js サービスと、新しく追加された外注開発の Java 製 Web クローラーが同居していました。

ある日の午後3時、突如アラートが鳴り響き、サーバーへの SSH 接続が途絶えました。クラウドコンソールから強制再起動後、調査したところ、Java クローラーに深刻なメモリリークが発生し、16GB のメモリをブラックホールのように飲み干していたことが判明しました。Linux カーネルのメモリ防壁が決壊し、SSH デーモンさえも OS に強制終了させられていたのです。

「Docker コンテナに閉じ込めていたのに、なぜホストサーバー全体を巻き込んで死ぬんだ？」エンジニアは愕然としました。

一、コンテナの「無制限リソース」という幻想を打ち破る

初心者は、コンテナが仮想マシンのように最初から厳格なハードウェア制限を持っていると勘違いしがちです。それは大間違いです！

デフォルト状態の Docker コンテナは、リソース消費の上限が完全に無制限です。ホストに 100 コアの CPU と 1TB のメモリがあれば、暴走したコンテナプロセスはそれらを限界まで使い果たします。だからこそ、コンテナに「リソースの枷（制限）」をかけることは本番運用の鉄則なのです。

Docker は Linux カーネルの Cgroups（Control Groups） 技術を利用してリソース制限を実現しています。これにより、コンテナごとの最大メモリ容量や CPU 使用率を精密にコントロールできます。

二、メモリの枷：メモリ上限の設定（Memory Limits）

ホストの Out-of-Memory（OOM）クラッシュを防ぐには、まずメモリ上限を設定します。-m または --memory フラグを使用します：

# Java コンテナの最大物理メモリ使用量を 512MB に制限
docker run -d --name java-app -m 512m my-java-image

単位には m（メガバイト）や g（ギガバイト）が指定できます。

🧠
隠れた Swap の罠に注意

-m 512m だけを指定した場合、Docker はデフォルトで 512MB の物理メモリに加えて同量の 512MB の Swap（仮想メモリ）を割り当てます！ つまり、実質 1GB までメモリを消費できてしまいます。
Swap を一切使わせず厳格に 512MB で止めたい場合は、--memory-swap をメモリ制限値と同値に設定します：
--memory 512m --memory-swap 512m

上限を超えると何が起きるのか？

コンテナ内のプログラムがメモリを確保し続け、設定した 512MB の閾値に達するとどうなるでしょうか？
ホストの Linux カーネルが OOM Killer を発動し、コンテナプロセスを即座に強制終了させます！
docker ps -a を確認すると、悪名高い終了ステータスが記録されています：Exited (137)。終了コード 137 は、100% の確率で OOM による強制停止（128 + SIGKILL 9 = 137）を意味します。

以下のコマンドを使えば、OOM による強制終了かどうかを一瞬で判定できます：

docker inspect --format='{{.State.OOMKilled}}' java-app
# "true" が返ってきた場合、OOM Killer による終了です。

三、CPU の枷：CPU 上限の設定（CPU Limits）

CPU の制限には、主に絶対制限（Absolute Limits）と相対ウェイト（Relative Weights）の2つの戦略があります。

1. 絶対制限（--cpus）

最も直感的な方法で、コンテナが使用できる最大 CPU コア数を明示的に指定します：

# ホストのコア数に関わらず、このコンテナは最大 1.5 コア分の計算リソースしか使えない
docker run -d --name math-app --cpus="1.5" my-image

2. 相対ウェイト（--cpu-shares）

動的な比例配分の仕組みです。デフォルトでは全コンテナに 1024 のシェアが与えられます。コンテナ A に 2048、コンテナ B に 1024 を割り当てた場合、ホストの CPU が空いているときは両者とも自由に使えますが、CPU 使用率が 100% で競合した際には、コンテナ A がコンテナ B の 2 倍の処理時間を優先的に獲得します！

docker run -d --name priority-app --cpu-shares 2048 my-image
pie title CPU 100% 競合時のリソース配分比率 (--cpu-shares)
    "アプリ A (ウェイト 2048)" : 66.6
    "アプリ B (ウェイト 1024)" : 33.3

四、稼働中のリソース消費をリアルタイム確認する

制限を設定したら、docker stats コマンドで確認してみましょう。LIMIT 列にホスト全体のメモリではなく、指定した上限値（512MiB など）が正しく反映されていることがわかります：

CONTAINER ID   NAME       CPU %     MEM USAGE / LIMIT     MEM %
a1b2c3d4e5f6   java-app   0.12%     120MiB / 512MiB       23.4%
🚑 トラブル救護室
Q1: Docker でメモリ制限を設定したら、Java アプリがクラッシュ（Exit 137）を繰り返す
A: Java 仮想マシン（JVM）のヒープメモリ管理が原因です。古い JDK 8 では JVM がコンテナの cgroups 制限を認識できず、ホストの物理メモリ全体を基準にデフォルトヒープサイズを確保しようとするため、Docker の制限値を超えて OOM で即死します。解決策： JVM の起動オプションに -XX:MaxRAMPercentage=75.0 を追加してコンテナ制限値に連動させるか、コンテナ cgroups をネイティブ認識する JDK 11 以降にアップグレードしてください。
🚀
プロの知恵：適切なリソース制限値の割り出し方

勘で適当に制限値を決めてはいけません！ 実務での標準的な割り出しフロー：
1. ステージング環境で最初は制限なしで起動し、本番同等の負荷テストを実施する。
2. docker stats でピーク時の CPU・メモリ消費量をモニタリングする。
3. ピーク値に 20%〜30% の安全マージン を上乗せした値を正式な Limit として設定する。
（Node.js / Python などのシングルスレッド言語は 1 CPU で十分な場合が多く、Java / Go などのマルチスレッド言語は目標同時接続数に応じて CPU 数を調整します）。
