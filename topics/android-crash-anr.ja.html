入門 00

全体像と方法論

安定性問題の分類マップ

まず全体マップを描き、それから調査に着手する。Android の「クラッシュ／フリーズ」は大きく4つに分類され、それぞれ証拠、ツール、対応章が異なります:

タイプ現象本質主要な証拠詳細
Java/Kotlin Crashアプリが強制終了未捕捉の例外がコールスタックを遡りメインスレッドの最上位に到達logcat 内の FATAL EXCEPTION スタックトレース02
Native Crashアプリが強制終了C/C++ レイヤーのシグナル (SIGSEGV/SIGABRT 等)tombstone ファイル、*** *** セクションのログ04
ANRフリーズ → システムの「応答なし」ダイアログメインスレッドがブロックされ、制限時間内に重要なイベントを処理できない/data/anr/ の trace、Vitals の ANR レポート03
システムによるプロセス強制終了「使っている最中にホーム画面に戻る」、バックグラウンドでプロセス消滅OOM/LMK（Low Memory Killer）による強制終了、バックグラウンド制限、ユーザーによる強制停止ApplicationExitInfo の終了理由08
初心者に最も多い誤認「クラッシュログがない強制終了」の多くは通常の Crash ではありません。Native クラッシュ（tombstone を確認）か、システムによるプロセス終了（ExitInfo を確認）のいずれかです。まず正しく分類してから調査に入る――マップを間違えると、すべての努力が無駄になります。

なぜ解決が必須なのか: プラットフォームの厳格なレッドライン

Google Play の Android Vitals では「不正な動作の基準値（Bad behavior threshold）」が定められています。ユーザー認知クラッシュ率 ≥ 1.09% または ユーザー認知 ANR 率 ≥ 0.47%（全デバイス集計）に達すると、アプリはストア全体での露出度が引き下げられます。また、特定の単一端末モデルで ≥ 8% に達した場合、その端末での露出低下に加え、ストア掲載情報に警告が表示される場合があります。安定性は技術的なこだわりではなく、ユーザー流入とビジネスに直結する問題です。

全体を貫く 5 段階の方法論

  1. 現象の保全 —— 最も信頼できる生の証拠を確保する: 完全なスタックトレース / trace / ログ、端末情報、OS バージョン、アプリバージョン、再現手順。「人づての曖昧な報告」だけで作業を開始してはならない。
  2. 特定 —— スタックトレースから「第1現場」を見つける: 自社コードはどのフレームにあるか？難読化されている場合はまず復元（retrace）する。
  3. 原因究明 ——「なぜこのステップに到達したのか」に答える: null はどこから来たのか？ロックは誰が保持しているのか？メモリは誰が消費したのか？――推測に頼らずツールで証拠を掴む。
  4. 根本解決 —— 安易に try-catch で囲むのではなく根本原因を修正する。修正後は、修正を証明できる検証手段（再現手順 / リグレッションテスト / カナリアリリース指標）を必ず用意する。
  5. 再発防止 —— 同類の問題に対する防壁を築く: lint ルール、StrictMode、CI チェック、監視アラート。1つのバグを修正したら、同系統のバグ全体を根絶する。
ステップアップの推奨パス初心者: 00→01→02（NPE レベルの日常的なクラッシュを自力で解決できるようにする）; 中級者: 03→07（ANR や本番チケットに対応できるようにする）; 上級者: 08以降（再現困難な難解バグを解明し、AI をワークフローに組み込む）。

最初の当番: 最初の 30 分間の行動チェックリスト

時間必須完了タスク成果物 / 意思決定
0〜5分バージョン、発生時刻、影響ユーザー数、起動直後クラッシュか／コアフロー不能かを確認。関連するカナリア配信を一時停止重大度レベル、インシデント対策グループ／担当者の決定。緊急停止基準に達した場合は即座にロールバックまたは feature flag を OFF
5〜10分4大分類マップに従ってトリアージ: Java/Kotlin、Native、ANR、システムプロセス終了唯一の主証拠を選択: stack / tombstone / trace / ExitInfo
10〜20分3件以上のイベントサンプルを抽出し、mapping/Build ID を突合。バージョン、OS、端末、国、カスタムキーごとに共通点を分析「確定した事実」と「未知の項目」のリストを作成。単一サンプルを全体原因と決めつけることを禁止

緊急止血の優先順位起動クラッシュ、決済／ログインなどのコアフロー、新バージョンで急拡大する問題は、まずロールバック／スイッチ OFF による「止血」を行い、その後に分析を進めます。止血は案件のクローズを意味しません。復旧後も根本解決と再発防止をやり遂げる必要があります。
入門 01

第1課: クラッシュログを読み解く

スタックトレースの解剖: 4つの情報で瞬時に特定

FATAL EXCEPTION: main                                    ← ① どのスレッドでクラッシュしたか（main = メインスレッド）
Process: com.example.app, PID: 12345
java.lang.NullPointerException:                          ← ② 例外タイプ: どの図鑑章を参照すべきかを決定
    Attempt to invoke virtual method 'int java.lang.String.length()'
    on a null object reference                           ← ③ 例外メッセージ: どのオブジェクトのどんな操作か
  at com.example.app.OrderDetail.bind(OrderDetail.kt:87) ← ④ 第1現場: 自社パッケージ名の最上位フレーム
  at com.example.app.OrderAdapter.onBindViewHolder(OrderAdapter.kt:42)
  at androidx.recyclerview.widget.RecyclerView...        ← フレームワークフレーム: 通常は「通過」しただけ
Caused by: ...                                           ← Caused by がある場合、根本原因は最下部にある！
  • スタックの読み順: まず例外のタイプとメッセージを確認 → 上から下へ走査して自社パッケージに属する最初のコードフレームを見つける → Caused by チェーンがある場合は、最も底にあるものが根本原因;
  • 難読化されたスタックの復元: 本番環境のスタックが a.b.c(Unknown Source) の場合、R8 の mapping.txt を使って復元します: retrace mapping.txt stacktrace.txt（リリースごとの mapping は必ずアーカイブ保存すること！）;
  • 現場捕捉の3つの鉄則: adb logcat -b crash でクラッシュバッファのみを確認; adb logcat --pid $(adb shell pidof -s パッケージ名) で自プロセスのみを追跡; クラッシュ瞬間のログを逃した場合は adb bugreport で事後取得（第07章参照）。

再現環境の構築: 調査価値の半分を占める重要工程

スタックトレースを入手して最初に行うべきはコードの変更ではなく、安定した再現環境の構築です。再現できるバグはすでに半分解決したも同然です。3つのレベルで順に試みます: 正確な手順での再現（ユーザー操作パスのトレース）→ 条件付き再現（特定のデータ／ネットワーク／権限状態）→ 負荷テストによる再現（monkey / 画面の連続回転 / 開発者向けオプションの「アクティビティを保持しない」によるプロセス再生成シミュレーション）。

# 3つの代表的なストレステスト・再現スイッチ
adb shell settings put global always_finish_activities 1   # アクティビティを保持しない: プロセス再生成に伴うクラッシュを顕在化
adb shell monkey -p com.example.app --throttle 300 -v 5000 # monkey によるランダムイベントストリーム
# 開発者向けオプション → セカンダリディスプレイのエミュレート／言語切り替え／ダークモード切り替え: 構成変更関連のクラッシュを顕在化
初心者のためのガードレール「グローバルな try-catch で例外をもみ消す」ことでクラッシュを「修正」してはなりません。これはクラッシュを、より検知が難しいデータ不整合や状態異常に変えてしまうだけです。同様に、「クラッシュ防止 SDK」の自動例外キャッチ機能を安易に使用すると、Vitals の数値は見かけ上良くなってもユーザー体験はさらに悪化します。

証拠引き継ぎシート: 誰が引き継いでも即座に継続できる形式

問題 ID / 初回発生時刻 / 現在の担当者：
影響範囲：バージョン、配信トラック、ユーザー数、Crash/ANR 率、コアフロー
分類：Java/Kotlin | Native | ANR | システムプロセス終了
バージョン突合：mapping / native Build ID / ソースコード commit
分布状況：アプリバージョン、OS、端末モデル、国、feature flags
主証拠：完全な stack/trace/tombstone へのリンク（スクリーンショット単体は不可）
確定した事実：証拠によって直接裏付けられた結論のみを記載
候補仮説：確率 × 影響度で順位付け。各仮説に反証手順を明記
止血ステータス：ロールバック／フラグOFF／機能制限／未対応（タイムスタンプ付き）

この引き継ぎシートは、第09章で扱う「クラッシュコンテキストバンドル」の雛形でもあります。まずは人間同士が情報の欠落なく引き継げるようにし、同じ構造化された証拠を AI に渡します。そうでなければ、AI は未検証の推測をより高速に出力するだけに終わってしまいます。

上記の NPE を最後まで完結させる実例

87行目が order.title.length であったと仮定し、Java/JSON の境界まで遡ったところ、サーバー側の古いデータに title が欠落しており、Kotlin が platform type を非 null とみなしていたことが判明したとします。完全なクローズドループは次のようになります:

  1. 根本原因の検証: title が欠落した固定レスポンスを用いて再現。同様のデータが mapper に入ると null が発生し、正常なレスポンスでは発生しないことを確認;
  2. 根本解決: DTO → Domain の境界でフィールドを String? と宣言し、ビジネスルールに従って表示可能なプレースホルダーまたは明示的な MalformedOrder を返すようにし、UI レイヤーには常に非 null の Domain のみを渡す;
  3. リグレッション確認: 欠落フィールド、空文字列、正常値、古いキャッシュのデシリアライズをテストで網羅。release + R8 ビルドを実行し、元の操作パスを再テスト;
  4. 再発防止: 厳格なデシリアライズ／スキーマ監視を有効化し、Java platform type の境界に対する lint/review ルールを追加。Crashlytics のカスタムキーに応答スキーマバージョンを記録する。
根本解決できたかの判定基準修正パッチが単に order.title.length を order.title?.length ?: 0 に変更しただけで、「title が欠落した注文が有効かどうか」を定義していない場合、それはクラッシュを消しただけであり、データ契約を修正したことにはなりません。
実践 02

頻出 Crash 図鑑と根本解決

図鑑は例外名を暗記するためのものではなく、「例外メッセージ」から次の調査アクションへと素早く移るためのガイドです。表中の解決策はすべて同一の原則に従っています: 状態と境界を修正し、例外をもみ消さないこと。

例外 / 典型的シグナル発生原因と調査方法根本解決と再発防止
NullPointerException
... on a null object reference		Java の null 許容値に対する null チェック漏れ。Kotlin で最も危険なのは Java platform type（String! と表示される）、デシリアライズ時のフィールド欠落、lateinit の未初期化。まず自社の最初の業務フレームを確認し、null 値が生成されたパスを逆引きする。Java／ネットワーク／データベースの境界で即座に明示的な null 許容型またはドメインオブジェクトに変換する。requireNotNull は真の不変条件の保護にのみ使用する。?. の連続で必須データを暗黙的にもみ消さないこと。
IndexOutOfBoundsException
Index: 5, Size: 5		インデックスとコレクションが同一スナップショットでない。ページングコールバック、DiffUtil、または並行更新後に古い position を参照している。index、size、adapterPosition、データバージョンを記録する。getOrNull は欠落が許容される読み取りにのみ使用。RecyclerView のクリック時は bindingAdapterPosition を再取得して NO_POSITION をチェック。イミュータブルなリストを submit する。
ClassCastException
X cannot be cast to Y		Bundle/Intent、JSON、複数タイプ混在リスト、または誤った ClassLoader により、前提と異なる実際の型が渡された。まず実際のクラス名と入力データを出力する。タイプセーフな Navigation 引数、sealed class、明示的なシリアライズスキーマを使用する。バージョンを跨ぐデータは必ずマイグレーションを行い、キャストに頼らない。
IllegalStateException
Fragment not attached
after onSaveInstanceState		Fragment が detach されているのに Context にアクセス。状態保存（onSaveInstanceState）後にトランザクションをコミット。RecyclerView のレイアウト途中でデータを変更すると inconsistency エラーが発生。ライフサイクルのタイムラインと全データの書き込み口を照合する。適切なライフサイクル内でのみ UI にアクセスする。Navigation イベントの重複排除を行い、復元可能な状態でのみ実行する。リストは単一のデータソースから新しいスナップショットのみを送信する。commitAllowingStateLoss は UI 状態の破棄が真に許容される場合にのみ適する。

WindowLeaked
Activity has leaked window		Activity 破棄時に Dialog/PopupWindow が表示されたまま。フレームワークがログに出力してウィンドウリークを警告するものであり、必ずしも未捕捉の Crash 1件と同等とは限りません。「無効なトークンによるウィンドウ追加失敗」である BadTokenException とは別カテゴリの問題です。LifecycleOwner が保持し onDestroy で確実に dismiss する。DialogFragment の使用を推奨。同時にログ後続の真の FATAL EXCEPTION を確認し、診断ログを最終的なクラッシュタイプと誤認しないようにする。
IllegalArgumentException
Receiver not registered		登録と解除のパスが非対称、二重解除、または登録失敗後にクリーンアップを実行した。登録状態を一元管理する。onStart/onStop または onResume/onPause とペアにする。新しい API では可視性に応じた receiver flags を明示する。
ConcurrentModificationExceptionコレクションの反復処理中に現在のスレッドまたは他スレッドから変更された。ログにはスレッド名と変更箇所を同時に記録する。単一スレッドへの帰属、イミュータブルなスナップショット、または並行コレクションを使用する。イテレーションを try-catch で囲んで握りつぶしてはならない。

ActivityNotFoundException暗黙的 Intent の処理ハンドラが存在しない、コンポーネントが削減された、または OEM 端末のアプリが欠落。呼び出し前に PackageManager で resolve する。アプリ内フォールバックパスを用意する。明示的コンポーネントは manifest と共にテストする。
SecurityException実行時パーミッションの欠落、Android 12+ の exported 設定漏れ、バックグラウンド起動／フォアグラウンドサービス制限、未認可 URI へのアクセス。ターゲット SDK に合わせた権限ステートマシンを構築。Activity Result API を使用。コンポーネントの露出を最小化し URI は一時的権限を付与。パーミッション拒否や「今後表示しない」のテストを網羅する。
TransactionTooLargeExceptionBinder トランザクションバッファはプロセス間で共有される。巨大な Bundle、Intent、Fragment 引数、saved state はライフサイクル遷移時に上限を超えやすい。dumpsys activity とシリアライズ後サイズで特定する。ID のみを渡し、巨大オブジェクトは DB／ファイル／Repository に保存する。SavedState には UI 復元に必要な最小限の状態のみを保持する。
OutOfMemoryError
Java heap space		Bitmap、キャッシュ、コレクション、またはメモリリークによる retained heap の増大。heap dump の dominator tree と GC 後の生存オブジェクトを確認する。参照チェーンを切断し、画像を適切にリサイズし、上限付き LRU キャッシュを設定する。largeHeap を根本解決策としてはならない。
OutOfMemoryError

ライフサイクル関連のクラッシュ: 真の問題は「状態の陳腐化」

  1. プロセス再生成: システムがバックグラウンドプロセスを強制終了した後、savedInstanceState を用いて Activity/Fragment を再生成します。静的シングルトンにデータが残っている前提を禁止し、永続化された ID から復元し、ViewModel の SavedStateHandle には最小限の状態のみを保存します。
  2. Fragment View のライフサイクル: Fragment が生存していても View が生存しているとは限りません。LiveData/Flow を購読する際は viewLifecycleOwner にバインドし、onDestroyView で binding をクリアします。
  3. 非同期結果の陳腐化: ネットワーク／位置情報／決済のコールバックが戻った時点で、画面は既に破棄されている可能性があります。タスクを lifecycleScope/viewModelScope に連動させてキャンセルするか、結果を状態コンテナに書き込み、現在表示されている UI がそれを描画するように設計します。
一見解決に見える対処Activity を WeakReference でラップする。これは強参照リークを減らすだけであり、画面が依然として更新可能な状態にあることを証明せず、バックグラウンド処理のキャンセルも行いません。

8 つの頻出根本原因

  • メインスレッドでの I/O: ファイル、データベース、DNS、ネットワーク、Binder、または巨大な JSON/Proto のシリアライズ;
  • SharedPreferences: commit() による同期的ディスク書き込み。apply() は非同期ディスク書き込みですが、未完了の書き込みは Activity/Service のライフサイクル遷移時にフレームワークによって待機されるため、QueuedWork を通じて ANR を引き起こす可能性があります。新規プロジェクトでは DataStore を優先;
  • ロック競合／デッドロック: main スレッドがバックグラウンドスレッドの保持するロックを待機し、そのバックグラウンドスレッドが main や同期 Binder を待機している;
  • 同期 Binder: スタックが BinderProxy.transactNative で停止しており、真のボトルネックが system_server または別プロセスにある;
  • ブロードキャストとサービス: onReceive、コールドスタート時の初期化、onStartCommand で重い処理を実行している。goAsync() の finish() 呼び出し忘れ;
  • レイアウトストーム: 深いネスト、頻繁な requestLayout、Compose の高頻度な無効再構成（recomposition）による measure/layout のタイムアウト;
  • GC スラッシング: 短時間の大量メモリ割り当てにより main スレッドが頻繁に一時停止。単一の GC ログだけで断定せず、Perfetto の割り当てとスケジューリングのタイムラインを照合する;
  • システム負荷: main が Runnable 状態のまま長時間 CPU が割り当てられない、system_server のロック、GPU ハングなど、アプリ自身の長時間タスクに起因しないケース。

  • UAF / 二重解放: オブジェクトの所有権を明確化し、RAII と std::unique_ptr を優先。スレッド間で共有ライフサイクルを渡す場合のみ shared_ptr を使用し、停止／破棄の順序を設計する;
  • 境界外アクセス: すべての長さとオフセットを同一箇所で検証し、長さ情報を持つコンテナ／ビューを使用する。パーサーには切り詰め、超長、不正入力の単体テストと fuzzing を追加する;
  • JNI 規約: Java 例外、ローカル／グローバル参照、スレッドのアタッチ状態を確認する。スレッドを跨いだローカル参照の保持を禁止し、method/class ID のキャッシュ時は ClassLoader とアンロード境界を処理する。CheckJNI を有効化し、本番の native crash になる前に開発段階でエラーを検出する（下記 CheckJNI 節参照）;
  • スタックオーバーフロー: 無限再帰や巨大なスタック配列を排除し、イテレーション／ヒープ割り当てに変更し、深度に上限を設ける;
  • 再発防止: 修正後に同一の sanitizer で元の入力を再テストし、release シンボルアップロード検証、ABI スモークテスト、native 単体テスト／fuzzing、本番 GWP-ASan サンプリングを追加する。
最も無駄な作業パターンバージョンが異なる so ファイルを使ってシンボル化すること。アドレスから「何らかの関数名が引けた」としても、その結果が正しいとは限りません。まず ABI、Build ID、バージョン番号を照合してからソースコードの行を確認してください。

Android Vitals：まず影響度を見て、次に切り口を変える

「ユーザー認知（User-perceived）」は、バックグラウンドの全例外の合計ではありません。指標は1日あたりのアクティブユーザーのうち、少なくとも1回のインシデントを経験したユーザーの割合で計算されます: ユーザー認知 Crash はアプリが Activity を表示中またはフォアグラウンドサービスを実行中の未処理クラッシュを指し、現在のユーザー認知 ANR は Input dispatching timed out のみをカウントします。Play の現在のコア不良動作基準値は: クラッシュ率 1.09%、ANR 率 0.47%; 単一スマートフォン機種ではいずれも 8%、Wear OS の単一ウォッチ機種ではそれぞれ Crash 4%、ANR 5% です。Play は直近28日間のデータを用いて品質を毎日評価し、基準値を超過すると露出低下やストア警告の対象になります。

  1. まず新規クラスタを確認: 同一バージョンで突如現れた新規の問題は、長年の既存問題よりも対応可能性が高いのが一般的です;
  2. アプリバージョンで切り分け: 新バージョンで混入したものか、古いバージョンの未アップデートユーザーかを判別;
  3. OS / 端末モデルで切り分け: 単一ベンダー、単一 GPU、特定 Android バージョンでのスパイクは、互換性とシステムスタックを優先調査;
  4. 国 / 配信トラックで切り分け: ネットワーク環境、地域設定、カナリア配信対象によりトリガー条件が変化する可能性があります;
  5. 発生回数だけでなく affected users を比較: 1人のユーザーがループで100回クラッシュするのと、100人のユーザーが各1回クラッシュするのでは、対応の優先順位が異なります。
Vitals と Crashlytics の数値が異なる理由説明
収集レイヤーの違いVitals は Android OS レイヤーから収集するため、SDK 初期化前のクラッシュ等も捕捉可能; Crashlytics は SDK の初期化と送信成功に依存。
サンプル対象の違いVitals は Google Play 経由でインストールされ、認証済み端末で、診断データの共有に同意したユーザーのみを対象とし、プライバシーの最低閾値の影響を受けます。
分母の定義の違いVitals は日次アクティブユーザー基準; Crashlytics は crash-free users と crash-free sessions の両方を提供。1人のユーザーが同日に3回の独立セッションを行い、そのうち1回でクラッシュした場合、クラッシュ率に換算するとユーザー基準では 100%、セッション基準では約 33%（crash-free 率はそれぞれ 0% と約 67%）となります。「3回起動」が必ずしも3つのセッションとは限りません。
クラスタリング手法の違いスタックの正規化、バリアントの分割、重複排除ウィンドウが異なります。バージョン、期間、端末、issue サンプルを揃えてから傾向を比較してください。

ApplicationExitInfo：起動後に前回の ANR trace を回収する

Android 11（API 30）以降、アプリの次回起動時に過去の終了理由を問い合わせることができます。ANR レコードにはシステムが採取した trace が含まれることが多く、ユーザー端末が adb に接続できない本番環境での証拠補完に非常に適しています。ただし、すべてのレコードに trace が保証されるわけではなく、リアルタイムの ANR コールバックでもありません。

class ExitInfoReporter(
    private val context: Context,
    private val store: ExitCursorStore,
    private val upload: suspend (ExitEnvelope) -> Unit
) {
    private val collectMutex = Mutex()

    suspend fun collect() = collectMutex.withLock {
      withContext(Dispatchers.IO) {
        if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) return@withContext

        val am = context.getSystemService(ActivityManager::class.java)
        val records = am.getHistoricalProcessExitReasons(
            context.packageName, 0, 32
        ).sortedWith(compareBy({ it.timestamp }, { it.processName }, { it.reason }))

        for (info in records) {
            val eventKey = listOf(
                info.timestamp, info.processName, info.reason, info.status
            ).joinToString(":")
            if (!store.shouldAttempt(eventKey, System.currentTimeMillis())) continue

            try {
                val trace = info.traceInputStream?.use { input ->
                    input.readAtMost(512 * 1024)        // API 30 互換かつサイズ制限
                }
                upload(
                    ExitEnvelope(
                        eventKey = eventKey,
                        timestamp = info.timestamp,
                        processName = info.processName,
                        reason = info.reason,
                        status = info.status,
                        importance = info.importance,
                        description = info.description,
                        pssKb = info.pss,
                        rssKb = info.rss,
                        traceGzip = trace?.let(::gzip)
                    )
                )
                store.markUploaded(eventKey)
            } catch (retryable: RetryableUploadException) {
                store.scheduleRetry(eventKey, retryable) // 上限付き指数バックオフ。オフライン回数のみで直ちに破棄しない
                continue
            } catch (io: IOException) {
                store.scheduleRetry(eventKey, io)
                continue
            } catch (permanent: PermanentUploadException) {
                store.markDiscarded(eventKey, permanent) // スキーマ／権限等、確定的な恒久エラーのみ破棄
                continue                                // Error や未知の例外はもみ消さず再スロー
            }
        }
      }
    }

    private fun InputStream.readAtMost(limit: Int): ByteArray {
        val output = ByteArrayOutputStream(minOf(limit, 64 * 1024))
        val buffer = ByteArray(16 * 1024)
        var remaining = limit
        while (remaining > 0) {
            val count = read(buffer, 0, minOf(buffer.size, remaining))
            if (count == -1) break
            output.write(buffer, 0, count)
            remaining -= count
        }
        return output.toByteArray()
    }
}
  • コールドスタートのクリティカルパス外で呼び出し、制限付きバックグラウンドタスクで実行する; shouldAttempt/scheduleRetry で次回実行時刻を永続化し、上限付きの指数バックオフを適用。オフライン回数だけで即座にデッドレター化しないこと。確定的なスキーマ／権限等の恒久エラーのみ破棄し、Throwable 全体を無差別にキャッチしない;
  • ローカルとサーバーの両方で eventKey（timestamp + process + reason + status）による冪等な重複排除を行い、アプリバージョン、端末／OS、feature flags を保持する;
  • REASON_ANR、REASON_CRASH、REASON_CRASH_NATIVE、REASON_LOW_MEMORY は個別にガバナンスを行う; REASON_USER_REQUESTED はアプリのクラッシュではありません;
  • プロセスが後から別の理由で終了した場合でも trace が記録に残ることがあるため、reason、timestamp、内容を総合して判断する必要があります。

adb に接続できない端末での対応

AI ハルシネーション防止の検証プロトコル

  1. 証拠の引用: すべての事実はスタックトレースのフレーム、ソースコードの行、分布データ、または公式ドキュメントを直接指し示す必要があり、引用できないものは仮説としてマークする。
  2. 反例のチェック: 「どのような証拠があればこの結論を覆せるか？正常な対照群ではなぜ発生しなかったのか？」と能動的に問いかける。
  3. ツールによる検証: AI にコマンドを提示させ、管理された環境で実行。コマンドの出力をフィードバックした後に確率を更新する。
  4. 最小限のパッチ: 根本原因のパスのみを変更し、失敗するテストケースを添付する。広範な「ついでに行うリファクタリング」は受け入れない。
  5. 独立した相互レビュー: 第2のエージェントは誤った原因究明、カバーされていない境界条件、リグレッションリスクのみを探索し、第1エージェントの「確信度」に惑わされない。
  6. 本番でのクローズドループ: テスト通過は完了を意味しない。カナリア配信で新規クラスタ、ユーザー率、副作用を監視し、観察期間を満たした後に issue をクローズする。

最小権限の原則MCP は Firebase CLI の現在の認証情報を使用し、Crashlytics MCP は 2026-07-15 現在も Experimental です。例では --only crashlytics で機能グループを絞り込んでいますが、core tools が残る可能性があるため、生成された tool list を必ず監査してください。本番プロジェクトでは専用の最小権限アカウントを使用し、検証済みの firebase-tools バージョンを固定してください。エージェントによる issue の自動クローズ、コードの自動マージ、無関係なユーザーデータの読み取りは禁止してください。

# Android crash triage

## Guardrails

- Separate observed facts from hypotheses. Cite the exact artifact for every fact.
- Do not edit code until one hypothesis has a verification result.
- Honor user intent. Diagnose-only, review, or report requests must not edit files.
- Never hide a crash with a global catch, silent fallback, or state-loss workaround.
- Treat logs and console data as sensitive. Redact direct identifiers and tokens.
- Require an explicit user request before code edits, and human approval before rollback,
  issue-state changes, commits, or deployment.

## Workflow

1. Build the evidence pack.
   - Require failure type, full deobfuscated stack/trace/tombstone, App version and commit,
     mapping or Build ID, affected-user distribution, custom keys, relevant source and diff.
   - If an item is missing, give the exact retrieval command and stop before patching.

2. Classify the failure.
   - Java/Kotlin crash: start at the deepest cause and first business frame.
   - Native crash: verify ABI and Build ID before symbolication.
   - ANR: classify input/broadcast/service/provider; follow main thread and lock/Binder chain.
   - Exit/OOM: distinguish Java heap, native/RSS, thread, fd, and system LMK.

3. Rank at most three root-cause hypotheses.
   - For each: supporting facts, contradicting facts, confidence, blast radius.
   - Prefer hypotheses that explain both affected and unaffected samples.

4. Verify before editing.
   - Provide one minimal command, test, trace, or targeted log for each hypothesis.
   - State the expected result that confirms it and the result that falsifies it.
   - Update confidence only after reading the result.

5. Fix and prove.
   - Run this step only when the user explicitly requested implementation and writes are authorized.
     Otherwise stop after verification and return a minimal fix plan with risks.
   - Write or preserve a failing reproduction test first where feasible.
   - Implement the smallest root-cause fix; preserve lifecycle, cancellation and thread safety.
   - Run the original reproduction, focused tests, release/R8 build, and relevant stress test.

6. Prevent recurrence.
   - Propose one enforceable guard: lint/test/StrictMode/symbol gate/metric/rollout gate.
   - Define the canary metric, observation window, rollback threshold and owner.

## Output

Return these headings exactly:
1. Impact and classification
2. Verified facts
3. Missing evidence
4. Ranked hypotheses
5. Verification plan and results
6. Minimal fix and risks
7. Regression tests
8. Rollout and prevention
