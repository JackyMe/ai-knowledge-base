왜 배워야 하는가

이런 경험이 있으신가요? Vercel에 배포한 사이드 프로젝트가 갑작스러운 트래픽이나 DDoS 공격으로 과도한 청구서 폭탄을 맞을까 봐 불안하거나, Cloudflare Pages의 대역폭 한계와 지역 제한에 부딪히거나, 심야에 Supabase 커넥션 풀 한도에 걸려 서비스가 멈추는 일…….

SaaS 플랫폼은 매우 편리하지만, 플랫폼 제약이나 가격 장벽에 부딪히는 순간 그 편리함은 족쇄가 됩니다. 그 한계를 벗어나려 할 때 SSH, systemd, 리버스 프록시, DNS 레코드, TLS 핸드셰이크 같은 인프라 용어에 압도당하는 개발자가 많습니다.

이 문서가 다루는 것과 다루지 않는 것다루는 것: 5단계 로드맵 + 서버·네트워크·배포의 필수 핵심 지식 + 5대 장애 30초 처방전. 읽고 나면 중규모 프로젝트 서버를 스스로 안정적으로 운영할 수 있습니다.
다루지 않는 것: 대규모 Kubernetes 클러스터 운영, GPU 분산 추론 인프라, 99.999% 극한의 고가용성 튜닝 등은 다루지 않습니다.

대상 독자

  • Next.js / Node / Python / Go 등으로 풀스택 앱을 개발해 보았으나 배포는 Vercel / Netlify / Cloudflare / Supabase / Railway에 전적으로 의존해 온 분.
  • 도메인을 구매해 본 적은 있지만, DNS 해석과 TLS 인증서 뒷단에서 일어나는 과정을 정확히 알지 못하는 분.
  • 프로덕션 장애가 발생했을 때 로그를 스스로 추적하지 못해 막막했던 경험이 있는 분.
  • SRE나 전문 인프라 엔지니어가 될 생각은 없지만, 내 서비스를 직접 안정적으로 호스팅하고 싶은 1인 개발자 및 풀스택 개발자.

로드맵 R1

R1 · 현재 상태 점검

VPS를 무작정 결제하기 전에, 현재 운영 중인 프로젝트들의 인프라 구성을 정리해 봅니다. 이를 통해 SaaS를 유지할 항목과 자체 호스팅으로 전환할 항목을 명확히 구분할 수 있습니다.

실전: 프로젝트 배포 현황표 작성

운영 중인 앱마다 다음 4개 항목을 정리합니다:

  1. 실행 환경: Vercel / Netlify / Cloudflare Pages / Supabase / VPS / 기타
  2. 월 비용: Free Tier / Pro 요금제 / 예상 월 비용
  3. 현재의 병목: 응답 지연 / 타임아웃 / 예상치 못한 종량 과금 / 리전 제약 등
  4. 자체 호스팅 가치: 정적 프론트엔드는 SaaS 유지가 유리. 장시간 백그라운드 워커, WebSocket 상시 연결, 커스텀 런타임이 필요하다면 자체 운영의 가성비가 높음.
판단 기준프로젝트의 80%가 정적 사이트 + 외부 SaaS DB 구조라면 굳이 마이그레이션할 필요가 없습니다. 상시 실행 데몬, 대용량 파일/이미지 처리, 로컬 LLM 연동, 지역 제약 우회가 필요한 서비스부터 자체 운영을 도입하는 것이 현명합니다.
로드맵 R2

R2 · Linux 기초

1코어 1GB 메모리 수준의 저렴한 VPS(월 3~5달러)를 대여하여 Ubuntu 24.04 LTS를 설정합니다. SSH 키 인증으로 로그인하고 Nginx를 실행하여 브라우저 접속을 확인합니다.

실전 단계

  1. VPS 선택: DigitalOcean, Vultr, AWS Lightsail, Linode 등에서 사용자 위치와 가까운 리전 선택. OS는 문서가 가장 풍부한 Ubuntu 24.04 LTS 권장.
  2. 로컬에서 SSH 키 생성: ssh-keygen -t ed25519 -C "your@email" 실행 후, ~/.ssh/id_ed25519.pub 내용을 VPS 관리자 콘솔의 SSH Key 항목에 등록.
  3. VPS 접속: 터미널에서 ssh root@YOUR_VPS_IP로 접속. 첫 접속 시 핑거프린트 확인에 "yes" 입력.
  4. Nginx 설치: apt update && apt install -y nginx 실행 후, systemctl status nginx로 active (running) 확인.
  5. 브라우저 확인: http://YOUR_VPS_IP에 접속하여 Nginx 환영 페이지가 보이면 R2 완료.
로드맵 R3

R3 · 네트워크 핵심

IP 주소 직접 접속에서 벗어나, 독립 도메인 + HTTPS(SSL 인증서)를 적용한 안전한 환경으로 업그레이드합니다. DNS, Certbot, Nginx 리버스 프록시 연동을 완벽히 구축합니다.

실전 단계

  1. 도메인 구매: Cloudflare Registrar, Namecheap, 가비아 등에서 도메인 구매.
  2. DNS 레코드 설정: 관리 패널에서 A 레코드를 생성하여 도메인을 VPS 공인 IP에 연결. dig yourdomain.dev로 반영 확인.
  3. SSL 인증서 발급: apt install -y certbot python3-certbot-nginx 실행 후 certbot --nginx -d yourdomain.dev로 무료 Let's Encrypt 인증서 자동 발급 및 설정.
  4. 리버스 프록시 설정: Nginx를 통해 443 포트(HTTPS)로 들어온 트래픽을 로컬 Node/Python 앱(예: 3000 포트)으로 전달.
  5. 브라우저 접속: https://yourdomain.dev에서 자물쇠 마크와 함께 내 서비스가 정상 구동되면 R3 완료.
로드맵 R4

R4 · 배포 파이프라인

수동 파일 전송이나 SSH 직접 접속 방식에서 벗어나, git push만으로 서버에 자동 배포되는 CI/CD 파이프라인을 구축합니다.

실전 단계

  1. systemd 서비스 정의: /etc/systemd/system/myapp.service를 생성하여 SSH 세션 종료 후에도 앱이 백그라운드에서 상시 구동되고 크래시 시 자동 재시작되도록 설정.
  2. GitHub Actions 워크플로 작성: .github/workflows/deploy.yml을 설정하여 main 브랜치 push 시 VPS로 자동 SSH 접속, 코드 pull, 빌드 및 서비스 재시작 실행.
  3. 시크릿 안전 관리: SSH 개인키를 GitHub Repository Secrets에 등록. 프로덕션 환경변수는 서버 내부 .env 파일로 격리.
  4. 배포 테스트: 코드 수정 후 push하여 GitHub Actions가 성공하고 30초 내에 프로덕션에 반영되는지 확인.
로드맵 R5

R5 · 장애 분석 및 트러블슈팅

프로덕션 운영에서 가장 중요한 역량은 '장애가 전혀 안 나는 것'이 아니라 '장애 발생 시 30초 이내에 원인을 파악하고 대응하는 것'입니다.

실전: 5대 대표 장애 재현 및 복구 실습

  1. 502 Bad Gateway: systemctl stop myapp으로 앱을 중지시키고 Nginx의 에러 로그를 확인한 뒤 재시작으로 복구.
  2. SSH 접속 차단: 포트 설정 오류 및 방화벽 차단 시나리오를 이해하고 콘솔(VNC)을 통한 복구 절차 숙지.
  3. 디스크 용량 고갈: df -h로 확인하고 과도한 로그 파일 및 미사용 Docker 이미지를 정리하는 방법 실습.
  4. OOM (메모리 부족): 메모리 누수 발생 시 OOM Killer 로그를 dmesg -T로 확인하고 스왑(Swap) 메모리 추가.
  5. SSL 인증서 갱신 오류: certbot renew --dry-run으로 자동 갱신 시뮬레이션 및 문제 해결.
모듈 1 · Linux

1.1 서버란 무엇인가

'서버'라는 단어에 막연한 두려움을 가질 필요가 없습니다. 서버의 본질은 24시간 365일 전원이 켜진 채 네트워크에 연결되어 있는 컴퓨터에 불과합니다. 사용하는 PC와 하드웨어 아키텍처는 거의 동일하며, 모니터나 키보드 없이 데이터센터 랙에 장착되어 SSH를 통해 원격으로 제어한다는 점만 다릅니다.

모듈 1 · Linux

1.2 3대 추상화 개념: 파일 시스템, 프로세스, 포트

Linux 서버를 '아파트'에 비유할 수 있습니다. 각 호실의 입주자가 프로세스, 호실 번호가 포트, 출입 카드와 계약서가 권한에 해당합니다. 일상적인 서버 운영의 80%는 어떤 프로세스가 돌고 있는지, 어떤 포트를 열고 있는지, 어떤 권한으로 실행되는지를 점검하는 작업입니다.

파일 시스템: 모든 것은 파일이다 (Everything is a File)

Linux의 근본 철학은 '모든 것은 파일이다'라는 점입니다. 디스크 저장소뿐만 아니라 하드웨어 장치, 네트워크 소켓, 프로세스 정보까지 모두 /(루트 디렉터리) 하위의 파일 형태로 표현됩니다.

ls /                  # 루트 디렉터리 확인
ls /etc/nginx/         # Nginx 설정 파일 목록
ls /var/log/           # 시스템 및 서비스 로그 파일
cat /proc/cpuinfo      # CPU 정보 (메모리 상의 가상 파일)

프로세스: 실행 중인 프로그램

node server.js를 실행하면 고유한 PID(프로세스 ID)를 가진 프로세스가 생성됩니다. 필수 관리 명령어:

ps aux | grep node     # Node 프로세스 상태 확인
top                    # 실시간 CPU/메모리 사용량 확인 (q로 종료)
htop                   # 시각화 리소스 모니터 (apt install htop)
kill -9 1234           # PID 1234 프로세스 강제 종료
systemctl status myapp # systemd 관리 서비스 상태 확인

포트: 통신의 호실 번호 (0~65535)

모듈 1 · Linux

1.3 SSH는 단순 로그인이 아니다

SSH(Secure Shell)는 암호화된 안전한 통신 터널을 제공하는 프로토콜입니다. 쉘 접속뿐 아니라 포트 포워딩, 안전한 파일 전송(SFTP/rsync), Git 코드 동기화의 핵심 기반입니다.

비밀번호 로그인 비활성화 및 공개키 인증 필수화

비밀번호 로그인은 무차별 대입 공격(Brute Force)에 취약합니다. 비대칭 공개키 암호화(Ed25519)를 사용하면 개인키가 없는 공격자의 접속 시도를 원천 차단할 수 있습니다.

# /etc/ssh/sshd_config 권장 보안 설정
PasswordAuthentication no
PermitRootLogin prohibit-password
PubkeyAuthentication yes

~/.ssh/config로 간편 접속 설정

로컬 PC의 ~/.ssh/config에 서버 정보를 등록하면 ssh myserver 한 줄로 편리하게 접속할 수 있습니다:

Host myserver
    HostName 203.0.113.195
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519
    Port 22

1.5 권한과 사용자 관리

모든 권한을 가진 root로 일상 작업을 수행하는 것은 위험합니다. 일반 사용자 계정을 생성하고 필요한 경우에만 sudo로 권한을 상승시키는 것이 정석입니다.

adduser deployer                 # 신규 사용자 생성
usermod -aG sudo deployer        # sudo 관리자 그룹 추가
chmod 600 ~/.ssh/authorized_keys # 인증키 파일 권한을 소유자 전용으로 제한
chown -R deployer:deployer /var/www # 디렉터리 소유권 변경

2.1 HTTP → TCP → IP 계층 구조

웹 통신은 캡슐화된 계층 구조로 이루어집니다:

  • 애플리케이션 계층 (HTTP/HTTPS): 클라이언트와 서버가 주고받는 요청(GET /api/users)과 응답 데이터.
  • 전송 계층 (TCP): 패킷의 순서 보장, 패킷 유실 시 재전송, 연결 수립(3-Way Handshake).
  • 네트워크 계층 (IP): 출발지와 목적지 IP 주소를 기반으로 최적의 경로를 찾아 패킷 라우팅.
모듈 2a · 네트워크 개념

2.2 DNS (도메인 네임 시스템)

사람이 기억하기 쉬운 도메인 이름(예: example.com)을 컴퓨터 통신용 IP 주소(예: 203.0.113.195)로 변환해 주는 분산형 이름 풀이 시스템입니다.

레코드 종류용도설정 예시
A도메인을 IPv4 주소에 매핑@ -> 203.0.113.195
AAAA도메인을 IPv6 주소에 매핑@ -> 2001:db8::1
CNAME다른 도메인으로의 별칭(Alias)www -> example.com
TXT도메인 소유권 검증 및 SPF/DKIM 이메일 인증v=spf1 include:...

2.3 HTTPS / TLS 암호화와 인증서 관리

HTTPS는 HTTP 통신을 TLS(Transport Layer Security)로 암호화하여 패킷 감청, 데이터 위변조, 피싱 사이트를 방지합니다. 현대 웹에서는 필수 표준입니다.

Let's Encrypt와 Certbot비영리 인증기관 Let's Encrypt를 통해 신뢰할 수 있는 SSL/TLS 인증서를 무료로 발급받을 수 있습니다. Certbot 도구를 사용하면 인증서 발급, Nginx 설정 자동 수정, 90일 주기 자동 갱신까지 원클릭으로 처리됩니다.
모듈 2a · 네트워크 개념

2.4 리버스 프록시 (Reverse Proxy)의 역할

인터넷 최전선에서 사용자 요청을 받아 뒷단의 적절한 내부 백엔드 애플리케이션(Node.js, Python, Go 등)으로 중계해 주는 프록시 서버입니다 (대표 도구: Nginx, Caddy).

  • SSL 종단 (SSL Termination): 리소스 소모가 큰 암호화/복호화 처리를 프록시가 전담.
  • 라우팅 및 로드 밸런싱: /api는 백엔드로, 정적 파일은 디스크에서 직접 서빙.
  • 보안 장벽: 내부 백엔드의 실제 포트를 외부에 직접 노출하지 않음.
모듈 2a · 네트워크 개념

2.5 방화벽과 접근 제어

불필요한 포트에 대한 외부 접근을 차단하고 서비스에 필수적인 포트(22, 80, 443)만 허용합니다. Ubuntu에서는 ufw(Uncomplicated Firewall)가 가장 직관적입니다.

ufw default deny incoming  # 외부 인입 트래픽 기본 차단
ufw default allow outgoing  # 아웃바운드 트래픽 허용
ufw allow 22/tcp            # SSH 허용 (누락 시 원격 접속 불가 주의)
ufw allow 80/tcp            # HTTP 허용
ufw allow 443/tcp           # HTTPS 허용
ufw enable                  # 방화벽 활성화

2.6 공격 표면 (Attack Surface) 최소화

서버를 공인 인터넷에 연결하는 순간부터 전 세계 봇들의 스캔이 시작됩니다. 공격당할 수 있는 접점을 최소화해야 합니다:

❌ 위험한 설계데이터베이스(MySQL 3306, Redis 6379) 포트를 0.0.0.0으로 외부에 전체 공개하고 단순 비밀번호에만 의존하는 구조.
✅ 안전한 설계DB는 127.0.0.1(로컬 루프백)에만 바인딩하고, 외부 접속은 SSH 터널링이나 비공개 사설망(VPN)을 통해서만 허용.

2.8 127.0.0.1 vs 0.0.0.0 바인딩 차이

앱 서버 기동 시 설정하는 바인딩 주소는 보안에 직결됩니다:

  • 127.0.0.1 (localhost): 동일 머신 내부에서만 접근 가능. 외부 인터넷 접속이 물리적으로 차단됨.
  • 0.0.0.0: 서버의 모든 네트워크 인터페이스(공인 IP 포함)에서 들어오는 요청을 수신.

3.1 프로덕션 배포 7단계 파이프라인

  1. 코드 체크아웃: 서버에서 git pull 실행 또는 CI 환경에서 최신 코드 수령.

  3. 정적 자산 빌드: npm run build를 통한 번들링 최적화.
  4. DB 마이그레이션: prisma migrate deploy 등으로 스키마 반영.
  5. 헬스체크 검증: 로컬 포트에서 /api/health가 200을 반환하는지 확인.
  6. 프로세스 리로드: systemctl reload myapp 또는 무중단 재시작.
  7. 결과 알림: 배포 성공/실패 여부를 Slack 또는 Discord로 통보.

3.2 systemd 프로세스 데몬화 및 자동 복구

터미널을 닫아도 프로세스가 상시 구동되고, 서버 재부팅 시 또는 예기치 않은 크래시 발생 시 자동 복구되도록 systemd 서비스를 등록합니다.

# /etc/systemd/system/myapp.service
[Unit]
Description=My Fullstack Web Application
After=network.target

[Service]
Type=simple
User=deployer
WorkingDirectory=/var/www/myapp
EnvironmentFile=/var/www/myapp/.env
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5s

[Install]
WantedBy=multi-user.target
systemctl daemon-reload
systemctl enable --now myapp   # 서비스 자동 시작 등록 및 즉시 기동
systemctl status myapp         # 상태 확인
journalctl -u myapp -f         # 실시간 로그 스트리밍 확인

3.3 Nginx 리버스 프록시 프로덕션 템플릿

# /etc/nginx/sites-available/yourdomain.conf
server {
    listen 80;
    server_name yourdomain.dev;
    return 301 https://$host$request_uri; # HTTPS 강제 리다이렉트
}

server {
    listen 443 ssl http2;
    server_name yourdomain.dev;

    ssl_certificate /etc/letsencrypt/live/yourdomain.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.dev/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
