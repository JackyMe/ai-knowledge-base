トラブルマップ：すべての環境問題は4つの根本原因に集約される

Claude Code と Codex の「環境問題」は多種多様に見えますが、分解すると4つの根本原因しかありません。原因を正確に把握すれば、以降の全セクションで迷わず特定・修復できます。

根本原因典型的な症状なぜ発生するのか
① 複数のインストール経路の競合バージョンが勝手に新旧入れ替わる、更新しても反映されない、コマンドの挙動がおかしいネイティブインストーラー、npm グローバル、Homebrew/WinGet、IDE 拡張機能の内蔵バイナリ——4つの経路が同時に存在し、PATH の優先順位によって実行バイナリが決まるため
② 認証情報の複数ソースによる競合「ログインしているのに Invalid API key になる」、有料会員なのに API 課金される、organization disabled環境変数に設定された API キーは、ブラウザでログインしたサブスクリプション認証情報よりも優先順位が高いため——他人が残した export ANTHROPIC_API_KEY 1行でセッション全体がハイジャックされます
③ 設定の階層的オーバーライド「変更しても反映されない」、社用PCで一部の設定が変更できないEnterprise管理ポリシー > コマンドライン引数 > プロジェクトローカル > プロジェクト共有 > ユーザー設定——編集した設定が上位レイヤーによって上書きされているため
④ ネットワークおよびシステム環境ログインが停止する、TLS エラー、OAuth コールバック失敗、ダウンロード 403企業のプロキシ / プライベートCA / ファイアウォールがコールバックポートを遮断；システム時計のズレによってトークン検証が失敗する場合もあります
重要マインドセット環境問題が発生した際、いきなり再インストールしてはいけません。まず次章の5層診断法でどのレイヤーの問題かを特定してください——「難解な不具合」の90%は②（認証情報の競合）であり、環境変数を1つクリアするだけで解決します。再インストールすると逆に①（複数インストールの競合）を引き起こす原因になります。

方法論 01

5層診断法 ＋ ワンクリック診断スクリプト

体系的な診断アプローチにおける唯一の規律：下位レイヤーから上位レイヤーへ順に確認し、1つの層を確認し終えてから次の層へ進むこと。各レイヤーには明確な確認コマンドと「正常時の状態」が定義されています。

L1
バイナリ層 —— 実際に実行されているのはどのプログラムか？

which -a claude / which -a codex で PATH 内の同名コマンドをすべて一覧表示；claude --version でバージョンを確認。正常：パスが1行のみ。異常：複数行存在 → 複数インストールの競合。まず不要なものを削除する。

L2
環境変数層 —— 動作をハイジャックしている変数はないか？

env | cut -d= -f1 | grep -iE 'anthropic|claude|codex|openai|proxy' を実行。正常：完全に空白（純粋なサブスクリプションユーザー）。異常：意図しない ANTHROPIC_API_KEY / ANTHROPIC_BASE_URL / *_PROXY が存在する場合は出所を確認する。

L3
認証情報（クレデンシャル）層 —— 現在どのユーザーのどの認証情報が使われているか？

Claude Code セッション内で /status を実行し Login method を確認（API key 行がある場合は環境変数が優先適用中）；Codex は codex login status を使用。アカウントのメールアドレスや組織が自分のものであるか確認する。

L4
設定層 —— どの階層の設定が実際に適用されているか？

Claude Code：claude doctor で診断、/config で適用値のソースを確認；Codex：/debug-config で設定の階層レイヤーを出力。変更が反映されない＝上位層でオーバーライドされているか、セッションの再起動が必要。

L5
ネットワーク層 —— リクエストは正常に送受信できているか？

curl -sI https://downloads.claude.ai/claude-code-releases/latest で接続性をテスト；社内ネットワークではプロキシ変数とプライベートCAを確認；OAuth が停止する場合はコールバックポート（Codex は 1455）を確認する。

なぜこの順序なのか下位レイヤーが上位レイヤーを決定するためです。プログラム自体が間違っている場合（L1）、認証情報を見ても意味がありません。環境変数（L2）は認証情報の選択（L3）を歪めます。認証情報が正しいことを確認して初めて設定（L4）が意味を持ちます。これら4層がすべて正常でも通信できない場合に初めてネットワーク（L5）を疑います。逆順で調査すると無駄な労力を費やすことになります。

ワンクリック診断スクリプト（読み取り専用・コピーしてすぐ使える）

5つのレイヤーのチェックを1つのスクリプトにまとめました。読み取り専用で変更は一切行わないため、どのようなマシンでも安心して実行できます。見知らぬPCを操作する前にまず実行し、30秒で全状態を把握しましょう：

#!/bin/bash
# ai-env-check.sh —— Claude Code / Codex 環境ワンクリック診断（読み取り専用）
# 使い方: bash ai-env-check.sh   (macOS / Linux / WSL)
echo "═══ L1 バイナリ層 ═══"
for c in claude codex; do
  echo "--- $c ---"
  if command -v "$c" >/dev/null 2>&1; then
    which -a "$c"; "$c" --version 2>/dev/null | head -1
  else echo "(未インストールまたは PATH にありません)"; fi
done
[ -d ~/.claude/local ] && echo "⚠️  レガシー npm インストールを検出: ~/.claude/local (削除を推奨)"
npm -g ls @anthropic-ai/claude-code 2>/dev/null | grep -q claude-code && echo "⚠️  npm グローバルインストールを検出 (ネイティブインストールと競合する可能性があります)"

echo; echo "═══ L2 環境変数層 ═══"
env | grep -iE 'anthropic|claude|codex|openai|https?_proxy|no_proxy|node_extra_ca'   || echo "(クリーン: 関連する環境変数はありません)"
echo "--- shell 設定ファイル内の残存定義 (他人が残した export を重点確認) ---"
grep -nE 'ANTHROPIC|CLAUDE_|CODEX|OPENAI' ~/.zshrc ~/.zprofile ~/.bashrc ~/.bash_profile ~/.profile 2>/dev/null   || echo "(クリーン: rc ファイルに関連設定はありません)"

echo; echo "═══ L3 認証情報層 ═══"
codex login status 2>/dev/null || echo "codex: 未ログインまたは未インストール"
[ -f ~/.codex/auth.json ] && echo "codex: auth.json が存在します (平文クレデンシャル)"
echo "claude: セッションに入り /status を実行して Login method とアカウント所属を確認してください"

echo; echo "═══ L4 設定層 (ファイル一覧) ═══"
ls -la ~/.claude/settings.json ~/.claude.json ~/.codex/config.toml 2>/dev/null
ls -la .claude/settings.json .claude/settings.local.json .mcp.json 2>/dev/null   || echo "(カレントディレクトリにプロジェクト設定はありません)"

echo; echo "═══ L5 ネットワーク層 ═══"
curl -sI --max-time 8 https://downloads.claude.ai/claude-code-releases/latest | head -1
curl -sI --max-time 8 https://auth.openai.com | head -1
echo "診断完了 ✅  各層を照合してください: 複数インストール? 不審な変数? アカウント所属? 設定ソース? ネットワーク導通?"

Claude Code 02

Claude Code · 認証メカニズムと優先順位

Claude Code のログイン問題の8割は、見落とされがちな1つの事実に起因します：7種類もの認証情報ソースを同時にサポートしており、厳格な優先順位が存在することです。サブスクリプションを使用しているつもりでも、存在すら知らなかった環境変数によって動作している場合があります。

認証優先順位（公式完全順序・高から低へ）

  1. クラウドプロバイダーチャネル：CLAUDE_CODE_USE_BEDROCK / CLAUDE_CODE_USE_VERTEX / CLAUDE_CODE_USE_FOUNDRY が設定されている場合、AWS/GCP/Azure の認証情報を使用（注：ログイン済みエンタープライズ Gateway セッションはこれよりさらに上位）
  2. ANTHROPIC_AUTH_TOKEN：Bearer ヘッダーとして送信——LLM ゲートウェイ / リレープロキシ構成で使用
  3. ANTHROPIC_API_KEY：X-Api-Key ヘッダーとして送信。対話モードの初回に「このキーを使用するか」の確認ダイアログが表示されますが、非対話モード（-p）では存在すれば確認なしで直接使用されます
  4. apiKeyHelper スクリプト：settings.json で設定された動的キー取得スクリプト（デフォルト5分ごと、または 401 受信時に自動更新）
  5. CLAUDE_CODE_OAUTH_TOKEN：claude setup-token で生成された1年有効なトークン（CI 環境用）
  6. サブスクリプション OAuth：/login によるブラウザログイン認証情報——最下位に位置。そのため、環境変数が1つでも存在するとサブスクリプションが「ハイジャック」されます
有料会員必読：なぜ二重請求されるのか？Pro/Max 会員であるにもかかわらず、マシン上に ANTHROPIC_API_KEY が残っている場合（以前の個人実験、前任者の設定、チュートリアルのコピペなど）、サブスクリプションより優先して適用されるため、すべての対話がAPI従量課金されるか、そのキーの所属組織が無効化されていて This organization has been disabled エラーが発生します。解決策：unset ANTHROPIC_API_KEY ＋ shell 設定ファイルから export 行を削除 ＋ /status で Login method がサブスクリプションに戻っていることを確認。

優先順位は上記テーブルの上から下の順です——Enterprise管理が常に最優先され、CLI引数、プロジェクトローカル、プロジェクト共有、ユーザー設定の順で適用されます。設定が反映されない原因の9割は上位層でのオーバーライドです。/status の「Setting sources」行で実際に読み込まれたソースを確認できます。claude doctor で無効なフィールドも検出されます。

二、最小実行可能構成

Claude Code は settings.json が存在しなくても正常に動作します——ファイルがなくてもデフォルト値でログイン可能です。チーム用のスターターテンプレートとして明示的に宣言する場合、以下のみで十分です：

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json"
}

schema 宣言は動作には影響しませんが、VS Code や Cursor で編集する際の自動補完と検証を有効にします。実用的かつ極めてシンプルなスターター構成例：

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}

  • 保存先の選択：config.toml 内の cli_auth_credentials_store = "file" | "keyring" | "auto"。file＝平文 ~/.codex/auth.json；keyring＝システムキーチェーン；auto＝キーチェーンを優先。
  • 自動更新：トークンが期限切れ（約8日間未使用で stale）になった場合、Codex の実行中に自動的に更新され、auth.json に書き戻されます——CI の永続化はこの仕組みの上に成り立っています（第10章参照）。
  • CLI と IDE 拡張機能で同一の認証情報を共有：一方を logout すると、もう一方もログアウトされます——「IDE で突然再ログインを求められた」原因の多くはターミナル側でのログアウトです。
  • マルチアカウント：公式のファーストクラスサポートは現時点で未提供（上流 issue #4432 にて議論中）；CODEX_HOME によるディレクトリ分離で実現可能（手順は第08章参照）。コミュニティ製管理ツール codex-multi-auth も利用可能。
  • 企業ポリシー管理：forced_login_method / forced_chatgpt_workspace_id によりログイン方式やワークスペースを固定可能。不一致時は強制ログアウトされます——社用PCで「ログイン方式が変更できない」のはポリシーによる正常な制限です。

認証情報ソースの優先順位：オーバーライド関係

この順序は公式ドキュメントには完全公開されていませんlearn.chatgpt.com/docs では3つのログイン方式と model_providers.<id>.env_key が個別に紹介されているのみで、Claude Code のような完全な優先順位表はありません。以下の順序は Codex オープンソースリポジトリ（openai/codex）のソースコード本体から検証したものです。

Claude Code の単一リニアリストとは異なり、Codex の認証解決は2段階で行われます：まずどの model provider が使われているかを確認し、次にその provider におけるキー取得方法を解決します。

  1. カスタム model_provider の優先短絡：トップレベルの model_provider がカスタム [model_providers.<id>] を指しており、そのテーブルに env_key / experimental_bearer_token / auth.command のいずれかが設定されている場合——この認証情報がその provider のリクエストに直接使用され、以降の ChatGPT/API key の判定は完全にスキップされます（ログイン状態やサブスクリプション有効性は無関係；ソース：model-provider/src/auth.rs · bearer_auth_for_provider()）。
  2. 内蔵 openai provider（デフォルト：通常 ChatGPT / API key でログインして利用する場合）では、以下の順序で解決されます（ソース：login/src/auth/manager.rs · load_auth()）：
順位ソース説明
1CODEX_API_KEY 環境変数codex exec（非対話実行）でのみ有効。対話型 codex TUI ではこの変数は一切チェックされません——ソースコード上のフラグ enable_codex_api_key_env は exec モードで true、TUI で false となっています
2ホストアプリによって注入された一時 ChatGPT セッションIDE 拡張機能等のホストプログラムがブリッジするメモリ内クレデンシャル。内部メカニズムであり、一般的なユーザーが意識することは稀です
3CODEX_ACCESS_TOKEN 環境変数エンタープライズ access token / Agent Identity。CI での対話なしログインに多用（第10章参照）
4永続化された auth.json（またはキーチェーン）codex login (ChatGPT OAuth) / codex login --with-api-key / --with-access-token / --device-auth によって保存された認証情報。日常ユースの99%がここに該当
よくある誤解：OPENAI_API_KEY は Claude のようにセッションをハイジャックしない多くの人が ANTHROPIC_API_KEY の挙動からの類推で、OPENAI_API_KEY 環境変数を設定すると ChatGPT ログインが上書きされると考えがちですが、ソースコード上にそのようなロジックは存在しません。OPENAI_API_KEY が読み込まれるのは唯一：対話型 codex login で「API key の入力」ステップに進んだ際に、テキストボックスに初期値として自動補完される用途のみです（ソースコード）。リクエスト送信時に暗黙的に読み込まれることはなく、上記の優先順位表にも登場しません。内蔵プロバイダーのリクエストをハイジャックできるのは、表内の①③④および [model_providers.<id>].env_key に指定された変数のみです。

forced_login_method / forced_chatgpt_workspace_id は「優先順位」としてのソースではなく、起動時のゲートキーパー（制約検証）です：Codex は現在有効な認証情報をロードした後にポリシーを照合し、モードやワークスペースが一致しない場合は即座にログアウトして理由を出力します。例えばポリシーが API key を要求しているのに ChatGPT ログインになっている場合は API key login is required, but ChatGPT is currently being used. Logging out. と出力され、ワークスペース不一致時は Login is restricted to workspace(s) <許可ワークスペース>, but current credentials belong to <実際ワークスペース>. Logging out. と出力されます（ソース：manager.rs · enforce_login_restrictions()）。

auth.json の構造と失効判定

オープンソースリポジトリの構造体定義（login/src/auth/storage.rs · AuthDotJson）に基づくフィールド構造です（機密値はダミーに置換）：

// ChatGPT OAuth ログイン時の auth.json（簡略化・マスク済み）
{
  "auth_mode": "chatgpt",
  "OPENAI_API_KEY": null,
  "tokens": {
    "id_token": "<JWT: email / chatgpt_plan_type / chatgpt_account_id 等を含む>",
    "access_token": "<JWT: 各リクエストで送信>",
    "refresh_token": "<更新用: 長期有効>",
    "account_id": "..."
  },
  "last_refresh": "2026-08-17T08:00:00Z"
}

// API key ログイン時の auth.json: tokens / last_refresh は null
{ "auth_mode": "apikey", "OPENAI_API_KEY": "sk-…", "tokens": null, "last_refresh": null }

stale（期限切れ）の判定方法：トークン自動更新が行われるのは ChatGPT ログイン（tokens が非 null）のみです。判定は last_refresh フィールドに基づき、ソースコード上の閾値定数 TOKEN_REFRESH_INTERVAL = 8（日、ソースコード）と一致します。確認コマンド：python3 -c "import json,datetime;d=json.load(open('~/.codex/auth.json'));print(d.get('last_refresh'))"。前回の更新から8日以上経過している場合、次回実行時に自動更新されます。API key ログインではこのフィールドは常に null です。

auth.json ＝ あなたのアカウントそのもの平文のトークンであるため、パスワードと同等に扱ってください：commit しない、チャットに貼らない、スクリーンショットに含めない。別マシンへの移行はデバイスコード認証を推奨します。コピーする場合は安全な経路のみを使用し、用済み後は削除してください。

シナリオ C · SSH ／ コンテナ ／ ヘッドレス機 ／ CI

ブラウザが存在しない環境では、ログインのアプローチが異なります。2つのツールの公式推奨アプローチは異なるため、混同しないようにしてください。

Claude Code：3つのアプローチ

  1. SSH / WSL2 / コンテナでの対話利用：通常通り claude を実行し、ターミナルに表示された OAuth URL をローカルマシンのブラウザにコピーしてログインを完了。ブラウザに表示された code をターミナルに貼り付けます（貼り付けが動作しない環境では claude auth login を使用して stdin から読み込ませる）。
  2. CI / スクリプト（サブスクリプション利用枠）：ローカル環境で claude setup-token を実行して1年間有効な OAuth トークンを生成し、CI Secret に保存。実行環境の環境変数 CLAUDE_CODE_OAUTH_TOKEN に設定します。注意：--bare モードではこの変数は読み込まれないため、bare 環境では ANTHROPIC_API_KEY または apiKeyHelper を使用してください。
  3. CI（API 従量課金）：環境変数 ANTHROPIC_API_KEY を直接設定——最もシンプルですが、従量課金となります。

Codex：公式推奨の3大アプローチ（優先度順）

  1. デバイスコード認証（第一推奨）：codex login --device-auth を実行し、ローカルの任意のブラウザで使い捨てワンタイムコードを入力。ワークスペース管理者が事前にデバイスコード認証権限を有効化している必要があります。
  2. auth.json のコピー（公式フォールバック）：ブラウザのあるマシンでログイン後、生成された ~/.codex/auth.json を対象マシンへ安全にコピー（scp / docker cp）。ローカルマシンの保存先がキーチェーンの場合は、あらかじめ cli_auth_credentials_store を file に設定してログインし直す必要があります。
  3. SSH ポートフォワーディング：ssh -L 1455:localhost:1455 user@remote で接続した上でリモート側で codex login を実行し、ローカルブラウザで標準の OAuth コールバックを完了させます。

Codex CI での長期認証（公式 auth.json 更新サイクル）

ChatGPT サブスクリプション利用枠で CI を実行する公式推奨パターン——Codex 実行時にトークンが自動更新され auth.json に書き戻される仕組みを利用します：

  1. 信頼できるマシン上で codex login (file ストレージ) を実行し、生成された auth.json を CI の Secret 管理に登録；
  2. 各ジョブ実行時：auth.json を復元 → Codex を実行（トークンは約8日間未使用で stale になりますが、実行中に自動更新されます） → 更新された auth.json を CI Secret に書き戻す；
  3. 禁止事項：複数の並行ジョブで同一の auth.json を共有しないこと；初期の古いファイルを毎回上書きしないこと；更新チェーンが途切れた場合は信頼できるマシンで再度ログインして再シードすること。セルフホスト runner の場合は永続ボリュームに CODEX_HOME を割り当てる方がシンプルです。
コンテナ ／ DevContainer でのログイン永続化ホームディレクトリをボリュームマウントすることで、コンテナを再構築しても再ログインが不要になります：Claude Code は CLAUDE_CONFIG_DIR が指すボリューム（Linux の認証情報は配下の .credentials.json に保存）；Codex は CODEX_HOME ボリュームをマウント。重要原則：認証情報はボリューム内にのみ保持し、イメージレイヤーに絶対に焼き込まないこと。

実戦ケーススタディ：症状から根本原因への徹底追跡

高頻度で発生する4つの実戦シナリオを通じて、5層診断法の実際の適用フローを解説します。これら4つの構造を理解すれば、大半の「原因不明のトラブル」を自力で解決できるようになります——特にエラーメッセージのテキストと真の根本原因がいかに乖離しているかに注目してください。

ケース1 · 「Max 会員なのに組織が無効化されていると表示される」

現場の状況同僚から引き継いだ PC に Claude Code をインストールし、有料サブスクリプションアカウントでログイン成功したものの、プロンプトを入力した瞬間に API Error: 400 "This organization has been disabled" が発生。再インストールを2回試みたが全く改善しない。
診断プロセスL1 正常（単一インストール、最新バージョン）；L2 で原因特定——env | cut -d= -f1 | grep -i anthropic を実行したところ ANTHROPIC_API_KEY=sk-ant-… が検出された。調査の結果 ~/.zshrc 内に記述されており、前任者が残したもので、そのキーの Console 組織はすでに解約済みだった。
修正手順変数を unset ＋ rc ファイルから export 行を削除 → ターミナルを再起動 → /status で Login method がサブスクリプションに戻ったことを確認。所要時間3分、再インストールは一切不要だった。
得られた教訓エラーメッセージは「組織」と言い、ユーザーは「サブスクリプション」を疑い、真の原因は「環境変数」にあった——エラーメッセージは結果を述べているだけであり、根本原因そのものではありません。これが L2 の問題に対して再インストール（L1 の操作）が永久に効かない理由です。

ケース2 · 「VS Code 拡張機能だけ Invalid API key になり、ターミナルは正常に動く」

現場の状況ターミナルでの claude は完全に正常動作しているが、VS Code 拡張機能側では Invalid API key · Please run /login が繰り返しポップアップし、ログイン成功後も画面が真っ暗なままになる（anthropics/claude-code#12204 に記録された典型例）。
診断プロセスL3 認証情報層で発生しているが、根本原因は L2：マシン上に3つの認証情報ソースが同時に存在していた（OAuth ログイン、手動設定された API key、shell 内の環境変数）。ターミナルが rc ファイルから読み込んだ環境と、VS Code が GUI 起動時に継承した環境が異なっており、両者が別々の認証情報をロードし、一方が有効でもう一方が無効となっていた。
修正手順認証ソースを1つに集約：すべての ANTHROPIC_* 変数と手動キーをクリア → CLI と拡張機能の双方でクリーンに再ログイン → 両側の /status で同一のサブスクリプションアカウントが表示されることを確認。
得られた教訓「ターミナルは正常で IDE だけ異常」という現象は、ほぼ確実に2つのプロセスから見える環境変数の不一致です。複数の認証情報が混在していると、どのプロセスがどれを掴むか予測できません——認証ソースは必ず1つに絞りましょう。

ケース3 · 「翌朝PCを開くと、すべての並行セッションが一斉に再ログインを要求してくる」

現場の状況前夜に3つの並行 Claude Code セッションを開いたままMacBookの蓋を閉じて就寝。翌朝スリープから復帰すると3つのセッションが同時にログイン画面を表示し、1つでログインし直すと他のセッションが切断される現象が連続した。
診断プロセスL2/L3 はクリーンであり、直感に反して L1 バージョン層 に原因があった：公式 changelog を確認したところ、v2.1.211 以前に既知のバグが存在した——スリープ復帰時に複数セッションが同一トークンで同時に更新をかけ、互いの認証を無効化し合っていた。
修正手順v2.1.211 以上にアップデート（更新処理が単一プロセスによる協調制御に変更）、1回再ログインした後は一度も再発しなくなった。
得られた教訓全体的かつ不可解な時間帯に起きる現象は、自分の設定を疑う前にバージョンと changelog を確認すること。公式がすでに修正したバグは、ローカル環境をどれだけ調査しても原因究明できません。

ケース4 · 「Codex が CI で1週間安定動作していたのに、突然すべてのパイプラインで 401 エラーが発生」

現場の状況ChatGPT サブスクリプション利用枠で CI を運用：ローカルの auth.json を CI Secret に登録し、ジョブ実行ごとに復元して実行。1週間後に全パイプラインが一斉に 401 を出し始め、ローカルから再エクスポートすると数日間持ち直す、というサイクルを繰り返していた。
診断プロセスL3 認証情報層の問題：Codex のトークンは約8日間未使用で stale になります。実行中に自動更新されて auth.json に書き戻されていたにもかかわらず、CI パイプラインが毎回 Secret にある「初期の古いファイル」で上書き復元していたため、自動更新の成果が破棄され、更新チェーンが途切れて失効していた。
修正手順公式 CI パターンに則りクローズドループを構築：復元 → 実行 → 更新された auth.json を Secret に書き戻す；並行ジョブ間で同一の認証情報を共有しないよう分離。セルフホスト runner では永続 CODEX_HOME を割り当てて完全自動化。
得られた教訓認証情報は静的な設定ファイルではなく、生きている（状態を持つ）ものです。「N日おきに定期的に壊れる」問題は、期限切れになるリソースの更新ライフサイクルが途切れていないかを疑ってください。

事例の根拠：公式 troubleshoot-install / authentication ドキュメント、anthropics/claude-code#12204、Codex CI/CD auth 公式ガイド（2026-07 照合済み）。マシンや人物の状況はわかりやすく再構成していますが、調査経路と根本原因はすべて実際の動作メカニズムに基づいています。

復元できる調査とリセット

エラー、版、有効設定、秘匿済みログを保存します。認証が原因と分かった場合のみ再認証します。部分バックアップでは全履歴を復元できないため、設定全体を消さないでください。

隔離が必要なら実際の保存先を確認し、日時付きで全体を複製して読めることを検証します。原本を残し、一項目ずつ変更・復元します。
