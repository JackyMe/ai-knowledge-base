認識 00

Codex の全景と選定プリズム

Codex は OpenAI が提供するエージェント型（Agentic）スマートコーディングツール体系です。単に「コードを書くチャットボット」にとどまらず、プロジェクト構造の理解、ツール呼び出し、OSレベルのサンドボックス分離、コード修正・検証、クロスプラットフォーム実行能力を備えた自律型エンジニアリングパートナーです。Codex を使いこなす第一歩は、明確な選定のメンタルモデルを確立することです。

三、選定プリズム ②：App / CLI / IDE / Cloud の効果的な組み合わせ

✅ 推奨されるゴールデンコンビネーション（現場のベストプラクティス）
  • 要件定義と方針策定：デスクトップ App や CLI で /plan を実行し、アーキテクチャと影響範囲を把握；
  • コアコードの実装：IDE 拡張機能または CLI の対話モードで開発し、差分を即座に確認；
  • 時間のかかる大規模リファクタリング/複数ファイルの移行：codex cloud exec --attempts 3 に委譲し、ローカルでは別作業を並行；
  • PR 作成前の品質担保：@codex review をトリガーして自動レビューを実施。
❌ 避けるべきアンチパターン（効率低下や事故の原因）
  • 通常の Web チャットに長いコードを書かせ、手動でコピペを繰り返す；
  • ローカルの CLI で30分以上かかる大規模移行タスクを同期実行し、ターミナルを占有させてしまう；
  • Git の作業ツリーが汚れた状態のまま、IDE で広範囲の自動置換を実行する；
  • 実際のブラウザ検証が必要なフロントエンドのUIタスクを、ヘッドレス環境に推測任せで丸投げする。

認識 01

4つの目的別学習ロードマップ

すべてのドキュメントを先頭からやみくもに読む必要はありません。現在の技術的背景や達成したい目標に合わせて、適切な学習パスを選択してください：

🌱ロードマップ 01：基礎入門（安全性と変更の巻き戻しやすさを確立）TRACK 01

対象：初めて Codex を触る方、または安全に変更をロールバックできる実務タスクをまだ完了したことがない方。

  1. 環境準備：インストールを完了し、codex login で ChatGPT アカウントにログイン；
  2. 安全な足場作り：専用のテスト用 Git ブランチに切り替え、git status で未コミットの変更がないことを確認；
  3. 読み取り専用での探索：codex --sandbox read-only で起動し、ファイルを改変せずにプロジェクト構造や README を分析させる；
  4. 最初の最小タスクの達成：15分以内に検証可能な小さなタスク（1行の型エラー修正やコメント追加など）を実行し、/diff で確認後、ローカルテストをパスしてコミット。
⚡ロードマップ 02：プロ開発者向け実践（高品質デリバリーと TDD サイクル）TRACK 02

対象：Git および主要なバックエンド/フロントエンド言語に精通し、開発効率を極限まで高めたいエンジニア。

  1. プロジェクト記憶の初期化：リポジトリルートで /init を実行し、ビルドやテストのコマンドを定義した簡潔な AGENTS.md を生成；
  2. TDD（テスト駆動開発）の先行：バグ修正時はまず Codex に再現用の失敗テストを書かせ、テストがグリーンになるまで修正を実行；
  3. 長大タスクの4段階分権：計画（Plan）→ 実行（Exec）→ 査読（Review）→ 記憶定着（Closeout）の4ステップで複雑なモジュールを推進；
  4. GitHub Issue から PR までの自動化：クラウドタスクと @codex review による自動コードレビューを統合。
🛠️ロードマップ 03：機能拡張と自動化（専用 AI ツールチェーンの構築）TRACK 03

対象：チーム内の定型作業を自動化し、開発基盤を強化したいリードエンジニアや DevOps 担当者。

  1. カスタム Skill の開発：オープン標準 Agent Skills 仕様に準拠し、SKILL.md、scripts/、references/ を含む独自スキルを構築；
  2. MCP プロトコルの双方向連携：DB、Sentry、Figma などの MCP サーバを接続し、codex mcp-server で Codex 自身を外部エージェントに公開；
  3. E2E ブラウザとログイン状態での検証：内蔵ブラウザや CDP プロトコルを活用し、リリース前のビジュアル・操作フローのスクリーンショット検証を実施；
  4. CI/CD とスクリプト実行：codex exec --json を定期実行タスクや自動テストパイプラインに組み込む。
📑ロードマップ 04：非エンジニア / PM / サイト運営ワークフロー（安全なコンテンツ・データ運用）TRACK 04

対象：ドキュメントサイト、ナレッジベース、メディアアセット、データ集計を管理する運営者・PM・ディレクター。

  1. 保護された安全操作：デスクトップ App やサンドボックス制限下でファイルを操作し、常にバックアップまたは Git ブランチ上で作業；
  2. 画像・メディアの一括処理：実績ある Skill を使用して、画像圧縮、フォーマット変換、動画エンコード、字幕校正を自動化；
  3. 構造化ナレッジの蓄積：Notion 連携や Markdown 記憶システムを活用し、調査結果や業務データを構造化ドキュメントとして出力；
  4. 差分確認と公開：diff レポートとレンダリング結果を厳格に確認し、ハルシネーション（誤情報）の混入を防止。

三、新規プロジェクト開始時の標準4ステップ

  1. /init —— リポジトリを自動解析し、ビルド・テスト・設計規約をまとめた簡潔な AGENTS.md を生成；
  2. /model —— モデルと推論強度を選択（デフォルト: GPT-5.6 Sol、または Terra / Luna）。/status でセッション設定を確認；
  3. サンドボックスと承認レベルの確認 —— デフォルト: workspace-write + on-request（後述の 3×3 マトリクスを参照）；
  4. /mcp と /skills —— プロジェクト専用の外部ツールや業務スキルパッケージを確認し、必要に応じてロード。

最近の重要動向と重大な変更

本ページの確認ステータス最終確認日 2026-08-25 · 情報源: Codex 公式 Changelog。本セクションでは使い勝手や操作性に直接影響する変更のみを抜粋しています。完全な履歴は ツールチェイン更新履歴 を参照してください。

🆕 0.148.0 最新機能 (2026-08-18)

  • Markdown エクスポート：/export コマンドが追加され、TUI の対話ログ全体を Markdown 形式で出力可能に。
  • ヘッドレス環境でのセッション分岐 (Session Forking)：codex exec fork によるセッション分岐を導入。セッションのアーカイブ (archive) と復元 (restore) にも対応。
  • コスト見積もり表示：/status、ステータスバー、ターミナルタイトルに、トークン消費量に基づくスレッド推定コストのリアルタイム表示を追加。
  • インフラ連携の拡張：組み込み推論バックエンドとして Amazon Bedrock Runtime をサポート。フック (hooks) による非同期コマンド実行や MCP ツール呼び出しに対応。

🚨 重要な破壊的変更とモデル移行

  • GPT-5.4 シリーズの提供終了：OpenAI は GPT-5.4 および mini を 2026-08-31 に完全退役させることを発表。config.toml を確認し、gpt-5.6-sol、gpt-5.6-terra、または gpt-5.6-luna への移行を行ってください。
  • codex exec --full-auto の廃止：バージョン 0.147.0 で --full-auto 引数が廃止されました。スクリプト内では codex exec --sandbox workspace-write --ask-for-approval on-request に書き換えてください。無人実行での全自動承認が必要な場合は新オプション --approve-for-me を使用します。
  • ローカルリポジトリの明示的信頼メカニズム：未信頼のリポジトリを開く際にセキュリティ警告が表示され、リポジトリ設定ファイルを悪用したプロンプトインジェクション攻撃を防止。
  • 機密情報の自動マスキング：TUI の出力において Bearer Token や API Key などの機密資格情報が自動検出され、*** に置換されます。

心法 05

コア方法論と初心者が陥りやすい落とし穴

一、実践タスクにおける4要素の法則（Goal-Context-Constraints-Done）

タスクが制御不能になる原因の9割は、最初のプロンプトが曖昧であることに起因します。質の高いプロンプトには次の4つのアンカーを含める必要があります：

  • Goal（目標）：「このモジュールを見ておいて」ではなく、納品すべき具体的な結果を1文で明確に定義する；
  • Context（コンテキスト）：関連するコアファイルや Issue/API 仕様書を明示する（/mention を活用）；
  • Constraints（制約条件）：変更を禁止するファイル、導入不可の外部ライブラリ、後方互換性の要件などを明記する；
  • Done-when（完了条件）：客観的かつ定量的に検証可能な合格基準を提示する（例: 特定の単体テストが全件グリーン、特定の JSON レスポンスが返るなど）。

協調 06

長大タスクのワークフローとマルチセッション運用

30分以上かかる大規模リファクタリングや複雑なモジュール開発において、単一セッションですべてをこなそうとすると、コンテキストの肥大化により注意力が散漫になりハルシネーションを招きます。Codex の高度なプラクティスは、「4段階の分権（Separation of Concerns）」とセッションの適切な分離です。

一、長大タスクの「4段階分権」ワークフロー

  1. 検討・計画フェーズ (Discuss / Plan)：read-only サンドボックス下で /plan を実行し、リポジトリを安全に分析。詳細な改修計画、対象ファイル一覧、リスク評価を出力させる（コードは一切書かせない）。
  2. 隔離実行フェーズ (Execute)：新規セッションまたは子スレッドを開き、合意した Plan を読み込ませる。workspace-write 権限を与え、モジュールごとに段階的に実装を進め、各ステップで最小限のテスト検証を義務付ける。
  3. 独立査読フェーズ (Review)：まったく新しいセッションを立ち上げるか /review を実行し、「実装に関与していない第三者」の客観的な視点から堅牢性・境界条件・セキュリティを精査させる。
  4. 完了・引き継ぎフェーズ (Closeout & Handover)：テストの実行ログやスクリーンショット等のエビデンスを回収し、DECISIONS.md や AGENTS.md を更新して、構造化された PR 説明文を生成する。

二、マルチセッション分散と協調ツールキット

  • 一時的なサイド会話 /side (/btw)：疑問点（例：「なぜこのライブラリのバージョンが 2.1 に固定されているのか」など）が生じた際にサブ会話を開き、調査完了後に結論だけを持って本筋に復帰。メインセッションのコンテキストを無駄な調査ログで汚さない。
  • セッション分岐 codex fork：1つの複雑な課題に対して A案（リファクタリング）と B案（ホットフィックス）を比較したい場合、メインセッションから2つの独立スレッドに分岐させて並行検証が可能。
  • 2台構成のリモート操作 (Remote Control)：薄型ノートPC（MacBook Air など）から --remote ws://... を経由して、常時稼働しているハイスペックデスクトップやクラウドサーバ上の Codex app-server に接続。ローカルの手軽さとリモートの潤沢な計算資源を両立。

> 【目標】src/auth/jwt.ts に Refresh Token のスライディングウィンドウ更新ロジックを追加してください。

  まず tests/auth/jwt.test.ts に3つのテストケース（並行更新テストを含む）を作成すること。

🚀 二、 黄金の4段階連携パラダイム：構想から実装完了までの SOP

成果を最大化するアプローチは「関心の分離・動的試行と静的実行の切り分け」です。試行錯誤はコストが低く視野の広い Web/音声で行い、確定した実装のみをローカルターミナルに任せます：

第 1 段階：構想策定とアーキテクチャ壁打ち（Voice + Deep Research）

新しい機能の追加や未知のライブラリ導入を検討する際、いきなりターミナルでコードを書き始めてはいけません：

  • 音声によるブレインストーミング：高度な音声モードを起動し、5分間で構想を AI に伝えます：「既存の Next.js アプリに Stripe 決済フローを組み込みたい。考慮すべきエッジケースと DB 設計案を挙げて」。口頭対話でロジックの抜け漏れを素早く特定します。
  • Deep Research による技術検証：新規のライブラリや規約について、Web 版で詳細な調査を実行させます：
構造化リサーチ Prompt テンプレート 詳細リサーチを開始し、最新の公式ドキュメントおよびベストプラクティスを網羅的に調査した上で、【対象技術スタック】の導入ガイドを出力してください。必須項目：1. コアアーキテクチャとデータフロー図；2. 破壊的変更 (Breaking Changes) リスト；3. JSON Schema に準拠したデータモデル定義。余計な挨拶は省き、技術的要点のみを出力すること。

第 2 段階：ビジュアル＆UI デザインの確定（Image / Vision to Code）

フロントエンド開発ではスタイルの微調整で膨大なトークン枠を浪費しがちです。ビジュアル決定とコード生成を切り離します：

  1. Web 版の画像生成機能で UI コンセプト画像を 2〜3 パターン出力し、最適な 1 枚を選定します。
  2. 選んだ UI 画像を Vision 機能に読み込ませ、デザインシステム仕様を出力させます："この画面からカラーパレット（16進数）、グリッド間隔、フォント階層、Flex/Grid 構造を抽出し、Tailwind CSS 設定として出力して"
  3. 確定したデザイン仕様をテキストとして取得してからコーディングに移ることで、手戻りを最小限に抑えられます。

第 3 段階：局所推敲とサンドボックス検証（Canvas 協調）

重要なアルゴリズムやビジネスロジックを作成する際は、ChatGPT の Canvas モード を活用します：

  • 局所的なピンポイント修正：修正したいコード箇所（10行程度）をハイライトし、「この処理にリトライロジックとエラーログを追加して」と指示。Canvas は選択範囲のみを更新するため、ファイル全体の再出力による無駄なトークン消費を 80% 以上削減できます。
  • 組み込みレビューツール：「コードレビュー」や「ログ追加」ショートカットを活用し、その場で品質を底上げします。

第 4 段階：ローカルターミナルでの確実な落とし込み（Codex ターミナル）

最後にローカルターミナルへ戻り、Codex を実行します：

  • すでに前段階で明確な設計仕様、Tailwind 設定、検証済みのアルゴリズムコードが手元に揃っています。
  • ターミナルで簡潔に指示："設計仕様に従い、src/modules/ にファイルを作成してローカルテストを実行して"
  • 入力が極めて明確なため、1回の実行でテストが通り Git Commit まで完了。ターミナル枠の消費を最小限に抑えられます。

🛡️ 三、 クォータ節約とコンテキスト管理の鉄則

実務で実証された、利用枠を延命させるための基本ルール：

1. 「新規返信」ではなく「直前メッセージの編集」を活用する

多くのユーザーが見落としているテクニックです。AI の回答が期待とずれていた場合、新しいメッセージで指示を重ねてはいけません。追加質問をするたびに過去の失敗履歴がすべて再送されます。直前のプロンプトの「編集」ボタンを押し、指示を修正して再送信すれば、過去の誤答コンテキストが累積することはありません。

2. 明確な Custom Instructions（カスタム指示）を設定する

毎回「TypeScript で書いて」「挨拶は不要」と入力する手間を省くため、設定内のカスタム指示やプロジェクト直下の SKILL.md にあらかじめ記述しておきます。

推奨カスタム指示テンプレート (設定 -> ChatGPT をカスタマイズ) - 役割：シニアフルスタックアーキテクト。 - 出力スタイル：簡潔、厳格、エンジニアリング重視。前置きや結びの挨拶（「承知しました」など）は一切不要。 - コード規則：変更箇所のみを出力（未変更部分は // ... existing code ... と表記）。TypeScript 型定義を必須とする。 - 音声モード制約：要点のみを簡潔に回答し、「他にお手伝いできることはありますか？」などの定型句は省くこと。

3. モデルの使い分け：用途に応じた適材適所

  • Reasoning / 思考モデル (o3 / 深度思考)：複雑な競合状態の解消、アルゴリズムの証明、アーキテクチャの全面再設計など高難度タスクに限定。
  • Fast / Mini モデル：正規表現の作成、JSON/YAML 変換、Git コミットメッセージ生成、軽微な修正などに活用。圧倒的に高速で枠の消費もごくわずかです。

❓ 四、 よくあるトラブルと対策

🛡️ 五、 実運用時の留意点とライセンス・コンプライアンス

アプリ内で複数枚のイラストのトーン＆マナーを統一するには？
「共通のスタイル修飾句」とパレットを固定します。 すべてのプロンプト末尾に同一のスタイル定義（例: --style: flat geometric 2D vector, mint and slate palette, soft outlines, pure white background）を付与し、Web 版の同一スレッド内で連続生成することで、画風とキャラクターの一貫性を維持できます。
生成画像の商用利用における注意点は？
OpenAI の利用規約により、有料サブスクリプションユーザーは生成した画像の商用利用権を完全に保有します。ただし、著名なキャラクターや商標ロゴの直接的な名称指定は避け、「抽象的な幾何学スタイル」「モダンなフラットテックデザイン」など一般的なデザイン表現を用いることで、安全に商用利用を行えます。
