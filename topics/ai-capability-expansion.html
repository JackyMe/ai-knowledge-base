认知 00

认知框架

过去,跨出一个陌生技术栈时,真正吃时间的往往不是概念本身,而是查文档、试错踩坑的过程——一个报错在论坛里翻半天,一个陌生 API 的参数含义读官方文档三遍才敢下手。AI 把这段时间压缩到接近实时:报错粘进去秒级定位大概率原因,陌生用法一句话问明白,原本要啃一整天的文档十分钟内提炼出可执行结论。但没有被压缩的是另一头——AI 给出的答案是否真的对,这一步的判断仍然只能靠人。 实测共识 Google DORA 团队《2025 State of AI-assisted Software Development》报告中一项针对 1,110 份开放式回复的专题分析得出了相近结论:生成阶段省下的时间,相当一部分被重新分配成了验证阶段的开销;该文另引用《2025 DORA report》数据指出,仍有三成开发者对 AI 生成的代码信任度很低——这项数据来自 DORA 另一份报告。换句话说,能力边界扩展路上真正的新瓶颈不是"学不会新语法"——语法这层 AI 基本能包办;卡住人的是"AI 写出来的东西对不对、我能不能判断出来"。

核心论点核实自 DORA 官方洞察《Balancing AI tensions》——验证开销结论出自该文中 1,110 份开放式回复的专题分析(非报告整体约 5000 人样本);信任度数据引自该文链接的 《2025 DORA report》 官方页面,原文未披露该项数据的具体样本量,2026-07 核实。

但边界扩展不等于无所不能,这条线要诚实划清楚:如果新领域和你已经掌握的心智模型同构——比如你已经会一门带类型系统的语言,换一门语法不同但范式相近的语言;你已经理解声明式 UI,换一个框架实现同一套心智模型——AI 提效非常明显,省下来的大部分时间是"记住这门语言/框架具体怎么写",这恰恰是 AI 最擅长补的那块。但如果新领域你完全陌生,没有任何可迁移的心智模型——比如你第一次要在一个业务域里做架构决策,判断"这个方案好不好"需要的是踩过坑、扛过后果积累出来的经验,这种判断力 AI 给不了;它能列选项、摆权衡清单,但拍板需要你自己积累到能拍板的地步。不划清这条线,边界扩展很容易被误解成"有了 AI 就无所不能"。

两个常见误区 误区一:装了 AI 编程工具就等于学会了新技术栈。能让 AI 写出一段能跑起来的代码,不代表你能独立读懂它、调试它出问题时的报错、或者在评审里对它提出有质量的意见——"能跑"和"你掌握了"是两件事。
误区二:把 AI 的产出当真理,不做验证就用。这正是上面论点里"没被压缩的那一半";具体怎么把验证做成一道能落地的闭环,而不是"多测试一下"这种空话,留给下一节方法论引擎的第④步展开。
方法论 01

通用方法论:五步扩展引擎

五步不是五个孤立技巧,是一条链:①先诊断出"哪些是真正陌生的",②只把这部分知识速通,③立刻动手搭一个能跑的最小产物,④用可验证的方式确认它是对的,⑤回头把踩过的坑变成自己真正理解、能沉淀下来的东西。每一步都按"学什么 / 怎么学 / 用什么 / 怎么用"四问展开,"怎么用"给的是可以直接复制的提示词,不是"多问 AI"这种空话。

①诊断差距

学什么

这一步不是学新技术,是先把一件事搞清楚:我已经会的心智模型,能覆盖新领域的哪些部分。这个诊断结果直接决定后面四步怎么走——覆盖到的部分不用重学,没覆盖到的才是真正要啃的硬骨头(具体怎么把"已有心智模型"喂给 AI 做映射,是下一节跨域映射技法要展开的)。诊断阶段要问清楚三个具体问题,不能停在"我感觉自己懂多少":

  • 这个新领域和我熟悉的领域,概念模型有多大重叠?
  • 哪些是纯换名词的翻译,哪些是真正陌生的新概念?
  • 我现在最想做成的第一个具体产出是什么?

怎么学

这一步的动作不是"学",是"问"——而且是反过来让 AI 问你,而不是你自己先列一份自评清单。自评清单这个做法本身就不可靠:你对熟悉领域的部分容易高估(觉得"这个我肯定懂"结果一细问漏洞百出),对陌生领域又容易低估(觉得"这个我完全不懂"结果其实换个名词就是你天天在用的东西)。让 AI 主动追问、边问边判断你的回答里透出的知识边界,比自己给自己打分准得多。

用什么

这一步不需要项目上下文,纯聊天模式就够——Claude Code / Codex 的对话模式直接开一个新会话即可,不用挂载任何代码库。

怎么用

我是 [你的背景,例如:5 年 Java 后端开发经验,熟悉 Spring / MySQL / 消息队列]。
我现在想把能力边界扩展到:[目标新领域,例如:分布式系统架构设计]。
我现在最想做成的第一个具体产出是:[越具体越好,例如:给现有系统设计一版能落地的多活容灾方案]。

在我说更多之前,先反问我 3-5 个诊断性问题,目的是摸清我在这个新领域里的真实知识边界——
不要假设我什么都不会,也不要假设我都懂。问题要具体到我一眼就能判断"这个我懂"或"这个我确实没听过"。

等我回答完,请根据我的回答把这个新领域拆成三类,列成表格:
① 重叠区:和我已有领域的概念模型基本相同,只是换了个名词
② 翻译区:概念不完全等价,但能用我已有的概念类比理解——你要具体指出怎么类比
③ 全新区:我完全没有对应心智模型,需要从零建立的概念

②AI 知识速通

学什么

只学上一步诊断出的"全新区"里,阻碍你验证产出正确性的最小概念集——不是别的。这里要明确排除一种直觉做法:体系化通读官方文档或教材。那是学新技术栈时的老办法,在能力边界扩展场景里效率很低,因为"全新区"往往只占新领域的一小部分,通读整本文档等于把"重叠区"和"翻译区"也从头学一遍,白白浪费时间。

怎么学

用 AI 做"概念翻译",而不是"从头听课"。具体技巧:每学一个新概念,立刻用第①步已经确认的"重叠区"里对应的旧概念去类比,并且要求 AI 反向出题验证你真的理解了——它讲完不算数,你答对题才算数。这一步最容易犯的错是"听懂了就以为学会了",反向出题是唯一能戳破这个错觉的手段。

用什么

AI 对话 + 官方文档两样都要。官方文档不是可有可无的补充,是校验 AI 说法的必要环节——AI 的类比讲解可能生动但不准确,尤其是在版本细节、边界条件这类地方,单方面信 AI 讲解容易把错误的类比当成事实记下来。

怎么用

我在 [全新区里的具体概念,例如:分布式事务的 Saga 模式] 上完全没有心智模型。
我已有的心智模型里,和它可能沾边的是:[重叠区里对应的旧概念,例如:数据库事务的 ACID、业务上的补偿/冲正机制]。

请:
1. 用我已有的 [对应旧概念] 做类比,讲清楚 [新概念] 到底是什么、解决什么问题、和我熟悉的东西本质区别在哪
2. 讲完不要停,立刻出 3 道判断题或场景题考我——题目要能测出"我是记住了你的话"还是"我真的理解了",不要出送分题
3. 我答完,你先判断对错,再指出我具体错在哪个环节的理解上

最后告诉我:如果我理解错了,官方文档/权威资料里哪一节可以直接核对?给出具体章节或关键词,不要只说"查官方文档"。

③脚手架起步

学什么

这一步不追求"理解全部原理",目标是搭一个能跑起来的最小产物,建立手感。刻意允许"知其然不知其所以然"——这是这一步和第②步的本质区别:第②步学的是"验证产出对不对"要用到的最小概念集,第③步则是先让东西跑起来,原理层面的空白留到第⑤步回头补。

怎么学

边搭边问,卡住了才深挖,不要在动手前先把所有概念学透。这是最容易拖慢进度的反模式:总觉得"再学一点就能动手了",结果一直停在学的阶段没有产出。能跑的最小产物本身就是最好的反馈——跑不通、报错了,再回去问对应的概念,针对性比预先通学高得多。

用什么

这一步需要两份可以直接复制进项目的资产:一份放进项目根目录约束 AI 协作方式的配置模板,一份覆盖高频场景的提示词库。两份都是通用版,不绑定任何具体技术栈,占位符按你的实际项目填。

怎么用

资产一:AI 协同配置模板(存成项目根目录的 CLAUDE.md,或对应工具读取的规则文件,让 AI 每次协作时自动遵守):

# 项目约定 —— [你的项目名称/一句话描述]

## 技术栈
[你的技术栈:语言 / 框架 / 数据层 / 部署方式 —— 按项目实际情况列清楚,AI 才不会瞎猜环境]

## 硬性规则
- 改动前先给出计划;方案涉及 3 个以上文件的改动必须先列清单,确认后再动手
- 不确定的地方直接问,不要自己猜着实现——猜错了返工比问一句贵得多
- 引入新依赖 / 新概念前,先说明为什么需要、有没有更简单的替代方案
- 改动完成后运行:[你的 lint / typecheck / test 命令,例如 npm run lint && npm test,或 pytest,或 go vet && go test ./...]

## 沟通约定
- 我熟悉 [你的已有技术栈/领域],新概念用它类比解释,不要假设我从零开始
- 给我代码时,顺带说明这段代码可以怎么验证正确性(呼应下面④验证闭环)

④验证闭环

学什么

AI 产出的正确性不能只靠"看起来对"判断——这正是本页开篇提到的那个没被压缩的环节:生成阶段省下的时间,相当一部分要重新花在验证阶段。要学的不是某个具体工具怎么用,是针对新领域挑选合适的验证手段的判断力:单元测试、类型检查、真实环境跑通、官方文档逐条对照,哪种能确认你手头这个产出是对的,取决于产出的类型,不是套用一种万能验证法。

怎么学

具体技巧是要求 AI 自己说出它的产出怎么验证,而不是你自己想验证方法。AI 通常清楚自己写的这段东西该配什么测试、哪里最容易出错,但默认不会主动给出来——它给你代码就停在那,除非你明确要求,否则"这段代码怎么验证"这一步会被两边都跳过。

用什么

按类别记住这几种工具,不需要绑定某个具体技术栈:单元测试框架(在大多数技术栈里都有对应物,比如 JavaScript 生态的 Jest/Vitest、Python 的 pytest、Go 内置的 testing 包)、类型检查器(比如 TypeScript 的 tsc、Python 的 mypy)、linter/静态检查工具(比如 JavaScript 生态的 ESLint、Python 的 Ruff/Pylint、Go 的 golangci-lint,专门抓类型检查器管不到的代码规范和常见坑)、以及针对该领域的官方文档作为最终校验源。

怎么用

实现 [功能/改动] 之后,请在给出代码的同时必须附带以下几项——不要等我问:

1. 这段代码可以用什么方式验证正确性?按优先级列出:
   ① 能否写单元测试?给出测试用例框架(用我项目里已有的测试框架,没有就说明推荐哪个)
   ② 有没有类型检查/静态检查能直接抓出这类改动最容易犯的错?
   ③ 这段代码必须在什么样的真实环境/真实数据下跑一遍才算数?给出具体验证步骤
   ④ 涉及外部 API/官方行为的部分,你的说法是从哪个版本的官方文档得出的?列出来源,我要逐条核对,不能只信你的转述

2. 如果以上四类里有些不适用(比如这段改动没法写单测),明确说明为什么不适用,不要跳过不提。

3. 最后用一句话告诉我:如果这段代码是别人交给你审查,你自己会不会直接合并?

⑤深化沉淀

学什么

从"能跑"到"理解为什么"。具体做法是回头针对第③④步里踩过的坑,追问 AI"为什么这样写是对的,还有没有别的写法"——脚手架阶段允许的"知其然不知其所以然",到这一步必须补上。

怎么学

费曼法的 AI 版本:试着自己给 AI 讲一遍你刚学会的东西,让 AI 挑错,而不是被动接受它讲解。能不能讲清楚,是检验"真懂了"还是"以为懂了"最诚实的一道关卡——被动听讲解时的"我懂了"感觉很容易是错觉,自己讲一遍立刻会暴露哪里其实说不清楚。

用什么

AI 对话 + 自己的笔记文件。"沉淀"这个词的关键在"沉"——必须落到你自己持续维护的文档或模板里,只留在聊天记录里等于没沉淀,过两周你还是想不起来当时踩过什么坑、为什么后来改了写法。

怎么用

费曼验证——学完一个模块,先做这一步:

我来给你讲一遍我这周学会的 [概念/模块],你先别打断,等我讲完。
讲完之后按这三项挑我的错:
① 我讲的哪些地方是错的或不准确的
② 我漏掉了哪些关键点(哪怕我讲的部分都对,但整体理解不完整)
③ 追问我 1-2 个"为什么这样做是对的,换一种写法行不行"的问题,逼我说出理由而不是背答案

周期复盘——把费曼环节暴露出的问题和这段时间的产出一起沉淀下来:

这是我这周期的代码 diff、踩坑记录,以及刚才费曼环节里被挑出的错误。请总结:
① 我反复犯的模式是什么
② 下周期该刻意练什么,给具体到"用什么场景练"的建议,不要只说"多练"
③ 哪些知识点我以为懂了、费曼环节暴露出其实没懂
④ 把①②③整理成一段可以直接粘进我笔记文件([你的笔记文件名/路径])的 markdown,不要留在这轮对话里就算完
方法论 02

跨域映射技法

跨域映射就是五步扩展引擎第①步"诊断差距"里"重叠区/翻译区/全新区"三分类的具体操作方法:把你已经会的 A 域心智模型完整喂给 AI,让 AI 帮你把新概念逐个分进两个可执行的桶——"这是 A 的翻译"(对应①重叠区+②翻译区:概念基本对得上,换个名词或者需要一点类比就懂,学习成本低)和"这是 A 没有的新概念"(对应③全新区:真正要花时间理解的部分)。诊断阶段的三分类负责"看清楚差距在哪",这里的两个桶负责"决定每条差距具体怎么处理"——分完桶,能翻译的直接类比过去,真新的才值得投入学习时间。这个技法不是"第一次学新领域"专用的一次性动作,而是一项可复用能力:以后每换一个新域——今天是移动到 Web,明天可能是前端到后端,后天是单体到分布式——都能重复用同一套提问方式,把已有经验最大化利用,只把力气花在真正陌生的部分上。

Android ↔ iOS:声明式 UI 范式互译

概念Android(Compose)iOS(SwiftUI)
声明式 UI 单元@Composable 函数遵循 View 协议的 struct + body
组件内本地状态remember { mutableStateOf() }@State

移动端 → Web 前端:Compose/Kotlin → React/TS 精华摘要

移动端(Compose/Kotlin)Web 前端(React/TS)关键差异

Web 前端 → 后端/服务端:前端最容易带错的三个直觉

前端心智(你已有)后端新概念类比要点
每次 setState 都从头重新渲染,没有跨渲染保留的变量HTTP 请求默认无状态,服务端不会"记得"上一个请求是谁你熟悉的"无副作用重渲染"心智,后端把它搬到了"请求"这个粒度——状态必须显式存进数据库/缓存,不能指望服务端替你记着
浏览器帮你管理 TCP 连接、复用 Tab数据库连接池(connection pool)类比"提前建好一批可复用的连接,请求来了借一个用完还回去",不是每个请求都重新握手,道理和"复用而不是每次新建"一致
前端"防抖/禁用按钮"防止用户手滑重复提交API 幂等性(idempotency)前端的直觉是"别让用户点两下",后端幂等性是更严格的契约:同一个请求不管重发几次,服务端最终状态只变化一次——GET/PUT/DELETE 语义上天然幂等,POST 默认不是,要额外设计(比如幂等键)才能保证

案例 A:移动端 → 全栈跨端

你是一名 Android 或 iOS 背景的移动端工程师,声明式 UI、ViewModel/StateFlow 状态管理、Room 本地持久化这些心智已经很扎实,现在想往上再走一层——不只是"写一个跑在手机里的 App",而是能独立搭一个前端渲染、后端写操作、数据库读写全部自己拿下的全栈应用,不用等后端同事排期。下面按五步扩展引擎把这条跨越走一遍,技术选型以 Next.js 全栈框架为例,原理同样适用于 Nuxt、SvelteKit 等其他全栈框架。

①诊断差距(案例化)

学什么

结合跨域映射两张映射表(Android↔iOS 的 remember/@State 互译、移动端→Web 前端的 remember→useState、LaunchedEffect→useEffect)理清一件事:全栈比"移动端→前端"多出的那两层,是后端服务与数据库——这两层你目前完全没有对应心智模型,才是这次诊断真正要划出来的③全新区;前端这层因为你已有声明式 UI 直觉,大概率落在①重叠区/②翻译区,不用重新花时间学。

怎么学

不要自己先估"我大概懂多少",在#mapping 给的前端层映射基础上,把同一套"重叠区/翻译区/全新区"三分类往后端和数据库层继续问下去,让 AI 主动追问,而不是自己先列清单。

用什么

AI 对话诊断,纯聊天模式即可,不用挂载代码库。

怎么用 
我是 [Android/iOS] 移动端工程师,写过 [N] 年 [Kotlin+Compose / Swift+SwiftUI],
熟悉声明式 UI、ViewModel/StateFlow 状态管理、Room 本地持久化、Retrofit 网络层。

我现在想把能力边界扩展到:能独立搭一个前端+后端+数据库都自己拿下的全栈应用
(以 Next.js 为例,原理同样适用于其他全栈框架)。
我现在最想做成的第一个具体产出是:[例如,一个带登录、能持久化私有数据的个人项目管理小工具]。

在我说更多之前,先反问我 3-5 个诊断性问题,分别覆盖:
① 前端渲染层——哪些和我的声明式 UI 直觉重叠
② 后端服务层——我从没写过接口,这层要重点问
③ 数据库层——我只用过 Room 这种本地嵌入式库,没碰过真正的服务端数据库和权限模型

等我回答完,请把结果按三层拆成表格:①重叠区 ②翻译区 ③全新区,
并特别标出:"后端服务层"和"数据库层"里,哪些概念是移动端完全没有对应物、必须从零建立的。

②AI 知识速通(案例化)

学什么

从诊断出的③全新区里挑一个真正卡点:"哪段代码到底在哪跑"——服务端组件与客户端组件的边界,以及页面 HTML 什么时候生成(SSR/SSG/ISR)。这是移动端心智完全没有对应物的部分:App 里所有代码都在设备上跑,全栈应用第一次出现"同一份代码,一部分在服务器执行、一部分在浏览器执行"这件事。

怎么学

用你已有的"哪层能力归哪层管"的直觉做类比引子,但要求 AI 讲完立刻出题,而不是听完类比就以为懂了——这正是#engine 步骤②"反向出题"技巧在这个具体全新区上的应用。

用什么

AI 对话即可,概念澄清阶段不需要挂载真实项目代码。

怎么用 
我是移动端工程师,对"代码只在设备上跑"这个心智很熟。请给我讲清楚 Next.js
(或同类全栈框架)里"服务端组件"和"客户端组件"的边界:

1. 默认情况下,我写的组件在哪跑?什么声明会让它换到另一边跑?
2. 举一个具体反例:如果我把数据库查询逻辑放进了本该在浏览器跑的组件,后果是什么——
   是编译期报错,还是运行时才炸,还是更糟(比如密钥被下发到浏览器)?
3. 再讲清楚 SSR/SSG/ISR 这三种"页面 HTML 什么时候生成"的模式,分别对应我要做的
   应用里哪种页面(登录后的个性化面板 / 纯展示的落地页 / 更新不频繁的详情页)?
4. 讲完出 3 道判断题考我,题目要能测出我是不是真分清了"服务端组件默认能力"
   和"客户端组件必须显式声明才有的能力"。

一次靠谱的回答通常长这样(结构比逐字文案更重要,判断"AI 是不是真讲清楚了"就看有没有这三块):先给一张判断表——能不能用 useState/onClick、能不能直接查库或读密钥、默认该选哪个,这张表应该 30 秒内能背下来;再给具体反例——数据库查询放进声明了 "use client" 的组件会在构建期直接报错,因为浏览器端根本拿不到数据库连接,而反过来"服务端组件里想用 onClick 却忘了声明 "use client""才是最容易在 AI 生成代码里漏检的坑;最后给 SSR/SSG/ISR 一句话结论——静态内容用 SSG,更新不频繁的内容页用带 revalidate 的 ISR,登录后的个性化面板用 SSR,对应的正是你在 Room/本地缓存里已经很熟的"要不要缓存、缓存多久"判断,只是这次要在页面粒度上做决定。

③脚手架起步(案例化)

学什么

不追求学完整个技术栈,先搭出"一个能登录、有一条私有数据能读写"的最小全栈产物——这条线比"能跑起来的 Hello World"高一格,因为它同时验证了前端渲染、后端写操作、数据库权限三层是否真的打通,而不只是跑通了最简单的静态页面。

怎么学

边搭边问,卡住哪层就针对性问哪层,配合#engine 步骤③已经给出的通用起手命令与 CLAUDE.md 模板——起步阶段不需要先读完框架文档或数据库文档。

用什么

这里以 Next.js 为例点名具体命令,原理同样适用于其他全栈框架;数据库以 Supabase/Postgres 为例,原理同样适用于其他数据库服务。

怎么用

④验证闭环(案例化)

学什么

承接#engine 步骤④"AI 产出正确性不能只看起来对",全栈案例里最有代表性的一处是数据权限:AI 很容易写出"看起来能跑"但权限有漏洞的代码——查询忘了带 owner 过滤,或者把无视权限的万能密钥用到了浏览器端。这一步要学的是给这类"必须验证、不能只读代码"的产出配一个可执行的验证方法。

怎么学

以 Supabase/Postgres 的行级安全(RLS)为例,原理同样适用于其他数据库的权限模型(比如自建后端的中间件鉴权 + ORM 层过滤、或其他云数据库自带的行级权限):先让 AI 给出策略,再反过来让 AI 扮演攻击者列出几种绕过尝试,用两个真实测试账号互相查询验证挡得住——这正是#engine 步骤④"要求 AI 自己说出产出怎么验证"的具体落地。

用什么

数据库的策略配置界面或 SQL Editor + 两个测试账号(不能自己一个账号自测,必须两个身份互相攻击才算验证)。

怎么用 
-- 以 Supabase/Postgres 为例,给一张表开启行级安全并写最小策略(原理同样适用于其他数据库权限模型)
alter table projects enable row level security;
-- 开启后默认拒绝一切访问——这正是它的价值,漏写一条策略 = 请求被拒,不是数据裸奔

create policy "只能读自己的项目"
  on projects for select
  using ( owner_id = (select auth.uid()) );
这张表已经开了行级安全、写了上面这条策略。请扮演攻击者,给出 3 种可能绕过这条
策略、读到别人数据的尝试(比如:忘记给某个操作写策略、policy 条件写反、用错误
的密钥绕过)。

然后我会用两个真实测试账号(A 账号登录后尝试查 B 账号的数据)逐条复现验证——
你先告诉我每种尝试具体该怎么操作,我验证完回来告诉你结果。
验证不能只看代码两把钥匙的边界也要一并复查:面向浏览器的公开密钥受权限策略约束可以出现在前端,无视权限策略的万能密钥只允许留在服务端环境变量——这条红线不分数据库品牌都成立,AI 生成的任何写操作,照这个"策略 + 攻击场景验证"的模板审。

案例 B:前端/客户端 → 后端与服务端工程

你是一名前端(React/Vue 等)或客户端背景的工程师,组件化拆分、状态管理、"发一个请求、拿到数据渲染出来"这套心智已经很熟练,现在想往下再扎一层——不只是消费别人写好的接口,而是能自己设计 API 契约、选一门后端语言把服务真正跑起来、并对它在生产环境里的稳定性负责。下面同样按五步扩展引擎走一遍,技术选型以 Fastify(Node.js)为主线,原理同样适用于其他后端框架;起点正是#mapping 里"Web 前端 → 后端/服务端"那张映射表——那张表已经点出前端最容易带错的三个直觉(无状态请求、连接池、幂等性),这里从它们继续往下诊断。

①诊断差距(案例化)

学什么

#mapping 给出的三条映射基本落在①重叠区/②翻译区——你已经有"受控副作用"的直觉,只是把粒度从"组件重渲染"搬到了"一次 HTTP 请求"。这一步真正要划进③全新区的是那张表还没覆盖的两块:路由与契约设计(你一直是"消费" API 的一方,现在要变成"定义"这份契约的一方——路径怎么分层、状态码怎么选、错误结构怎么统一,都要自己决定,不再是读文档拿现成的)和鉴权的服务端视角(前端只需要"读"登录态——拿到 token 判断要不要显示某个按钮、要不要跳登录页;后端要"写"并对它的安全边界负责——token 怎么签发、怎么校验、过期怎么处理、一旦泄露怎么撤销,这些前端从来不用操心)。

怎么学

不要自己先估,直接把#mapping 那张映射表贴给 AI 当作"已确认的重叠区",让 AI 只在剩下的部分继续追问——这样能省掉重复诊断已经诊断过的内容,把追问力气集中在契约设计和鉴权这两块真正陌生的地方。

用什么

用什么

后端语言/框架当前有不少主流选择,这里点名一个经 WebFetch 核实过生态活跃度的例子作为主线:如果你的前端背景是 JS/TS,Node.js 生态的 Fastify 是自然延伸,复用同一门语言,原理同样适用于 Go(如 net/http+chi)、Java(Spring Boot)、Python(FastAPI,这两年采用率呈现出这几年少见的涨幅)等其他语言与框架。数据库用一张最小表起步即可,不需要先起一个独立的数据库服务——Node.js 24 LTS 起不需要额外 flag 就能用内置的 node:sqlite 模块,官方稳定性标注是 1.2(Release Candidate,接近稳定,API 已可直接用于起步验证)。但要注意 DatabaseSync 是同步阻塞 I/O——在 Fastify 这类基于事件循环的异步框架里,一次同步查询会卡住整个进程、阻塞其他并发请求,这正是"仅适合教学/起步阶段的最小验证,真正上生产库前应评估更成熟的异步数据库方案(比如 PostgreSQL 搭配异步驱动,或专用 ORM)"这条建议真正站得住的理由。

怎么用 
# 以 Node.js + Fastify 为例,原理同样适用于 FastAPI/Spring Boot 等其他框架
mkdir my-api && cd my-api
npm init -y
npm i fastify
# package.json 里加 "type": "module" 才能用下面的 import 语法
// server.js —— 最小可跑的 API + 一张表,用内置 node:sqlite,零外部依赖
import Fastify from 'fastify'
import { DatabaseSync } from 'node:sqlite'

// export function build() 只组装实例、不监听端口——test.js 靠它拿到可 inject 的 app
export function build() {
  const db = new DatabaseSync('app.db')
  db.exec(`
    CREATE TABLE IF NOT EXISTS todos (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      done INTEGER DEFAULT 0
    )
  `)

  const app = Fastify({ logger: true })

  app.get('/todos', (req, reply) => {
    const rows = db.prepare('SELECT * FROM todos').all()
    reply.send(rows)
  })

  app.post('/todos', (req, reply) => {
    const { title } = req.body
    const stmt = db.prepare('INSERT INTO todos (title) VALUES (?)')
    const info = stmt.run(title)
    reply.code(201).send({ id: info.lastInsertRowid, title, done: 0 })
  })

  app.get('/me', (req, reply) => {
    if (!req.headers.authorization) {
      reply.code(401).send({ error: 'unauthorized' })
      return
    }
    reply.send({ id: 1 })
  })

  return app
}

// 直接运行本文件(node server.js)才真正监听端口;被 test.js 当模块 import 时不会执行到这里
if (import.meta.url === `file://${process.argv[1]}`) {
  build().listen({ port: 3000 })
}

④验证闭环(案例化)

学什么

承接#engine 步骤④"AI 产出正确性不能只看起来对",后端服务里最容易被 AI 生成代码糊弄过去的三处是:API 契约(响应结构、状态码是不是真的和文档/前端约定的一致)、鉴权边界(没登录/没权限的请求是不是真的被拒绝,而不是"代码里写了检查但漏了某条路径")、并发下的数据一致性(两个请求同时改同一行数据,最终结果对不对——这是前端几乎不会遇到的问题,浏览器里没有"两个用户同时点提交"这种真正的并发)。

三层学习法(总纲)

层目标做法投入
① 快速扫盲知道"是什么"让 AI 用类比讲清轮廓,先建立地图,坚决不在细节里打转进入每个新领域时集中完成
② 边做边学真正掌握项目卡点 → 问 AI → 动手解决 → 继续前进;每个问题沉淀成一个知识点贯穿整个扩展过程
③ 刻意内化转为长期记忆用费曼法讲给 AI 批改 + 周期复盘 + 下方动态自测在每个学习周期持续重复

让 AI 生成自己的动态自测清单

不要背一份绑定某个技术栈的固定题库。你当前处于扫盲、项目推进还是内化阶段,最近实际学了什么,决定了此刻最该被追问什么。每个学习周期把阶段、已学内容、做过的产出和仍然含糊的地方交给 AI,让它专门攻击那些"看过就以为会了"的盲区;题目答不上来就回到项目或资料补课,下一周期再按新进度重新生成。

可直接复制的自测提示词:

我当前的学习阶段是:[快速扫盲 / 边做边学 / 刻意内化]。
这是我当前学习周期学的内容清单:
- [内容 1]
- [内容 2]
- [内容 3]

我实际做过的产出是:[项目、代码、文章或演示]。
我仍然含糊的地方是:[列出;没有把握也可以写"不确定"]。

请基于以上信息给我出 10 道"能对着空气流利说出即算过"的自测题。
要求:
1. 覆盖概念边界、底层机制、方案取舍、故障诊断和验证方法;
2. 优先追问我可能自以为懂、其实没懂的地方,不要考名词背诵;
3. 难度匹配我当前阶段,并至少包含 3 道结合实际产出的场景题;
4. 先只出题,不要给答案。我逐题口述后,再指出错误、遗漏和含糊表述,
   给出最小补课动作,最后整理成下一轮自测要重点复查的缺口清单。
五条铁律 + 日节奏不要等 · 不要抄 · 要动手 · 要记录 · 要输出。日节奏不必锁死时长:先做一次短回顾,把主要精力放在项目推进,结束前记录新概念、未解问题和当天产出;每个学习周期再按五步扩展引擎第⑤步复盘,让当天记录变成下一轮刻意练习和动态自测的输入。
