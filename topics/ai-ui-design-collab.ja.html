導入 00

全景：なぜ2026年にこの取り組みが「必須」となったのか

デザイン・コードの溝：ツールの問題ではなく構造の問題

2024年以前、デザイナーは Figma でピクセル単位の仕様を注記し、開発者はそれを見ながらコードを一から書き直していました。汎用 AI コーディングツール（初期の Copilot など）は「Web 全体で学習したパターン」に基づいて「それっぽい」コンポーネントを生成するだけで、あなたのデザインシステムを認識することはできませんでした。出力されたコードは「デザイン稿の遠い親戚」のようなもので、配色が微妙にズレていたり、余白が数ピクセル異なっていたり、ホバー状態の仕様が抜けていたりと、修正する手間のほうがゼロから書くよりも大きくかかっていました。

2026年、3つの技術が同時に成熟し、この溝は無視できるレベルまで縮まりました：

  1. MCP（Model Context Protocol）がデファクトスタンダードに——pen.dev、Figma、Google Stitch が公式に MCP サーバーを提供。Claude Code や Codex に設定するだけで、デザインの正確な構造、トークン、ノード関係を「直接読み取る」ことが可能になり、画像からの推測が不要になりました。
  2. デザインツールが「ビジュアル + コード」のデュアル出力をネイティブサポート——pen.dev の .pen ファイルは JSON 形式で Git による diff が可能。Figma の Dev Mode + Variables は構造化データを公開。Stitch / Galileo はコンポーネントコードを直接生成します。
  3. 実機・仮想スクリーンショット回帰テストのコストがゼロに——Paparazzi / Roborazzi が JVM 上で Compose のレンダリングを実行。AI が UI を修正した後、30秒以内に全デバイスのスクリーンショットを取得でき、フィードバックループが極めて短縮され CI への組み込みが容易になりました。
本ページで習得できること読み終えた後に実践できること：① 任意のデザインツール（pencil / Figma / Stitch）に MCP を設定し、Claude Code から直接読み取らせる；② Figma Variables → Material 3 Color Scheme → Compose Theme を一貫して連携させる；③ AI が UI を修正した際、Paparazzi / Roborazzi で自動 diff 回帰テストを実行する；④ どのタスクを AI に任せ、どのタスクを手動で書くべきかを的確に判断する。

前提として合意しておくべき3つの原則

  • デザイン稿は「一等市民（ファーストクラス）」の入力である——PR、Issue、CLAUDE.md と同格です。単なる参考画像ではなく、信頼できる唯一の情報源（Source of Truth）です。
  • デザイン トークンはビジュアルに優先する——AI が色を変更する場合、特定の 16 進数カラーコードではなく colorScheme.primary を修正します。余白を変更する場合、16.dp ではなく Spacing.md を修正します。
  • 回帰テストには低コストなフィードバックループが必須——AI が30秒で作成した PR を人間がすべて目視で確認するのは不可能です。スクリーンショットの自動 diff 比較と主要プロパティのアサーションに頼り、異常時のみ人間にエスカレーションする仕組みが必要です。

マップ 02

AI エージェントがデザインを「見る」仕組み：3つの経路

AI コーディングエージェント（Claude Code、Codex 等）がデザイン入力を受け取る方法は、本質的に3つの経路しかありません。それぞれの違いを理解して使い分ける必要があります：

経路代表例取得できる情報精度コスト / 代償
MCP 構造化 Figma MCP、pen.dev MCP、Stitch MCP ノードツリー、トークンのキーバリュー、コンポーネントインスタンス、変数定義、アクセシビリティ属性 損失ゼロ——レンダリング画像ではなく構造化データを取得 MCP サーバーの起動が必要；ツールごとに提供機能が異なる
視覚（ビジュアル） スクリーンショット / 写真 / 画面録画；Claude / GPT のマルチモーダル 見た目の印象、大まかな要素配置 中——色味は正確に把握できるが、具体的な数値（正確な余白、フォントサイズ）は推測になる 高速・依存関係なしで常時利用可能；トークンは直接取得できない
エクスポート成果物 Figma Dev Mode「Copy as Compose」、pen.dev「Export React」、Stitch「Export to Code」 デザインツール自体が生成したコードスニペット 高（ただしツールの固有制約あり） 単発のコピー＆ペーストであり、双方向同期ができない
MCP は 2026 年の「分岐点」MCP を使用すると、Claude Code はコード生成時に「Figma 側で brand/primary/500 と定義されているため、プライマリカラーには colorScheme.primary を使用する」と判断できます。一方、MCP を使わない場合、スクリーンショットを見て「ここは青色を使う」としか言えません。前者はデザインシステム協調であり、後者はピクセル模倣です。以降の解説はすべて MCP 経路を前提とします。

3つの経路の具体的な接続手順

① Figma MCP（公式 · 最も安定）

# 公式プラグインのインストール（推奨・最速）
claude plugin install figma@claude-plugins-official

# または手動で MCP サーバーを追加
claude mcp add --transport http figma https://mcp.figma.com/mcp

# 接続の確認
claude mcp list
# figma / connected と表示されれば完了

Figma ファイル内で任意の Frame を選択し、Claude Code で「Figma MCP を使ってこの Frame の構造と変数を読み取り、対応する Compose 実装を生成してください」と指示すると、ツールが自動で呼び出されます。主要なツール：

ツール名機能説明
get_design_context構造化された React + Tailwind 表現を返す（Web に最適。Android は後続で変換）
get_variable_defsVariables（カラーパレット、フォントサイズ、余白）および Light/Dark モードを抽出
get_metadata高レベルなノードマップ：どの Frame、どのコンポーネントか、階層関係を取得
get_screenshotビジュアル参照（ピクセル単位）

Codex の場合は config.toml の [mcp_servers.figma] セクションに url = "https://mcp.figma.com/mcp" を追加することで同様に利用できます。

② pen.dev MCP（ネイティブ、ローカル、クラウド不要）

VS Code 拡張機能 highagency.pencildev をインストールすると、pen.dev 付属の MCP サーバーがローカルマシン上で実行されます。デザインデータがローカル外に出ないため、セキュリティやプライバシーに厳しい要件に適しています。Claude Code / Codex で /mcp から pencil を認識させた後は、ノードの読み取り、直接修正、変数の取得、スクリーンショットなど、より細やかなツールセットが利用可能です。詳細は pen.dev × Claude Code 特集を参照してください。

③ 視覚経路（常時使えるフォールバック）

MCP が利用できない場合の最も素朴かつ汎用的なアプローチです。デザインのスクリーンショット（または PDF）を Claude Code に直接渡し、「スクリーンショットに基づいて Compose を生成し、色値には Material 3 ColorScheme のセマンティック名を使用すること」と指示します。ピクセル情報は得られますが、トークン情報は得られません。そのため、Figma Variables のエクスポートを補完するか、生成されたコードの配色がブランドカラーと微妙に乖離するリスクを受け入れる必要があります。

Codex における MCP の現状Codex 0.146.0 以降で MCP（Claude Code と同等のプロトコル）がネイティブサポートされ、config.toml の [mcp_servers] で設定可能です。UX の違いとして、Codex は「タスク完遂型」であり「Figma Frame を読み取った後、直接 Android プロジェクトを修正せよ」と明確に指示する必要があります。一方、Claude Code は「対話・探索型」であり、「なぜこの色に secondary ではなく primary を使うのか」を対話しながら進めることができます。

なぜ3ステップではなく5ステップなのか？ステップを削ると、トークン同期が欠落する（デザインが変更されてもコードに反映されない）か、回帰テストが欠落する（AI が行った UI 変更を誰も検証しない）ことになります。これら5つのステップは並行して進めることはできますが、省略することはできません。

STEP 1 · デザイン トークン：Figma Variables が真のソース

デザイン トークンとは、色、フォントサイズ、余白、角丸などの値をセマンティックに命名したものです。Figma 内では以下のように定義されます：

brand/primary/500      → #476810
brand/primary/600      → #3a5609
brand/secondary/500    → #586a4f
surface/background     → #fefbff
surface/onBackground   → #1b1c18
text/display/large     → 57sp / 64lh
text/title/medium      → 16sp / 24lh
spacing/xs             → 4dp
spacing/md             → 16dp
radius/lg              → 16dp

このステップは Figma 側で Material Theme Builder（material.io/material-theme-builder）または公式の Material 3 Design Kit を用いて行います。Claude Code はこの段階では直接何もしませんが、後続で活用される構造化コンテキストとして機能します。

STEP 2 · コンポーネント / 画面：Figma Frame が契約

実装対象の各画面は Figma 内で1つの Frame として定義し、命名規則を一貫させます（開発側が識別キーとして利用）：

📁 Figma: App / 1.0
  📄 Page: ProductDetail
    🟦 Frame: ProductDetailScreen / 360×800 (mobile)
    🟦 Frame: ProductDetailScreen / Dark

Auto Layout（Figma の Flexbox 相当）と 100% 拘束を使用することで、Claude Code が get_metadata を読み取った際に、絶対座標ではなく構造化されたレイアウト情報を取得できるようになります。

STEP 3 · 読み取り + 計画：Claude Code / Codex の起動

既存の Android プロジェクトルート（app/ ソースが存在する場所）で Claude Code を起動し、明確な指示を与えます：AI に「適当に考えて」進めさせるのではなく、何を読み取り、どこへ書き込み、何をテストするかを厳格に指定します。

PROMPT 03-A · 起動プロンプト
figma MCP を使用して、Figma Frame `ProductDetailScreen` (node-id 1:23) を読み取ってください。 - まず get_variable_defs を呼び出し、すべての Variables を app/src/main/java/.../theme/Color.kt および Type.kt に反映（セマンティック名は Material 3 に準拠） - 次に get_design_context と get_metadata を呼び出し、Frame の構造を把握 - その後、以下の計画を策定：1) 作成する Composable；2) 作成する Preview；3) 作成する Paparazzi テスト；4) リポジトリにコミットする Preview スクリーンショット - 計画は ExitPlanMode で提示し、私の承認を得てから実装に進むこと。直接コード変更を開始しないでください
なぜ「コードを書く前に計画する」のかClaude Code の Plan モード（Shift+Tab で切替）は、コードベースを事前に探索し、レビュー可能な実施手順を生成してから実行します。UI の変更は手戻りが発生しやすい領域です——最初の一歩を誤ると、後続のスクリーンショットテストがすべて赤（失敗）になります。2分かけて計画をレビューすることは、20分の手戻りを防ぐことにつながります。Codex の --plan モードでも同様です。

STEP 4 · コード生成：Compose + テスト + スクリーンショットの3点セット

AI は実際に以下の3種類の成果物を出力します。どれか1つでも欠けてはなりません：

  1. Composable 関数——ビジネスコンポーネント。ハードコードを排除しトークンを使用することが重要（Color(0xFF476810) ではなく MaterialTheme.colorScheme.primary）。
  2. @Preview アノテーション——Android Studio の Design プレビューパネルで即座に確認可能にし、Roborazzi がこのアノテーションをスキャンして自動的にスクリーンショットテストを生成。
  3. Paparazzi / Roborazzi テスト——ベースラインのスナップショットを保存し、以降の AI による UI 変更時に同じベースラインで diff 比較。
PROMPT 03-B · 実装プロンプト
計画に沿って実装を進めてください。制約事項： 1. Composable は Material 3 API を使用し、すべての色・フォント・余白は MaterialTheme.colorScheme / typography / shapes 経由で取得すること 2. カラーコードのハードコードは禁止。余白は Spacing.xs/sm/md/lg 定数を使用すること 3. 各画面コンポーネントに @Preview(name = "Light") および @Preview(name = "Dark", uiMode = UI_MODE_NIGHT_YES) を付与すること 4. src/test/.../ProductDetailSnapshotTest.kt を追加し、Paparazzi で 2 つの Preview を実行。まず recordPaparazzi でベースラインを記録すること 5. 完了後、./gradlew verifyPaparazziDebug を実行して結果を報告してください

STEP 5 · 視覚回帰テスト：Paparazzi / Roborazzi の選択

このステップはパイプライン全体の品質ゲートです。詳細は 実機・仮想スクリーンショット回帰テスト の章で解説します。要点は一つ：AI が UI を修正する前にベースラインを用意し、修正後に自動 diff 比較を行い、異常時のみ人間に通知することです。

エンドツーエンド 04

Figma → Material 3 トークン：標準的な連携ブリッジ

Material 3 の ColorScheme / Typography / Shapes は Compose における第一級のデザイン トークンです。Figma Variables はデザインツール側における第一級のデザイン トークンです。両者を厳密に 1 対 1 で対応させなければ、「デザインが修正されたのにコードに反映されない」問題が必然的に発生します。

公式の標準プラクティス：Material Theme Builder

  1. m3.material.io/theme-builder でベースカラーとセカンダリカラーを選択。ツールが自動的に M3 カラーパレット（各ロールに対して13階調のトーン）を展開。
  2. 「Jetpack Compose」形式でエクスポートし、Color.kt（5つのキーカラーと派生ロール）および Theme.kt（lightColorScheme(...) / darkColorScheme(...)）を取得。
  3. これら2つのファイルを app/src/main/java/.../ui/theme/ に配置。
  4. MainActivity 内で AppTheme（または独自定義のテーマ）で setContent { ... } をラップ。
  5. 同一の「ベースカラー + セカンダリカラー」を Figma の Material 3 Design Kit にも設定（プラグインの同期機能を利用）し、Variables を自動一致させる。

Typography と Shapes の連携

M3 Typography は 15 個の TextStyle（displayLarge/Medium/Small、headlineLarge/...、titleLarge/...、bodyLarge/...、labelLarge/...）で構成され、Shapes は 5 個の RoundedCornerShape（extraSmall/small/medium/large/extraLarge）で構成されます。

Figma 側では公式の Figma Material 3 Design Kit コンポーネントを使用し続けることが重要です。Text Styles と Shape の命名が M3 と一致しているため、Claude Code が get_metadata を読み取った際に直接マッピングできます。

ダイナミックカラー（Material You）とブランドカラーのバランスAndroid 12+ 端末ではシステム壁紙からのカラー抽出（dynamicLightColorScheme(LocalContext.current)）が利用可能ですが、ブランドカラーを上書きさせるかどうかはプロダクト判断です。一般的なアプローチ：① 強固なブランドの場合 → ダイナミックカラーを無効化し、常にブランド ColorScheme を使用；② 一般コンシューマー向けの場合 → ダイナミックカラーを有効化し、1〜2色のブランド強調色のみを ExtendedColors として個別定義。Claude Code / Codex に指示する際は、CLAUDE.md / AGENTS.md にこの方針を明記してください。

規律 1：トークン優先、ハードコードの絶対禁止

規律 2：状態変更はすべて State hoisting（状態の巻き上げ）を行う

AI はコンポーネント内部で直接 remember { mutableStateOf(...) } を抱え込むコードを生成しがちです。これではプレビューは動いても、実際の業務コードでは状態制御が破綻します。原則：ステートレスな Composable を最優先とし、状態は呼び出し元から引数で渡し、イベントはコールバックで通知します。

規律 4：コードからデザインシステムへの書き戻し

デザイナーが Figma を修正し、Claude Code が Compose を修正するのが順方向です。では逆方向はどうでしょうか？Compose を修正して実装が完了した後に「ボタンの角丸が Figma と一致していない」と判明した場合、どちらがどちらを更新すべきでしょうか？

ルール：先にマージされた側が同期の責任を持つ。Figma が真のソースなら Figma を変更し、コードが先行したなら Figma Variables を更新します。両方を手動で変更し、どちらが正しいか分からなくなる状態を絶対に避けます。

具体的な書き戻しフロー（Figma が真のソースの場合）：

  1. デザイナーが Figma で Variables を修正（例：brand/primary/500 を #476810 から #507810 へ変更）。
  2. デザイナーはCompose コードを直接修正せず、Slack やコメントで「primary を変更したので PR を確認してください」と通知。
  3. Claude Code が Figma MCP の get_variable_defs を読み取り → Color.kt と比較 → パッチを生成 → PR を作成。
  4. PR の CI で Paparazzi 回帰テストを実行 → 差分が問題なければマージ。予期せぬ diff があればデザイナーに確認。
双方向同期の潜む落とし穴デザイン トークンの同期は通常の業務コードと異なり、単一画面だけでなくプロダクト全体のビジュアルに影響を及ぼします。わずか1箇所のカラーコードの誤変更が、Paparazzi で一度に200枚の画像差分を引き起こす可能性があります。推奨：トークンの変更は独立した PR ブランチで扱い、社内テストビルドで十分に検証してから本番へマージしてください。これは AI エージェントの問題ではなく、ワークフロー設計の問題です。

実機・仮想スクリーンショット回帰テスト：AI UI 修正の安全弁

品質 07

双方向同期：デザインシステムを真に「生きたもの」にする

自動撮影とアサーションでフィードバックを短縮できます。時間は画面数・端末・環境に依存し、重要な操作と差分は人が確認します。

3つの同期パターン

① Figma → Code（順方向、最も標準的）

デザイナーが Figma を修正し、Claude Code が Compose を修正するパターンです。これまでの章で説明した内容がこれに該当します。重要な制約：デザイナーが Variables を更新した後は、Claude Code にキャッシュではなく get_variable_defs を再実行させてからコードを生成させる必要があります。

② Code → Figma（書き戻し、デザイナー主導のシナリオ）

エンジニアが ColorScheme を変更し、Figma 側を追従させたい場合の手段：

  • Claude Code で Figma REST API リクエストを生成——Figma 公式 API は Variables の更新をサポートしており、AI にリクエストボディを構築させてプッシュします（中程度の導入難易度）。
  • CSS スタイルの Token JSON をエクスポート（Style Dictionary / Theo）し、デザイナーが Figma プラグイン（Tokens Studio 等）で手動インポートします（導入難易度は低いが完全自動ではない）。

③ Figma ↔ Code 双方向（高度、中間層が必要）

Style Dictionary や Theo をトークンの唯一の信頼源（Single Source of Truth: JSON 1つ）として配置し、Figma 側は Tokens Studio プラグインで同期、Compose 側は Gradle プラグインで ColorScheme を生成します。1箇所変更すれば両側が自動で追従します。これが2026年におけるデザインシステムエンジニアリングの「理想形」ですが、インフラ構築に1週間程度の工数を確保できるチーム向けです。

現時点での空白領域：Figma ↔ pen.dev に公式の双方向同期は存在しない

2026-08-05 時点で一次ドキュメントを確認した結果：Figma Variables と pen.dev Variables の間には公式の「双方向同期」リンクは存在しません。pen.dev 公式プラグインから Figma へ変数をプッシュする仕組みも、Figma 側から .pen ファイル形式をネイティブに読み込むブリッジも提供されていません。両ツールとも変数を機械可読な JSON（Figma REST API、.pen ファイル）として公開していますが、1対1の公式インターフェースはありません。

もしデザインシステムが Figma と pen.dev の両方で運用されている場合、現在最も実用的な解決策は「4ホップ・ブリッジ」（DTCG JSON をハブとする構成）です：

Figma ←(Tokens Studio)→ DTCG JSON ←(Style Dictionary v4)→ .pen ファイル / Compose / iOS / Web

# 例 A: Figma Variables → ローカル JSON の取得
curl -sS -H "X-Figma-Token: $FIGMA_TOKEN" \
  "https://api.figma.com/v1/files/$FILE_KEY/variables/local" \
  | jq '.meta.variables, .meta.variableCollections' \

# 例 B: Figma Variables の色変更（POST、Tier 3 + Enterprise + file_variables:write スコープが必要）
POST https://api.figma.com/v1/files/{file_key}/variables
{
  "variableModeValues": [
    { "variableId": "VariableID:1:3", "modeId": "1:0",
      "value": { "r": 1, "g": 0, "b": 0, "a": 1 } }
  ]
}

# 例 C: Style Dictionary v4 による Compose 向けコンパイル

    buildPath: 'app/src/main/java/.../theme/',

await sd.buildAllPlatforms();

デザインシステム保守のための6つの規律

  1. トークン名はそのままドキュメントになる——gray-100 よりも surface/container/high を推奨。AI はセマンティック名を見ることで用途を理解できますが、カラーコードだけでは単なる「グレー」としか認識できません。
  2. Color.White などのシステムカラーを直接使用しない——すべての色は ColorScheme 経由で取得します。「どうしても白にしたい」場合でも colorScheme.surface を使用することで、ダークモード時に自動で反転されます。
  3. 余白は Spacing.xs/sm/md/lg/xl 定数を使用する——4 / 8 / 16 / 24 / 32 dp などを基準とし、Composable 内で直接 13.dp などを記述しないこと。
  4. 角丸は Shapes.small/medium/large を使用する——同様に RoundedCornerShape(7.dp) などのアドホックな記述を避けます。
  5. Typography は MaterialTheme.typography.* を使用する——fontSize = 17.sp などの直接指定を行わないこと。
  6. アイコンには Material Symbols または Lucide を使用する——SVG をあちこちに直接配置せず、Figma 側と R.drawable 側で同一のシンボル体系を使用し、プラットフォーム間で統一します。
PROMPT 07-A · デザイン規律の監査
src/main/java/.../ui 以下のすべての .kt ファイルをスキャンし、以下をリストアップしてください： 1. Color(0xFF...) を直接指定している箇所（MaterialTheme.colorScheme.* への修正候補） 2. Spacing 定数を参照せず .dp 数値を直接記述している箇所（Spacing.* への修正候補） 3. fontSize = N.sp を直接指定している箇所（MaterialTheme.typography.* への修正候補） 結果を3つの表に出力してください。確認の上、順次修正します。

  1. PR マージ率——AI が作成した PR のうち、一発でレビューを通過した割合。50% 未満の場合、AI が手戻りを生み出しています。

  4. デザイン トークン遵守率——コード内で色や余白がハードコードされている割合。目標は 5% 未満。15% を超える場合はトークンリファクタリングを計画すべきです。

① セマンティックカラー + Asset Catalog

HIG（Human Interface Guidelines）では「16進数のハードコードを避け、セマンティックカラーを優先すること」が強く推奨されています。セマンティックカラーは Dark Mode、Increase Contrast、Reduce Transparency に自動追従します。

// ✅ 正しい実装: セマンティックカラー / 独自 Color Set の利用

② カスタム Theme コンテナ（iOS 18+ @Entry マクロ）

Compose の MaterialTheme.colorScheme に対応するのが、iOS 18 で導入された @Entry マクロです。@Environment 経由でブランドトークン一式にアクセスできます：

@Entry struct BrandTheme {                           // 1) トークンコンテナの定義
  let primary: Color; let onPrimary: Color; let surface: Color
  let radius: CGFloat; let spacing: (xs: CGFloat, sm: CGFloat, md: CGFloat, lg: CGFloat)
}
extension EnvironmentValues { var brandTheme: BrandTheme { .default } }

@main struct MyApp: App {                            // 2) ルートでの注入（Compose の Theme ラッパーに相当）
  var body: some Scene {
    WindowGroup { RootView().environment(\.brandTheme, .light) }
  }
}

struct PrimaryButton: View {                         // 3) 子 View での取得
  @Environment(\.brandTheme) private var theme
  var body: some View {
    Text("Tap").foregroundStyle(theme.onPrimary)
      .padding(.horizontal, theme.spacing.md)
      .background(theme.primary, in: .rect(cornerRadius: theme.radius))
  }
}

⑤ AI コーディングエージェントの SwiftUI における実力と境界

率直に言えば、AI による SwiftUI 生成にはいくつかの明確な弱点が存在します（2026.8 時点）：

@theme {

  --color-brand-50:  oklch(0.97 0.02 120);
