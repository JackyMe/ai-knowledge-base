입문 00

전체 개요와 방법론

안정성 문제의 분류 지도

Android의 '비정상 종료/멈춤' 현상은 크게 4가지로 분류되며, 각 유형별 증거, 도구, 대처법이 완전히 다릅니다:

유형현상본질핵심 증거상세 섹션
Java/Kotlin Crash앱이 즉시 강제 종료됨미처리 예외가 콜스택을 거슬러 올라가 메인 스레드 최상단에 도달logcat 내 FATAL EXCEPTION 스택 트레이스02장
Native Crash앱이 즉시 강제 종료됨C/C++ 레이어의 비정상 시그널 (SIGSEGV, SIGABRT 등)tombstone 파일, *** *** 섹션 로그04장
ANR화면이 멈추고 시스템 '응답 없음' 팝업 발생메인 스레드가 블로킹되어 제한 시간 내에 중요 이벤트를 처리하지 못함/data/anr/ 디렉토리의 traces.txt, Vitals ANR 리포트03장
시스템 프로세스 강제 종료사용 중 홈 화면으로 튕기거나 백그라운드에서 조용히 사라짐Low Memory Killer(LMK)에 의한 OOM kill, 백그라운드 제한, 사용자 강제 중지ApplicationExitInfo의 프로세스 종료 이유 코드08장
초보자가 가장 많이 하는 오판'크래시 로그가 없는 강제 종료'의 대부분은 일반 Crash가 아닙니다. Native 크래시(tombstone 확인)이거나 시스템 프로세스 kill(ExitInfo 확인)입니다. 먼저 정확히 분류한 뒤 조사에 들어가야 합니다. 지도가 틀리면 모든 노력이 허사가 됩니다.

왜 해결해야 하는가: 플랫폼의 엄격한 레드라인

Google Play의 Android Vitals에서는 '불량 동작 기준치(Bad behavior threshold)'를 규정하고 있습니다. 사용자 감지 비정상 종료율 ≥ 1.09% 또는 사용자 감지 ANR 비율 ≥ 0.47%(전체 기기 기준)에 도달하면 앱은 스토어 전체에서 검색 노출도가 강등됩니다. 특정 단일 기기 모델에서 ≥ 8%에 달할 경우 해당 기기에서의 노출 제한과 함께 스토어 등록정보에 경고가 표시될 수 있습니다. 안정성은 단순한 기술적 완결성을 넘어 비즈니스 유입과 직결되는 핵심 지표입니다.

전 과정을 관통하는 5단계 해결 방법론

  1. 현상 보존 —— 가장 신뢰할 수 있는 원시 증거 확보: 완전한 스택 트레이스 / trace / 로그, 기기 정보, OS 버전, 앱 버전, 재현 절차. 불명확한 구두 보고만으로 작업을 시작하지 말 것.
  2. 특정 —— 스택 트레이스에서 '제1현장' 식별: 내 비즈니스 코드가 어느 프레임에 있는가? 난독화된 경우 먼저 mapping.txt로 복원(retrace)할 것.
  3. 원인 규명 —— "왜 이 코드 라인에 도달했는가"에 답하기: null은 어디서 유입되었는가? 락은 누가 쥐고 있는가? 메모리는 누가 차지했는가? 추측이 아닌 도구로 증거를 확보할 것.
  4. 근본 해결 —— 안이하게 try-catch로 예외를 덮어버리지 말고 상태와 불변식을 바로잡을 것. 수정 후에는 재현 테스트나 카나리 지표로 수정 사실을 증명할 것.
  5. 재발 방지 —— 동류 문제에 대한 방어선 구축: lint 규칙, StrictMode, CI 체크, 모니터링 알림. 하나의 버그를 잡았으면 동종 결함 전체를 박멸할 것.
추천 성장 경로입문자: 00→01→02 (NPE 수준의 일상 크래시 자력 해결); 중급자: 03→07 (ANR 및 프로덕션 티켓 격파); 고급자: 08장 이후 (재현 불가 난치성 버그 규명 및 AI 워크플로우 내재화).

당직 엔지니어: 발생 첫 30분 행동 체크리스트

시간필수 완료 작업산출물 / 의사결정
0~5분버전, 발생 시각, 영향 유저 수, 시작 즉시 크래시 여부/핵심 결제 플로우 중단 여부 확인. 관련 카나리 배포 일시 중지심각도 등급, 대응 TF/담당자 지정. 긴급 기준 도달 시 즉시 롤백 또는 Feature flag OFF
5~10분4대 분류 지도에 따라 트리아지: Java/Kotlin, Native, ANR, 시스템 프로세스 kill단일 핵심 증거 선택: stack / tombstone / trace / ExitInfo
10~20분3건 이상의 이벤트 샘플을 추출하여 mapping/Build ID 대조. 버전, OS, 기기, 국가, 커스텀 키 공통점 분석'확정된 사실'과 '미확인 항목' 목록 작성. 단일 샘플을 전체 원인으로 속단 금지
20~30분반증 가능한 가설을 최대 3개 수립하고 각 가설에 검증 명령, 담당자, 기한 설정카나리 지속/중지/롤백 결정. 팀에 미검증된 수정 약속 대신 1차 팩트 리포트 공유

실전 03

ANR 심층 해부: 메인 스레드 블로킹의 8대 원인

타임아웃 유형과 기준선

유형AOSP 기본 타임아웃첫 번째 점검 사항
Input dispatching5 초main 스레드가 연산 중인지, 락/Binder를 대기하고 있는지
Broadcast포그라운드 10초 / 백그라운드 60초 (Android 14+ CPU 부하시 20/120초)onReceive에서 무거운 I/O 실행 여부, goAsync() 미종료 여부
Execute service포그라운드 서비스 20초 / 백그라운드 200초onCreate/onStartCommand 내 블로킹 I/O 여부
ContentProvider클라이언트 요청 타임아웃원격 쿼리 지연, Binder 스레드 풀 고갈 여부

8대 빈출 근본 원인

  • 메인 스레드 I/O: 파일, SQLite, DNS, 네트워크, 대형 JSON 역직렬화;
  • SharedPreferences commit(): commit()은 동기 디스크 쓰기. apply()도 Activity 전환 시 QueuedWork에서 대기하여 ANR 유발 가능 → DataStore 전환 권장;
  • 락 경합 / 데드락: main 스레드가 백그라운드 스레드가 쥐고 있는 락을 기다리고, 그 스레드가 다시 main을 기다림;
  • 동기 Binder 블로킹: BinderProxy.transactNative에서 멈춤. system_server나 타 프로세스 병목;
  • 브로드캐스트/서비스 내 무거운 작업: onReceive에서 긴 작업 수행;
  • 레이아웃 폭풍: 과도한 중첩, 잦은 requestLayout, Jetpack Compose의 무한 Recomposition;
  • GC 스래싱 (GC Thrashing): 짧은 시간 대량 메모리 할당으로 메인 스레드가 빈번히 Stop-The-World 정지;
  • CPU 기아 (CPU Starvation): 백그라운드 스레드들이 CPU 100%를 점유하여 main 스레드가 스케줄링되지 못함.

traces.txt 분석 3단계

  1. "main" prio=5 tid=1 ...을 찾아 state=BLOCKED, WAITING, NATIVE, RUNNABLE 확인;
  2. waiting to lock <0x1234567> held by thread 12가 보이면 thread 12번의 스택을 찾아 락을 쥐고 있는 원인 파악;
  3. CPU 사용량에서 TOTAL: 98% (80% user + 18% kernel)이면 CPU 경합, TOTAL: 5%이면 I/O나 락 대기 블로킹으로 판정.

심화 08

난치성·간헐적 결함 추적 기법

간헐적 버그(Heisenbug) 공략 4대 무기

  1. ApplicationExitInfo 활용 (Android 11+): 앱 시작 시 activityManager.getHistoricalProcessExitReasons()를 호출하여 직전 프로세스가 REASON_CRASH_NATIVE, REASON_LOW_MEMORY, REASON_ANR 중 무엇으로 죽었는지 서버에 로깅;
  2. Custom Breadcrumbs 궤적 기록: 화면 이동, 네트워크 요청 시작/완료, DB 쓰기 직전 단계들을 Crashlytics 링버퍼에 기록하여 크래시 직전 10초간의 행동 경로 역추적;
  3. StrictMode 강화: 개발/QA 빌드에서 메인 스레드 디스크/네트워크 접근 및 Activity 누수 발생 시 즉시 감지;
  4. Monkey 스트레스 테스트 자동화: CI 파이프라인에서 매일 밤 10만 회 무작위 터치 주입.
