Mental Models 00

Everything Revolves Around Context

Claude Code is not a chatbot, but an agentic coding environment: it reads your files, runs your commands, edits your code, and autonomously advances problems while you observe, course-correct, or simply step away. The official Best Practices open by revealing the underlying constraint behind almost all practices—

Core ConstraintThe context window holds the entire conversation: every message, every file read, every command output. It fills up quickly, and model performance degrades as a result—once context is full, Claude will start "forgetting" earlier instructions and make more mistakes. Context is the resource you need to manage most, bar none.

Most conclusions in this guide can be derived from this one rule:

  • Why use subagents for research → Exploration consumes their context, not yours;
  • Why CLAUDE.md should be short → It loads in every session, if it's too long, rules get drowned in noise;
  • Why Skills are better than piling knowledge into CLAUDE.md → Skills load on-demand, you don't pay if you don't use them;
  • Why use /clear, /compact, /btw → They are all tools to free up context space;
  • Why "restart if correcting twice fails" → Failed attempts stay in context and will lead the model into the same pitfalls.

Mental Models 01

Five Golden Rules

The thousands of words in the official Best Practices can be condensed into five rules. Every single one is worth sticking to the side of your monitor.

Rule 1: Give Claude a self-running validation

Claude stops when things "look complete." Without an executable check, you are the validation step—every mistake waits for you to discover it. Give it a signal that produces pass/fail (test suite, build exit code, linter, visual regression), and the loop closes automatically: do work → run checks → read results → iterate until passing.

❌ Weak"Implement an email validation function" / "The build broke, fix it"
✅ Strong"Write validateEmail, test cases: user@example.com→true, invalid→false, user@.com→false. Run tests after implementing" / "Build failed with [paste error]. Fix and verify the build passes. Solve the root cause, don't just suppress the error"

Four tiers of validation strength, progressing by level of autonomy: request "run check and iterate" in the same prompt → use /goal to set conditions for the evaluator to check every turn → use a Stop hook to make checks a hard gate (cannot end turn without passing) → let a validation subagent provide a second opinion with fresh context. Also: demand Claude show evidence (test output, command return, screenshots) rather than just claiming success.

Rule 2: Explore first, plan next, code last

Jumping straight into coding often solves the wrong problem. The recommended four-step approach: Explore (read files, ask questions in plan mode, no coding) → Plan (produce implementation plan, use Ctrl+G to edit the plan directly in editor) → Implement (exit plan mode to implement, self-verify against plan) → Commit (write clear commit messages, open PR).

Don't treat plans as dogmaLet it directly handle well-defined small changes (fixing typos, adding logs, renaming). The official heuristic: If you can describe what the diff looks like in one sentence, skip the plan. Plans are most valuable when: the solution is uncertain, multiple files are involved, or you are unfamiliar with the codebase.

Rule 3: Be specific with prompts, feed enough context

Claude can infer intent, but it cannot read minds. Name specific files, specify constraints, and point to existing patterns:

StrategyWeak PromptStrong Prompt
Scope bounds"Add tests for foo.py""Write tests for foo.py covering edge cases when the user is logged out. Do not use mocks"
Point to sources"Why is this API so weird?""Check the git history of ExecutionFactory and summarize how this API evolved into its current state"
Reference patterns"Add a calendar component""Reference the implementation pattern of existing widgets on the homepage (HotDogWidget.php is a good example), and implement the calendar component accordingly... do not introduce new dependencies outside the codebase"
Describe symptoms"Fix login bug""Users report login fails after session timeout. Check the auth flow in src/auth/, focusing on token refresh. Write a failing test that reproduces this first, then fix it"

Five ways to feed context: @file reference (Claude will read before answering), direct paste image (Ctrl+V), provide a URL (whitelist common domains via /permissions), pipe input (cat error.log | claude), or let it fetch it itself (run commands / MCP / read files).

Rule 4: Course-correct in small steps, clear context often

  • Esc interrupts at any time, context is preserved, direction can be changed immediately;
  • Esc Esc / /rewind opens the rollback menu: restore conversation, restore code, or both;
  • "Undo that" makes it revert its own changes;
  • /clear is a must between unrelated tasks; if two corrections for the same issue fail, don't get stuck—a /clear followed by a better prompt incorporating lessons learned almost always beats a long session stuffed with failed attempts.

Rule 5: Let it interview you first (essential for big features)

For large features, don't rush to give instructions. First, have Claude interview you using the AskUserQuestion tool:

I want to build [brief description]. Use the AskUserQuestion tool to interview me in detail about:
technical implementation, UI/UX, edge cases, concerns, and trade-offs. Don't ask obvious questions,
dig into hard problems I might not have considered. After asking, write the complete spec into SPEC.md.

After finalizing the spec, start a new session to execute: a clean context focuses entirely on implementation, and SPEC.md acts as a readily available anchor. A good spec inherently contains three elements: naming involved files and interfaces, explicitly stating what NOT to do, and ending with an end-to-end validation step.

Standard Five Steps When Entering a New Repo

  1. /init —— Analyze the codebase (build system, test framework, code patterns) to generate an initial CLAUDE.md draft, then use /memory to continuously refine it.
  2. /permissions —— Set up allow/ask/deny rules, put safe commands like npm run lint, git diff in the whitelist (or just run /fewer-permission-prompts to auto-generate a whitelist based on your history).
  3. /mcp —— Connect external tools needed for the project (Database, Figma, Notion, Sentry...).
  4. Install gh CLI —— Claude naturally uses it to create issues, open PRs, and read comments; without it, it can only call bare APIs and often hits rate limits.
  5. /statusline —— Configure the status bar to continuously display context usage (Rule Zero: always know how much context you have left).
CLAUDE.md Trade-off Standard (Official)Ask line-by-line: "If I delete this line, will Claude make a mistake?" If not, delete it. What to write: Unintuitive build commands, non-default coding styles, test execution methods, branch/PR conventions, project-specific architecture decisions, environment pitfalls. What NOT to write: Things obvious from reading the code, language common sense, detailed API docs (provide links instead), frequently changing info, "write good code" platitudes. Direct consequence of an overly long file: important rules drown, instructions get ignored. Use @path/to/file syntax to import other files; Hierarchy: ~/.claude/CLAUDE.md (Global) → Project root (Team shared, goes in git) → CLAUDE.local.md (Personal, goes in .gitignore) → Subdirectories (Loaded on demand).

Extension System 05

How to Choose Among the Six Extensions

Claude Code's extension system has six layers. Choosing the wrong layer is the biggest source of internal friction for beginners—like putting rules that belong in a Hook into CLAUDE.md and praying it follows them, or stuffing domain knowledge that is only occasionally used into every session. One decision table explains it all:

Your NeedWhich Layer to UseCore Reason
Short facts needed for every session (build commands, coding conventions)CLAUDE.mdAutomatically loaded per session—so it must be short
Domain knowledge used only in specific scenarios / repetitive multi-step processesSkillsLoaded on-demand, takes up no context if unused; can be manually invoked via /name
Rules that must 100% happen (enforcing linting, prohibiting writing to sensitive files)HooksDeterministic execution. Prompts are "requests", Hooks are "guarantees"
Research involving reading large numbers of files / review requiring an independent perspectiveSubagentsIndependent context window, exploring without polluting the main conversation
Connecting to external systems (Databases, Figma, Slack, Monitoring)MCPStandard protocol for tools, configure once and use everywhere
Packaging and distributing all the above to the teamPlugins1-click installation of skills+hooks+subagents+MCP; browse the market via /plugin
One-Sentence Mnemonic (Community Consensus)To force it, use Hooks or permission rules; if it's knowledge, use Skills; for isolation, use Subagents; for persistence, streamline and put it in CLAUDE.md; to connect externally, use MCP; to distribute, package as a plugin.

Skills / Hooks / MCP / Subagents: In-Depth on the Core Four

Skills: On-Demand Expert Skill Packs

One skill = one directory + one SKILL.md (can include templates, examples, scripts). Claude automatically loads it when matching the scenario, or you can invoke it manually with /skill-name. Signals that you should create a skill: You are repeatedly pasting the same instructions/checklists/processes, or a section in CLAUDE.md has grown from "facts" into a "process".

.claude/skills/my-skill/
├── SKILL.md        # Required: frontmatter + instruction body
├── examples/       # Optional: expected output examples
└── scripts/        # Optional: executable scripts
LocationScope
~/.claude/skills/Personal, all projects
.claude/skills/ (Project)This project (shared with team once in git); monorepo subdirectories are also discovered on-demand
skills/ inside pluginWhere plugin is enabled, namespace plugin-name:skill-name

Three advanced mechanics:

  • Dynamic Context Injection: Write !`git diff HEAD` in the body, which executes the command before loading the skill and inlines the output into the instructions—the skill inherently "knows the scene";
  • Frontmatter Control: disable-model-invocation: true ensures dangerous processes (like deployment) can only be triggered manually; description determines the auto-trigger accuracy when written as "routing rules";
  • Skill Directory Hot Reload: Changes to disk files take effect immediately; same-name priority is Enterprise > Personal > Project > Bundled Skills (so placing a code-review skill in the project overrides the official version).
Community Patterns for Writing Good SkillsWrite the description clearly like a routing rule stating "when to use me"; delegate deterministic work to included scripts rather than relying on model interpretation; keep SKILL.md lean and push details to on-demand auxiliary files; one skill does only one thing; provide specific positive/negative examples instead of stacking abstract rules.

Hooks: Deterministic Guardrails

Instructions in CLAUDE.md and skills are suggestions; things that must happen belong in Hooks. Hooks run scripts on lifecycle events and can block actions by exiting with code 2. Common events:

EventTimingTypical Usage
PreToolUseBefore tool invocation (blockable)Prohibit writing to .env/secret files, intercept dangerous commands
PostToolUseAfter successful tool invocationAuto-run prettier/eslint after every edit
StopClaude is about to end its turnRun tests, and block completion if they fail (allows passing after 8 consecutive blocks)
UserPromptSubmitAfter you submit prompt, before Claude processes itInject environment info, sensitive word check
SessionStart / SessionEndSession start/endInitialize environment / cleanup and reporting
PostToolUseFailure / PreCompact / SubagentStop / FileChanged…More granular eventsFailure alerts, pre-compact archiving, file change listening, etc. (30+ events, see official Hooks reference)
// .claude/settings.json —— Auto-format after every edit
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit",
        "hooks": [ { "type": "command", "command": "npx prettier --write \"$FILE\"" } ] }
    ]
  }
}
The Right Way to be LazyHooks can let Claude write for you: "write a hook that runs eslint after every file edit", "write a hook that prevents writing to the migrations directory". Use /hooks to view configured items.
A Safer Approach than HooksTo prevent reading sensitive files, permission rules are better than Hooks: deny rules (like Read(./.env), Read(./secrets/**)) make files directly "invisible" to Claude. Permission evaluation order: deny → ask → allow.

Subagents: Avatars with Independent Contexts

Defined in .claude/agents/*.md, having their own context window, toolset, and system prompt. Two main uses:

  • Research Isolation: "Use a subagent to investigate how the auth system handles token refresh"—it reads dozens of files, and your main context only receives a summary of conclusions;
  • Unbiased Review: A brand new context looks at the diff without being biased by "the thought process of just having written this code". Official recommended adversarial review prompt: explicitly ask for work to check, the plan to compare against, and what counts as a problem—"report gaps, do not report style preferences".
# .claude/agents/security-reviewer.md
---
name: security-reviewer
description: Code security review. Use proactively after code changes.
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review for: injection vulnerabilities (SQL/XSS/Command Injection),
authentication and authorization flaws, secrets in code, and insecure data handling.
Provide specific line number references and fix suggestions.
/btw and Subagents are Mirrors of Each Other/btw sees the entire conversation but has no tools (ask "known things"); subagents have all tools but start from an empty context (go "research new things"). Choosing the right direction saves half the context.
Common Malady of Review AgentsReviewers asked to find problems will always "find" problems—even if the work is flawless. Chasing every finding leads to over-engineering. Set rules for reviewers: only report gaps that affect correctness or stated requirements, treat the rest as optional.

MCP: Connecting the External World

MCP (Model Context Protocol) allows Claude Code to directly connect to external systems like databases, Figma, Slack, Sentry, etc. Configuration is not in settings.json—this is the most common point of confusion.

Adding and Managing

# Add a local stdio server
claude mcp add my-tool -- npx -y some-mcp-server

# Add a remote HTTP server
claude mcp add --transport http api-tool https://example.com/mcp

# Servers requiring OAuth go through separate authentication
claude mcp login api-tool

# In-session: /mcp to view status, authenticate, start/stop a server

Three Practical Disciplines

  • Tools also consume context: Tool definitions for every MCP server enter the window; the more you connect, the more crowded it gets—use /context to check usage, and disable unused servers in /mcp;
  • Treat MCP content as untrusted input: Text returned by external tools might contain injected prompt instructions. Use auto or manual mode instead of blind trust.

Eight Core Scenarios Playbook

🧭Scenario ① Onboarding to an Unfamiliar CodebaseONBOARDING

Ask directly as if asking a senior colleague, without any special prompts: "How is logging implemented?", "What's the process to create a new API endpoint?", "What does async move on line 134 in foo.rs do?", "Why is foo() called here instead of bar()?". If you want to trace history, point to git: "Review the commit history of this module and summarize why it's designed this way."

Combo: Use a subagent for large-scale discovery ("Use a subagent to trace the call chain of the entire payment module"), keeping only the conclusions in the main context; use /init to persistently save discovered conventions into CLAUDE.md.

🏗️Scenario ② Developing New FeaturesFEATURE

Standard pipeline: Interview for SPEC (Rule 5) → New session → /plan for exploration & planning → Ctrl+G to edit plan → Exit plan mode to implement → Verify against SPEC → Commit and open PR.

Key details: Include verification in implementation instructions ("Implement the OAuth flow in the plan, write tests for the callback handler, run tests, and fix any failures"); use /goal all tests green to attach acceptance criteria at the session level; when done, double-check with /code-review + "use a subagent to check for gaps against SPEC.md".

🐛Scenario ③ Debugging and Bug FixingDEBUG

Golden template: Symptom + Suspected location + Definition of "fixed"—"Users report login fails after session timeout. Check token refresh in src/auth/. First write a failing test that reproduces the issue, then fix it, and verify the test passes."

Efficiency tricks: Pipe errors directly in via cat error.log | claude -p "analyze root cause"; run tests using ! npm test (shell passthrough, output automatically enters context and gets analyzed); demand to "fix the root cause, do not just suppress the error"; after fixing, ask it to present test output as proof.

🔍Scenario ④ Code ReviewREVIEW

Choose from four tools as needed: /code-review (find bugs in local diff, --fix to fix directly; as of v2.1.223, /review is its alias), /simplify (cleanup only: reuse/simplify/remove redundancy), /security-review (security focused), /code-review 123 (quickly review GitHub PR). For deep needs, use /code-review ultra for cloud-based multi-agent review.

Dual-session mode: Session A writes code, Session B (fresh context) reviews—"Review @src/middleware/rateLimiter.ts, looking for edge cases, race conditions, and consistency with existing middleware patterns", then feed B's output back to A for fixing. Same for writing tests: one writes the tests, another writes the implementation.

🚚Scenario ⑤ Large-Scale Refactoring / MigrationMIGRATION

Interactive: A single command /batch migrate src/ from Solid to React—automatically breaks down into 5–30 independent units, each with a background subagent + independent worktree, implementing-testing-opening PRs independently.

Scripted (fan-out): First ask Claude to list all files to be migrated → pick 2–3 for trial runs to tune the prompt → full loop:

for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue, return OK or FAIL" \

done

Key points: --allowedTools narrows permissions, output conventions are machine-parsable (OK/FAIL), prototype first before scaling up.

Practice 08

Advanced Context Management

In the Era of 1M Context, Does This Still Apply?

The core constraints at the beginning of this page were written in the "context easily runs out of space" era, while models like Sonnet 5 / Opus 5 now feature native 1M context natively—these two points may seem contradictory, but the conclusion remains unchanged, only the underlying reasoning has shifted.

Stance: Still applies, but transitions from "won't fit" to "not worth it"The past issue was a physical limit: a 200K window quickly filled up with files and command outputs, making it impossible to continue without compacting. A 1M window pushes this physical limit out 5x, but it doesn't eliminate two inherent costs that were previously overshadowed by the "won't fit" problem: ① Every turn requires sending the entire history again—as the official costs documentation states, "Claude Code sends your full conversation with every message". The larger the window and the more history accumulated, the more a single follow-up question costs for the entire history, scaling linearly with conversation length; ② Compacting inherently loses details—specific instructions from early in the conversation not written to CLAUDE.md will likely be lost after compaction (official statement: "instructions from early in the conversation can get lost", detailed below). 1M buys you headroom to avoid "sudden cut-offs," not permission to "set it and forget it".

The only thing that can be relaxed: For short sessions and tasks that can be wrapped up in a day, you no longer need to nervously /compact manually every time you read a large file like in the 200K era—chances are you won't hit the auto-compaction threshold for the entire task (specific numbers below). But for scenarios involving cross-day recovery, long-running tasks, or cases where you care about the cost of each message (CI pipelines, unattended background agents), the following four methods are still the right approach, and none should be skipped. Currently, 1M context is only natively active on models like Sonnet 5 / Opus 5 / Fable 5; do not assume you have a 1M window without checking the model, always rely on what /context actually displays. v2.1.223 Behavior Change: Claude models with a native 1M window are by default restricted to 200K via auto-compaction (previously this only applied to a fixed list). Use CLAUDE_CODE_DISABLE_1M_CONTEXT to revert to the old behavior.

Diagnosis: See Clearly Before Acting

/context uses a colored grid to tell you what is occupying your window (which tools are heavy, if memory files are bloated, how much capacity is left), paired with the constant usage display in /statusline, keeping you informed.

Auto-Compaction: When It Acts and What It Discards

DISABLE_AUTO_COMPACT is currently just a lone line in the "Hidden Capabilities and Easter Egg Configurations" chapter on this page—it is actually the environment variable toggle for autoCompactEnabled (default true) in settings.json. When disabled, Claude will no longer automatically summarize; once the context is full, it will simply fail and abort. It is only suitable for scenarios where you actively monitor /context and manually /compact.

Trigger Thresholds (verified against official env-vars / model-config docs):

Model / ScenarioTrigger Point
Sonnet 5 (Native 1M, no 200K variant)Defaults to approx. 96.7%, i.e., approx. 967K / 1M tokens; controlled by CLAUDE_CODE_AUTO_COMPACT_WINDOW
Standard models without 1M context (e.g., Sonnet 4.6 / Opus 4.6)Approaching / Reaching 200K boundary
Other local sessions (e.g., running Opus 4.8 locally)Triggers as the conversation approaches the model's own context limit; no fixed percentage provided officially

CLAUDE_AUTOCOMPACT_PCT_OVERRIDE (values 1–100) can lower this percentage to trigger compaction earlier, but cannot increase it—if you want to know your true usage percentage, simply run /context rather than guessing "it's almost full".

What it Actually Does When Triggered: The official phrasing is "clears older tool outputs first, then summarizes the conversation if needed"—auto-compaction is essentially a two-stage rocket: the first stage only drops the contents of previously read large files or old command outputs—things that "you look at once and no longer need the original text for", leaving your instruction history intact; only if the first stage doesn't free up enough space does it trigger the second stage—compressing the entire conversation history into a structured summary. You might sometimes see usage drop significantly without the "Conversation compacted" prompt appearing, which likely means only the first stage occurred.

"Getting dumber after compaction" is not an illusionOfficial wording: "Your requests and key code snippets are preserved; detailed instructions from early in the conversation may be lost."—the summary preserves "what you want" and critical code snippets, but fails to preserve edge cases you highlighted early on unless those rules were written into CLAUDE.md (see table above, which reloads). The solution is not to complain about dumb compaction, but to move truly important constraints from "said once in conversation" into CLAUDE.md, or to set a summary strategy using /compact focus instructions before auto-compaction guesses for you.

There is also an edge case: if a single file or tool output is so massive that "every compaction instantly fills the context again," Claude Code will abort auto-compaction and error out after a few attempts, rather than falling into an infinite compaction loop—the official docs refer to this as a thrashing error. When this happens, don't expect clicking compress again to solve it; use a subagent or hook to extract that massive output first.

Using Files as External Memory

The Ralph loop in the "Practice Scenarios" chapter briefly mentions "using the file system rather than conversation history as memory," but didn't elaborate. The logic is quite simple: conversation history will be auto-compacted, cleared on /clear, and completely reset when starting a new session (sessions don't share history)—but files on disk do not. Explicitly writing state into files essentially creates a "source of truth" outside the context window that is immune to compaction, allowing you to Read it back whenever needed rather than relying on it hovering in the conversation.

Three common approaches:

  • SPEC.md: Already mentioned in Rule Five "Let it interview you first"—after finalizing specifications, write them to a file, start a new session to execute, giving the implementation phase a clean context. SPEC.md is an anchor point to check anytime, not something to memorize. A good SPEC.md has three elements: naming involved files and interfaces, clarifying what not to do, and ending with an end-to-end verification step.
  • NOTES.md / PROGRESS.md: For long-running tasks or Ralph-style loops, read before each turn starts, update before it ends—record "solutions confirmed viable," "dead ends eliminated," and "what to do next." Write them as checkable lists rather than narrative diaries, so after compaction or switching sessions, a new turn doesn't repeat the same mistakes.
  • The compaction strategy itself can be written in CLAUDE.md: The /compact prompt in the "Four Ways to Free Up Space" table above demonstrates this—"When compacting, always retain the complete list of modified files and test commands," this rule itself lives in a file, immune to any compaction.

The common thread among the three: none rely on "this sentence remaining in context," but rather "I can read this file again anytime."

Checkpoints: A Safety Net for Bold Trial and Error

Every prompt automatically creates a checkpoint, taking snapshots of file changes first. Esc Esc / /rewind can rollback only the conversation (if implementation is good but you want to phrase it differently), only code (if discussion was valuable but implementation needs changing), or rollback completely. Checkpoints persist with the session—you can close the terminal and still rollback tomorrow. Limitation: It only tracks changes made by Claude's editing tools; Bash commands and external process changes are excluded, it is not a replacement for git.

Sessions are Assets

Conversations are all kept locally: claude -c resumes the most recent, claude -r name accurately restores one, /rename gives it a branch-like name (e.g., oauth-migration), /branch forks in-place to test new directions, and --fork-session restores to a fresh slate without polluting the original. One named session per workflow, managing contexts just like git branches.

Three Rule Layers: deny → ask → allow

// .claude/settings.json —— A practical starter config
{
  "permissions": {
    "allow": [
      "Read", "Glob", "Grep",
      "Bash(npm run lint:*)", "Bash(npm run test:*)",
      "Bash(git status)", "Bash(git diff:*)"
    ],
    "ask":  [ "Bash(git push:*)" ],
    "deny": [
      "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"
    ]
  }
}
  • deny is evaluated first: Put sensitive files in deny, making them invisible to Claude—more thorough than blocking with Hooks;
  • Approval fatigue is a security risk: by the 10th "allow" you are no longer reviewing. The solution is whitelisting (/fewer-permission-prompts can auto-generate it) + OS-level /sandbox isolation, not toughing it out;
  • --dangerously-skip-permissions should only exist in isolated environments with no network or sensitive data (like running lint fixes in a container); enterprises can disable this globally via disableBypassPermissionsMode.

Syntax Cheat Sheet: What Each Pattern Matches

The rules like Bash(npm run lint:*), Read(./.env.*), Read(./secrets/**) in the above config are correct patterns you can copy, but without explaining the semantics of :*, ./, **, users can only guess. Here is a breakdown:

PatternMatches What (Correct)Do Not Assume (Wrong)
Read / Edit / Bash
Bare tool name		Matches every invocation of this tool, regardless of targetDon't assume "no rule means inactive"—a bare tool name is itself an allow-all / ask-all / deny-all rule.

Bash(npm run lint:*)

Edit(src/**)
As an allow rule		Single-segment directory, matches only <cwd>/srcDon't assume it matches packages/foo/src—behavior was tightened on 2026-07-18; previously it matched src anywhere in the tree.
Read(./secrets/**)
As a deny / ask rule		Also a single-segment directory, but deny/ask rules match secrets at any depth under the cwd (e.g., packages/foo/secrets is blocked)Don't treat single-segment behavior in allow and deny as identical—this rule in the example stays safe because it is deny; if it were allow, it would fall victim to the tightening in the previous row.
Edit(**/src/**)Explicit any-depth pattern, matches src anywhere in the tree for allow/deny/askDon't wonder if src/** is enough—if you want "everywhere", write it this way without guessing the rule type.

Example config is safe, but variations may breakThe Read(./secrets/**) in the deny section above is a single-segment pattern, but because it is a deny rule, the 2026-07-18 tightening does not affect it—it still blocks secrets at any depth. What was actually tightened is the same syntax in allow rules (e.g., Edit(src/**)): it now only allows <cwd>/src and won't allow nested directories with the same name. To cover any depth in an allow rule, you must explicitly use **/dir/**.

III. Priorities and "Why isn't it working"

When the same key conflicts: Enterprise Managed > CLI Args > .claude/settings.local.json > .claude/settings.json > ~/.claude/settings.json. Three common reasons for "changed it but nothing happened":

  • Changed the wrong layer: The project layer silently overrode your user layer → use /config to check the active value, or use --setting-sources user to load only a specific layer to eliminate interference;
  • Key requires restart: Most settings hot-reload, but model, outputStyle, etc., are read at session start—start a new session after changing (use /model to switch temporarily);
  • Config itself is broken: claude doctor (in terminal) / /doctor (in session) will report schema errors; adding "$schema": "https://json.schemastore.org/claude-code-settings.json" to the top of settings.json highlights errors in editors. If you suspect custom config broke everything, start with claude --safe-mode to isolate.

🥚 opusplan is the most hardcore easter egg found Binary ConfirmedSelecting it makes the Plan phase automatically upgrade to Opus for deep thinking, then downgrades to your chosen standard execution model (like Sonnet) when exiting plan mode—set it once to plan with the strongest model and execute with the cost-effective one. This mechanism is entirely undocumented in the official CLI docs, not even in --help. Just type /model opusplan in a session to activate.
