メンタルモデル 00

すべてはコンテキストを中心に回る

Claude Code は単なるチャットボットではなく、エージェント型コーディング環境（Agentic Coding Environment）です。ファイルを読み、コマンドを実行し、コードを書き換え、自律的に課題を解決していきます。ユーザーの役割は進捗を観察し、軌道修正を行い、あるいは作業を完全に任せることです。公式 Best Practices の冒頭では、ほぼすべての実践手法の根底にある決定的な制約が明かされています——

コアとなる制約コンテキストウィンドウには、会話全体（送受信した全メッセージ、読み込んだすべてのファイル、実行した各コマンドの出力）が格納されます。これは急速に満杯になり、それに伴ってモデルのパフォーマンスは低下します——コンテキストが満杯になると、Claude は初期の指示を「忘れ」始め、ミスが急増します。コンテキストこそが、あなたが最も厳密に管理すべきリソースです。

この一つの原則から、本ガイドの大部分のプラクティスが導き出されます：

  • なぜサブエージェントで調査するのか → 探索で消費されるのはサブエージェント側のコンテキストであり、あなたのメイン会話ではないから。
  • なぜ CLAUDE.md を短く保つのか → 毎セッション読み込まれるため、長すぎると重要なルールがノイズに埋もれるから。
  • なぜ CLAUDE.md への知識詰め込みより Skills が優れているのか → スキルは必要なときだけオンデマンドで読み込まれ、使わなければコンテキストを消費しないから。
  • なぜ /clear、/compact、/btw が必要なのか → すべてコンテキストの空き容量を確保するためのツールだから。
  • なぜ「2回修正してダメならリセット」なのか → 失敗した試行錯誤の履歴がコンテキストに残ると、モデルが同じ落とし穴に引きずり込まれるから。

メンタルモデル 01

5つの黄金法則

公式 Best Practices の膨大なテキストは、以下の5つの法則に凝縮できます。ディスプレイの横に貼っておく価値のある原則です。

法則1: Claude に自分で実行できる検証手段を与える

Claude は「作業が一見完了したように見える」段階で手を止めます。実行可能なチェック手段がなければ、あなた自身が検証ループに入らざるを得ず、すべてのエラーを人間が見つけ出さなければなりません。合否（pass/fail）を出力できるシグナル（テストスイート、ビルド終了コード、linter、比較スクリーンショットなど）を与えれば、サイクルは自律的に完結します：作業 → チェック実行 → 結果の確認 → 合格までイテレーション。

❌ 弱い指示「メールアドレスを検証する関数を実装して」 / 「ビルドが落ちたので直して」
✅ 強い指示「validateEmail を作成し、テストケース（user@example.com→true、invalid→false、user@.com→false）を用意して実装後にテストを実行して」 / 「ビルドエラーは以下の通り [エラーを貼付]。エラーを握りつぶさずに根本原因を修正し、ビルドが通ることを検証して」

検証の4段階（無人運用の強度順）：同一プロンプト内で「チェックを実行して改善」を指示 → /goal で評価器にターンごとに条件を再確認させる → Stop hook でチェックをハードゲート化（不合格ならターン終了を拒否） → 検証用サブエージェントにクリーンなコンテキストでセカンドオピニオンを出させる。さらに重要なのは、Claude に口頭での成功宣言ではなく**客観的な証拠**（テスト出力、コマンド戻り値、スクリーンショット）の提示を義務付けることです。

法則2: まず探索、次に計画、最後にコードを書く

いきなりコードを書き始めると、誤った問題を解いてしまう危険が高まります。推奨される4ステップ：Explore（計画モードでファイルを読み、質問し、コードは変更しない）→ Plan（実装計画を作成。Ctrl+G でエディタから直接編集可能）→ Implement（計画モードを抜けて実装し、計画と照らし合わせて自己検証）→ Commit（明確なコミットメッセージを作成して PR を作成）。

計画を教条主義にしない範囲が明確な小さな変更（タイポ修正、ログ追加、リネームなど）は直接実行させます。公式の判断基準：diff の形が1行で説明できるなら、計画はスキップする。計画が真価を発揮するのは、設計が不確定な場合、複数ファイルにまたがる場合、未知のコードベースを触る場合です。

法則3: プロンプトは具体的に、コンテキストは十分に

Claude は意図を推論できますが、心を読むことはできません。対象ファイルを名指しし、制約を明記し、既存の設計パターンを提示します：

戦略弱いプロンプト強いプロンプト
範囲の限定「foo.py にテストを追加して」「foo.py のテストを作成し、ログアウト済みユーザーの境界条件を網羅して。モック（mock）は使わないこと」
情報源の指定「この API どうしてこんなに変なの？」「ExecutionFactory の git 履歴を確認し、この API が現在の設計に至った経緯を要約して」
既存パターンの引用「カレンダーコンポーネントを追加して」「トップページの既存ウィジェットの実装パターン（HotDogWidget.php を参考）に倣ってカレンダーコンポーネントを実装して……リポジトリ外の新たな依存関係は追加しないこと」
症状の正確な記述「ログインのバグを直して」「セッションタイムアウト後にログインが失敗するという報告がある。src/auth/ の認証フロー、特にトークンリフレッシュを確認して。まず失敗を再現するテストを書いてから修正して」

コンテキスト供給の5つの手法：@ファイル 参照（Claude が先に読み込んでから回答）、**画像の貼り付け**（Ctrl+V）、**URL** の指定（/permissions で頻用ドメインを許可）、**パイプライン入力**（cat error.log | claude）、あるいは Claude 自身に取得させる（コマンド実行 / MCP / ファイル読み込み）。

法則4: 小刻みに軌道修正し、こまめにコンテキストをクリアする

  • Esc でいつでも中断可能。コンテキストは保持され、すぐに方向修正できます。
  • Esc Esc / /rewind でロールバックメニューを開く：会話の復元、コードの復元、またはその両方の復元。
  • 「Undo that」と指示すれば、直前の変更を自ら取り消させることができます。
  • 無関係なタスクの間では必ず /clear を実行します。同一の問題で2回修正しても直らない場合は深追いしないこと——/clear して教訓を反映した洗練されたプロンプトで再スタートする方が、失敗履歴で汚染された長時間のセッションを続けるより遥かに高い成果を生みます。

法則5: まず Claude にインタビューさせる（大規模機能では必須）

大きな機能を作るときは焦って指示を出さず、まず Claude に AskUserQuestion ツールを使ってあなたにインタビューさせます：

私は[簡潔な説明]を作成したいです。AskUserQuestion ツールを使って、
技術的な実装、UI/UX、エッジケース、懸念事項やトレードオフについて詳細にインタビューしてください。
自明な質問は避け、私が見落としている可能性のある難所を深掘りしてください。
質問が完了したら、完全な仕様書を SPEC.md に書き出してください。

仕様が確定したら、**新しいセッションを開いて実行**します。クリーンなコンテキストで実装に集中し、SPEC.md はいつでも参照できるアンカーとなります。優れた仕様書の3要素：関連ファイルとインターフェースの明記、やらないこと（Non-goals）の明確化、E2E検証ステップで締めくくること。

新規リポジトリに入る際の標準5ステップ

  1. /init —— コードベース（ビルドシステム、テストフレームワーク、コーディング規約）を分析して CLAUDE.md 初稿を作成。以降 /memory で継続的にブラッシュアップ

Claude Code には6層の拡張ポイントが存在します。層の選択ミスは初心者が最も陥りやすい罠です——Hook に書くべきルールを CLAUDE.md に書いて守られるよう祈ったり、たまにしか使わない専門知識を毎セッションに詰め込んでコンテキストを圧迫したりしてしまいます。以下の選定表で一発で判断できます：

あなたの要件使うべき層決定的な理由
全セッションで常に知っておくべき簡潔な事実（ビルドコマンド、コード規約）CLAUDE.md全セッションで自動読み込みされるため、常に短く保つ必要がある

大量のファイルを読み込む事前調査 / 先入観のない客観的なコードレビューサブエージェント独立したコンテキストウィンドウ。探索でメインの会話を汚染しない

拡張エコシステム 06

Skills / Hooks / MCP / サブエージェント: 4大機能の深層解剖

Skills: オンデマンド読み込みのエキスパート知識パック

1つのスキル ＝ 1つのディレクトリ ＋ 1つの SKILL.md（テンプレート、サンプル、スクリプトを同梱可能）。Claude がシナリオに応じて自動で読み込むか、ユーザーが /スキル名 で明示的に呼び出します。スキルを作成すべきシグナル：同じ説明・チェックリスト・手順を何度も貼り付けているとき、または CLAUDE.md のある項目が「簡潔な事実」から「複雑な手順」に肥大化してきたときです。

.claude/skills/my-skill/
├── SKILL.md        # 必須: frontmatter + 指示本文
├── examples/       # 任意: 期待される出力例
└── scripts/        # 任意: 実行可能スクリプト
配置場所適用スコープ
~/.claude/skills/ユーザー個人、すべてのプロジェクトで有効
.claude/skills/（プロジェクトルート）当該プロジェクト（git 管理すればチーム全体で共有）；monorepo のサブディレクトリも自動検出
プラグイン内の skills/プラグイン有効化スコープ、名前空間は プラグイン名:スキル名

3つの高度なテクニック：

  • 動的コンテキスト注入：本文中に !`git diff HEAD` と書くと、スキル読み込み前にコマンドを実行し、出力を指示にインライン展開——スキルが「現在の現場状況」を把握できます。
  • frontmatter による制御：disable-model-invocation: true を指定すると危険な処理（デプロイなど）をモデルの自動判断から除外し手動専用にできます。description をルーティングルールとして明確に記述することで自動発動の精度が向上します。
  • スキルのホットリロード：ディスク上のファイルを編集すると即座に反映されます。同名スキルの優先順位は「企業 > 個人 > プロジェクト > バンドルスキル」（プロジェクト内に同名 code-review を置くことで公式版を上書き可能）。
優れたスキルを書くためのコミュニティの定石description はルーターのように「いつこのスキルを使うべきか」を具体的に書く；決定論的な作業はモデルに任せず同梱スクリプトに処理させる；SKILL.md 本文はスリムに保ち、詳細はオンデマンド読み込みの別ファイルへ逃がす；1つのスキルには1つの責任のみを持たせる；抽象的なルールではなく具体的な良い例・悪い例を示す。

Hooks: 決定論的なガードレール

CLAUDE.md や Skills の指示はあくまで**推奨・提案**です。絶対に守らせるべきルールは Hook に委ねます。Hook はライフサイクルイベントでスクリプトを実行し、終了コード（exit code）2 を返すことで Claude のアクションを完全にブロックできます。代表的なイベント：

イベント発火タイミング典型的な用途
PreToolUseツール実行直前（ブロック可能）.env や秘密鍵への書き込み禁止、危険なコマンドの遮断
PostToolUseツール実行が成功した直後ファイル編集後に自動で prettier / eslint を実行
StopClaude がターンを終了しようとした時テストを実行し、失敗していればターン終了を拒絶（8回連続失敗でパス）

{

    "PostToolUse": [

スマートな作成法Hook の実装自体も Claude に依頼できます：「ファイル編集後に毎回 eslint を実行する hook を書いて」、「migrations ディレクトリへの書き込みを阻止する hook を書いて」。設定内容は /hooks で確認できます。
Hook よりも安全な機密保護手法機密ファイルの読み取り防止には Hook よりも権限ルールが推奨されます：deny ルール（例：Read(./.env), Read(./secrets/**)）を設定すると、ファイルが Claude から完全に「見えなく」なります。権限の評価順序：deny → ask → allow。

サブエージェント（Subagents）: 独立したコンテキストを持つ分身

.claude/agents/*.md に定義し、独自のコンテキストウィンドウ、ツールセット、システムプロンプトを持ちます。主な2大用途：

  • 調査のコンテキスト隔離：「サブエージェントを使って認証システムがトークンリフレッシュをどう処理しているか調査して」——サブエージェントが数十のファイルを読み込み、メインの会話には結論の要約だけが返ってきます。
  • 先入観のない客観的レビュー：直前の実装の思考のバイアスを受けないクリーンなコンテキストで diff を精査します。公式が推奨するレビュー用指示：「指定された作業内容と計画を対照し、問題点のみを報告せよ。スタイルの好みの指摘は不要」。
# .claude/agents/security-reviewer.md
---
name: security-reviewer
description: コードのセキュリティレビュー。コード変更後に自律的に使用。
tools: Read, Grep, Glob, Bash
model: opus
---
あなたはシニアセキュリティエンジニアです。以下を重点的に監査してください：
インジェクション脆弱性（SQL/XSS/コマンドインジェクション）、認証・認可の欠陥、
コード内の秘密鍵・クレデンシャル、安全でないデータ処理。
具体的な行番号の引用とともに修正案を提示してください。
/btw とサブエージェントの対比/btw は会話全体を把握していますがツールは使えません（「既知の事実」を素早く確認）；サブエージェントはすべてのツールを使えますが空のコンテキストから出発します（「未知の事柄」を新規調査）。使い分けることでコンテキストを大幅に節約できます。
レビュー用エージェントの陥りやすい罠「問題点を探せ」と指示されたレビュアーは、コードに問題がなくても何かしらの粗を探し出そうとしがちです。すべての指摘を盲従して直すと過剰設計（Over-engineering）に陥ります。レビュアーには「正確性や要求仕様に関わる重大な欠陥のみを報告し、その他は任意の提案として扱う」という前提を与えてください。

MCP: 外部世界との接続

MCP（Model Context Protocol）により、Claude Code をデータベース、Figma、Slack、Sentry などの外部システムと直接接続できます。MCP の設定は settings.json には書かないという点にご注意ください（初心者が最も迷いやすいポイントです）。

追加と管理

# ローカルの stdio サーバーを追加
claude mcp add my-tool -- npx -y some-mcp-server

# リモートの HTTP サーバーを追加
claude mcp add --transport http api-tool https://example.com/mcp

# OAuth 認証が必要なサーバーで個別にログイン
claude mcp login api-tool

# セッション内: /mcp で状態確認、認証、サーバーの有効化/無効化

3つのスコープ（--scope）

スコープ保存先適用範囲
local（デフォルト）~/.claude.json 内の該当プロジェクトエントリあなた個人、当該プロジェクトのみ
projectリポジトリルートの .mcp.json（git 管理）チーム共通——プロジェクト必須ツールを記載
user~/.claude.jsonあなた個人の全プロジェクト共通（ブラウザやメモツール等）

運用の3原則

  • ツール定義もコンテキストを消費する：MCP サーバーを追加するたび、各ツールのスキーマがコンテキストウィンドウを圧迫します——/context で消費量を確認し、使わないサーバーは /mcp で無効化しましょう。
  • MCP の戻り値は信頼できない入力として扱う：外部ツールから返されるテキストにはプロンプトインジェクションが含まれている可能性があるため、信頼できるサーバーのみを接続します。
  • 手作業で JSON を書かずコマンドを使う：claude mcp add を使用することで正確なフォーマットで書き込まれます。手動編集による JSON 破損は「MCP が認識されない」原因のトップです。

コンテキスト管理の極意

1M コンテキスト時代において、この管理手法はまだ有効か？

本ガイド冒頭の「コンテキストの逼迫」は 200K 時代に書かれたものですが、Sonnet 5 や Opus 5 はすでにネイティブ 1M コンテキストを備えています。一見矛盾するように思えますが、結論は変わりません。管理が必要な「理由」が変化しただけです。

結論：依然として必須。理由は「容量不足」から「コスト増と詳細の喪失」へ以前の問題は物理的な制限でした：200K ウィンドウはファイル読み込みやコマンド出力ですぐに埋まり、圧縮なしでは作業が続けられませんでした。1M ウィンドウはその物理制限を5倍に広げましたが、別の2つの本質的課題は解消されていません：①メッセージを送るたびに過去の全履歴が再送信される——公式 costs ドキュメントの記述「Claude Code sends your full conversation with every message」の通り、ウィンドウが大きく履歴が溜まるほど、たった1行の質問でも全履歴分の料金が発生し、コストが会話長に比例して跳ね上がります；②圧縮によって詳細が欠落する——初期に会話内で指示した詳細な制約事項は、CLAUDE.md に記載されていない限り圧縮時に失われる可能性が高いです（公式ドキュメント「instructions from early in the conversation can get lost」）。1M は「突然停止しないための安全マージン」であり、「放置してよいライセンス」ではありません。

緩和されたのは1点のみです：その日のうちに終わる短いタスクであれば、大きなファイルを読んでも神経質に手動 /compact を行う必要はなくなりました——自動圧縮の閾値に達することなく完了できるケースが増えたためです。しかし、複数日にわたるセッション、常時稼働させる自動化エージェント、API コストを重視する場面では、後述するコンテキスト管理手法が引き続き決定的に重要となります。なお、1M は Sonnet 5 / Opus 5 / Fable 5 等でのみネイティブ有効ですので、モデルの実際のコンテキスト長は /context で確認してください。v2.1.223 の挙動変化：ネイティブ 1M モデルもデフォルトで auto-compaction により 200K 相当に制限されます（旧動作に戻すには CLAUDE_CODE_DISABLE_1M_CONTEXT を設定）。

診断：手を動かす前に現状を把握する

/context を実行するとカラーグリッドで使用状況が表示されます（どのツールが消費しているか、メモリファイルが肥大化していないか、残り容量はどれくらいか）。/statusline での常時表示と合わせて現状を把握しましょう。

空き容量を確保する4つのアプローチ（軽度から重度順）

手段アクション適用シーン実行の目安（定量的トリガー）
サイド質問/btw 質問内容ちょっとした確認をしたいが、回答を会話履歴に残す必要がないときいつでも実行可能。コンテキストを消費せず、/context の使用量にも影響しません
指定要約圧縮/compact API変更とテストコマンドを保持会話を続けたいが履歴が重いとき——要約の方針を人間が指示自動圧縮が走る前に手動で主導権を握る：/context の使用率が閾値に近づいたとき（Sonnet 5 の標準では約 96.7%≈967K/1M トークン；1M 未適用のモデルでは 200K 到達時；いずれも CLAUDE_AUTOCOMPACT_PCT_OVERRIDE で前倒し可能）
部分要約Esc Esc で特定メッセージを選択 → Summarize from here / up to here前半または後半のみを圧縮し、重要な区間の詳細を完全に維持したいとき定量的数値ではなく、「この区間以降はまだ詳細が必要 / この区間はもう不要」という人間の判断に基づく
完全初期化/clear無関係な新規タスクへ移行するとき、または同一問題で2回修正しても直らないとき容量に関係なく、タスクの関連性で判断。新しい作業に移る際は残量に関わらず即実行
圧縮処理を思い通りに制御するCLAUDE.md に圧縮方針を記載しておくと、自動圧縮時にもそれが尊重されます。例：「会話を圧縮する際は、変更されたファイル一覧とテスト実行コマンドを常に保持すること」。

自動圧縮（Auto-compaction）：いつ動き、何を捨てるのか

DISABLE_AUTO_COMPACT は settings.json の autoCompactEnabled（デフォルト true）を上書きする環境変数です。これを無効化すると Claude は自動要約を行わず、コンテキストが満杯になるとエラーで停止します。/context を見ながら手動で /compact したいエキスパート専用の設定です。

発動閾値（公式 env-vars / model-config ドキュメントに基づく）：

モデル / シナリオ発動タイミング
Sonnet 5（ネイティブ 1M）デフォルトで約 96.7%（約 967K / 1M トークン）。閾値自体は CLAUDE_CODE_AUTO_COMPACT_WINDOW で制御
1M 未適用の標準モデル（Sonnet 4.6 / Opus 4.6 等）200K 境界への到達時
その他のローカルセッション（ローカル Opus 4.8 等）モデル固有の上限に近づいた時点（固定パーセンテージは非公開）

CLAUDE_AUTOCOMPACT_PCT_OVERRIDE（値：1〜100）によりパーセンテージを下げて早めに圧縮を発動させることができます（引き上げることは不可）。現状の正確な使用状況は /context で確認してください。

圧縮時に実行される2段階の処理：公式ドキュメントによると、まず「古いツールの出力を削除し、それでも不足している場合に会話全体を要約する（clears older tool outputs first, then summarizes the conversation if needed）」という2段構えになっています。第1段階では読み込み済みの巨大ファイル内容や過去のコマンド出力など「一度見れば十分な生データ」のみを削除し、対話履歴には手を付けません。第1段階で十分な空きが作れなかった場合のみ第2段階へ進み、会話履歴全体を構造化要約に圧縮します。「Conversation compacted」の通知が出ずに消費量がガクッと減った場合は第1段階のみが実行された状態です。

第2段階の要約後に保持されるもの・失われるもの：

要素圧縮後の状態
システムプロンプト・出力スタイル影響なし（元々会話履歴の外に存在するため）

過去に呼び出された Skill 本文再注入されるが、各 Skill 上限 5000 トークン、全体上限 25000 トークンを超えると古い順に破棄される
Hooks影響なし（Hook はコードでありコンテキストを消費しないため）
「圧縮後に頭が悪くなった」と感じる理由公式ドキュメント記載：「Your requests and key code snippets are preserved; detailed instructions from early in the conversation may be lost.」——要約によって「要求の大枠」と主要コードは残りますが、初期に口頭で伝えた細かなエッジケースの指示は失われます（CLAUDE.md に書かれていない限り）。これを防ぐには、重要な制約事項は会話の途中で伝えるだけでなく CLAUDE.md に昇格させるか、圧縮前に /compact 重点指示 で残すべき情報を指定してください。

単一のファイルやツール出力が巨大すぎて「要約してもすぐにコンテキストが満杯になる」場合、Claude Code は数回リトライした後に自動圧縮を停止しエラーを返します（thrashing エラー）。この場合は再圧縮を試みるのではなく、サブエージェントや Hook を使って巨大な出力をあらかじめトリミングしてください。

ファイルを外部記憶として活用する

後述の Ralph ループでは「会話履歴ではなくファイルシステムをメモリとして使う」という思想が登場します。会話履歴は自動圧縮で要約され、/clear で消去され、別セッションには引き継がれません。しかし、ディスク上のファイルは永続します。状態をファイルに明記することは、コンテキストウィンドウの外に圧縮の影響を受けない「信頼できる唯一の情報源（Single Source of Truth）」を持つことを意味します。

代表的な3つのファイル活用法：

  • SPEC.md：法則5「まずインタビューさせる」で作成する仕様書。仕様が確定したら**新規セッションを開いて実装を開始**します。実装担当のエージェントはクリーンなコンテキストで作業でき、SPEC.md をいつでも参照できます。
  • NOTES.md / PROGRESS.md：長時間タスクや Ralph ループを実行する際、各ターンの開始時に読み、終了時に更新します——「検証済みの実装方針」「試してダメだったアプローチ」「次にやるべきこと」をチェックリスト形式で記録。セッションを跨いでも過去の失敗を繰り返さずに済みます。
  • 圧縮ポリシー自体のファイル化：CLAUDE.md に「圧縮時は変更ファイル一覧とテストコマンドを常に保持せよ」と書いておけば、このルール自体がディスク上に存在し、どんな圧縮を経ても確実に守られます。

本節の根拠：公式 Explore the context window · 公式 How Claude Code works · 公式 Model configuration · 公式 Environment variables · 公式 Settings · 公式 Manage costs

チェックポイント：果敢な試行錯誤を支える安全網

プロンプトを送信するたびに自動でチェックポイントが作成され、ファイル変更のスナップショットが取得されます。Esc Esc / /rewind を使えば、会話のみの巻き戻し、コードのみの巻き戻し、あるいは両方の巻き戻しが可能です。チェックポイントはセッションとともに永続化されるため、ターミナルを閉じて翌日再開しても巻き戻せます。注意点：Claude の編集ツールによる変更のみを追跡し、Bash コマンドや外部プロセスによる変更は含まれません。git commit の代わりではない点に留意してください。

セッションを資産として管理する

対話履歴はローカルに保存されます：claude -c で直近を再開、claude -r 名前 でピンポイント復元、/rename でブランチ名のような名前（例：oauth-migration）を付与、/branch で現在の地点から別アプローチを分岐実験、--fork-session で元セッションを汚さずに新セッションを開始。ワークフローごとに名前付きセッションを作り、git ブランチのようにコンテキストを管理しましょう。

3層の評価順序：deny → ask → allow

// .claude/settings.json —— 実践的な初期設定の例
{
  "permissions": {
    "allow": [
      "Read", "Glob", "Grep",
      "Bash(npm run lint:*)", "Bash(npm run test:*)",
      "Bash(git status)", "Bash(git diff:*)"
    ],
    "ask":  [ "Bash(git push:*)" ],
    "deny": [
      "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"
    ]
  }
}
  • deny が最優先で評価される：機密ファイルは deny に指定することで Claude から完全に不可視化されます（Hook でブロックするより安全）。
  • 承認疲れ（Approval fatigue）はセキュリティの最大の敵です：10回目の「許可」をクリックする頃には人間は内容を見ていません。解決策はホワイトリストの適切な設定（/fewer-permission-prompts で自動生成可能）と /sandbox による OS レベルの隔離です。
  • --dangerously-skip-permissions は**ネットワークがなく、機密データも存在しないコンテナ環境**（CI での lint 修正など）でのみ使用すべきです。企業環境では disableBypassPermissionsMode で組織全体で無効化できます。

構文早見表：各記述がマッチする対象

設定例にある Bash(npm run lint:*)、Read(./.env.*)、Read(./secrets/**) の記法について、正確なマッチングルールを理解しておきましょう：

記述形式マッチする対象（正しい理解）誤った思い込み（注意点）
Read / Edit / Bash
括弧なしのツール単体		対象が何であれ、そのツールの**すべての**実行にマッチ「ルールを書いていないのと同じ」と思わないこと——ツール単体指定は全許可 / 全確認 / 全拒否のルールとなります
Read(./.env)**カレント作業ディレクトリ**（cwd、claude を起動した場所）からの相対パスで、この1ファイルに厳密一致プロジェクトルートからの相対パスと思わないこと——スラッシュで始まる /path が設定ファイルの階層基準です（下記7行目参照）
Bash(npm run lint:*)
Bash(git diff:*)		:* は「末尾にスペース + *」の省略記法で、**前方一致**：コマンドが npm run lint で始まれば許可コロンがフィールドセレクタであると思わないこと——Bash(command:rm *) のような構文は無効と判定され警告が出ます
Edit(src/**)
（allow ルールの場合）		単一セグメント記述。<cwd>/src の1箇所のみにマッチpackages/foo/src にもマッチすると思わないこと——2026-07-18 よりこの挙動に厳格化されました（以前はツリー全体の src にマッチ）
Read(./secrets/**)
（deny / ask ルールの場合）		単一セグメント記述だが、deny / ask ルールではカレントディレクトリ配下の**任意の深さ**の secrets にマッチ（packages/foo/secrets もブロック可能）allow と deny で単一セグメントの挙動が異なる点に注意——設定例の deny が安全なのはこのためです。allow で同じ書き方をすると直前の厳格化の影響を受けます
Edit(**/src/**)明示的な任意深度記述。allow / deny / ask のいずれでもツリー内のあらゆる src にマッチ単一セグメントで悩むより、「どこにあっても対象」としたいなら常にこの形式で書くのが確実です
Edit(/src/**)
先頭にスラッシュ1つ		**設定ファイルが存在する階層**（プロジェクト設定ならプロジェクトルート <project root>/src）を基準とする相対パス./path と混同しないこと——worktree 環境では「プロジェクトルート」はその worktree 自体のルートを指します
Read(//Users/alice/secrets/**)
先頭にスラッシュ2つ		ファイルシステムルートからの**絶対パス**。cwd やプロジェクトルートに依存しないチーム共有のプロジェクト設定に個人のユーザー名パスをハードコードしないこと——個人用 settings.local.json に書くべきです
allow ルールでパスを書く際の注意点deny の Read(./secrets/**) は 2026-07-18 の厳格化後も任意深度の secrets をブロックできますが、同じ書き方を allow ルールで行った場合（例：Edit(src/**)）、<cwd>/src のみが許可され、ネストした同名ディレクトリは許可されません。深い階層まで許可したい場合は必ず Edit(**/src/**) と明示してください。

三、優先順位と「設定が反映されない」ときのチェックリスト

設定キーが重複した場合の優先順位：企業管理設定 > コマンドライン引数 > .claude/settings.local.json > .claude/settings.json > ~/.claude/settings.json。「変更したのに反映されない」場合の典型的な3大原因：

  • 編集したレイヤーが上書きされている：プロジェクト設定がユーザー設定を上書きしている → /config で現在有効な値を確認、または --setting-sources user で指定レイヤーのみを読み込み確認；
  • セッションの再起動が必要な項目である：多くの設定はホットリロードされますが、model や outputStyle などはセッション開始時に読み込まれます——変更後はセッションを再起動（一時的なモデル変更は /model を使用）；
  • JSON の構文エラー：claude doctor（ターミナル診断）または /doctor（セッション内）でスキーマエラーを確認；settings.json の先頭に "$schema": "https://json.schemastore.org/claude-code-settings.json" を指定するとエディタで自動検証されます。カスタム設定が原因で不具合が疑われる場合は claude --safe-mode で素の状態で起動して切り分けます。

無限修正ループエラー → 修正指示 → 別のエラー → 再修正……失敗した試行の履歴がモデルを同じ罠に誘い込む2回指示して直らなければ即座に /clear。教訓を反映した新たなプロンプトで再スタートする
CLAUDE.md の過積載大量のルールを書き連ねた結果、Claude が最も重要なルールを無視する徹底的に削る。強制したいルールは Hook へ、特定場面の知識は Skill へ分離する
盲信による検証スキップ一見完璧に見えるコードが出力されたが、エッジケースでバグだらけになる検証手段のない成果物は「未完了」と見なす。自己申告ではなく実行結果の証拠を求める
無制限な探索指示「X について調査して」とだけ指示した結果、数百ファイルを読み込んでコンテキストを圧迫調査範囲を明確に限定するか、サブエージェントに任せて要約のみを受け取る
Hook の仕事を祈りに頼る「毎回 lint を実行すること」と CLAUDE.md に書いたが、時々実行を忘れる確実に実行すべき処理は Hook に任せる。プロンプトはあくまで提案に過ぎない
並行セッションのファイル衝突2つのセッションが同じファイルを同時に編集し、変更を上書きし合ってしまう並行作業を行う際はセッションごとに独立した git worktree（claude -w）を使用する
チェックポイントを git と誤認/rewind で元に戻せると思い込んでいたら、Bash コマンドで編集されたファイルが復元できないチェックポイントは Claude の編集ツールのみを追跡する。要所では通常通り git commit を行う

set -euo pipefail
INPUT="$(cat)"
FILE="$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')"
if echo "$FILE" | grep -qE '\.(env|pem|key)$'; then
  echo "機密ファイルへの書き込みは禁止されています: $FILE" >&2
  exit 2   # 終了コード 2 ＝ ツールの実行を拒絶
fi
exit 0
