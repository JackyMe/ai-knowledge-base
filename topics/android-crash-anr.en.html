Basics 00

Overview & Methodology

Stability Issue Classification Map

Build the map before debugging. There are only four main categories of "crashes/freezes" in Android, each with different evidence, tools, and chapters:

TypeSymptomNatureKey EvidenceSee
Java/Kotlin CrashApp crashesUncaught exception thrown up the call stack to the main threadFATAL EXCEPTION stack trace in logcat02
Native CrashApp crashesC/C++ layer signals (SIGSEGV/SIGABRT…)tombstone file, *** *** block in logs04
ANRFreezes → System "Not Responding" dialogMain thread blocked, crucial events not processed in time/data/anr/ trace, Vitals ANR report03
System Kills Process"Returns to home screen while using", lost background processOOM/LMK low memory kill, background restrictions, user force stopApplicationExitInfo exit reason08
Most Common Novice MisjudgmentA "crash without a crash log" is mostly not a Crash: it's either a Native crash (check tombstone) or the system killed the process (check ExitInfo). Categorize first, then debug—using the wrong map wastes all effort.

Why It Must Be Fixed: The Platform's Hard Red Lines

Google Play's Android Vitals defines "bad behavior thresholds": user-perceived crash rate ≥1.09% or user-perceived ANR rate ≥0.47% (all devices). Exceeding this means the app will be downranked across the entire store; if ≥8% on any single device model, that model is downranked and a warning may appear on the store page. Stability is not technical cleanliness, it's a traffic issue.

The Five-Step Methodology

  1. Fix the Symptom — Get the rawest evidence: full stack/trace/log, device, OS version, App version, repro steps. Never start work based on "second-hand descriptions".
  2. Locate — Find the "first scene" from the stack: which frame is your code? Retrace if obfuscated.
  3. Attribute — Answer "why did it get to this point": where did null come from? Who holds the lock? Who ate the memory? — Use tools to gather evidence, don't guess.
  4. Cure — Fix the root cause, don't just wrap it in try-catch; after fixing, there must be a validation path proving the fix (repro steps/regression tests/rollout metrics).
  5. Prevent Recurrence — Defenses for similar issues: lint rules, StrictMode, CI checks, monitoring alerts. Fix one bug, block a class of bugs.
Advancement Path AdviceNovice: 00→01→02, be able to independently handle NPE-level daily crashes; Intermediate: 03→07, handle ANRs and online tickets; Advanced: 08 onwards, chew through hard-to-reproduce issues and integrate AI into workflows.

Lesson 1: Read a Crash

Stack Trace Anatomy: 4 Pieces of Info for Quick Triage

FATAL EXCEPTION: main                                    ← ① Thread crashed (main=UI thread)
Process: com.example.app, PID: 12345
java.lang.NullPointerException:                          ← ② Exception type: dictates which chapter to check
    Attempt to invoke virtual method 'int java.lang.String.length()'
    on a null object reference                           ← ③ Exception message: which object, what operation
  at com.example.app.OrderDetail.bind(OrderDetail.kt:87) ← ④ First Scene: top frame with your package name
  at com.example.app.OrderAdapter.onBindViewHolder(OrderAdapter.kt:42)
  at androidx.recyclerview.widget.RecyclerView...        ← Framework frames: usually just "passing through"
Caused by: ...                                           ← With a Caused by chain, the root cause is at the very bottom!
  • Reading Order: Check exception type & message → Scan down for the first frame in your package → Follow any Caused by chain to the bottom for the root cause;
  • Deobfuscation: If production stacks show a.b.c(Unknown Source), use R8's mapping.txt to deobfuscate: retrace mapping.txt stacktrace.txt (mapping files for every release must be archived!);
  • Three Axes for Gathering Evidence: adb logcat -b crash shows only the crash buffer; adb logcat --pid $(adb shell pidof -s package_name) isolates your process; if missed, pull post-mortem via adb bugreport (see Chapter 07).

Reproduction: Half the Value of Debugging

After getting a stack trace, the first step is not changing code, but establishing a stable repro—a bug that can be reproduced is half fixed. Try these tiers sequentially: Exact step repro (user path replay) → Conditional repro (specific data/network/permission state) → Stress repro (monkey / screen rotation / Developer Options "Don't keep activities" for process recreation).

# Three classic stress repro toggles
adb shell settings put global always_finish_activities 1   # Don't keep activities: exposes process recreation crashes
adb shell monkey -p com.example.app --throttle 300 -v 5000 # monkey random event stream
# Developer Options → Simulate secondary displays/change language/dark mode: exposes config change crashes
Novice GuardrailDo not "fix" crashes with a "global try-catch swallowing exceptions"—this merely turns a crash into harder-to-debug data corruption. Similarly, beware of "one-click crash safety SDKs" that silently swallow exceptions; they make your Vitals look good but ruin user experience.

Evidence Handover Ticket: Anyone Can Take Over

Issue ID / First Seen / Current Owner:
Impact: Version, Track, User Count, Crash/ANR Rate, Core Flow
Category: Java/Kotlin | Native | ANR | System Exit

This handover ticket is also the prototype for the "Crash Context Pack" in Chapter 09. Make it lossless for humans first, then pass this structured evidence to AI; otherwise, AI will just generate unverified guesses faster.

Walking Through the NPE Example Completely

Suppose line 87 is order.title.length. Tracing up to the Java/JSON boundary, we find legacy server data lacks a title, and Kotlin treats the platform type as non-null. The full closure should be:

  1. Verify Root Cause: Repro with a fixed response lacking a title; confirm the same data yields null in the mapper, while normal responses don't;
  2. Cure: Declare the field as String? at the DTO → Domain boundary, return a presentable placeholder per business rules or an explicit MalformedOrder, UI only accepts non-null Domain;
  3. Regression: Cover missing fields, empty strings, normal values, and legacy cache deserialization; run a release + R8 build and replay the path;
  4. Prevent: Enable strict deserialization/schema monitoring, add lint/review rules for Java platform type boundaries, and log response schema versions via Crashlytics keys.
Judging a True FixIf the patch only changes order.title.length to order.title?.length ?: 0 without defining "is an order without a title valid?", it only eliminates the crash but doesn't fix the data contract.

Crash Catalog & Cures

This catalog isn't to make you memorize exception names, but to help you jump from the "exception message" to the next evidence-gathering action. The cures listed in the table follow one principle: Fix states and boundaries, do not swallow exceptions.

Exception / Typical SignalCauses & DebuggingCure & Prevention
NullPointerException
... on a null object reference		Unchecked nullable Java values; Kotlin's biggest dangers are Java platform types (shown as String!), deserialization missing fields, and uninitialized lateinit. Look at the first business frame, then trace the production path of the null value.Immediately convert to explicit nullable types or domain objects at the Java/Network/DB boundaries; use requireNotNull only to guard true invariants. Do not use chained ?. to silently swallow required data.
IndexOutOfBoundsException
Index: 5, Size: 5		Index and collection are not from the same snapshot; pagination callbacks, DiffUtil, or concurrent updates left using an old position. Log index, size, adapterPosition, and data version.Use getOrNull only for reads where absence is allowed; re-fetch bindingAdapterPosition and check for NO_POSITION on RecyclerView clicks; submit immutable lists.
ClassCastException
X cannot be cast to Y		Bundle/Intent, JSON, multi-type lists, or wrong ClassLoader produced an actual type that didn't match assumptions. Print the actual class name and input data first.Use type-safe navigation arguments, sealed classes, and explicit serialization schemas; cross-version data must be migrated, not casted.
IllegalStateException
Fragment not attached
after onSaveInstanceState		Accessing Context when Fragment is already detached; committing transactions after state is saved; modifying data midway through RecyclerView layout reports inconsistency. Compare lifecycle timeline with all data write entry points.Access UI only in appropriate lifecycles; deduplicate navigation events and execute in resumable states; submit new list snapshots strictly via a single source of truth. commitAllowingStateLoss is only for scenarios where dropping UI state is genuinely acceptable.
WindowManager.BadTokenException

Written to logs by the framework to indicate window leaks, not necessarily an uncaught Crash; completely different from BadTokenException.Owned by the lifecycle owner and dismissed in onDestroy, prefer DialogFragment; always check the actual FATAL EXCEPTION following the log to avoid treating diagnostic logs as the final crash type.
IllegalArgumentException

ConcurrentModificationExceptionCollection modified by the current or another thread while iterating; logs also record the thread name and modification entry point.Single-thread ownership, immutable snapshots, or concurrent collections; do not wrap iteration in try-catch to keep running.
ClassNotFoundException / NoSuchMethodErrorR8 incorrectly removed reflection targets, dynamic feature not installed, MultiDex initialization timing, dependency binary version conflicts. Check APK contents, dependencyInsight, mapping, and affected ABI/versions.Add precise keep rules for reflection/JNI/serialization entry points; lock dependency versions and smoke test release builds; check installation state before calling dynamic modules.
ActivityNotFoundExceptionImplicit Intent has no handler, component stripped, or OEM app missing.Resolve with PackageManager before calling; provide in-app fallback paths; explicit components should be tested with manifest.
SecurityExceptionMissing runtime permissions, Android 12+ exported config, background start/foreground service limits, accessing unauthorized URIs.Build permission state machines based on target SDK; use Activity Result API; minimum component exposure, temporary URI grants; test denial and "don't ask again" paths.

OutOfMemoryError
Java heap space		Retained heap growth due to Bitmaps, caches, collections, or leaks. Look at the heap dump dominator tree and post-GC surviving objects.Fix reference chains, downscale images, set capped LRUs; don't treat largeHeap as a cure.
OutOfMemoryError
pthread_create failed		Thread count or per-thread stack exhausted, not a full Java object heap. Capture thread list and cluster by name/creation stack.Shared bounded thread pools, limit concurrency, cancel leaking tasks; disable per-request new thread creation.
EMFILE / too many open filesfd exhaustion often wrapped as OOM, SQLite, or network exceptions. Compare /proc/PID/fd count to soft limits.Close all Cursors, streams, ParcelFileDescriptors, and Sockets using use; monitor fd curves during stress testing.
CursorWindowAllocationExceptionQuerying columns/rows too large, multiple unclosed Cursors, loading BLOBs at once. Check SQL, window sizes, and living Cursors.Query only required columns, paginate; move BLOBs to files/streams; Cursors must be structurally closed.
SQLiteException / SQLiteDatabaseLockedExceptionIncomplete migrations, schema code mismatch, concurrent long transactions, disk full or corrupted. Keep original SQLite error codes and check upgrade paths.Write actual DB tests for every version migration; keep transactions small; use Room singletons; make disk-full recoverable, forbid unconditional DB wiping.
Resources.NotFoundExceptionPassing color values as resource IDs, resource shrinking deleted reflection references, theme package version mismatch.Use type-safe resource APIs; precise keep resources; theme packages must carry and validate schema versions.
RxJava UndeliverableExceptionAsynchronous errors with no consumer after stream cancellation end up in the global error handler. Check cause first to distinguish expected post-cancellation network errors from real programming bugs.Properly handle dispose and business errors; global handler should only ignore explicitly harmless cancellation/interruption causes, reporting or throwing others to the thread uncaught exception handler.
CancellationException / Coroutine ExceptionsCancellationException is usually a cooperative cancellation signal; swallowing it keeps tasks running. Check Job hierarchy if sibling tasks cancel each other.Must rethrow cancellation after catching broad Exceptions; use SupervisorJob/supervisorScope for independent subtasks; CoroutineExceptionHandler only handles root coroutine uncaught exceptions, not a replacement for try-catch.
ForegroundServiceStartNotAllowedException
android.app, API 31+		App attempted to start a foreground service while in the background (push arrivals, direct startForeground in timer callbacks are major offenders). Some scenarios (e.g., user just tapped a notification) are exempt; others are strictly denied.Defer background-triggered work to WorkManager/JobScheduler; if a foreground service is strictly required, move the start action into a window where the app is still foregrounded, or verify exemption conditions before using startForegroundService.
MissingForegroundServiceTypeException
android.app, API 31+		Called startForeground() but corresponding <service> in AndroidManifest.xml didn't declare android:foregroundServiceType (location/camera/microphone, etc.).Explicitly declare types for every foreground service in the manifest; Android 14+ also requires runtime permissions for some types, run smoke tests on targetSdk 34+ devices before release.
InvalidForegroundServiceTypeException / StartForegroundCalledOnStoppedServiceException
android.app		The former is a mismatch between declared type and actual call; the latter is calling startForeground() after the service has called stopSelf()/been recycled by the system—common when async callbacks return after onDestroy.Check service lifecycle state before calling startForeground; route async result callbacks through a "is service still alive" check layer, similar to the "is page still alive" pattern on the Activity side.

Lifecycle Crashes: The Real Issue is "Expired State"

  1. Process Recreation: The system reconstructs Activity/Fragment using savedInstanceState after killing the background process. Never rely on static singletons still having data; restore via persistent IDs, keep minimal states in ViewModel's SavedStateHandle.
  2. Fragment View Lifecycle: A living Fragment doesn't mean a living View. Bind viewLifecycleOwner when observing LiveData/Flow, clear bindings in onDestroyView.
  3. Expired Async Results: Network/location/payment callbacks might return when the page is already destroyed. Let tasks cancel with lifecycleScope/viewModelScope, or write results into a state container rendered by the current UI.
False FixWrapping the Activity in a WeakReference. It only reduces strong reference leaks; it doesn't prove the page is still updatable, nor does it cancel background work.
True Cure PatternLifecycle handles cancellation, state containers handle result saving, pages only collect and render in STARTED state; process recreation restores from the persistence layer.
Three Universal Defenses① Tighten Kotlin boundaries: immediately perform nullability and schema checks at Java/JSON/DB entry points; ② Write high-frequency team mistakes into Android Lint/Detekt rules; ③ CI must run release + R8 smoke tests, migration tests, process recreation, and rotation regressions.

Advanced 03

Deep Dive into ANR: Tracing from Main Thread Snapshot to the Blocking Source

Recognize the Timeout Types First

TypeAOSP / Pixel Default TimeoutFirst Checkpoint
Input dispatch5 secondsWhether main is running, runnable but not scheduled, or waiting on a lock/Binder
BroadcastAndroid 13 and below: Foreground priority 10s, background 60s; Android 14+ can extend to 20 / 120s during CPU starvationIntent flags in ANR subject, cold start duration, whether onReceive/goAsync finished in time
Execute serviceForeground service 20s; background 200sWhether onCreate/onStartCommand/onBind and cold start blocked the main thread
ContentProviderSpecified by caller using ContentProviderClient.setDetectNotRespondingWhether remote queries, cold start, and Binder thread pools are blocking
Version BoundariesThe above are current AOSP/Pixel default values; OEMs can adjust them. There are also standalone ANR types like foreground services failing to call startForeground() within 5 seconds or JobScheduler callback timeouts; don't judge all ANRs simply by "5 seconds".

8 High-Frequency Root Causes

  • Main thread I/O: File, DB, DNS, network, Binder, or large JSON/Proto serialization;
  • SharedPreferences: commit() writes synchronously; apply() writes asynchronously, but pending writes will be awaited by the framework during Activity/Service lifecycle transitions, potentially causing ANRs via QueuedWork. Prefer DataStore for new projects;
  • Lock contention/Deadlocks: main waiting for locks held by background threads, while background is waiting for main or synchronous Binder;
  • Synchronous Binder: Your stack is paused at BinderProxy.transactNative, the real slow point might be in system_server or another process;
  • Broadcasts and Services: Heavy lifting in onReceive, cold start initialization, onStartCommand; forgetting to call finish() after goAsync();
  • Layout storms: Deep nesting, repeated requestLayout, or high-frequency invalid Compose recompositions causing measure/layout timeouts;
  • GC thrashing: Large allocations in a short time pausing main frequently; a single GC trace isn't enough to convict, must be combined with Perfetto's allocation and scheduling timeline;
  • System load: main is Runnable but has no CPU for a long time, system_server is locked up, or GPU hang; it might not be your app's own long task.

Reading a trace: Follow the Lock Chain to the Real Holder

"main" prio=5 tid=1 Blocked
  | group="main" sCount=1 dsCount=0 flags=1 obj=0x... self=0x...
  | sysTid=18420 nice=-10 cgrp=default sched=0/0 handle=0x...
  | state=S schedstat=(...) utm=82 stm=21 core=4 HZ=100
  | held mutexes=
  at com.example.Cache.read(Cache.kt:48)
  - waiting to lock <0x07c1> (a java.lang.Object)
  at com.example.HomeActivity.onResume(HomeActivity.kt:91)

"sync-worker" prio=5 tid=27 TimedWaiting
  - locked <0x07c1> (a java.lang.Object)
  at android.os.BinderProxy.transactNative(Native method)
  at com.example.remote.ISyncService$Stub$Proxy.refresh(...)
  1. Check main state: Runnable means calculating or starving; Blocked means waiting for a monitor; Waiting/TimedWaiting requires seeing who it's waiting for; Native requires checking the top native method and Perfetto.
  2. Find the awaited object: Copy <0x07c1> and search the entire file for locked or "held by thread N" to locate the thread holding the lock.
  3. Follow the chain: If the holding thread is waiting on Binder/another lock, keep tracing until you find the ultimate runner; also check system_server and Binder thread stacks.
  4. Calibrate the snapshot: The trace might be captured after the timeout; if the top is nativePollOnce and main is idle, prioritize checking other events in the same cluster and Perfetto rather than guessing blindly.

Cure and Early Exposure

if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectAll()
            .penaltyLog()
            .penaltyDeath()
            .build()
    )
}
  • Move I/O and serialization down to bounded dispatchers, and design boundaries for cancellation, timeouts, and returning results to the main thread;
  • Do not execute I/O/Binder/callbacks while holding locks; shrink critical sections, replace shared mutable state with immutable snapshots or single-thread state machines;
  • Broadcasts should only schedule work; ensure they run using appropriate WorkManager/JobScheduler, don't wait for results in onReceive;
  • ANR-Watchdog can grab internal thread stacks early when threads are unresponsive for long periods, but it will false-alarm on debuggers, system starvation, and long frames, and it can't see full system ANR context; it's a supplementary observation, not a replacement for Vitals, ExitInfo, and bugreports.

*** *** *** *** *** *** *** *** *** *** *** *** *** *** *** *** *** *** ***
  1. Abort message: Intentional failures usually explicitly state the condition; handle this first—the one above clearly states the assertion file, line number, and condition;
  2. signal / code / fault addr: This example is SIGABRT (intentional termination, fault addr is empty); if it were SIGSEGV, this line would look like signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0—0x0 or very low addresses are often null pointers and field offsets; high random addresses are typically wild pointers/out-of-bounds, but must be cross-referenced with maps and sanitizer evidence; near the stack guard implies stack overflow;
  3. backtrace: Each line follows the format #frame_num pc relative_address library_path (symbol_name+offset) (e.g., #00 pc 00042c98 /system/lib/libc.so (tgkill+12)); find the first pc offset belonging to your own .so, don't stop at libc's memcpy/free;
  4. registers: Determine which register holds the bad pointer based on the crashing instruction;
  5. memory map: Verify if the fault addr falls in a mapped area, if permissions match, and verify the library's Build ID. Symbol files must exactly match the ABI and Build ID of the production APK.

The Symbolication Trio

# List candidate directories first; use readelf -n to match the Build ID in the tombstone, never silently pick an old hash
find app/build/intermediates/cxx -type d \
  -path '*/RelWithDebInfo/*/obj/arm64-v8a' -print

# Single .so + relative PC; -C deobfuscates C++ names, -f shows functions, -e specifies ELF

From Hit Point to Root Cure in Source

  • UAF/Double Free: Clarify object ownership, prefer RAII and std::unique_ptr; only use shared_ptr when passing shared lifecycle across threads, and design stop/reclaim order;
  • Out of Bounds: Validate all lengths and offsets in one place, use containers/views with bounds; add unit tests and fuzzing for truncation, oversized, and malformed inputs to parsers;
  • JNI Contracts: Check Java exceptions, local/global refs, and thread attachments; forbid saving local refs across threads, handle ClassLoader and unload boundaries when caching method/class IDs; enable CheckJNI to expose these issues during development instead of waiting for a production native crash (see CheckJNI section below);
  • Stack Overflow: Eliminate unbounded recursion and huge stack arrays, switch to iteration/heap allocation and cap depths;
  • Recurrence Prevention: Rerun original inputs under the same sanitizer after fixing, then add release symbol upload verification, ABI smoke tests, native unit test/fuzzing, and production GWP-ASan sampling.
Most Common Invalid ActionSymbolicating with the wrong version of so. Just because an address can "spit out a function name" doesn't mean the result is reliable; always verify ABI, Build ID, and version number before looking at the source line.

CheckJNI: Expose JNI Contract Violations Early During Development

Enabled by default on emulators (logcat shows CheckJNI is ON); how to enable on physical devices:

# Without root, only affects processes started afterwards
adb shell setprop debug.checkjni 1

# With root, enable persistently at the system level

Apps with android:debuggable="true" will also enable it automatically. CheckJNI will directly crash and block in the following scenarios, rather than letting it quietly run into a native crash later:

Check CategoryTypical Trigger Scenario
Bad Reference/Bad PointerPassing a freed jobject/jarray/jstring back to JNI; passing NULL when an object is expected
Thread OwnershipUsing a JNIEnv* that doesn't belong to it from the wrong thread (each thread's JNIEnv* cannot be used across threads)
Calling JNI with Pending ExceptionMaking a new JNI call while an uncleared Java exception exists (exceptions are DeleteGlobalRef/DeleteLocalRef/exception-related functions, which are allowed when an exception is pending)

The two most common pitfalls for local references: bulk creating local refs in loops without releasing them (should use DeleteLocalRef or wrap with PushLocalFrame/PopLocalFrame); local refs created in native threads attached via AttachCurrentThread will not be automatically released until the thread detaches, must be manually deleted. The most common pitfall for global references is using == to check if two refs point to the same object—you must use IsSameObject. Official docs emphasize "you cannot assume that object references are constant or unique".

Development Guardrails and Memory Tools

  • StrictMode: Expose main thread disk/network, leaked Closeables and registered objects early in debug; penaltyDeath is only for development builds;

Play Console & Firebase: Two Lenses on Production Issues

Android Vitals: Look at Impact First, Then Slice Dimensions

"User-perceived" is not the sum of all background exceptions. Metrics are calculated based on the percentage of daily active users experiencing at least one event: User-perceived Crashes refer to unhandled crashes while the App is displaying an Activity or running a foreground service; current User-perceived ANRs only count Input dispatching timed out. Play's current core bad behavior thresholds are: crash rate 1.09%, ANR rate 0.47%; for a single phone model both are 8%, while for Wear OS single watch models it's 4% and 5% respectively. Play evaluates quality daily using the last 28 days of data; exceeding thresholds may affect visibility and show store warnings.

  1. Check new clusters first: New issues appearing suddenly in the same version are usually more actionable than multi-year backlog;
  2. Slice by App version: Confirm if it was introduced by a new version, or if old version users haven't upgraded;
  3. Slice by OS / model: Single OEM, single GPU, single Android version spikes—prioritize checking compatibility and system stacks;
  4. Slice by country/track: Network, regional configs, rollout cohorts might change trigger conditions;
  5. Compare affected users, not just counts: One user crashing in a loop 100 times versus 100 users crashing 1 time each have different mitigation priorities.

Different denominatorsVitals typically calculates per daily active user; Crashlytics provides both crash-free users and crash-free sessions. ApplicationExitInfo: Recover Previous ANR Traces on Next Startup

Starting from Android 11 (API 30), you can query historical exit reasons on the app's next startup; ANR records often include system-captured traces. It is excellent for supplementing online evidence when "user device cannot connect to adb", but doesn't guarantee a trace for every record, nor is it a real-time ANR callback.

class ExitInfoReporter(
    private val context: Context,
    private val store: ExitCursorStore,
    private val upload: suspend (ExitEnvelope) -> Unit
) {
    private val collectMutex = Mutex()

    suspend fun collect() = collectMutex.withLock {
      withContext(Dispatchers.IO) {
        if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) return@withContext

        val am = context.getSystemService(ActivityManager::class.java)
        val records = am.getHistoricalProcessExitReasons(
            context.packageName, 0, 32
        ).sortedWith(compareBy({ it.timestamp }, { it.processName }, { it.reason }))

        for (info in records) {
            val eventKey = listOf(
                info.timestamp, info.processName, info.reason, info.status
            ).joinToString(":")
            if (!store.shouldAttempt(eventKey, System.currentTimeMillis())) continue

            try {
                val trace = info.traceInputStream?.use { input ->
                    input.readAtMost(512 * 1024)        // API 30 compatible and size constrained
                }
                upload(
                    ExitEnvelope(
                        eventKey = eventKey,
                        timestamp = info.timestamp,
                        processName = info.processName,
                        reason = info.reason,
                        status = info.status,
                        importance = info.importance,
                        description = info.description,
                        pssKb = info.pss,
                        rssKb = info.rss,
                        traceGzip = trace?.let(::gzip)
                    )
                )
                store.markUploaded(eventKey)
            } catch (retryable: RetryableUploadException) {
                store.scheduleRetry(eventKey, retryable) // Exponential backoff with limit, don't dead-letter just based on offline count
                continue
            } catch (io: IOException) {
                store.scheduleRetry(eventKey, io)
                continue
            } catch (permanent: PermanentUploadException) {
                store.markDiscarded(eventKey, permanent) // Discard only on deterministic permanent errors like schema/permissions
                continue                                // Don't swallow Error and unknown exceptions, keep throwing up
            }
        }
      }
    }

    private fun InputStream.readAtMost(limit: Int): ByteArray {
        val output = ByteArrayOutputStream(minOf(limit, 64 * 1024))
        val buffer = ByteArray(16 * 1024)
        var remaining = limit
        while (remaining > 0) {
            val count = read(buffer, 0, minOf(buffer.size, remaining))
            if (count == -1) break
            output.write(buffer, 0, count)
            remaining -= count
        }
        return output.toByteArray()
    }
}
  • Call it outside the cold start critical path, put it in a constrained background task; shouldAttempt/scheduleRetry persists next retry time and uses exponential backoff with limits. Don't dead-letter just based on offline retries; discard only on deterministic permanent errors like schema/permissions. Do not catch all Throwables;
  • Deduplicate idempotently by eventKey (timestamp + process + reason + status) on both local and server sides, and save App version, device/OS, feature flags;
  • Govern REASON_ANR, REASON_CRASH, REASON_CRASH_NATIVE, REASON_LOW_MEMORY separately; REASON_USER_REQUESTED is not an app crash;
  • The trace might be retained with the record even if the process later exits for other reasons; must be judged in combination with reason, timestamp, and content.

Master 08

Intractable Issue Detective Work: Turning the Unobservable into the Verifiable

🧩Script 1: Hard to Reproduce, Few SamplesCLUSTER

Evidence Collection: Cluster by version, model, OS, country, network, account status, and feature flags; check affected users and cardinality for each dimension first to avoid treating 100% of a small sample as the main cause.

Progression: List falsifiable hypotheses → add low-cardinality keys/state transition logs for the highest priority hypothesis → targeted rollout → compare hit group with control group. Only change one observable variable at a time.

📱Script 2: Crashes Only on a Specific OEM ROMOEM

Evidence Collection: Confirm if the crash frame belongs to the App, public Android API, or OEM framework; find AOSP/other OEM controls for the same Android version, collect Build fingerprint and system component versions.

Eradication: Prefer switching to public APIs; reflection compatibility should detect capabilities rather than guess brands, with a no-op/fallback path. Submit minimal repro, bugreport, time, and model to OEM channels; don't swallow all Throwables in the business layer.

🧠Script 3: Everything Looks Like an OOMMEMORY
# fd and threads are two independent budgets; /proc visibility is restricted by version and permissions
PID=$(adb shell pidof -s com.example.app)
adb shell ls -l /proc/$PID/fd | wc -l
adb shell 'cat /proc/'$PID'/status | grep -E "Threads|VmRSS"'
adb shell cat /proc/$PID/limits

Triage: Java heap space check hprof dominator; pthread_create failed check thread creation stack/count; EMFILE check fd type. If ExitInfo is LOW_MEMORY/LMK, combine with RSS/PSS and system pressure; don't just tune Java heap.

🔒Script 4: Stuck but No ANR YetDEADLOCK
PID=$(adb shell pidof -s com.example.app)
adb shell kill -3 $PID        # Request Java thread dump from ART process, output location varies by OS
adb logcat -d -v threadtime > manual-thread-dump.log

Capture 2-3 copies consecutively: identical lock chains without movement look more like deadlocks, while a progressing stack might just be slow. When main is waiting for a lock, find the owner; if the owner is in Binder/IO, trace further down; debugger attach changes timing and should only be used as a supplement.

🧯Script 5: Startup Crash Storm, Users Can't Open the AppRECOVERY

Fuse: Record startup attempts at the earliest and most stable process entry point possible; if the same version fails N times consecutively in a short period, enter minimal recovery mode: turn off remote switches, skip optional initializations, clear safely rebuildable caches, and show a recovery/feedback portal.

Boundaries: The counter must be persisted across processes and have a successful startup reset, time window, and version isolation; do not automatically delete user databases or login states. Ultimately, the root cause must still be fixed; the fuse is only responsible for stopping the bleeding.

✂️Script 6: Bisecting Unknown RegressionsBISECT
git bisect start
git bisect bad BAD_COMMIT
git bisect good LAST_KNOWN_GOOD
# Use the same automated reproduction script to evaluate each time, then execute git bisect good/bad
git bisect reset

When there is no stable reproduction, bisect feature flags, initialization modules, or request paths instead; CI should save every candidate artifact and mapping. An unstable evaluation script will pollute the entire bisection; quantify the false positive rate first.

Three High-Value Task-Oriented Prompts

💥Stack → Source Code Root CauseSTACK

"Start from the deepest cause and find the first business frame; trace upwards along the parameter/state production chain. Output where null values/invalid states entered from, why they didn't fail at the boundary, and which callers need to be read. Do not treat null checks as default answers."

⏳ANR → Lock Chains and SchedulingTRACE

"First determine if main is Running/Runnable/Blocked/Waiting; if waiting for a lock, trace the owner by object address down to the running thread; if Binder, point out which peer/system_server trace segment is needed; distinguish between App blocking, CPU starvation, and late snapshots."

🗂️Top 20 → Root Cause PortfoliosPORTFOLIO

"Do not mechanically group by exception class. Cluster by common root cause/fix levers: lifecycle, state boundaries, version compatibility, memory budgets, threads/locks, symbol/release chains. Output affected users, consolidatable fix items, priorities, and responsible modules."

AI Anti-Hallucination Verification Protocol

  1. Cite Evidence: All facts must point to stack frames, source code lines, distributions, or official docs; if they cannot be cited, mark them as hypotheses.
  2. Counterexample Checks: Proactively ask "What evidence would overturn this conclusion? Why didn't the normal control group trigger this?".
  3. Tool Verification: Let the AI provide commands, but execute them in a controlled environment; backfill the command output before updating probabilities.
  4. Minimal Patch: Only modify the root cause path and attach failing tests; do not accept large-scale "convenient refactoring".
  5. Independent Review: A second agent looks only for misattributions, uncovered boundaries, and regression risks, ignoring the first agent's "confidence".
  6. Online Closed Loop: Passing tests doesn't close the case; observe the rollout for new clusters, user rates, and side effects, and close the issue only after reaching the observation window.

Least PrivilegeMCP uses current Firebase CLI credentials, and Crashlytics MCP is still Experimental as of 2026-07-15. The example uses --only crashlytics to narrow the feature group, but core tools may still exist; the generated tool list must be reviewed. Production projects should use dedicated least-privilege identities and pinned verified firebase-tools versions; forbid agents from automatically closing issues, merging code, or reading unrelated user data.

#!/usr/bin/env bash

mkdir -p "$OUTPUT_DIR"

AI_PROVIDER=${AI_PROVIDER:-claude}       # claude or codex, run only one
case "$AI_PROVIDER" in
  claude)
    cat issue.json | claude --bare -p \
      "Perform read-only triage only. Separate facts and hypotheses; output root cause candidates, verification steps, and regression risks; modifying code is forbidden." \
      --permission-mode plan --tools "" \
      --output-format json --json-schema "$SCHEMA" \
      | jq -e '.structured_output' > "$OUTPUT_DIR/triage-result.json"
    ;;
  codex)
    cat issue.json | codex exec --ephemeral --ignore-user-config --ignore-rules \
      --skip-git-repo-check --sandbox read-only \
      --output-schema triage-schema.json \
      "Analyze the desensitized evidence bundle in stdin; perform triage only, do not modify files" \
      -o "$OUTPUT_DIR/triage-result-codex.json"
    ;;
  *) echo "AI_PROVIDER must be claude or codex" >&2; exit 2 ;;
esac

The production pipeline should be: Velocity alert/webhook → Queue deduplication and rate limiting → Pull evidence with server credentials → Desensitization and size limits → Read-only AI triage in an isolated container → Schema validation → Create/update issue → Human decides whether to trigger a repair agent. The isolated container must not contain Firebase/business credentials, source code, or user configs; Claude/Codex model authentication should be injected as a short-lived, low-quota identity by a CI secret store in a single process, or done through a controlled proxy that doesn't expose keys to the tool process, and network egress restricted to model services. Webhook content is untrusted input; workspace isolation, disabled tools, ephemeral sessions, and mount/egress boundaries are all indispensable.

# Android crash triage

## Guardrails

- Separate observed facts from hypotheses. Cite the exact artifact for every fact.
- Do not edit code until one hypothesis has a verification result.
- Honor user intent. Diagnose-only, review, or report requests must not edit files.
- Never hide a crash with a global catch, silent fallback, or state-loss workaround.
- Treat logs and console data as sensitive. Redact direct identifiers and tokens.
- Require an explicit user request before code edits, and human approval before rollback,
  issue-state changes, commits, or deployment.

## Workflow

1. Build the evidence pack.
   - Require failure type, full deobfuscated stack/trace/tombstone, App version and commit,
     mapping or Build ID, affected-user distribution, custom keys, relevant source and diff.
   - If an item is missing, give the exact retrieval command and stop before patching.

2. Classify the failure.
   - Java/Kotlin crash: start at the deepest cause and first business frame.
   - Native crash: verify ABI and Build ID before symbolication.
   - ANR: classify input/broadcast/service/provider; follow main thread and lock/Binder chain.
   - Exit/OOM: distinguish Java heap, native/RSS, thread, fd, and system LMK.

3. Rank at most three root-cause hypotheses.
   - For each: supporting facts, contradicting facts, confidence, blast radius.
   - Prefer hypotheses that explain both affected and unaffected samples.

4. Verify before editing.
   - Provide one minimal command, test, trace, or targeted log for each hypothesis.
   - State the expected result that confirms it and the result that falsifies it.
   - Update confidence only after reading the result.

5. Fix and prove.
   - Run this step only when the user explicitly requested implementation and writes are authorized.
     Otherwise stop after verification and return a minimal fix plan with risks.
   - Write or preserve a failing reproduction test first where feasible.
   - Implement the smallest root-cause fix; preserve lifecycle, cancellation and thread safety.
   - Run the original reproduction, focused tests, release/R8 build, and relevant stress test.

6. Prevent recurrence.
   - Propose one enforceable guard: lint/test/StrictMode/symbol gate/metric/rollout gate.
   - Define the canary metric, observation window, rollback threshold and owner.

## Output

Return these headings exactly:
1. Impact and classification
2. Verified facts
3. Missing evidence
4. Ranked hypotheses
5. Verification plan and results
6. Minimal fix and risks
7. Regression tests
8. Rollout and prevention

Keep SKILL.md concise, put deterministic repetitive work into scripts/: e.g., retrace-stack.sh handles finding mappings by version and validating, unpack-bugreport.py extracts only ANR/tombstone/logcat indices, check-native-build-id.sh compares tombstones with so files. Scripts must fail and exit on missing/multiple candidate versions; "guessing the closest one" is forbidden. Put team schemas, severity levels, and privacy rules in references/, load on demand, and don't cram all background into the main Skill body.

SLOs and Error Budgets: Far Below Platform Red Lines

Play's bad behavior threshold is a store penalty line, not a quality goal. Teams should set stricter SLOs based on business criticality, historical baselines, and user scale, and separate new issues from existing debt. The following is just a sample starting point, not an official Android goal:

MetricSample GoalGates
User-Perceived Crash RateCritical Apps ≤0.20%, or crash-free users ≥99.8%Pause immediately if a new version degrades against baseline and stats are reliable, don't wait until 1.09%
User-Perceived ANR Rate≤0.10%Trigger a task force for new input dispatch clusters or single-model spikes
Startup/Core Path CrashesZero tolerance for new onesStop the bleeding first for any reliable new cluster
Evidence Completeness RateTop issues ≥95% have matched versions and identifiable ownersMissing mapping/symbol/version archives treated as a release chain failure

On-Call SOP: Triage → Stop Bleeding → Eradicate

  1. Triage: Base on user impact, growth rate, core paths, and recoverability, rather than exception names; startup storms/data corruption have the highest priority.
  2. Stop Bleeding: Pause rollouts, rollback, flip switches, server-side degradation, or recovery modes; record the time and effect of every action.
  3. Eradicate: Build evidence bundles, verify hypotheses, make minimal fixes, run regressions, and rollout; bleed-stopping patches cannot replace permanent fixes.
  4. Review: Answer "why did it happen, why didn't tests catch it, why didn't monitoring catch it earlier, what automated mechanism can prevent similar issues".

One-Page Closure Checklist

  • Impact and version scopes quantified; Play vs Crashlytics reporting metrics specified;
  • Primary evidence matched, root causes have reproducible/falsifiable results, not just inferred via AI/clustering;
  • Bleed-stopping and permanent fixes recorded separately, patches have original repros and boundary regressions;
  • Rollout observation windows, success metrics, rollback thresholds, and owners explicitly defined;
  • Similar defense lines added to at least one of lint/test/StrictMode/release gates/monitoring;
  • Crashlytics/ticket notes link to PRs, verification evidence, and RCAs, making it easy for the next on-call person to trace.
