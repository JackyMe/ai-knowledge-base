导读 00

全景:为什么 2026 年这件事突然变得"非做不可"

设计-代码鸿沟:不是工具问题,是结构问题

2024 年之前,设计师在 Figma 标注像素,开发者照着重写。通用 AI 编码工具(早期的 Copilot)只能基于"全网见过的模式"生成"看起来差不多"的组件,完全看不见你的设计系统。出来的代码像是"设计稿的远房表亲"——配色偏一点、间距错几像素、hover 态没文档,改起来比从零写还累。

2026 年,三件事一起成熟,把鸿沟压到了可忽略的尺度:

  1. MCP(Model Context Protocol)成事实标准——pen.dev、Figma、Google Stitch 都暴露了 MCP 服务器,Claude Code / Codex 装上就能"读到"设计稿的精确结构、Token、节点关系,不再是看图猜。
  2. 设计工具原生支持"画 + 码"双产出——pen.dev 的 .pen 文件是 JSON,Git 可 diff;Figma 的 Dev Mode + Variables 暴露结构化数据;Stitch / Galileo 直接吐组件代码。
  3. 真机/虚拟回归成本归零——Paparazzi / Roborazzi 在 JVM 上跑 Compose 截图,AI 改 UI 后 30 秒内拿到全设备快照,反馈环短到能进 CI。
这一页的承诺学完你能做:① 给任意设计工具(pencil / Figma / Stitch)装上 MCP,让 Claude Code 直接读;② 把 Figma Variables → Material 3 Color Scheme → Compose Theme 一路串通;③ 让 AI 改 UI 后,Paparazzi / Roborazzi 自动比对回归;④ 判断什么活该 AI 做、什么活必须手写。

三件事你必须先认同

  • 设计稿是"一等公民"输入——和 PR、issue、CLAUDE.md 同级。不是参考图,是 source of truth。
  • 设计 Token 优先于视觉——AI 改色,改的是 colorScheme.primary 而不是某个十六进制;改间距,改的是 Spacing.md 而不是 16.dp。
  • 回归必须有低成本闭环——AI 30 秒出一个 PR 没人看得过来,必须靠截图自动比对 + 关键属性断言,异常才推人。

地图 02

AI 编码代理如何"看到"设计:三种通道

AI 编码代理(Claude Code、Codex 等)拿设计输入,本质只有三种通道。理解差异才能选对:

通道代表能拿到什么精度代价
MCP 结构化 Figma MCP、pen.dev MCP、Stitch MCP 节点树、Token 键值对、组件实例、变量定义、可访问性属性 零损耗——拿到的是结构化数据,不是渲染后的图像 需要 MCP 服务在跑;每个工具的 MCP 工具集不一样
视觉 截图 / 拍照 / 录屏;Claude / GPT 的多模态 看起来什么样,大概有什么元素 中——颜色能读准,数值(具体间距、字号)猜不准 快、无依赖,任何时候都能用;不能拿 Token
导出物 Figma Dev Mode "Copy as Compose"、pen.dev 导出 React、Stitch "Export to Code" 设计工具自己生成的代码片段 高(但有工具的固有限制) 一次性的复制粘贴,没法双向同步
MCP 是 2026 年的"分水岭"用了 MCP,Claude Code 在生成代码时能说"主色用 colorScheme.primary,因为 Figma 那边叫 brand/primary/500";不用 MCP,它只能看截图说"这里用蓝色"。前者是设计系统协同,后者是像素级仿写。下面所有讨论默认走 MCP 通道。

三种通道的具体接法

① Figma MCP(官方 · 最稳)

# 装官方 plugin(最简)
claude plugin install figma@claude-plugins-official

# 或手工加 MCP server
claude mcp add --transport http figma https://mcp.figma.com/mcp

# 验证
claude mcp list
# 应该看到 figma / connected

在 Figma 文件里选中一个 Frame → Claude Code 里说"用 Figma MCP 读这个 Frame 的结构与变量,生成对应的 Compose 实现",工具会自动调用。核心工具:

工具干什么
get_design_context返回结构化 React + Tailwind 表示(对 Web 最友好;Android 需要后续翻译)
get_variable_defs抽取 Variables(色板、字号、间距)及其 Light/Dark 模式
get_metadata高层节点地图:什么 Frame、什么组件、层级关系
get_screenshot视觉参照(像素级)

Codex 用 config.toml 的 [mcp_servers.figma] 块加 url = "https://mcp.figma.com/mcp" 同理可达。

② pen.dev MCP(原生,本地,零云)

装好 VS Code 扩展 highagency.pencildev 后,pen.dev 自带的 MCP 服务跑在本机——设计数据不出本地,适合隐私敏感场景。Claude Code / Codex 用 /mcp 看到 pencil 后,工具集更细:读节点、执行修改、读变量、截图。详见 pen.dev × Claude Code 专题。

③ 视觉通道(任何时候的兜底)

没有 MCP 时,最朴素也最万能的做法:把设计稿截图(或 PDF)直接喂给 Claude Code,搭配提示词说明"按截图生成 Compose,色值用 Material 3 ColorScheme 的语义化命名"。像素能拿,但 Token 拿不到——所以这一步要么补 Figma Variables 的导出,要么接受"出来的代码配色和品牌色对不上"的风险。

Codex 的 MCP 现状Codex 0.146.0 起原生支持 MCP(同 Claude Code 一样的协议),config.toml 配 [mcp_servers] 即可。差异在 UX:Codex 更倾向"任务交付型",要明确说"读完 Figma Frame 后直接改 Android 项目";Claude Code 倾向"探索型",你可以一路问"为什么这个色用 primary 不用 secondary"。
端到端 03

Android 端到端:五步流水线

把上面所有工具拼起来,就是这条最高效率路径。每步都有可复现的输入输出,不依赖任何"灵感":

STEP 1
🎨
设计 Token
Figma Variables
STEP 2
🖼
组件/页面
Figma Frame
STEP 3
🤖
读取 + 计划
Claude Code / Codex
STEP 4
⚙️
生成代码
Compose + 单元测试
STEP 5
📸
视觉回归
Paparazzi / Roborazzi

为什么是 5 步不是 3 步?少一步就要么少了 Token 同步(设计改了色代码没改),要么少了回归(AI 改 UI 没人审)。这 5 步可以并行(多页面同时推进)但不能省。

STEP 1 · 设计 Token:Figma Variables 是事实源

设计 Token 是颜色 / 字号 / 间距 / 圆角的命名化值。在 Figma 里长这样:

brand/primary/500      → #476810
brand/primary/600      → #3a5609
brand/secondary/500    → #586a4f
surface/background     → #fefbff
surface/onBackground   → #1b1c18
text/display/large     → 57sp / 64lh
text/title/medium      → 16sp / 24lh
spacing/xs             → 4dp
spacing/md             → 16dp
radius/lg              → 16dp

这一步在 Figma 端用 Material Theme Builder(material.io/material-theme-builder)或 Figma 自带的 Material 3 Design Kit 完成;Claude Code 这一步什么都不做——它是结构化背景,后面要用。

STEP 2 · 组件/页面:Figma Frame 是契约

每个要实现的页面在 Figma 里是一个 Frame,Frame 命名要稳定(开发会拿来当 key):

📁 Figma: App / 1.0
  📄 Page: ProductDetail
    🟦 Frame: ProductDetailScreen / 360×800 (mobile)
    🟦 Frame: ProductDetailScreen / Dark

用 Auto Layout(Figma 的 Flexbox)+ 100% 约束,这样 Claude Code 读 get_metadata 拿到的就是结构化布局,不是绝对坐标。

STEP 3 · 读取 + 计划:Claude Code / Codex 启动

在 Android 项目根目录(已有 app/ 源码)启动 Claude Code,给一段明确指令:不要让它"自己想办法",把读什么、写哪里、测什么写死。

PROMPT 03-A · 启动
读 Figma Frame `ProductDetailScreen` (node-id 1:23),用 figma MCP。 - 先调 get_variable_defs,把所有 Variables 落到 app/src/main/java/.../theme/Color.kt 和 Type.kt(语义名对齐 Material 3) - 再调 get_design_context 和 get_metadata,理解 Frame 的结构 - 然后规划:1) 哪些 Composable;2) 哪些 Preview;3) 哪些 Paparazzi 测试;4) 哪些 Preview 截图入仓 - 计划用 ExitPlanMode 给我审,不要直接动手
为什么要"先计划后写码"Claude Code 的 Plan 模式(Shift+Tab 切)会先探查代码,生成可审的实施步骤再执行。改 UI 是高频返工区——一步错后面截图全红。花 2 分钟审计划 = 省 20 分钟重做。Codex 同理(--plan 模式)。

STEP 4 · 生成代码:Compose + 测试 + 截图三件套

AI 实际会写出三类产物,缺一不可:

  1. Composable 函数——业务组件;用 Token 不用硬编码是核心纪律(MaterialTheme.colorScheme.primary 而不是 Color(0xFF476810))。
  2. @Preview 注解——让 Android Studio 的 Design 面板能直接看;Roborazzi 会扫这个注解自动生成截图测试。
  3. Paparazzi / Roborazzi 测试——上一组基线快照,后面 AI 改 UI 用同一份基线 diff。
PROMPT 03-B · 实施
按计划实施,约束: 1. Composable 用 Material 3 API,所有色/字/间距走 MaterialTheme.colorScheme/typography/shapes 2. 不要硬编码颜色值;spacing 走 Spacing.xs/sm/md/lg 常量 3. 每个屏幕组件加 @Preview(name = "Light"),@Preview(name = "Dark", uiMode = UI_MODE_NIGHT_YES) 4. 加 src/test/.../ProductDetailSnapshotTest.kt 用 Paparazzi 跑两个 Preview,先 recordPaparazzi 入基线 5. 完成后跑 ./gradlew verifyPaparazziDebug 给我看结果

STEP 5 · 视觉回归:Paparazzi / Roborazzi 二选一

这一步是整条流水线的质量门。详见 真机/虚拟截图回归章节,核心一句话:AI 改 UI 前先有基线,改完自动 diff,异常才推人。

端到端 04

Figma → Material 3 Token:一条标准桥

Material 3 的 ColorScheme / Typography / Shapes 是 Compose 的一等设计 Token;Figma Variables 是设计端的一等设计 Token。两者必须严格一一对应,否则"设计改了代码没改"是必然。

官方标准做法:Material Theme Builder

  1. 在 m3.material.io/theme-builder 选基色 + 二级色,工具自动展开成 M3 调色板(13 个 tone 之一给每个 role)。
  2. 导出"Jetpack Compose"格式,得到 Color.kt(5 个 key color + 衍生 role)和 Theme.kt(lightColorScheme(...) / darkColorScheme(...))。
  3. 把这两个文件落进 app/src/main/java/.../ui/theme/。
  4. 在 MainActivity 用 ReplyTheme(或你命名的主题)包 setContent { ... }。
  5. 把同样的"基色 + 二级色"在 Figma Material 3 Design Kit 里也设一份(插件自带同步),Variables 自动对齐。

Figma Variables ↔ Compose ColorScheme 完整映射

Material 3 ColorScheme 的所有 role 与 Figma Material 3 Design Kit 的 Variables 命名完全一致(都是 primary / onPrimary / primaryContainer / onPrimaryContainer / secondary / onSecondary / ...),Claude Code 用 Figma MCP 的 get_variable_defs 读出来,直接写到 lightColorScheme(primary = Color(0xFF...), ...) 即可。下面是完整 role 清单(便于你核对没漏):

// M3 ColorScheme 完整 32 个 role(亮/暗各一套)
lightColorScheme(
  primary, onPrimary, primaryContainer, onPrimaryContainer,
  secondary, onSecondary, secondaryContainer, onSecondaryContainer,
  tertiary, onTertiary, tertiaryContainer, onTertiaryContainer,
  error, onError, errorContainer, onErrorContainer,
  background, onBackground,
  surface, onSurface, surfaceVariant, onSurfaceVariant,
  outline, outlineVariant,
  inverseSurface, inverseOnSurface, inversePrimary,
  surfaceTint, scrim,
)

Typography 与 Shapes 的桥

M3 Typography 是 15 个 TextStyle(displayLarge/Medium/Small、headlineLarge/...、titleLarge/...、bodyLarge/...、labelLarge/...),Shapes 是 5 个 RoundedCornerShape(extraSmall/small/medium/large/extraLarge)。

Figma 端要保持用 Figma Material 3 Design Kit 的官方组件——它的 Text Styles 与 Shape 命名跟 M3 一致,Claude Code 读 get_metadata 时能直接 map。

动态色(Material You)与品牌色怎么平衡Android 12+ 设备有系统取色(dynamicLightColorScheme(LocalContext.current)),你的品牌色要不要被覆盖是产品决策。常见做法:① 强品牌 → 关动态色,始终用品牌 ColorScheme;② 弱品牌(消费类)→ 开动态色,但单独保留 1-2 个品牌强调色不进 ColorScheme,改用 ExtendedColors 自定义。Claude Code / Codex 处理这种决策时,要在 CLAUDE.md / AGENTS.md 里写明。

动态色 vs 品牌色:决策矩阵

产品类型动态色品牌色做法
金融 / 工具型(强品牌识别)关始终用品牌val colors = if (darkTheme) DarkColors else LightColors 不用 dynamicXxx
消费 / 内容型(用户主导)开仅强调按钮/LogodynamicXxx 作主,品牌色作 ExtendedColors.brand 单独取
企业内嵌 / 白标关运行时可换ColorScheme 不写死,从后端/BuildConfig 拉
端到端 05

Compose 代码生成与回写:AI 改 UI 的纪律

这一步是"出活"环节,也是最容易出"看起来能用、实则跑不起来"代码的环节。下面是从 30+ 真实 PR 里收敛出的纪律:

纪律 1:Token 优先,绝不硬编码

❌ 硬编码(常见 AI 出错姿势) 
Text("Save",
  color = Color(0xFF476810),
  fontSize = 16.sp,
  modifier = Modifier.padding(16.dp)
)
✅ 走 Token(纪律) 
Text("Save",
  style = MaterialTheme.typography.titleMedium,
  color = MaterialTheme.colorScheme.primary,
  modifier = Modifier.padding(Spacing.md)
)

纪律 2:任何状态变化都用 State hoisting

AI 经常写出"组件自己 remember { mutableStateOf(...) }"的代码——预览能跑,真用就坏。规则:无状态 Composable 优先,状态从调用方传进来,事件回调出来。

PROMPT 05-A · 改 AI 出错的 Compose
检查 src/.../ProductDetailScreen.kt,把所有内部 remember { mutableStateOf } 改成 hoisted 参数;Preview 里包 remember。改完用 ./gradlew :app:compileDebugKotlin 验证。

纪律 3:每一个 Composable 至少一个 @Preview

这是 Paparazzi / Roborazzi 能跑回归的前提,也是设计-开发协作的最低成本反馈——AI 写完,Android Studio Design 面板里直接看,不用装到设备。

@Preview(name = "Light", showBackground = true)
@Composable
private fun ProductDetailScreenLightPreview() {
  AppTheme(darkTheme = false) {
    ProductDetailScreen(state = fakeState(), onIntent = {})
  }
}

@Preview(name = "Dark", showBackground = true, uiMode = UI_MODE_NIGHT_YES)
@Composable
private fun ProductDetailScreenDarkPreview() {
  AppTheme(darkTheme = true) {
    ProductDetailScreen(state = fakeState(), onIntent = {})
  }
}

纪律 4:从代码回写设计系统

设计师改 Figma → Claude Code 改 Compose 是正向;反过来呢?改完 Compose 跑通了才发现"按钮圆角和 Figma 不一致",谁改谁?

规矩:谁先合并谁负责同步。Figma 是源就改 Figma;代码是源(改 token 配)就改 Figma Variables。最忌讳两套都改,最后谁都不知道哪边是对的。

具体回写流程(以 Figma 为源):

  1. 设计师在 Figma 改 Variables(比如 brand/primary/500 从 #476810 改 #507810)。
  2. 设计师不直接改 Compose 代码,发 Slack / 邮件 / 评论说"primary 改了,看 PR"。
  3. Claude Code 读 Figma MCP get_variable_defs → 比对 Color.kt → 生成 patch → 提 PR。
  4. PR 跑 Paparazzi 回归 → 绿就合;有非预期 diff 推设计师确认。
双向同步的隐藏陷阱设计 Token 同步不像业务代码——它影响的不是单页面,而是整个产品的视觉。一个手抖的色值改动可能让 Paparazzi 一次红 200 张图。建议:Token 改动走单独 PR 分支,先在内部测试包验证完再发生产。这不是 AI 编码代理的问题,是流程问题。
质量 06

真机/虚拟截图回归:AI 改 UI 后的保险栓

AI 改 UI 30 秒出一个 PR,人眼审不过来。必须靠自动化视觉回归——AI 改完,机器比对所有页面截图,异常才推人。

为什么"真机测试"在 AI 时代反而退居二线

Instrumented test 跑一台 Pixel 6 要 90 秒,跑 10 台设备 15 分钟,根本跟不上 AI 改 UI 的速度。JVM 上的截图测试(Paparazzi / Roborazzi)几秒出全设备快照,才是新时代的正解。

Paparazzi(JVM 渲染,无设备)

由 Cash App 出品,在 JVM 上用 LayoutLib 渲染 Android View 与 Jetpack Compose,产出 PNG,可与基线 diff。优势:不依赖模拟器,CI 上跑比 Robolectric 还快。

配置用途
PIXEL_5 / PIXEL_6 / NEXUS_5设备尺寸 + DPI,影响 dp→px 换算
theme = "android:Theme.Material.Light.NoActionBar"传统 View 用;Compose 用 AppTheme 自己的
nightMode = NIGHT_MODE_NIGHT一次跑亮 + 暗两套快照

关键 Gradle 任务:

./gradlew :app:recordPaparazziDebug   # 首次录基线 → src/test/snapshots/
./gradlew :app:verifyPaparazziDebug   # 改完跑这个,有 diff 失败
./gradlew :app:testDebug               # 跑全部单元测试(包括 Paparazzi)

注意:Paparazzi 与 Robolectric 不兼容(都 mock Android Framework,只能选一个)。

Roborazzi(Robolectric 路线,可集成 Hilt)

由 takahirom 出品,基于 Robolectric 在 JVM 渲染 Compose,支持 @Preview 自动生成测试、与 Hilt 等 DI 框架无冲突。优势:可以测有依赖注入的真组件。

  • captureRoboImage() 给定节点截图

  • (实验)roborazzi-ai-gemini / roborazzi-ai-openai:用 AI 做"截图差异语义判定",能区分"故意改"和"误改"

质量 07

双向同步:让设计系统真正"活"起来

"设计系统"不是一张 Figma 页面,是会持续演化的活物。AI 编码代理在中间起到的作用是让设计 ↔ 代码的同步成本归零。

三种同步模式

① Figma → Code(正向,最常见)

设计师改 Figma → Claude Code 改 Compose,前面流水线讲的全是这一条。关键约束:设计师改完 Variables 后,要让 Claude Code 重新拉一次 get_variable_defs 再生成代码,不能基于缓存。

② Code → Figma(回写,设计师主导场景)

开发者改完 ColorScheme 想让 Figma 跟上,有两种做法:

  • Claude Code 生成 Figma REST API 请求——Figma 官方 API 支持改 Variables,AI 拼请求体推上去。门槛中等。
  • 导出 .css 风格的 Token JSON(Style Dictionary / Theo),让设计师手动 import 到 Figma 插件(如 Tokens Studio)。门槛低,但不是真的"自动同步"。

③ Figma ↔ Code 双向(高级,需要中间层)

用 Style Dictionary 或 Theo 做Token 单一来源(一个 JSON),Figma 用 Tokens Studio 插件同步,Compose 用 Gradle 插件生成 ColorScheme。一处改,两边自动跟。这是 2026 年设计系统工程的"正确姿势",但要小团队愿意花一周搭基础设施。

已知空白:Figma ↔ pen.dev 没有官方双向同步

2026-08-05 核对一手文档后,确认:Figma Variables 与 pen.dev Variables 之间没有任何官方"双向同步"链路——既没有 pen.dev 官方 plugin 推变量回 Figma,也没有 Figma 端原生读 .pen 文件格式的桥。两端都把变量暴露成可机器读的 JSON(Figma REST API、.pen 文件),但 1→1 的官方接口不存在。

如果你的设计系统在 Figma + pen.dev 之间并存,目前最实用方案是"四跳桥"(DTCG JSON 作枢纽):

Figma ←(Tokens Studio)→ DTCG JSON ←(Style Dictionary v4)→ .pen 文件 / Compose / iOS / Web

# 示例 A:Figma Variables → 本地 JSON
curl -sS -H "X-Figma-Token: $FIGMA_TOKEN" \
  "https://api.figma.com/v1/files/$FILE_KEY/variables/local" \
  | jq '.meta.variables, .meta.variableCollections' \
  > figma-variables.json

# 示例 B:Figma Variables 改色(POST,需 Tier 3 + Enterprise + file_variables:write scope)
POST https://api.figma.com/v1/files/{file_key}/variables
{
  "variableModeValues": [
    { "variableId": "VariableID:1:3", "modeId": "1:0",
      "value": { "r": 1, "g": 0, "b": 0, "a": 1 } }
  ]
}

# 示例 C:Style Dictionary v4 编译到 Compose
const sd = new StyleDictionary({
  source: ['design/tokens/tokens.json'],
  platforms: { compose: { transformGroup: 'compose',
    buildPath: 'app/src/main/java/.../theme/',
    files: [{ destination: 'Color.kt', format: 'compose/object',
      options: { className: 'AppColorScheme' } }] }
});
await sd.buildAllPlatforms();

中间桥梁的选择:

桥梁能力限制
Tokens Studio(原 Figma Tokens)Figma Variables ↔ DTCG JSON,30 万用户,9+ sync provider(GitHub/GitLab/JSONBin)UI 在 Figma 端,需要单独授权
Style Dictionary v4(Amazon 出品)DTCG JSON → Compose Kotlin / iOS Swift / Android XML / CSS / SCSS / Flutter Dart,多端覆盖只编译,不解决 Figma ↔ JSON 那段
自建脚本(Figma REST API + pen.dev CLI)完全可控,定时 + 触发都可需要写胶水代码 + CI 部署
小主提醒Figma Variables POST 接口需要 Tier 3 + Enterprise 完整席位 + file_variables:write scope,个人版账号写不进去;另外每个 Collection 限制 ≤ 40 modes、≤ 5000 variables,POST 请求体 ≤ 4 MB,变更以原子事务提交。核对日期 2026-08-05——如果之后发现 Figma 或 pen.dev 出了官方双向同步,这里会更新。

设计系统维护的 6 条纪律

  1. Token 命名即文档——surface/container/high 优于 gray-100。AI 看到语义名会知道用在哪儿,看到颜色名只知道是灰。
  2. 不直接用 Color.White 等系统色——所有色都走 ColorScheme,即使"我就是要白色"也用 colorScheme.surface。这样暗色模式自动反相。
  3. 间距走 Spacing.xs/sm/md/lg/xl 常量——4 / 8 / 16 / 24 / 32 起步,不要在 Composable 里随手写 13.dp。
  4. 圆角走 Shapes.small/medium/large——同理,不要 RoundedCornerShape(7.dp)。
  5. Typography 走 MaterialTheme.typography.*——不要 fontSize = 17.sp。
  6. 图标用 Material Symbols 或 Lucide——不要到处塞 SVG。Figma 端用 Material Symbols,R.drawable 也用同一份,跨端一致。
PROMPT 07-A · 审计设计纪律
扫描 src/main/java/.../ui 下所有 .kt 文件,列出: 1. 直接用 Color(0xFF...) 的位置(应改为 MaterialTheme.colorScheme.*) 2. 直接用 .dp 数字且不含 Spacing 引用的(应改为 Spacing.*) 3. 直接用 fontSize = N.sp 的(应改为 MaterialTheme.typography.*) 输出三张表,我来逐项改。
实战 08

真实案例:从 Figma 到 Play Store,一个商品详情页

把上面所有点串成一个端到端例子。背景:某电商 App 要加一个"商品详情页",设计稿在 Figma,代码在 Android Studio,5 个屏幕(Light/Dark × 2 状态 × 中英文),要求一周内 Play Store 上架。

Day 1 · 准备阶段(2 小时)

  1. 在 Figma 安装 Material 3 Design Kit(官方),把基色贴进去,生成 Variables。
  2. 导出 Variables 描述文件(JSON),存入 design/tokens/figma-variables.json,Git 跟踪。
  3. 在 Android 项目跑 ./gradlew :app:dependencies | grep material3 确认依赖在。
  4. 装 Claude Code 插件 figma@claude-plugins-official,claude mcp list 确认 figma connected。

Day 2-3 · 流水线打通(2 天)

  1. Claude Code 读 Figma Variables,生成 Color.kt / Type.kt / Shape.kt。
  2. 读 Figma Frame ProductDetailScreen,生成 Composable + @Preview + Paparazzi 测试。
  3. ./gradlew :app:recordPaparazziDebug 入基线(2 套亮/暗 × 中英 = 4 张)。
  4. 提交 PR #1:"design system 接入 + 详情页初版"。

Day 4 · 业务逻辑接入(1 天)

  1. 把 Composable 改成 hoisted state(ProductDetailScreen(state, onIntent))。
  2. 加 ViewModel + Hilt 注入,从 Repository 取数据。
  3. 用 fake state 写 Roborazzi 测试,模拟 loading / loaded / error 三态。
  4. ./gradlew :app:verifyPaparazziDebug 应该全绿(没改视觉)。
  5. 提交 PR #2:"业务接入"。

Day 5 · 设计师改动 + 同步(0.5 天)

  1. 设计师说"主色想调亮一点",改 Figma Variables 里 brand/primary/500。
  2. Claude Code 自动检测:读最新 get_variable_defs → 比对 Color.kt → 生成 patch。
  3. 跑 Paparazzi → 4 张基线有 diff → 人工 spot check → 接受。
  4. ./gradlew :app:recordPaparazziDebug 更新基线。
  5. 提交 PR #3:"品牌色调整",附 Paparazzi diff 截图。

Day 6-7 · 国际化 + 上架(1.5 天)

  1. 加 values-zh-rCN/strings.xml、values-en/strings.xml。
  2. 录新基线(中英各 2 套),Paparazzi 跑 8 张。
  3. Play Console 跑 Pre-launch report,真机/真网络再过一遍。
  4. 提交审核。

避坑 09

反模式与避坑清单

下面这些是社区(以及我自己的项目)反复踩过的坑,每条都附"为什么错"和"应该怎么做":

设计端反模式

❌ 设计师只导图,不给 Token

让 AI 看截图去"猜"色值,出来的代码和品牌永远差几度。

✅ 必须给 Variables JSON 或可访问的 Figma 文件

用 Material Theme Builder 一次到位,后面 Claude Code 自动对。

❌ 设计稿用绝对定位

所有元素 x=137, y=204, w=320,改文案就崩。

✅ 必须 Auto Layout + 100% 约束

AI 读到的 Flexbox 结构才能正确转成 Compose Row/Column/Box。

❌ 一个 Frame 塞 5 个屏幕

AI 不知道怎么切 Composable 边界。

✅ 一个 Frame = 一个 Composable

Figma Frame 命名和 Compose 函数名一一对应,Claude Code 推断最准。

编码端反模式

❌ AI 直接改 production 代码

无计划无回归,改出来 5 个错只发现 2 个。

✅ Plan 模式 + PR 评审 + 截图回归 三件套

Claude Code Shift+Tab 进 Plan,ExitPlanMode 给你审,合 PR 必跑 Paparazzi。

❌ 改 UI 不加测试

"AI 改的应该不会错吧"——会的,而且会经常错。

✅ 改一个 Composable,加一个 Paparazzi 测试

成本是 30 秒,挡掉的回归是无数次。

❌ AI 一次改 10 个页面

Prompt 一句话改 10 个,出来 1 个能跑 9 个错。

✅ 一次一个,跑通再下一个

AI 上下文有限 + 出错难追,小步快跑比大跃进稳 10 倍。

流程端反模式

❌ Figma 与代码两套都改,没记录

三方(设计 / 前端 / AI)都改,改完对不上。

✅ 约定唯一源 + 改完发 PR 评论

Figma 是源就只动 Figma,代码源同上;改动必须可追溯。

❌ Paparazzi 基线永不更新

3 个月后基线全红,没人敢 reset。

✅ 设计改动 PR 必带"基线更新说明"

截图 diff 是 PR 评审的一部分,基线更新有理由。

判断 AI 改 UI 是否真提效的 4 个指标

不要被"看起来 30 秒出 PR"迷惑,真提效要看:

  1. PR 合入率——AI 提的 PR 里一次过审的比例。低于 50% 说明 AI 在制造返工。
  2. Paparazzi 误报率——AI 改完的截图 diff 里"实际有视觉问题"的比例。高于 30% 就要重新训练提示词。
  3. 设计师改动到代码上线的时间——目标 <2 小时,>1 天就是流程断了。
  4. 设计 Token 一致率——代码里硬编码颜色 / 间距的比例。目标 <5%,>15% 就要把 Token 重构排上日程。

附录 X

跨端落地:iOS × Web(把正文 Android 那条流水线照搬)

读者画像:你在读这本小册子,但自己不写 Android——写 SwiftUI 或 React/Tailwind。本附录只补两件事:① 那条五步流水线在 SwiftUI / React 里怎么照搬;② 各自的"对位机制"是什么(Compose 有 MaterialTheme,iOS / Web 各自叫什么)。核对日期 2026-08-05,文末 X4 有全链接。

X1. iOS 落地(SwiftUI)

Apple 没有"Design Token"这个术语,但有三套等价机制一起构成"Figma Variables → SwiftUI"的桥:

① 语义色 + Asset Catalog

HIG 明确建议"优先用语义色而不是硬编码十六进制",语义色自动响应 Dark Mode / Increase Contrast / Reduce Transparency。

// ❌ AI 经常这么写(硬编码)
Text("Save").foregroundColor(Color(red: 0.28, green: 0.41, blue: 0.06))

// ✅ 正确:走语义 / 走自家 Color Set
Text("Save").foregroundStyle(.primary)
Button("Save") {}.tint(Color("BrandPrimary"))   // Asset Catalog 里的 Color Set

② 自定义 Theme 容器(iOS 18+ @Entry 宏)

和 Compose MaterialTheme.colorScheme 对位的是 iOS 18 起的 @Entry 宏——它让你像 Compose 一样通过 @Environment 拿到整套品牌 Token:

@Entry struct BrandTheme {                           // 1) 定义 Token 容器
  let primary: Color; let onPrimary: Color; let surface: Color
  let radius: CGFloat; let spacing: (xs: CGFloat, sm: CGFloat, md: CGFloat, lg: CGFloat)
}
extension EnvironmentValues { var brandTheme: BrandTheme { .default } }

@main struct MyApp: App {                            // 2) 根注入(对应 Compose 的 ReplyTheme)
  var body: some Scene {
    WindowGroup { RootView().environment(\.brandTheme, .light) }
  }
}

struct PrimaryButton: View {                         // 3) 任何子 View 取
  @Environment(\.brandTheme) private var theme
  var body: some View {
    Text("Tap").foregroundStyle(theme.onPrimary)
      .padding(.horizontal, theme.spacing.md)
      .background(theme.primary, in: .rect(cornerRadius: theme.radius))
  }
}

③ Figma Variables → Swift Color 的桥

Figma 官方 Dev Mode 没出 "Copy as SwiftUI"(有 Compose / React / HTML / CSS)。要桥需要自己接:

# 1) Figma Variables 拉成本地 JSON(标准 REST API,任何套餐都行)
curl -sS -H "X-Figma-Token: $FIGMA_TOKEN" \
  "https://api.figma.com/v1/files/$FILE_KEY/variables/local" \
  | jq '.meta.variables' > figma-vars.json

# 2) Style Dictionary v4 编译到 Swift(支持 ios-swift / ios-swift-separate)
const sd = new StyleDictionary({
  source: ['figma-vars.json'], platforms: {
    ios: { transformGroup: 'ios-swift',
      buildPath: 'Sources/Theme/',
      files: [{ destination: 'BrandTheme.swift', format: 'ios-swift/class',
        options: { className: 'BrandTheme' } }] }
  }
});
await sd.buildAllPlatforms();

⑤ AI 编码代理 SwiftUI 的真实能力边界

坦诚说,AI 写 SwiftUI 有几个明显短板(2026.8 现状):

  • 手势链——DragGesture + simultaneousGesture + 状态机很容易出错,AI 第一版经常漏边界 case
  • Combine——Publisher 链 / debounce / switchToLatest,AI 写得出但容易过度复杂
  • SwiftData migration——版本迁移 schema 经常需要人手审
  • 状态提升 / 复杂 navigation——navigationDestination / NavigationStack 路径控制,AI 第一版几乎都是错的

对策:这些场景让 AI 写第一版,然后跑 Preview + Snapshot,人在 diff 上审;不要直接信 AI 自报"完成了"。

X2. Web 落地(Tailwind v4 × shadcn)

Web 侧"设计 Token 一等公民"过去三年的演进:Tailwind v3 config.js → Tailwind v4 @theme CSS 变量 → shadcn 语义 CSS 变量。v4 的意义在于 Tailwind 直接吃 CSS variables,不用 tailwind.config.js 那条路径。

① Tailwind v4 @theme 指令

/* app.css */
@import "tailwindcss";

@theme {
  /* 颜色(走 OKLCH 色彩空间更准) */
  --color-brand-50:  oklch(0.97 0.02 120);
  --color-brand-500: oklch(0.55 0.18 145);
  --color-brand-900: oklch(0.25 0.05 145);

  /* 字体 / 间距 / 圆角 */
  --font-display: "Inter", "SF Pro SC", sans-serif;
  --spacing-app: 0.25rem;
  --radius-card: 0.75rem;
}

关键变化:v4 的 @theme 直接生成 utility class——bg-brand-500 / font-display / rounded-card 都是它来的,不用再写 tailwind.config.js。三个进阶指令(对应 Compose Token 体系):

指令干什么类比 Compose
@theme inline { ... }Token 直接展开成 utility,不生成 CSS variable(类似) colorScheme.primary 的"展开"模式
@theme static { ... }不允许覆盖,真正的"硬编码"(类似) MaterialTheme 不可在运行时改
--*: initial重置 Tailwind 默认 spacing / radius,把命名权交给你全局重置到自家设计基线

② shadcn 的"代码即设计"哲学

shadcn 不发 npm 包,你装的是组件源码(贴进 components/ui/),所以"改设计 Token" = 改源里的 bg-primary 那几个 CSS 变量。它和 Figma Variables 一一对应:

shadcn CSS 变量对位 Figma Variable用途
--background / --foregroundsurface / onSurface容器底色 + 文字
--primary / --primary-foregroundprimary / onPrimary按钮、链接主色
--secondary / --muted / --accentsecondaryContainer / surfaceVariant / tertiary次级容器 / 弱化 / 强调
--destructiveerror危险动作(删除、报错)
--border / --input / --ringoutline / outlineVariant / focus边 / 输入框边 / 焦点环
--radiusshape.cornerMedium全局圆角基准

小心坑:shadcn 默认中性灰色调,品牌色直接覆盖 --primary 即可。不要去改组件源码里的硬编码颜色——下次 shadcn add 加新组件又会拉回默认。
