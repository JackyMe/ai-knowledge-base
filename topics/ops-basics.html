为什么要学这个

你大概率经历过这样的场景:Vercel 部署的个人项目突然被 DDoS,联系客服要走工单;Cloudflare Pages 部署到一半发现中国大陆访问巨慢,配置改动被锁在企业版;Supabase 项目某个深夜数据库连接被打满,你只能干瞪眼看着 Stripe 钱照扣。

SaaS 托管很爽——直到它的边界开始挡住你。而当你准备跨越这道边界时,迎面扑来的运维黑话(SSH / systemd / 反向代理 / DNS 解析 / TLS 握手 / 防火墙入站规则……)会让你觉得自己从一个文明世界掉进了中世纪。

这份文档能给你什么,不能给你什么能给的:5 阶段路线 + 服务器/网络/部署 3 模块的最小必要知识,加上 5 类故障的 30 秒对症表。读完并完成动手项目,你能独立负责一个中小项目的服务器。不能给的:k8s 集群运维 / GPU 推理部署 / 高可用架构 / 性能调优到极致——这些是另一个量级的工种,留给未来的专题。

读者画像

  • 做过 Next.js / Node / Python / Go 全栈项目,部署主要靠 Vercel / Netlify / Cloudflare Pages / Supabase / Railway;
  • 最多买过域名,不知道 DNS 解析到底发生了什么;
  • 被"上线后出问题只能到处求人"困扰过至少一次;
  • 愿意花 1-2 周学完,但不打算成为 SRE。

路线 R1

R1 · 现状盘点

不要急着买 VPS——先把你现在所有项目的部署方式列出来。这一步看似浪费时间,实际上能让你看清"SaaS 托管真的贵吗"和"自托管真的省吗"。

动手:一张部署清单

打开记事本,给每个在跑的项目写 4 行:

  1. 在哪跑:Vercel / Netlify / Cloudflare Pages / Supabase / 自建 / 其它
  2. 花多少钱:免费层 / Pro / 估算月费
  3. 卡过什么:慢 / 报错 / 计费爆 / 区域受限 / 客服不理你
  4. 是否值得自建:个人项目不值得(继续 SaaS);商业项目值得(继续往下)
经验法则如果你 80% 的项目是纯前端静态站 + SaaS 数据库,别折腾自托管,优化掉贵的那个就行;如果你至少有一个项目需要长任务、长连接、自定义运行时、绕开地域限制,自托管收益就回来了。
路线 R2

R2 · Linux 基座

挑一个下午,买一台 1核1G 的 VPS(20-30 元/月),装 Ubuntu 24.04 LTS,SSH 上去装好 Nginx。这一步结束,你就拥有了一台真·自己的服务器——后面对着它随便造。

动手步骤

  1. 选 VPS:DigitalOcean / Vultr / 阿里云 / 腾讯云 / 搬瓦工。挑离你用户最近的机房,系统选 Ubuntu 24.04 LTS(新手友好、社区最旺)。
  2. 本地生成 SSH 密钥:ssh-keygen -t ed25519 -C "your@email"。把 ~/.ssh/id_ed25519.pub 内容贴到 VPS 控制台的"SSH 公钥"框里。
  3. 登录 VPS:ssh root@你的VPS_IP。第一次会问 fingerprint,输入 yes。
  4. 装 Nginx:apt update && apt install -y nginx,然后 systemctl status nginx——看到 active (running) 就成了。
  5. 浏览器访问 http://你的VPS_IP:看到 Nginx 欢迎页 = R2 收工。

详细知识展开见模块 1。

路线 R3

R3 · 网络骨干

让 Nginx 欢迎页变成你的 yourdomain.dev,并且浏览器看绿锁。这一步涵盖独立开发者最常踩的 80% 网络坑:域名、DNS、HTTPS、反向代理。

动手步骤

  1. 注册域名:Cloudflare Registrar / Namecheap / Porkbun / 阿里云(国内)。后缀选 .dev 强制 HTTPS,或 .com 通用。
  2. DNS 解析:在域名商后台,把 yourdomain.dev 的 A 记录指向你的 VPS IP。dig yourdomain.dev 验证解析生效。
  3. 签 SSL 证书:apt install -y certbot python3-certbot-nginx,然后 certbot --nginx -d yourdomain.dev。跟着交互走完,自动续期。
  4. 配置反向代理:把 HTTPS 请求(443 端口)反向代理到本地的 Node 应用(比如 3000 端口)。
  5. 浏览器访问 https://yourdomain.dev:看到绿锁 + 你的页面 = R3 收工。

详细知识展开见模块 2。

路线 R4

R4 · 部署链路

告别 FTP 拖文件、SSH 上手改代码。让 git push 自动触发部署,30 秒后线上生效。这一步是独立开发者"看起来像团队"的最短路径。

动手步骤

  1. 应用加 systemd 单元:写一个 /etc/systemd/system/myapp.service,让 node server.js 作为后台进程托管,关 SSH 也不死。
  2. 写 GitHub Actions workflow:在 .github/workflows/deploy.yml 配 SSH key + rsync,实现 git push main → 自动登录 VPS → 拉代码 → 重启 systemd。
  3. 配密钥管理:GitHub 仓库 Settings → Secrets 填 VPS SSH 私钥;本地 .env 走 EnvironmentFile。
  4. 推一次试试:改一行 README,commit → push。看 GitHub Actions 变绿、线上 30 秒后生效 = R4 收工。

详细知识展开见模块 3。

路线 R5

R5 · 故障排查

第一次部署上线后 24 小时内,你大概率会遇到至少 2 个故障。R5 的目标不是"不出问题",而是"出问题能在 30 秒内定位到表"。

动手:制造 5 类故障并逐一修复

  1. 502 Bad Gateway:把 systemd 服务停掉(systemctl stop myapp),看 Nginx 返回什么——再恢复。
  2. SSH 连不上:改一下 /etc/ssh/sshd_config 配错端口(或临时关防火墙),看 ssh root@IP 怎么报错。
  3. 磁盘写满:dd if=/dev/zero of=/tmp/bigfile bs=1M count=10000 制造大文件,然后 df -h 看满盘。
  4. 服务 OOM:写一个死循环占内存的 Node 脚本,看 OOM Killer 怎么杀。
  5. SSL 证书过期:certbot renew --dry-run 看续期流程;或临时把系统时间改到过期之后,看浏览器反应。

故障详细对症表见附录 A。

1.1 什么是"服务器"

不要被"服务器"这个词吓住。它就是一台 24 小时开机的电脑——和你笔记本几乎一样的硬件,只是装了个 Linux,扔在机房里接了根网线,没有显示器,没有键鼠,你通过 SSH 在自己电脑上"远程"操作它。

从你的笔记本到云上,发生了什么变化

维度你的笔记本云服务器
操作系统macOS / WindowsUbuntu / Debian / CentOS(几乎只有 Linux)
交互方式屏幕 + 键鼠SSH 命令行(没显示器)
运行时间你用的时候开24×7 不关机
公网 IP通常没有有一个公网 IP

模块 1 · Linux

1.2 三大抽级概念:文件系统、进程、端口

把一台 Linux 服务器想成一座"公寓楼",住客是进程,门牌号是端口,房本归用户。运维 80% 的操作都围绕这三个东西:查谁在住(进程)、门牌号被谁占用(端口)、哪个房本归你(权限)。

文件系统:一切皆文件

Linux 的核心哲学:磁盘是文件、网卡是文件、鼠标是文件、进程信息也是文件。这听起来抽象,但用起来非常一致——所有东西都在 / 下面,都能用 ls cat cd 操作。

ls /                  # 根目录
ls /home              # 用户的家
ls /etc/nginx/         # nginx 配置
ls /var/log/           # 日志
cat /proc/cpuinfo      # CPU 信息(在内存里,不是真文件)

进程:正在运行的程序

你 node server.js 一下,就生成了一个 Node 进程,进程有 PID(身份证号)。运维最常用的几个命令:

ps aux | grep node     # 看所有 node 进程
top                    # 实时看 CPU/内存占用(q 退出)
htop                   # top 的美化版(需 apt install htop)
kill 1234              # 杀 PID 1234
pkill -f "node server" # 按名字杀
systemctl status myapp # 看 systemd 托管的服务

端口:窗口编号(0-65535)

一台服务器可以同时跑很多服务,客户端靠"端口号"区分——就像公寓楼里每户的"门牌号"。常见约定:

端口谁在用
22SSH(远程登录)
80HTTP
443HTTPS
3000 / 8080开发者自己起服务(Node/Python 常用)
3306 / 5432MySQL / PostgreSQL
6379Redis
ss -tlnp               # 看哪些端口在监听
netstat -tlnp          # 旧命令,功能类似
lsof -i :3000           # 看 3000 端口被谁占了
端口冲突"Address already in use" 是 90% 新手的第一次挫败。必杀技:lsof -i :你的端口 查谁占了,然后杀掉或换端口。

模块 1 · Linux

1.3 SSH 不只是"远程登录"

SSH = Secure Shell。表面上是"远程登录",实际上它能做所有加密的网络连接——端口转发、文件传输(SFTP)、跑 Git。

密钥登录:别再用密码

密码登录有两个问题:(1) 慢且烦;(2) 服务器暴露 22 端口,全世界都在暴力破解。改用密钥登录后,服务器只接受持有"私钥"的机器,暴力破解直接无效。

# 本地生成密钥对
ssh-keygen -t ed25519 -C "you@example.com"
# 私钥:~/.ssh/id_ed25519(绝对不能泄露!)
# 公钥:~/.ssh/id_ed25519.pub(贴到服务器的 ~/.ssh/authorized_keys)

# 一键推送公钥(前提是还能用密码登录)
ssh-copy-id root@你的VPS_IP

# 登录
ssh root@你的VPS_IP
私钥权限必须是 600如果 ~/.ssh/id_ed25519 权限是 644,SSH 会拒绝使用(防别人读你的私钥)。chmod 600 ~/.ssh/id_ed25519。

配置文件:给常用服务器起别名

不要每次都 ssh root@123.45.67.89。写 ~/.ssh/config:

Host my-vps
  HostName 123.45.67.89
  User root
  Port 22
  IdentityFile ~/.ssh/id_ed25519

# 之后只用
ssh my-vps

端口转发和跳板

假设你的数据库在"内网"机器 10.0.0.5:5432,你只能通过跳板机 vpn.example.com 进去。本地命令 psql 想要直连,SSH 可以帮你"打洞":

ssh -L 5432:10.0.0.5:5432 vpn.example.com
# 之后本地 psql -h 127.0.0.1 -p 5432 就会通过 ssh 隧道转发到内网
没查到的细节2026 年 SSH 跳板机(ProxyJump)的官方最佳实践我没查到统一定论,本人建议结合云厂商文档自查。常用写法 ssh -J jump user@target(OpenSSH 7.3+)。

1.4 包管理器速查

包管理器 = 应用商店的命令行版。Linux 发行版不同,包管理器不同——Ubuntu/Debian 系用 apt,CentOS/RHEL 新版用 dnf,老版本用 yum,Alpine 用 apk。

系统装包删包更新索引升级全部
Ubuntu / Debianapt install nginxapt remove nginxapt updateapt upgrade
CentOS / RHEL (新版)dnf install nginxdnf remove nginxdnf check-updatednf upgrade
Alpineapk add nginxapk del nginxapk updateapk upgrade
macOS(参考)brew install nginxbrew uninstall nginxbrew updatebrew upgrade
装软件的两条铁律(1) 先 update 再 install——索引没更新会装到过时的版本;(2) 不混用发行版源——Ubuntu 的 deb 包不能装到 CentOS 上,反之亦然。
模块 1 · Linux

1.5 权限与用户

Linux 是多用户系统。每个文件都有"谁能读 / 谁能写 / 谁能执行"三组权限,分别给"自己 / 同组 / 别人"。

看权限:ls -l

-rw-r--r-- 1 root root  1234 Aug  5 10:00 myapp.conf
drwxr-xr-x 2 root root  4096 Aug  5 09:00 nginx/

# 第 1 位:d = 目录,- = 文件
# 接下来 9 位:三组 rwx(自己/组/别人)
# r=读(4) w=写(2) x=执行(1)

改权限:chmod vs chown

命令干什么例子
chmod 600 mykey改权限(数字 = 自己的+组+别人)600 = 自己可读写,别人啥都不能
chmod +x script.sh加执行权限脚本第一次跑前必做
chown user:group file改归属chown www-data:www-data /var/www

sudo:临时当 root

root 是 Linux 的"上帝账号",什么都能改。日常用普通用户登录,要装包/改系统配置时 sudo 临时提权。

sudo apt install nginx      # 提权装包
sudo systemctl restart nginx # 提权重启服务
sudo !!                     # 把上一条命令加 sudo 重跑(神器)
别用 root 干日常事root 误删一个 rm -rf /(理论上要带 --no-preserve-root 但实际可能执行)就 Game Over。新建专用用户、sudo 提权是好习惯。
模块 2 · 网络

2.1 一张图看懂 HTTP → TCP → IP → 网卡

📌 30 秒结论你点开网址的 1 秒里,你的请求过了 4 道关,经历 4 层"信封"包装。你只要搞清楚这四层谁负责啥,就能听懂所有网络黑话。

它到底是个啥

你打开浏览器输入 aidoc-zq.netlify.app,大概 1 秒后看到页面。这 1 秒里,你的请求从浏览器出发,经过了 4 道关:

  1. 应用层 HTTP——你写的 GET /index.html,意思是"我要这个文件"
  2. 传输层 TCP——把 HTTP 切成小包、编号,保证按顺序到达,就像快递公司
  3. 网络层 IP——每个包写上"从哪里来、到哪里去",就像快递单上的地址
  4. 链路层 网卡——把包变成电信号/光信号发出去,就是真正跑的车

四层协议栈(ASCII 图)

   你发的请求(下行)               你看到的响应(上行)
   ────────────────               ────────────────
   ┌──────────────┐               ┌──────────────┐
   │ HTTP  GET /  │               │ 200 OK  │
   ├──────────────┤               ├──────────────┤
   │ TCP  SYN/ACK │               │ TCP  FIN/ACK │
   ├──────────────┤               ├──────────────┤
   │ IP  src→dst  │               │ IP  dst→src  │
   ├──────────────┤               ├──────────────┤
   │ 网卡电/光信号│               │ 网卡电/光信号│
   └──────────────┘               └──────────────┘
   ▲ 层层包装(从下往上)          ▲ 层层拆包(从下往上)

怎么用:看一次实际握手

跑 curl -v https://example.com,你能看到 TCP 的"三次握手四次挥手"全过程,这就是 TCP 的核心:

curl -v https://example.com
# * Trying 93.184.216.34:443...        ← TCP 开始:发 SYN
# * Connected to example.com          ← 收到 SYN+ACK,发 ACK(握手完成)
# > GET / HTTP/1.1                    ← HTTP 请求开始发
# < HTTP/1.1 200 OK                   ← HTTP 响应回来
# * Connection #0 to host example.com left intact

实战:真抓一次包

想看真正的 IP 包长啥样?tcpdump 抓给你看(不需要 root 也能抓自己发的):

tcpdump -i any -n port 80 -c 5
# 抓 80 端口的前 5 个包
# 看到 src=192.168.1.5.dst=93.184.216.34.80 之类
# 这就是 IP+TCP+HTTP 三层在同一条线上的样子

🚧 小剧场:OSI 七层是哪七层?

2.3 HTTPS / TLS / Let's Encrypt

📌 30 秒结论HTTP 是明信片——咖啡店抓包能偷看。HTTPS = 挂号信,只有你和收件人能拆。Let's Encrypt 让免费 SSL 证书 + 自动续期成为现实,2026 年全网主流。

它到底是个啥:HTTP vs HTTPS

HTTP(超文本传输协议)是明文——你在咖啡店连 Wi-Fi 输"账号/密码",隔壁桌抓包能看到。

HTTPS = HTTP + TLS 加密层,让传输内容变成密文,只有你和服务器能解开。地址栏的小锁图标就是这个意思。

TLS 1.3 握手(1-RTT,ASCII 图)

客户端                                服务器
  │                                      │
  │── ClientHello(支持的算法) ─────────►│
  │                                      │
  │◄── ServerHello + Certificate ───────│
  │     + Finished(密钥已算好)           │
  │                                      │
  │── Finished(开始加密通信) ──────────►│
  │                                      │
  │▼ 应用数据加密传输(双方都有密钥)      │

比 TLS 1.2 少一次往返,延迟更低。2026 年主流浏览器 + 服务器默认 TLS 1.3。

SNI:一个 IP 多域名怎么办

早期 HTTPS 一个 IP 只能挂一个证书,但你一台服务器要服务 a.com / b.com / c.com 怎么办? SNI(Server Name Indication) 让客户端在握手时就把域名告诉服务器,服务器挑对应证书。

理解 SNI就像酒店前台,客人进门前先说"我找 302 房的张三",前台直接对应房间,不用挨个房间敲门问。

2.4 反向代理:Nginx 为什么是瑞士军刀

📌 30 秒结论反向代理就是"大楼前台"——你只管说"找张三",前台帮你定位到具体办公室。用户访问 yourdomain.dev,其实是 Nginx 在替你分配到后端的多个 Node 服务。

它到底是个啥:正向 vs 反向

很多人把"代理"和"反向代理"搞混,其实方向不同:

【正向代理】 客户端 ←→ 代理 ←→ 互联网
  替客户端出头,典型场景:企业统一翻墙
  客户端知道有代理存在

【反向代理】 客户端 ←→ 反代 ←→ 后端服务器
  替服务端接活,典型场景:Nginx 配 Node
  客户端不知道后面有几个服务器

请求流转步骤(ASCII 图)

用户浏览器        Nginx 反代              后端服务器
   │                  │                       │
   │ GET /api/users   │                       │
   ├─────────────────►│                       │
   │                  │ 选择 Node1             │
   │                  ├──────────────────────►│
   │                  │◄──── 200 OK JSON ─────┤
   │◄────── 200 OK ───┤                       │
   │                  │                       │
   │ GET /static/x.js │                       │
   ├─────────────────►│                       │
   │                  │ 直接返回磁盘上的文件   │
   │◄────── 200 OK ───┤  (没经过 Node,省 CPU)│

Nginx 的 5 个关键作用

  • HTTPS 终结——Nginx 负责 SSL,Node 跑明文 HTTP(省 CPU)
  • 多应用共用 80/443——根据域名分发到不同 Node 服务
  • 静态文件加速——让 Nginx 直接返回静态资源,不进 Node
  • 负载均衡——把请求分散到多个 Node 实例
  • 缓存/压缩/Gzip——Nginx 一行配置搞定

Nginx 为什么是"瑞士军刀"

Nginx 是事实标准的反向代理服务器——开源、稳定、配置简单、内存占用低。Netcraft / W3Techs 等机构长期统计显示,Nginx 在全球 Web 服务器市场份额稳居前 2(另一家是 Apache),新兴部署以 Nginx 为主流。(2026.8 具体百分比本节未逐字核对,以 w3techs.com 最新报告为准)

2.5 防火墙:为什么 80/443 通了别的还连不上

📌 30 秒结论独立开发者 50% 的"连不上"故障是防火墙干的——而且不是一层,是两层以上。本机放行了,云厂商不一定放行;同样本地服务跑了,也不代表外网能进。

两层防火墙(独立开发者必踩)

你的电脑 ←───→ [云厂商安全组] ←───→ [本机 ufw/iptables] ←───→ 服务
   全国大门                          楼层大门                      房间门

两个门都开,才能进。任何一个门锁着,外面就连不上。

第一层:服务器本机防火墙 (iptables / ufw)

Ubuntu 默认没装 ufw,但很多人会装:ufw allow 22、ufw allow 80、ufw allow 443、ufw enable。装好后忘了 allow 80/443,Nginx 跑着也访问不了。

ufw status                # 看规则
ufw allow 80/tcp          # 放行 HTTP
ufw allow 443/tcp         # 放行 HTTPS
ufw allow from 1.2.3.4 to any port 22  # 只允许某 IP SSH

第二层:云厂商安全组

阿里云 / 腾讯云 / AWS / 华为云 在"控制台 → 安全组"里维护另一套防火墙规则。本机 ufw 放行了 80,但安全组没放行,外面还是连不上 — 这是新手最常踩的"双重防火墙"陷阱。

故障排查顺序(4 步)连不上某端口时,按这个顺序检查:
  1. 服务本身在听吗 → ss -tlnp | grep 端口
  2. 本机防火墙放行了吗 → ufw status
  3. 云厂商安全组放行了吗 → 去控制台看
  4. 公网 IP 对吗 → curl ifconfig.me

🚧 小剧场:"80 通了但 3000 不通"

你跑 Node 监听 3000 端口,本机 curl localhost:3000 正常,但外网访问不到。原因:3000 端口既没在云厂商安全组放行,你也忘了让 Nginx 反代到 3000。解决:

ufw allow 3000/tcp       # 1. 本机放行(或用 Nginx 反代)
# 2. 云厂商控制台:安全组 → 入站规则 → 3000
# 3. 或者更优雅:让 Nginx 监听 80/443,反代到 3000(用户只接触 80/443)
💡 记忆口诀"连不上查三层:服务、墙、IP"——服务起没起、墙放没放、IP 对不对,逐层推。

2.8 本地服务与 loopback:你跟自己说话

📌 30 秒结论localhost = "你跟自己说话",家里喊一声全家都听不见。Node 监听 127.0.0.1 只接本机请求,监听 0.0.0.0 才对外接受所有网卡访问。想让本地服务被外网访问?用内网穿透 3 方案之一。

它到底是个啥:三个特殊地址的区别

【127.0.0.1】  loopback 网卡上的 IP
  → 只走本机,网卡都不发出去
  → 隔壁电脑 ping 不通你

【localhost】  操作系统解析出来的名字
  → 通常 = 127.0.0.1
  → 在 /etc/hosts 里改可以指向别的 IP

【0.0.0.0】    监听所有网卡
  → 接受任何接口的访问(本机 + 公网)
  → 真正"对外开放"的服务应该监听这个

Node 监听实例

// 只接本机(默认)
app.listen(3000, '127.0.0.1', () => {
  console.log('只在 localhost:3000 能访问');
});

// 接受所有接口
app.listen(3000, '0.0.0.0', () => {
  console.log('本机、公网、内网都能访问');
});

// 默认(通常 = 0.0.0.0,但有些版本不同)
app.listen(3000, () => console.log('默认监听'));

内网穿透 3 方案(本地服务被外网访问)

Cloudflare Tunnel(2026.8 已核对原理)

cloudflared 守护进程运行在你的服务器上,主动向 Cloudflare 发起出站连接(outbound-only),不需要公网 IP,不需要在防火墙开放入站。隧道用 UUID 标识,流量双向通行,但防火墙只需放行出站。

2.9 VPN 与代理:四种"过墙"姿势辨析

📌 30 秒结论VPN、正向代理、反向代理、应用层代理四者经常被搞混,其实各管一层。VPN 是"在网络层拉条专线",反代是"在应用层替服务端接活",正代是"在应用层替客户端出头"。

它到底是个啥:四个场景引入

  • 公司 VPN — 你在家能访问公司内网 Git,OS 以为你坐在公司工位
  • 企业正向代理 — 公司统一从代理出公网,所有员工走同一出口
  • 反向代理(Nginx) — 用户访问公司网站,Nginx 在前面分发
  • 应用层代理 — 浏览器设 SOCKS5/HTTP Proxy 插件出公网

四者对比 ASCII 图

【正向代理】                          【反向代理】
   客户端 ─→ 代理 ─→ 互联网             互联网 ─→ 反代 ─→ 后端服务器
   替客户端出头                         替服务端接活

【VPN】                                【应用层代理】
   客户端 ─→ VPN ─→ 目标网络           客户端 ─→ SOCKS5/HTTP Proxy ─→ 互联网
   拉专线,OS 视角下虚拟网卡             应用层代转,SOCKS5 看上层协议

作用层一览

类型作用层典型场景
VPNL3 网络层整条虚拟专线,OS 路由表视角
反向代理L7 应用层(HTTP)Nginx 替你接 HTTP 流量
正向代理L7 应用层(HTTP)浏览器设代理出公网
SOCKS5 代理L5 会话层任意 TCP/UDP 流量转发

VPN 协议三档

  • IPsec — 企业级老牌,1980s 起的协议族,配置复杂但稳定
  • SSL VPN — 轻量,装客户端即可(Cisco AnyConnect 等)
  • WireGuard — 新锐,代码 4000 行,Linux 5.6(2020-03-29) 起合并入主线

WireGuard 的核心优势

  • 配置像 SSH — 交换公钥即可建立连接
  • 代码量小 — 约 4000 行,易审计
  • 现代加密 — Curve25519、ChaCha20、Poly1305 等
  • 内核实现 — 性能高,适合嵌入式和骨干
  • 内置漫游 — 切换网络不重连(类似 Mosh)

ssh -D 1080 是什么

SSH 自带的动态 SOCKS 代理。把 SSH 当 SOCKS5 服务器用,所有走 1080 端口的应用流量都会被 SSH 转发出去。

🚧 小剧场:"公司 VPN 能访问内网是为什么"

VPN 客户端拨号时,OS 收到一组"路由表变更指令":通往 10.0.0.0/8 的包走 utun0(虚拟网卡),其他走原默认网卡。从你的 OS 视角看,这就是坐在公司工位的网络栈。

2.10 公网 / 私网 / NAT:小区传达室的活儿

📌 30 秒结论公网 IP 是你家门牌号(全国唯一),私网 IP 是小区内单元号(小区内可重复)。整个小区共用一个公网 IP,小区传达室(NAT)负责把外面的快递按"门牌号"分发回各户 —— 这就是 NAT 在干的事。

它到底是个啥

如果每台设备都要一个公网 IP,IPv4(43 亿个)早就不够用。NAT(Network Address Translation)让一个小区可以共用一个公网 IP —— 内部的私网 IP 由路由器"翻译"。

三类私网段(RFC 1918)

段地址范围数量典型场景
10.0.0.0/810.0.0.0 - 10.255.255.2551677 万大型企业 / 云厂商内网
172.16.0.0/12172.16.0.0 - 172.31.255.255104 万中型网络
192.168.0.0/16192.168.0.0 - 192.168.255.2556.5 万家用路由器(最常见)

你在家里 Wi-Fi 看到的 192.168.1.x,公司内网可能是 10.0.0.x。

NAT 原理 ASCII 图

你的电脑 192.168.1.100:5000 ─→ 小区路由器 ─→ 公网 1.2.3.4:40001 ─→ baidu.com
                                  ▲
                                  │ NAT 翻译表:
                                  │ 内网 IP:端口          → 公网 IP:端口
                                  │ 192.168.1.100:5000    → 1.2.3.4:40001
                                  │ 192.168.1.101:5001    → 1.2.3.4:40002

百度回复到 1.2.3.4:40001 → 路由器查表 → 转给 192.168.1.100:5000

端口映射 = 路由器做的"反向代理"

家里的 NAS 想被外网访问?在路由器上做"端口映射":把公网的某个端口(如 8081)映射到 NAS 内网 IP 的 5000 端口。外网访问 你的公网 IP:8081 = 访问 NAS 的 5000。

类比小区传达室替你收快递,快递单只写"传达室收"。传达室记住每件快递是 18 楼哪户的,你来取时再分发。端口映射就是"给某户固定留个柜子"。

IPv4 耗尽历史 + IPv6 出场

2019 年 11 月,IANA 分配完最后 5 个 /8 段,IPv4 正式"分完"。NAT 是 IPv4 续命的权宜之计。IPv6(2.13 详述)有 128 位地址,理论上每粒沙子都能分到 IP,不再需要 NAT。

🚧 小剧场:"为什么我家 IP 跟邻居一样都是 192.168.1.100"

所有家用路由器默认用 192.168.1.x 段。你的 192.168.1.100 和邻居的 192.168.1.100 在各自小区里互不干扰 —— 因为它们都在 NAT 后面,公网上看到的只是小区公网 IP。

💡 记忆口诀"公网全国唯一,私网小区内用,出门靠 NAT"——家里几百台设备的 IP 可以重复,因为公网只看小区大门。

2.12 HTTP/2 与 HTTP/3 演进:协议为啥要升级

📌 30 秒结论HTTP/2 解决"一个 TCP 连接一个请求"的浪费,多路复用让一个连接并发多个请求。HTTP/3 更进一步,直接放弃 TCP 用 QUIC(UDP 之上的"类 TCP"),干掉 TCP 队头阻塞。2026 年 Cloudflare 等主流 CDN 已默认启用 HTTP/3。

它到底是个啥:HTTP/1.1 哪里痛

HTTP/1.1 时代,浏览器对同一个域名最多开 6 个 TCP 连接(IE 时代),后改到无限制但每个连接只能串行处理一个请求(队头阻塞)。一个页面 100 个资源,要排很久。

HTTP/2 三大招

  • 多路复用——一个 TCP 连接并发多个请求,资源并行到达
  • 头部压缩(HPACK)——重复的 Header 不重传,省带宽
  • 二进制分帧——不再用文本,改二进制传输,解析更快

HTTP/3 革命:基于 QUIC

HTTP/2 解决不了 TCP 本身的队头阻塞 —— 一个包丢了,后续包都要等。HTTP/3 直接放弃 TCP,改用 QUIC(基于 UDP):

HTTP/1.1: 多个请求排队 → TCP 阻塞 → 全队等
HTTP/2:   多路复用    → TCP 仍可能阻塞 → 部分解决
HTTP/3:   QUIC(UDP)  → 丢包不影响其他流 → 彻底解决

HTTP/3 额外优势

  • 0-RTT 握手——第二次访问几乎瞬开(QUIC 内置加密)
  • 连接迁移——手机 WiFi 切 4G 不重连
  • 内置加密——默认 TLS 1.3,无法明文

2026.8 部署现状(部分待核对)

  • Cloudflare:默认开启 HTTP/3(自 2019 年起)
  • Google:全站默认 HTTP/3
  • 国内 CDN:阿里云/腾讯云 CDN 已支持 HTTP/3
  • 全球 HTTP/3 启用比例:本节未逐字核对 Cloudflare Radar 最新数据,以 2026.8 官方报告为准

"为什么我还在用 HTTP/1.1 也行"

对中小项目,HTTP/1.1 + 静态资源 CDN 已经足够。升级到 HTTP/2/HTTP/3 的成本是 Nginx/Node 服务升级,收益主要在"高并发 + 全球用户"场景。独立开发者 v1 项目不必追新。

💡 记忆口诀"H2 多路复用,H3 干掉 TCP"——两代协议各解决一类问题。

2.13 IPv6 扫盲:128 位地址够给每粒沙子分一个

📌 30 秒结论IPv6 用 128 位地址,理论上够给地球每粒沙子分一个 IP。最大优势是端到端可达,不需要 NAT。2026.8 全球部署率持续提升(具体百分比本节未逐字核对,以 Google / APNIC 最新数据为准),国内三大运营商大部分已支持,但出口流量仍多走 v4。

它到底是个啥:为什么 IPv4 不够

IPv4 地址 32 位 = 43 亿个。2019 年 11 月 IANA 分配完最后 5 个 /8 段后,新地址只能从回收的存量里挤。NAT 续命了十几年,IPv6 是根本解。

地址格式

IPv4: 192.168.1.100                  (4 段,每段 0-255)
IPv6: 2001:0db8:85a3:0000:0000:8a2e:0370:7334
      ┗──── 8 段,每段 4 个十六进制位(0-ffff) ────┛

简化规则:
  → 前导零可省:2001:db8:85a3:0:0:8a2e:370:7334
  → 连续 0 段可合并:2001:db8:85a3::8a2e:370:7334
  → 但 :: 只能出现一次

三大优势

  • 海量地址——128 位,2^128 ≈ 3.4 × 10^38 个
  • 端到端可达——不再需要 NAT,每台设备公网 IP
  • 内置 IPsec——协议栈自带加密选项

2026.8 部署现状(部分待核对)

  • Google IPv6 Statistics:全球部署率持续提升,具体百分比以 google.com/intl/en/ipv6/statistics.html 2026-08 最新数据为准
  • APNIC 测量:可访问 stats.labs.apnic.net/ipv6 看各国部署率
  • 国内三大运营商:大部分已支持 IPv6,但出口流量可能仍走 v4
没核对到的数据2026.8 全球 / 中国 IPv6 部署率具体百分比本节未逐字核对(Google / APNIC 页面 2026-08-07 当前返回受限),以官方最新统计为准。

要不要上 IPv6

看目标用户:

  • 国内用户为主 → 大部分已可用,但 CDN 仍以 v4 为主,可暂缓
  • 海外用户为主 → 启用 v6 有性能优势
  • 面向未来 → 早用早享受,v4/v6 双栈已成本接近零

启用检测

curl -6 ifconfig.co          # 看自己有没有 v6 IP
curl -6 https://test-ipv6.com # 全面 v6 连通性测试

🚧 小剧场:"为什么我开了 v6 服务但还是 IPv4 优先"

很多客户端默认走 v4(因为 v4 网络成熟,丢包/防火墙都少),v6 协商失败后才回退 v4。想强制 v6,客户端需要显式配置。

💡 记忆口诀"IPv4 32 位不够分,IPv6 128 位随便用"——数量级的差距。

3.2 systemd 进程托管:让 Node 不再"关 SSH 就挂"

直接 ssh my-vps && node server.js & 有两个致命问题:(1) SSH 断开 = 进程被杀;(2) 服务器重启 = 服务没了。systemd 是 Linux 自带的"进程管家",帮你解决这两个问题。

完整 service 文件模板(可直接用)

在 /etc/systemd/system/myapp.service 写入:

[Unit]
Description=My Node App
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/var/www/myapp
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5
EnvironmentFile=/var/www/myapp/.env
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

使用命令

systemctl daemon-reload                 # 重载配置
systemctl enable myapp                  # 开机自启
systemctl start myapp                   # 启动
systemctl status myapp                  # 状态
systemctl restart myapp                 # 重启(部署时常用)
journalctl -u myapp -f                  # 实时日志
journalctl -u myapp --since "1 hour ago"# 最近 1 小时日志
别用 root 跑服务生产环境永远用专用用户(www-data 或新建 deploy 用户),服务被攻破时不会直接拿到 root 权限。

3.3 Nginx 反代实战配置模板

在 /etc/nginx/sites-available/yourdomain.dev 写入(让 HTTPS 反代到本地 Node 3000 端口):

server {
    listen 80;
    server_name yourdomain.dev www.yourdomain.dev;
    return 301 https://$host$request_uri;  # HTTP 强转 HTTPS
}

server {
    listen 443 ssl http2;
    server_name yourdomain.dev www.yourdomain.dev;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.dev/privkey.pem;

    # 反向代理到 Node
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 静态资源直接 Nginx 返回(可选)
    location /static/ {
        alias /var/www/myapp/public/;
        expires 30d;
    }
}

3.4 Docker 最小必要集

Docker 解决的是"在我机器上能跑"这个老问题——把应用 + 依赖打包成镜像,任何装了 Docker 的机器都能跑出一致结果。

为什么独立开发者需要 Docker

  • 本机开发用的是 macOS,线上是 Ubuntu——Docker 让两边一致
  • 升级 Node 主版本时不用动系统,只换镜像
  • 多项目时不同 Node 版本不打架

为什么你不用现在就上 k8s

k8s(也写 Kubernetes)是 Docker 的"集群调度器",适合成百上千个容器协同工作。独立开发者的 1-3 个应用,直接 systemd + Nginx 完全够用。k8s 的运维成本远超收益,别提前上。

Dockerfile 模板(Node)

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
何时升级到 Docker当你有 ≥ 2 个 Node 服务要并行,或者 Node 主版本升级让你抓狂时——再切 Docker。在那之前,systemd 直接跑 node server.js 是最快路径。

        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /var/www/myapp
            git pull origin main
            systemctl restart myapp
            sleep 3
            systemctl status myapp

GitHub Secrets 配置

仓库 → Settings → Secrets and variables → Actions → New repository secret:

  • VPS_HOST:VPS 公网 IP
  • VPS_USER:deploy(新建的部署专用用户)
  • VPS_SSH_KEY:VPS 上 ~/.ssh/id_ed25519 的私钥内容

第一次配置后,每次 git push main 都会自动部署。

5 类故障 30 秒对症表

故障发生时不要慌。先看"症状",再跑"30 秒命令",然后按"根因"修。90% 的故障是这 5 类的变种。

症状 1 · 502 Bad Gateway

30 秒命令:systemctl status myapp && journalctl -u myapp -n 50

根因 90%:(a) 应用进程挂了 → 看 journalctl 报错重启;(b) 反代 upstream 端口不对 → 查 proxy_pass http://127.0.0.1:3000 的端口

深入:§3.2、§3.3

症状 2 · SSH 连不上

30 秒命令:本机 ssh -v root@IP 看详细日志,VPS 控制台 VNC/串口控制台进

根因 90%:(a) 端口被墙(国内云厂商默认 22 经常被墙,改 22222);(b) 密钥权限 600 没设;(c) 云厂商安全组没放行 22

救命:VPS 控制台 → 实例 → "VNC 登录"或"救援模式",绕过 SSH 直接进系统

症状 3 · 磁盘写满

30 秒命令:df -h && du -sh /* | sort -h | tail -10

根因 90%:(a) 日志没轮转(/var/log/nginx 几十 GB);(b) 临时文件没清(/tmp);(c) 数据库爆了

处置:journalctl --vacuum-size=500M 砍日志;find /var/log -type f -size +100M 找大文件

症状 4 · 服务内存泄漏 OOM

30 秒命令:dmesg | grep -i "out of memory" | tail -5(看 OOM Killer 记录)

根因 90%:(a) 应用代码泄漏(全局 Map/Array 一直 push);(b) 配置缓存过大;(c) 突发流量

临时:加 swap fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile;根治:重启服务 + 排查内存泄漏代码

症状 5 · SSL 证书过期

30 秒命令:certbot certificates && certbot renew --dry-run

根因 90%:(a) certbot 自动续期 cron/timer 挂了;立刻续期:certbot renew --force-renewal + systemctl reload nginx

预防:systemctl list-timers | grep certbot 确认 timer 在跑
