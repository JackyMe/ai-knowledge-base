为什么要学这个

你大概率经历过这样的场景:Vercel 部署的个人项目突然被 DDoS,联系客服要走工单;Cloudflare Pages 部署到一半发现中国大陆访问巨慢,配置改动被锁在企业版;Supabase 项目某个深夜数据库连接被打满,你只能干瞪眼看着 Stripe 钱照扣。

SaaS 托管很爽——直到它的边界开始挡住你。而当你准备跨越这道边界时,迎面扑来的运维黑话(SSH / systemd / 反向代理 / DNS 解析 / TLS 握手 / 防火墙入站规则……)会让你觉得自己从一个文明世界掉进了中世纪。

这份文档能给你什么,不能给你什么能给的:5 阶段路线 + 服务器/网络/部署 3 模块的最小必要知识,加上 5 类故障的 30 秒对症表。读完并完成动手项目,你能独立负责一个中小项目的服务器。不能给的:k8s 集群运维 / GPU 推理部署 / 高可用架构 / 性能调优到极致——这些是另一个量级的工种,留给未来的专题。

读者画像

  • 做过 Next.js / Node / Python / Go 全栈项目,部署主要靠 Vercel / Netlify / Cloudflare Pages / Supabase / Railway;
  • 最多买过域名,不知道 DNS 解析到底发生了什么;
  • 被"上线后出问题只能到处求人"困扰过至少一次;
  • 愿意花 1-2 周学完,但不打算成为 SRE。

路线 R

五阶段路线图

把整个学习过程切成 5 个阶段。每个阶段都有可验证的产出——完成一个,打勾一个,不会"学完不知道学到哪了"。

路线 R1

R1 · 现状盘点

不要急着买 VPS——先把你现在所有项目的部署方式列出来。这一步看似浪费时间,实际上能让你看清"SaaS 托管真的贵吗"和"自托管真的省吗"。

动手:一张部署清单

打开记事本,给每个在跑的项目写 4 行:

  1. 在哪跑:Vercel / Netlify / Cloudflare Pages / Supabase / 自建 / 其它
  2. 花多少钱:免费层 / Pro / 估算月费
  3. 卡过什么:慢 / 报错 / 计费爆 / 区域受限 / 客服不理你
  4. 是否值得自建:个人项目不值得(继续 SaaS);商业项目值得(继续往下)
经验法则如果你 80% 的项目是纯前端静态站 + SaaS 数据库,别折腾自托管,优化掉贵的那个就行;如果你至少有一个项目需要长任务、长连接、自定义运行时、绕开地域限制,自托管收益就回来了。
路线 R2

R2 · Linux 基座

挑一个下午,买一台 1核1G 的 VPS(20-30 元/月),装 Ubuntu 24.04 LTS,SSH 上去装好 Nginx。这一步结束,你就拥有了一台真·自己的服务器——后面对着它随便造。

动手步骤

  1. 选 VPS:DigitalOcean / Vultr / 阿里云 / 腾讯云 / 搬瓦工。挑离你用户最近的机房,系统选 Ubuntu 24.04 LTS(新手友好、社区最旺)。
  2. 本地生成 SSH 密钥:ssh-keygen -t ed25519 -C "your@email"。把 ~/.ssh/id_ed25519.pub 内容贴到 VPS 控制台的"SSH 公钥"框里。
  3. 登录 VPS:ssh root@你的VPS_IP。第一次会问 fingerprint,输入 yes。
  4. 装 Nginx:apt update && apt install -y nginx,然后 systemctl status nginx——看到 active (running) 就成了。
  5. 浏览器访问 http://你的VPS_IP:看到 Nginx 欢迎页 = R2 收工。

详细知识展开见模块 1。

路线 R3

R3 · 网络骨干

让 Nginx 欢迎页变成你的 yourdomain.dev,并且浏览器看绿锁。这一步涵盖独立开发者最常踩的 80% 网络坑:域名、DNS、HTTPS、反向代理。

动手步骤

  1. 注册域名:Cloudflare Registrar / Namecheap / Porkbun / 阿里云(国内)。后缀选 .dev 强制 HTTPS,或 .com 通用。
  2. DNS 解析:在域名商后台,把 yourdomain.dev 的 A 记录指向你的 VPS IP。dig yourdomain.dev 验证解析生效。
  3. 签 SSL 证书:apt install -y certbot python3-certbot-nginx,然后 certbot --nginx -d yourdomain.dev。跟着交互走完,自动续期。
  4. 配置反向代理:把 HTTPS 请求(443 端口)反向代理到本地的 Node 应用(比如 3000 端口)。
  5. 浏览器访问 https://yourdomain.dev:看到绿锁 + 你的页面 = R3 收工。

详细知识展开见模块 2。

路线 R4

R4 · 部署链路

告别 FTP 拖文件、SSH 上手改代码。让 git push 自动触发部署,30 秒后线上生效。这一步是独立开发者"看起来像团队"的最短路径。

动手步骤

  1. 应用加 systemd 单元:写一个 /etc/systemd/system/myapp.service,让 node server.js 作为后台进程托管,关 SSH 也不死。
  2. 写 GitHub Actions workflow:在 .github/workflows/deploy.yml 配 SSH key + rsync,实现 git push main → 自动登录 VPS → 拉代码 → 重启 systemd。
  3. 配密钥管理:GitHub 仓库 Settings → Secrets 填 VPS SSH 私钥;本地 .env 走 EnvironmentFile。
  4. 推一次试试:改一行 README,commit → push。看 GitHub Actions 变绿、线上 30 秒后生效 = R4 收工。

详细知识展开见模块 3。

路线 R5

R5 · 故障排查

第一次部署上线后 24 小时内,你大概率会遇到至少 2 个故障。R5 的目标不是"不出问题",而是"出问题能在 30 秒内定位到表"。

动手:制造 5 类故障并逐一修复

  1. 502 Bad Gateway:把 systemd 服务停掉(systemctl stop myapp),看 Nginx 返回什么——再恢复。
  2. SSH 连不上:改一下 /etc/ssh/sshd_config 配错端口(或临时关防火墙),看 ssh root@IP 怎么报错。
  3. 磁盘写满:dd if=/dev/zero of=/tmp/bigfile bs=1M count=10000 制造大文件,然后 df -h 看满盘。
  4. 服务 OOM:写一个死循环占内存的 Node 脚本,看 OOM Killer 怎么杀。
  5. SSL 证书过期:certbot renew --dry-run 看续期流程;或临时把系统时间改到过期之后,看浏览器反应。

故障详细对症表见附录 A。

模块 1 · Linux

1.1 什么是"服务器"

不要被"服务器"这个词吓住。它就是一台 24 小时开机的电脑——和你笔记本几乎一样的硬件,只是装了个 Linux,扔在机房里接了根网线,没有显示器,没有键鼠,你通过 SSH 在自己电脑上"远程"操作它。

从你的笔记本到云上,发生了什么变化

维度你的笔记本云服务器
操作系统macOS / WindowsUbuntu / Debian / CentOS(几乎只有 Linux)
交互方式屏幕 + 键鼠SSH 命令行(没显示器)
运行时间你用的时候开24×7 不关机
公网 IP通常没有有一个公网 IP
你在意什么美观、流畅稳定、能跑、不挂
为什么必须是 Linux?绝大多数服务器软件(nginx、Node、Python、Docker、systemd)都是 Linux 优先;macOS 内核虽是 BSD 系但和 Linux 命令 95% 兼容,Windows 完全两套生态,这就是为什么"做后端"几乎等于"用 Linux"。
模块 1 · Linux

1.2 三大抽级概念:文件系统、进程、端口

把一台 Linux 服务器想成一座"公寓楼",住客是进程,门牌号是端口,房本归用户。运维 80% 的操作都围绕这三个东西:查谁在住(进程)、门牌号被谁占用(端口)、哪个房本归你(权限)。

文件系统:一切皆文件

Linux 的核心哲学:磁盘是文件、网卡是文件、鼠标是文件、进程信息也是文件。这听起来抽象,但用起来非常一致——所有东西都在 / 下面,都能用 ls cat cd 操作。

ls /                  # 根目录
ls /home              # 用户的家
ls /etc/nginx/         # nginx 配置
ls /var/log/           # 日志
cat /proc/cpuinfo      # CPU 信息(在内存里,不是真文件)

进程:正在运行的程序

你 node server.js 一下,就生成了一个 Node 进程,进程有 PID(身份证号)。运维最常用的几个命令:

ps aux | grep node     # 看所有 node 进程
top                    # 实时看 CPU/内存占用(q 退出)
htop                   # top 的美化版(需 apt install htop)
kill 1234              # 杀 PID 1234
pkill -f "node server" # 按名字杀
systemctl status myapp # 看 systemd 托管的服务

端口:窗口编号(0-65535)

一台服务器可以同时跑很多服务,客户端靠"端口号"区分——就像公寓楼里每户的"门牌号"。常见约定:

端口谁在用
22SSH(远程登录)
80HTTP
443HTTPS
3000 / 8080开发者自己起服务(Node/Python 常用)
3306 / 5432MySQL / PostgreSQL
6379Redis
ss -tlnp               # 看哪些端口在监听
netstat -tlnp          # 旧命令,功能类似
lsof -i :3000           # 看 3000 端口被谁占了
端口冲突"Address already in use" 是 90% 新手的第一次挫败。必杀技:lsof -i :你的端口 查谁占了,然后杀掉或换端口。

模块 1 · Linux

1.3 SSH 不只是"远程登录"

SSH = Secure Shell。表面上是"远程登录",实际上它能做所有加密的网络连接——端口转发、文件传输(SFTP)、跑 Git。

密钥登录:别再用密码

密码登录有两个问题:(1) 慢且烦;(2) 服务器暴露 22 端口,全世界都在暴力破解。改用密钥登录后,服务器只接受持有"私钥"的机器,暴力破解直接无效。

# 本地生成密钥对
ssh-keygen -t ed25519 -C "you@example.com"
# 私钥:~/.ssh/id_ed25519(绝对不能泄露!)
# 公钥:~/.ssh/id_ed25519.pub(贴到服务器的 ~/.ssh/authorized_keys)

# 一键推送公钥(前提是还能用密码登录)
ssh-copy-id root@你的VPS_IP

# 登录
ssh root@你的VPS_IP
私钥权限必须是 600如果 ~/.ssh/id_ed25519 权限是 644,SSH 会拒绝使用(防别人读你的私钥)。chmod 600 ~/.ssh/id_ed25519。

配置文件:给常用服务器起别名

不要每次都 ssh root@123.45.67.89。写 ~/.ssh/config:

Host my-vps
  HostName 123.45.67.89
  User root
  Port 22
  IdentityFile ~/.ssh/id_ed25519

# 之后只用
ssh my-vps

端口转发和跳板

假设你的数据库在"内网"机器 10.0.0.5:5432,你只能通过跳板机 vpn.example.com 进去。本地命令 psql 想要直连,SSH 可以帮你"打洞":

ssh -L 5432:10.0.0.5:5432 vpn.example.com
# 之后本地 psql -h 127.0.0.1 -p 5432 就会通过 ssh 隧道转发到内网
没查到的细节2026 年 SSH 跳板机(ProxyJump)的官方最佳实践我没查到统一定论,本人建议结合云厂商文档自查。常用写法 ssh -J jump user@target(OpenSSH 7.3+)。

模块 1 · Linux

1.4 包管理器速查

包管理器 = 应用商店的命令行版。Linux 发行版不同,包管理器不同——Ubuntu/Debian 系用 apt,CentOS/RHEL 新版用 dnf,老版本用 yum,Alpine 用 apk。

系统装包删包更新索引升级全部
Ubuntu / Debianapt install nginxapt remove nginxapt updateapt upgrade
CentOS / RHEL (新版)dnf install nginxdnf remove nginxdnf check-updatednf upgrade
Alpineapk add nginxapk del nginxapk updateapk upgrade
macOS(参考)brew install nginxbrew uninstall nginxbrew updatebrew upgrade
装软件的两条铁律(1) 先 update 再 install——索引没更新会装到过时的版本;(2) 不混用发行版源——Ubuntu 的 deb 包不能装到 CentOS 上,反之亦然。
模块 1 · Linux

1.5 权限与用户

Linux 是多用户系统。每个文件都有"谁能读 / 谁能写 / 谁能执行"三组权限,分别给"自己 / 同组 / 别人"。

看权限:ls -l

-rw-r--r-- 1 root root  1234 Aug  5 10:00 myapp.conf
drwxr-xr-x 2 root root  4096 Aug  5 09:00 nginx/

# 第 1 位:d = 目录,- = 文件
# 接下来 9 位:三组 rwx(自己/组/别人)
# r=读(4) w=写(2) x=执行(1)

改权限:chmod vs chown

命令干什么例子
chmod 600 mykey改权限(数字 = 自己的+组+别人)600 = 自己可读写,别人啥都不能
chmod +x script.sh加执行权限脚本第一次跑前必做
chown user:group file改归属chown www-data:www-data /var/www

sudo:临时当 root

root 是 Linux 的"上帝账号",什么都能改。日常用普通用户登录,要装包/改系统配置时 sudo 临时提权。

sudo apt install nginx      # 提权装包
sudo systemctl restart nginx # 提权重启服务
sudo !!                     # 把上一条命令加 sudo 重跑(神器)
别用 root 干日常事root 误删一个 rm -rf /(理论上要带 --no-preserve-root 但实际可能执行)就 Game Over。新建专用用户、sudo 提权是好习惯。
模块 2 · 网络

2.1 一张图看懂 HTTP → TCP → IP → 网卡

不要背 OSI 七层。你只要理解这四层"信封"层层包装——

  1. 应用层 HTTP:你写的 GET /index.html——"我要这个文件"
  2. 传输层 TCP:把 HTTP 切成小包,编号,保证按顺序到达——"快递公司"
  3. 网络层 IP:每个包写上"从哪里来,到哪里去"——"快递单上的地址"
  4. 链路层 网卡:把包变成电信号/光信号发出去——"实际跑的车"

回程是反过来的:网卡收到信号 → 还原 IP 包 → TCP 拼起来 → HTTP 看到完整响应 → 浏览器渲染。

实操可见打开终端跑 curl -v https://example.com,你能看到完整的"握手 → 发请求 → 收响应 → 挥手"四步。这就是 TCP 的"三次握手四次挥手"。
模块 2 · 网络

2.2 DNS:为什么 ping 不通但 nslookup 行

DNS(Domain Name System)把"人记得住的域名"翻译成"机器记得住的 IP"。比如 aidoc-zq.netlify.app → 75.2.60.5。

为什么 ping 不通但 nslookup 行

很多服务器(尤其 Cloudflare 后面)主动屏蔽 ICMP 协议——所以 ping 返回超时,但 nslookup/dig/curl 都能拿到 IP 并正常访问。这是故意的反 DDoS 措施,不是故障。

ping aidoc-zq.netlify.app     # 可能超时 ≠ 不可达
nslookup aidoc-zq.netlify.app # 能查到 IP = 域名正常
curl -I https://aidoc-zq.netlify.app # 真实访问测试

DNS 记录类型速查

类型作用例子
A域名 → IPv4 地址example.com → 93.184.216.34
AAAA域名 → IPv6 地址example.com → 2606:2800:220:1::1
CNAME域名 → 另一个域名(别名)www.example.com → example.com
MX邮件服务器mail.example.com
TXT任意文本(SPF/DKIM/域名验证)Google 站点验证 google-site-verification=...
DNS 生效要时间改完 DNS 记录后,全球生效可能要 5 分钟到 48 小时——不同 DNS 缓存策略不同。想立刻知道是否生效,用 dig @8.8.8.8 yourdomain 直接问 Google DNS。
模块 2 · 网络

2.3 HTTPS / TLS / Let's Encrypt 30 秒讲完

HTTP 是明文的——你在咖啡店连 Wi-Fi 发"账号/密码",隔壁桌抓包就能看到。HTTPS = HTTP + TLS 加密,让传输内容变成密文,只有你和服务器能解开。

TLS 握手(简化版)

  1. 客户端:"我要 HTTPS,支持这些加密算法"
  2. 服务器:"我用这个算法,这是我的证书"
  3. 客户端验证证书(用浏览器内置的 CA 列表)
  4. 双方协商出一个对称密钥,开始加密通信

Let's Encrypt:免费 SSL 证书

以前 SSL 证书一年几百块,Let's Encrypt 让它变成免费 + 自动续期。工具 certbot 三命令搞定:

apt install -y certbot python3-certbot-nginx
certbot --nginx -d yourdomain.dev -d www.yourdomain.dev
certbot renew --dry-run    # 测试自动续期
自动续期certbot 会自动加 systemd timer 或 cron 任务,每 60 天跑一次续期,90 天有效期内始终保持。你什么都不用管,只要机器不挂。
没查到的细节Let's Encrypt 速率限制的官方最新数值(每周每域名多少张证书)没逐字核对,以 letsencrypt.org/docs/rate-limits 为准——常见上限是每周 50 张同域重复证书,签错时容易撞。

2.4 反向代理是什么

你跑 Node 应用监听 127.0.0.1:3000——但用户访问的是 yourdomain.dev。中间那个"翻译官"就是反向代理。

为什么需要它

  • HTTPS 终结:Nginx 负责 SSL,Node 跑明文 HTTP(省 CPU)
  • 多应用共用 80/443:根据域名分发到不同 Node 服务
  • 静态文件加速:让 Nginx 直接返回静态资源,不进 Node
  • 负载均衡:把请求分散到多个 Node 实例
  • 缓存/压缩/Gzip:Nginx 一行配置搞定

Nginx 为什么是"瑞士军刀"

Nginx 是事实标准的反向代理服务器——开源、稳定、配置简单、内存占用低。占全球 Web 服务器市场份额前 2(另一家是 Apache)。

配置样板见 3.3完整可用的 nginx.conf 在模块 3.3,直接抄走。

2.5 防火墙与端口:为什么 80/443 通了别的还连不上

独立开发者 50% 的"连不上"故障都是防火墙干的——而且不是一台防火墙,是两层:

第一层:服务器本机防火墙 (iptables / ufw)

Ubuntu 默认没装 ufw,但很多人会装:ufw allow 22(SSH)、ufw allow 80、ufw allow 443、ufw enable。如果你装好后忘了 allow 80/443,Nginx 跑着也访问不了。

ufw status           # 看规则
ufw allow 80/tcp     # 放行 HTTP
ufw allow 443/tcp    # 放行 HTTPS
ufw allow from 1.2.3.4 to any port 22 # 只允许某 IP SSH

第二层:云厂商安全组

阿里云 / 腾讯云 / AWS 在"控制台 → 安全组"里维护另一套防火墙规则。本机 ufw 放行了 80,但安全组没放行,外面还是连不上——这是新手最常踩的"双重防火墙"陷阱。

故障排查顺序连不上某端口时,按这个顺序检查:(1) 服务本身在听?ss -tlnp | grep 端口(2) 本机防火墙放行?ufw status(3) 云厂商安全组放行?去控制台看(4) 公网 IP 对吗?curl ifconfig.me

3.1 部署 7 步流水线

从 git push 到线上生效,一条独立开发者的标准流水线长这样:

  1. 开发者本地 commit + push
  2. GitHub 触发 Actions workflow(仓库 .github/workflows/deploy.yml)
  3. CI 跑 lint / test / build(坏了不部署,直接报错)
  4. CI 用 SSH 登录 VPS(密钥在 GitHub Secrets)
  5. VPS 拉新代码(git pull 或 rsync)
  6. 重启 systemd 服务(systemctl restart myapp)
  7. Nginx 反向代理转发新进程

全流程冷启动 10-30 秒,热更新 5-10 秒。R4 阶段会一步步带你跑通。

模块 3 · 部署

3.2 systemd 进程托管:让 Node 不再"关 SSH 就挂"

直接 ssh my-vps && node server.js & 有两个致命问题:(1) SSH 断开 = 进程被杀;(2) 服务器重启 = 服务没了。systemd 是 Linux 自带的"进程管家",帮你解决这两个问题。

完整 service 文件模板(可直接用)

在 /etc/systemd/system/myapp.service 写入:

[Unit]
Description=My Node App
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/var/www/myapp
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5
EnvironmentFile=/var/www/myapp/.env
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

使用命令

systemctl daemon-reload                 # 重载配置
systemctl enable myapp                  # 开机自启
systemctl start myapp                   # 启动
systemctl status myapp                  # 状态
systemctl restart myapp                 # 重启(部署时常用)
journalctl -u myapp -f                  # 实时日志
journalctl -u myapp --since "1 hour ago"# 最近 1 小时日志
别用 root 跑服务生产环境永远用专用用户(www-data 或新建 deploy 用户),服务被攻破时不会直接拿到 root 权限。

3.3 Nginx 反代实战配置模板

在 /etc/nginx/sites-available/yourdomain.dev 写入(让 HTTPS 反代到本地 Node 3000 端口):

server {
    listen 80;
    server_name yourdomain.dev www.yourdomain.dev;
    return 301 https://$host$request_uri;  # HTTP 强转 HTTPS
}

server {
    listen 443 ssl http2;
    server_name yourdomain.dev www.yourdomain.dev;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.dev/privkey.pem;

    # 反向代理到 Node
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 静态资源直接 Nginx 返回(可选)
    location /static/ {
        alias /var/www/myapp/public/;
        expires 30d;
    }
}

启用配置

ln -s /etc/nginx/sites-available/yourdomain.dev /etc/nginx/sites-enabled/
nginx -t                  # 测配置语法
systemctl reload nginx    # 重载(不中断服务)

3.4 Docker 最小必要集

Docker 解决的是"在我机器上能跑"这个老问题——把应用 + 依赖打包成镜像,任何装了 Docker 的机器都能跑出一致结果。

为什么独立开发者需要 Docker

  • 本机开发用的是 macOS,线上是 Ubuntu——Docker 让两边一致
  • 升级 Node 主版本时不用动系统,只换镜像
  • 多项目时不同 Node 版本不打架

为什么你不用现在就上 k8s

k8s(也写 Kubernetes)是 Docker 的"集群调度器",适合成百上千个容器协同工作。独立开发者的 1-3 个应用,直接 systemd + Nginx 完全够用。k8s 的运维成本远超收益,别提前上。

Dockerfile 模板(Node)

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
何时升级到 Docker当你有 ≥ 2 个 Node 服务要并行,或者 Node 主版本升级让你抓狂时——再切 Docker。在那之前,systemd 直接跑 node server.js 是最快路径。

3.5 GitHub Actions 自动部署

在 .github/workflows/deploy.yml 写入:

name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'

      - name: Install & Build
        run: |
          npm ci
          npm run build
          npm test

      - name: Deploy to VPS
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /var/www/myapp
            git pull origin main
            systemctl restart myapp
            sleep 3
            systemctl status myapp

GitHub Secrets 配置

仓库 → Settings → Secrets and variables → Actions → New repository secret:

  • VPS_HOST:VPS 公网 IP
  • VPS_USER:deploy(新建的部署专用用户)
  • VPS_SSH_KEY:VPS 上 ~/.ssh/id_ed25519 的私钥内容

第一次配置后,每次 git push main 都会自动部署。

3.6 环境变量 / 密钥管理 / .env 的正确打开方式

代码里绝不出现密钥。密钥只活在两个地方:(1) 本地 .env 文件;(2) GitHub Secrets / CI 环境变量。

Node 读 .env

# npm install dotenv
require('dotenv').config()
const dbUrl = process.env.DATABASE_URL

.gitignore 必须有 .env

# .gitignore
.env
.env.local
node_modules/

线上 .env 的安全做法

  1. VPS 上 vim /var/www/myapp/.env,填好密钥
  2. chmod 600 .env(只有自己能读)
  3. systemd service 文件用 EnvironmentFile=/var/www/myapp/.env 加载(见 3.2)
  4. GitHub Secrets 用于 CI 部署
密钥泄露应急如果密钥不小心 push 到了 GitHub:(1) 立刻去对应服务(数据库/支付)换密钥;(2) 用 BFG Repo-Cleaner 清历史;(3) 删仓库重推(最干净)。密钥泄露不等于 Game Over,但必须立刻处理。

5 类故障 30 秒对症表

故障发生时不要慌。先看"症状",再跑"30 秒命令",然后按"根因"修。90% 的故障是这 5 类的变种。

症状 1 · 502 Bad Gateway

30 秒命令:systemctl status myapp && journalctl -u myapp -n 50

根因 90%:(a) 应用进程挂了 → 看 journalctl 报错重启;(b) 反代 upstream 端口不对 → 查 proxy_pass http://127.0.0.1:3000 的端口

深入:§3.2、§3.3

症状 2 · SSH 连不上

30 秒命令:本机 ssh -v root@IP 看详细日志,VPS 控制台 VNC/串口控制台进

根因 90%:(a) 端口被墙(国内云厂商默认 22 经常被墙,改 22222);(b) 密钥权限 600 没设;(c) 云厂商安全组没放行 22

救命:VPS 控制台 → 实例 → "VNC 登录"或"救援模式",绕过 SSH 直接进系统

症状 3 · 磁盘写满

30 秒命令:df -h && du -sh /* | sort -h | tail -10

根因 90%:(a) 日志没轮转(/var/log/nginx 几十 GB);(b) 临时文件没清(/tmp);(c) 数据库爆了

处置:journalctl --vacuum-size=500M 砍日志;find /var/log -type f -size +100M 找大文件

症状 4 · 服务内存泄漏 OOM

30 秒命令:dmesg | grep -i "out of memory" | tail -5(看 OOM Killer 记录)

根因 90%:(a) 应用代码泄漏(全局 Map/Array 一直 push);(b) 配置缓存过大;(c) 突发流量

临时:加 swap fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile;根治:重启服务 + 排查内存泄漏代码

症状 5 · SSL 证书过期

30 秒命令:certbot certificates && certbot renew --dry-run

根因 90%:(a) certbot 自动续期 cron/timer 挂了;立刻续期:certbot renew --force-renewal + systemctl reload nginx

预防:systemctl list-timers | grep certbot 确认 timer 在跑
