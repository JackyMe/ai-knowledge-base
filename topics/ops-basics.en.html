Why Learn This

You've likely experienced this: A personal project deployed on Vercel suddenly gets DDoS'd, and you have to submit a support ticket; you deploy halfway on Cloudflare Pages only to find it terribly slow in mainland China, but configuration changes are locked behind the Enterprise plan; your Supabase project's database connections get maxed out late at night, and you can only stare blankly as Stripe charges continue.

SaaS hosting is great — until its boundaries start blocking you. When you're ready to cross that boundary, the influx of ops jargon (SSH / systemd / reverse proxy / DNS resolution / TLS handshake / firewall inbound rules...) can make you feel like you've dropped from the civilized world into the Middle Ages.

What this document can and cannot give youCan give: 5-stage roadmap + minimum necessary knowledge of server/network/deployment, plus a 30-second remedy table for 5 types of failures. After reading and completing the hands-on projects, you'll be able to independently manage the server for a mid-sized project.Cannot give: k8s cluster operations / GPU inference deployment / high-availability architecture / extreme performance tuning — these are different tiers of work left for future topics.

Target Audience

  • Has built Next.js / Node / Python / Go full-stack projects, primarily relying on Vercel / Netlify / Cloudflare Pages / Supabase / Railway for deployment;
  • Has bought a domain at most, doesn't know what actually happens during DNS resolution;
  • Has been troubled by "only being able to beg others for help when things break in production" at least once;
  • Willing to spend 1-2 weeks learning, but doesn't plan to become an SRE.

Roadmap R1

R1 · Status Inventory

Don't rush to buy a VPS — first list the deployment methods of all your current projects. This step seems like a waste of time, but it actually helps you see clearly whether "SaaS hosting is really expensive" and "self-hosting really saves money."

Hands-on: A Deployment List

Open Notepad and write 4 lines for each running project:

  1. Where it runs: Vercel / Netlify / Cloudflare Pages / Supabase / Self-hosted / Other
  2. Cost: Free Tier / Pro / Estimated Monthly Fee
  3. Bottlenecks: Slow / Errors / Billing surprises / Region limits / Support ghosting
  4. Worth Self-Hosting?: Personal projects not worth it (stay on SaaS); Commercial projects worth it (continue below)
Rule of ThumbIf 80% of your projects are pure frontend static sites + SaaS DBs, don't bother self-hosting; just optimize the expensive part. If you have at least one project needing long tasks, persistent connections, custom runtimes, or bypassing regional limits, self-hosting pays off.
Roadmap R2

R2 · Linux Foundation

Pick an afternoon, buy a 1-core 1GB VPS ($3-$5/month), install Ubuntu 24.04 LTS, SSH into it, and install Nginx. By the end of this step, you'll have a real server of your own — you can tinker with it freely afterwards.

Hands-on Steps

  1. Choose a VPS: DigitalOcean / Vultr / AWS / Linode. Pick a datacenter closest to your users. For the OS, choose Ubuntu 24.04 LTS (beginner-friendly, largest community).
  2. Generate SSH key locally: ssh-keygen -t ed25519 -C "your@email". Paste the contents of ~/.ssh/id_ed25519.pub into the "SSH Keys" box in your VPS console.
  3. Login to VPS: ssh root@YOUR_VPS_IP. Type "yes" when asked about the fingerprint the first time.
  4. Install Nginx: apt update && apt install -y nginx, then systemctl status nginx — seeing active (running) means success.
  5. Browser access http://YOUR_VPS_IP: Seeing the Nginx welcome page = R2 complete.

Detailed knowledge expanded in Module 1.

Roadmap R3

R3 · Network Backbone

Turn the Nginx welcome page into your yourdomain.dev, and get the green lock in the browser. This step covers 80% of the network pitfalls solo developers face: domains, DNS, HTTPS, and reverse proxies.

Hands-on Steps

  1. Register Domain: Cloudflare Registrar / Namecheap / Porkbun. Choose .dev to force HTTPS, or .com for general use.
  2. DNS Resolution: In the domain registrar's console, point the A record of yourdomain.dev to your VPS IP. Use dig yourdomain.dev to verify resolution.
  3. Sign SSL Cert: apt install -y certbot python3-certbot-nginx, then certbot --nginx -d yourdomain.dev. Follow the prompts; auto-renewal is set up.
  4. Configure Reverse Proxy: Reverse proxy HTTPS requests (port 443) to your local Node app (e.g., port 3000).
  5. Browser access https://yourdomain.dev: Seeing the green lock + your page = R3 complete.

Detailed knowledge expanded in Module 2.

Roadmap R4

R4 · Deployment Pipeline

Say goodbye to dragging files via FTP or modifying code via SSH. Make git push trigger auto-deployment, live in 30 seconds. This step is the shortest path for a solo developer to "look like a team."

Hands-on Steps

  1. Add systemd unit for app: Write an /etc/systemd/system/myapp.service to let node server.js run as a background service; it won't die when you close SSH.
  2. Write GitHub Actions workflow: Configure SSH key + rsync in .github/workflows/deploy.yml to achieve git push main → auto login to VPS → pull code → restart systemd.
  3. Manage Secrets: Fill the VPS SSH private key in GitHub Repo Settings → Secrets; use EnvironmentFile for local .env.
  4. Push to test: Change a line in README, commit → push. Watch GitHub Actions turn green, live in 30 seconds = R4 complete.

Detailed knowledge expanded in Module 3.

Roadmap R5

R5 · Troubleshooting

Within 24 hours of your first production deployment, you'll likely encounter at least 2 failures. The goal of R5 is not "no problems," but "finding the right remedy from the table within 30 seconds."

Hands-on: Create 5 types of failures and fix them

  1. 502 Bad Gateway: Stop the systemd service (systemctl stop myapp) and see what Nginx returns — then recover it.
  2. SSH Unreachable: Modify /etc/ssh/sshd_config with a wrong port (or temporarily disable firewall), and see how ssh root@IP fails.
  3. Disk Full: dd if=/dev/zero of=/tmp/bigfile bs=1M count=10000 to create a large file, then df -h to see the full disk.
  4. Service OOM: Write a Node script with an infinite loop consuming memory, and watch the OOM Killer terminate it.
  5. SSL Cert Expired: certbot renew --dry-run to see the renewal process; or temporarily change system time to after expiration and check the browser.

Module 1 · Linux

1.1 What is a "Server"

Don't be intimidated by the word "server". It's just a computer that's on 24/7 — hardware almost identical to your laptop, just with Linux installed, hooked up to an ethernet cable in a server room, without a monitor or keyboard, and you operate it "remotely" via SSH from your own computer.

From your laptop to the cloud, what changes

DimensionYour LaptopCloud Server
OSmacOS / WindowsUbuntu / Debian / CentOS (almost exclusively Linux)
InteractionScreen + Keyboard/MouseSSH Command Line (No screen)
UptimeOn when you use it24×7 Never turns off
Public IPUsually noneHas one public IP
PriorityAesthetics, smoothnessStability, runnable, doesn't crash
Why must it be Linux?The vast majority of server software (nginx, Node, Python, Docker, systemd) is Linux-first; macOS kernel is BSD-based and 95% compatible with Linux commands, but Windows is an entirely different ecosystem, which is why "doing backend" almost equals "using Linux".
Module 1 · Linux

1.2 Three Abstract Concepts: File System, Processes, Ports

Think of a Linux server as an "apartment building", the tenants are processes, the door numbers are ports, and the lease belongs to the user. 80% of ops work revolves around these three things: checking who lives there (processes), which door number is occupied (ports), and which lease is yours (permissions).

File System: Everything is a File

The core philosophy of Linux: disks are files, network cards are files, mice are files, process info is also files. This sounds abstract, but it's very consistent to use — everything is under /, and can be manipulated with ls, cat, cd.

ls /                  # Root directory
ls /home              # Users' home
ls /etc/nginx/         # nginx config
ls /var/log/           # Logs
cat /proc/cpuinfo      # CPU info (in memory, not a real file)

Processes: Running Programs

When you run node server.js, you spawn a Node process. A process has a PID (ID number). The most common ops commands:

ps aux | grep node     # View all node processes
top                    # Real-time CPU/memory usage (q to quit)
htop                   # Prettier top (requires apt install htop)
kill 1234              # Kill PID 1234
pkill -f "node server" # Kill by name
systemctl status myapp # Check systemd managed service

Ports: Window Numbers (0-65535)

A server can run many services simultaneously. Clients differentiate them by "port number" — just like the "door number" for each unit in an apartment building. Common conventions:

PortWho uses it
22SSH (Remote Login)
80HTTP
443HTTPS
3000 / 8080Developer local services (Common for Node/Python)
3306 / 5432MySQL / PostgreSQL
6379Redis
ss -tlnp               # Check which ports are listening
netstat -tlnp          # Old command, similar function
lsof -i :3000           # See who occupies port 3000
Common causes: inspect evidence before acting; do not terminate unknown processes.

Module 1 · Linux

1.3 SSH is Not Just "Remote Login"

SSH = Secure Shell. On the surface, it's "remote login", but it can actually handle all encrypted network connections — port forwarding, file transfer (SFTP), and running Git.

Key Login: Stop Using Passwords

Password login has two problems: (1) Slow and annoying; (2) Exposing port 22 means the whole world is brute-forcing your server. By switching to key login, the server only accepts machines holding the "private key", rendering brute force completely ineffective.

# Generate key pair locally
ssh-keygen -t ed25519 -C "you@example.com"
# Private key: ~/.ssh/id_ed25519 (NEVER LEAK THIS!)
# Public key: ~/.ssh/id_ed25519.pub (Paste into server's ~/.ssh/authorized_keys)

# One-click push public key (assuming password login still works)
ssh-copy-id root@YOUR_VPS_IP

# Login
ssh root@YOUR_VPS_IP
Private Key Permissions Must be 600If ~/.ssh/id_ed25519 has 644 permissions, SSH will refuse to use it (to prevent others from reading your private key). Run chmod 600 ~/.ssh/id_ed25519.

Config File: Aliases for Common Servers

Don't type ssh root@123.45.67.89 every time. Write ~/.ssh/config:

Host my-vps
  HostName 123.45.67.89
  User root
  Port 22
  IdentityFile ~/.ssh/id_ed25519

# Afterwards, just use:
ssh my-vps

Port Forwarding and Jump Hosts

Suppose your database is on an "internal" machine 10.0.0.5:5432, and you can only enter through a jump host vpn.example.com. For local psql to connect directly, SSH can "tunnel" for you:

ssh -L 5432:10.0.0.5:5432 vpn.example.com
# Then local psql -h 127.0.0.1 -p 5432 will forward through the ssh tunnel to the internal network
Undocumented DetailIn 2026, I couldn't find a unanimous conclusion on the official best practice for SSH ProxyJump, so I recommend checking your cloud provider's docs. The common syntax is ssh -J jump user@target (OpenSSH 7.3+).

Module 1 · Linux

1.5 Permissions and Users

Linux is a multi-user system. Every file has "who can read / who can write / who can execute" permissions for "owner / group / others".

View Permissions: ls -l

-rw-r--r-- 1 root root  1234 Aug  5 10:00 myapp.conf
drwxr-xr-x 2 root root  4096 Aug  5 09:00 nginx/

# 1st char: d = directory, - = file
# Next 9 chars: Three sets of rwx (owner/group/others)
# r=read(4) w=write(2) x=execute(1)

Change Permissions: chmod vs chown

CommandWhat it doesExample
chmod 600 mykeyChange permissions (number = owner + group + others)600 = Owner can read/write, others can do nothing
chmod +x script.shAdd execute permissionMust do before running a script for the first time
chown user:group fileChange ownershipchown www-data:www-data /var/www

sudo: Temporarily be root

root is the "God account" of Linux, it can change anything. Use a normal user for daily tasks, and use sudo to temporarily escalate privileges when installing packages or modifying system configs.

sudo apt install nginx      # Escalate to install
sudo systemctl restart nginx # Escalate to restart service
sudo !!                     # Re-run the previous command with sudo (lifesaver)
Don't use root for daily tasksIf root mistakenly runs rm -rf / (theoretically requires --no-preserve-root but might still execute), it's Game Over. Creating a dedicated user and using sudo is a good habit.
Module 2 · Network

2.1 One Picture to Understand HTTP → TCP → IP → Network Card

📌 30-Second ConclusionIn the 1 second it takes to open a website, your request passes through 4 gates and gets wrapped in 4 layers of "envelopes". As long as you figure out what these four layers do, you'll understand all network jargon.

What exactly is it

You type aidoc-zq.netlify.app in your browser, and about 1 second later you see the page. In this 1 second, your request leaves the browser and passes through 4 gates:

  1. Application Layer (HTTP) — You write GET /index.html, meaning "I want this file"
  2. Transport Layer (TCP) — Chops HTTP into small packets and numbers them to ensure they arrive in order, like a courier company
  3. Network Layer (IP) — Writes "where from, where to" on each packet, like an address on a shipping label
  4. Link Layer (Network Card) — Turns the packet into electrical/optical signals and sends it out, which is the actual vehicle driving

4-Layer Protocol Stack (ASCII Diagram)

   Your Request (Downstream)      Your Response (Upstream)
   ────────────────               ────────────────
   ┌──────────────┐               ┌──────────────┐
   │ HTTP  GET /  │               │ 200 OK  │
   ├──────────────┤               ├──────────────┤
   │ TCP  SYN/ACK │               │ TCP  FIN/ACK │
   ├──────────────┤               ├──────────────┤
   │ IP  src→dst  │               │ IP  dst→src  │
   ├──────────────┤               ├──────────────┤
   │ Card Signals │               │ Card Signals │
   └──────────────┘               └──────────────┘
   ▲ Wrap (Top to bottom)        ▲ Unwrap (Bottom to top)

How to use it: Watch an actual handshake

Run curl -v https://example.com, and you can see the entire "3-way handshake and 4-way wave" process of TCP. This is the core of TCP:

curl -v https://example.com
# * Trying 93.184.216.34:443...        ← TCP starts: sends SYN
# * Connected to example.com          ← Receives SYN+ACK, sends ACK (handshake complete)
# > GET / HTTP/1.1                    ← HTTP request starts sending
# < HTTP/1.1 200 OK                   ← HTTP response returns
# * Connection #0 to host example.com left intact

Hands-on: Capture a real packet

Want to see what a real IP packet looks like? tcpdump will show you (no root needed to capture your own outgoing packets):

tcpdump -i any -n port 80 -c 5
# Captures the first 5 packets on port 80
# You'll see things like src=192.168.1.5.dst=93.184.216.34.80
# This is what the IP+TCP+HTTP layers look like on the same wire

🚧 Mini-Theater: What are the OSI 7 layers?

OSI is an antique from 1984, but only four layers survive in reality. The OSI layers we actually use are: Physical → Data Link → Network → Transport → Application (the bottom four are enough; the "Session/Presentation" brothers in the middle are rarely implemented on their own).

💡 Memory Mnemonic"H writes, T delivers, I addresses, Card runs errands" — Four layers handle their own business without interfering with each other.

2.2 DNS Complete Picture: How directory assistance works

DNS visibility depends on record TTLs, resolvers, and local caches; there is no universal 48-hour guarantee. Compare authoritative and actual resolver answers.

What exactly is it

You input the string aidoc-zq.netlify.app, but computers only understand numbers like 75.2.60.5. DNS (Domain Name System) translates letters into numbers, like directory assistance — you say "Where is KFC", it tells you the specific address.

2.3 HTTPS / TLS / Let's Encrypt

📌 30-Second ConclusionHTTP is a postcard — a cafe packet sniffer can read it. HTTPS = registered mail; only you and the recipient can open it. Let's Encrypt made free SSL certs + auto-renewal a reality, making it the mainstream for the entire web in 2026.

What exactly is it: HTTP vs HTTPS

HTTP (Hypertext Transfer Protocol) is plaintext — if you enter "username/password" on a cafe Wi-Fi, the next table can see it by packet sniffing.

HTTPS = HTTP + TLS encryption layer, turning the transmitted content into ciphertext that only you and the server can decrypt. The little lock icon in the address bar means exactly this.

TLS 1.3 Handshake (1-RTT, ASCII Diagram)

Client (Browser)                        Server
  │                                      │
  │── ClientHello (Supported Algos) ───►│
  │                                      │
  │◄── ServerHello + Certificate ───────│
  │     + Finished (Key is computed)     │
  │                                      │
  │── Finished (Begin Encrypted Comm) ─►│
  │                                      │
  │▼ Application Data (Encrypted)        │

One round trip less than TLS 1.2, meaning lower latency. In 2026, mainstream browsers + servers default to TLS 1.3.

SNI: Multiple domains on one IP

Early HTTPS only allowed one certificate per IP, but what if your server hosts a.com / b.com / c.com? SNI (Server Name Indication) lets the client tell the server the domain name during the handshake, so the server picks the corresponding certificate.

Understanding SNILike a hotel receptionist: a guest says "I'm looking for John in Room 302" at the door, and the receptionist directs them, without knocking on every door.

Let's Encrypt + certbot (Verified 2026.8)

apt install -y certbot python3-certbot-nginx
certbot --nginx -d yourdomain.dev -d www.yourdomain.dev
certbot renew --dry-run    # Test auto-renewal

certbot automatically adds a systemd timer or cron, renewing every 60 days, keeping it valid indefinitely within the 90-day window.

2026.8 Let's Encrypt Rate Limits (Verified via Official Docs)

Good news: Normal renewals are exempt. Bad news: You can easily hit the 50 certs/week limit when constantly tweaking domains during testing.

🚧 Mini-Theater: "Cert expired, entire site down"

Let's Encrypt certs are valid for 90 days, certbot auto-renews at 30 days before expiry. But if your machine was off for a month, or the cron job crashed, the cert expires — browsers will block it as "Not Secure". First response:

certbot certificates               # View all certs and expiry
systemctl status certbot.timer     # Check if timer is running
certbot renew --force-renewal      # Force immediate re-sign
💡 Memory Mnemonic"HTTP runs naked, HTTPS wears a TLS coat" — Just looking at the URL protocol tells you if the transmission is secure.

2.4 Reverse Proxy: Why Nginx is the Swiss Army Knife

📌 30-Second ConclusionA reverse proxy is the "front desk receptionist" — you just say "I'm looking for John", and the receptionist locates the specific office. Users visiting yourdomain.dev are actually routed by Nginx, which distributes requests to backend Node services for you.

What exactly is it: Forward vs Reverse

Many confuse "proxy" with "reverse proxy", but their directions differ:

【Forward Proxy】 Client ←→ Proxy ←→ Internet
  Acts on behalf of the client. Typical scenario: Corporate VPN/firewall bypass
  Client knows the proxy exists

【Reverse Proxy】 Client ←→ Reverse Proxy ←→ Backend Servers
  Acts on behalf of the server. Typical scenario: Nginx with Node
  Client has no idea how many servers are behind it

Request Flow (ASCII Diagram)

User Browser      Nginx Reverse Proxy     Backend Server
   │                  │                       │
   │ GET /api/users   │                       │
   ├─────────────────►│                       │
   │                  │ Choose Node1          │
   │                  ├──────────────────────►│
   │                  │◄──── 200 OK JSON ─────┤
   │◄────── 200 OK ───┤                       │
   │                  │                       │
   │ GET /static/x.js │                       │
   ├─────────────────►│                       │
   │                  │ Return file from disk │
   │◄────── 200 OK ───┤ (Bypasses Node)       │

5 Key Roles of Nginx

  • HTTPS Termination — Nginx handles SSL; Node runs plaintext HTTP (saves CPU).
  • Multi-App Sharing 80/443 — Routes to different Node services based on domain.
  • Static File Acceleration — Nginx returns static assets directly, without involving Node.
  • Load Balancing — Distributes requests across multiple Node instances.
  • Caching/Compression/Gzip — Handled by Nginx with a single line of config.

Why Nginx is a "Swiss Army Knife"

Nginx is the de facto standard reverse proxy server — open-source, stable, easy to configure, low memory footprint. Long-term stats by Netcraft / W3Techs show Nginx consistently in the top 2 global web server market share (the other being Apache), with Nginx being the mainstream for new deployments. What exactly is it

Imagine a residential complex: The IP address is the complex's address (globally unique), and the port number is the building/apartment number. On the same machine, you can run over 60,000 services, each occupying an apartment number without interfering with each other.

2.8 Local Services: 127.0.0.1 vs 0.0.0.0

📌 30-Second ConclusionIf you want to let external users access your local service, you must listen on 0.0.0.0 instead of 127.0.0.1 (localhost). If you're blocked by NAT and don't have a public IP, use Cloudflare Tunnel or Tailscale to penetrate the intranet.

The Difference in Listening Addresses

【127.0.0.1】  Loopback address (localhost)
  → Only accessible from your own machine
  → Good for internal services like databases

【localhost】  Resolved name by the OS
  → Usually = 127.0.0.1
  → Can be pointed to other IPs by modifying /etc/hosts

【0.0.0.0】    Listen on all network interfaces
  → Accepts access from any interface (Local + Public)
  → Truly "publicly exposed" services should listen on this

Node Listening Examples

// Local only (Default)
app.listen(3000, '127.0.0.1', () => {
  console.log('Only accessible at localhost:3000');
});

// Accepts all interfaces
app.listen(3000, '0.0.0.0', () => {
  console.log('Accessible from local, public, and internal networks');
});

// Default (Usually = 0.0.0.0, but some versions vary)
app.listen(3000, () => console.log('Default listening'));

2.9 VPN and Proxy: Differentiating four "bypass" postures

📌 30-Second ConclusionVPNs, forward proxies, reverse proxies, and application-layer proxies are often confused, but they operate at different layers. A VPN is "drawing a dedicated line at the network layer", a reverse proxy "takes requests for the server at the application layer", and a forward proxy "acts on behalf of the client at the application layer".

What exactly is it: Four scenarios

  • Corporate VPN — You can access the company's internal Git from home; the OS thinks you are sitting at your desk
  • Corporate Forward Proxy — The company uses a unified proxy to access the public network; all employees share the same exit
  • Reverse Proxy (Nginx) — Users visit the company website, and Nginx distributes traffic at the front
  • Application Layer Proxy — Setting a SOCKS5/HTTP Proxy extension in the browser to access the public internet

Four-Way Comparison ASCII Diagram

【Forward Proxy】                     【Reverse Proxy】
   Client ─→ Proxy ─→ Internet         Internet ─→ Rev Proxy ─→ Backend Servers
   Acts on behalf of the client        Takes requests for the server

【VPN】                               【Application Layer Proxy】
   Client ─→ VPN ─→ Target Network     Client ─→ SOCKS5/HTTP Proxy ─→ Internet
   Dedicated line, virtual NIC         App layer routing, SOCKS5 sees upper protocols

Operating Layers Overview

TypeOperating LayerTypical Scenario
VPNL3 Network LayerEntire virtual dedicated line, OS routing table perspective
Reverse ProxyL7 Application Layer (HTTP)Nginx handling HTTP traffic for you
Forward ProxyL7 Application Layer (HTTP)Browser setting a proxy to the internet
SOCKS5 ProxyL5 Session LayerArbitrary TCP/UDP traffic forwarding

Three Tiers of VPN Protocols

  • IPsec — Enterprise-grade veteran, 1980s protocol suite, complex configuration but stable
  • SSL VPN — Lightweight, just install the client (Cisco AnyConnect, etc.)
  • WireGuard — Newcomer, 4000 lines of code, merged into mainline since Linux 5.6 (2020-03-29)

Core Advantages of WireGuard

  • Configures like SSH — Establish connection just by exchanging public keys
  • Small code base — Around 4000 lines, easy to audit
  • Modern encryption — Curve25519, ChaCha20, Poly1305, etc.
  • Kernel implementation — High performance, suitable for embedded and backbone
  • Built-in roaming — Switch networks without reconnecting (similar to Mosh)

What is ssh -D 1080

SSH's built-in dynamic SOCKS proxy. Uses SSH as a SOCKS5 server; all application traffic routed through port 1080 will be forwarded by SSH.

🚧 Mini-Theater: "Why can the corporate VPN access the intranet?"

When the VPN client dials in, the OS receives a set of "routing table change instructions": packets heading to 10.0.0.0/8 go through utun0 (virtual network card), others go through the original default card. From your OS's perspective, this is the network stack of sitting at your desk.

2.10 Public / Private Network / NAT: The Security Guard's Job

📌 30-Second ConclusionA public IP is your house address (globally unique), a private IP is your apartment unit number (can be repeated across complexes). The whole complex shares one public IP, and the security guard (NAT) distributes incoming packages based on the "unit number" — this is what NAT does.

What exactly is it

If every device needed a public IP, IPv4 (4.3 billion) would have run out long ago. NAT (Network Address Translation) allows an entire complex to share one public IP — internal private IPs are "translated" by the router.

Three Private Network Segments (RFC 1918)

SegmentAddress RangeCountTypical Scenario
10.0.0.0/810.0.0.0 - 10.255.255.25516.77 millionLarge enterprise / Cloud provider intranet
172.16.0.0/12172.16.0.0 - 172.31.255.2551.04 millionMedium-sized network
192.168.0.0/16192.168.0.0 - 192.168.255.25565,536Home router (most common)

The 192.168.1.x you see on your home Wi-Fi might be 10.0.0.x on your corporate intranet.

NAT Principle ASCII Diagram

Your PC 192.168.1.100:5000 ─→ Home Router ─→ Public 1.2.3.4:40001 ─→ baidu.com
                                  ▲
                                  │ NAT Translation Table:
                                  │ Internal IP:Port      → Public IP:Port
                                  │ 192.168.1.100:5000    → 1.2.3.4:40001
                                  │ 192.168.1.101:5001    → 1.2.3.4:40002

Baidu replies to 1.2.3.4:40001 → Router checks table → Forwards to 192.168.1.100:5000

Port Mapping = "Reverse Proxy" done by the router

Want your home NAS to be accessible from the outside? Use "port mapping" on the router: map a public port (e.g. 8081) to the NAS's internal IP port 5000. External access to Your Public IP:8081 = accesses NAS 5000.

AnalogyThe complex security guard receives a package for you, addressed only to the "security guard". The guard remembers which 18th-floor unit each package is for and distributes them when you come to pick them up. Port mapping is "reserving a specific locker for a unit".

IPv4 Exhaustion History + Enter IPv6

In November 2019, IANA allocated the last five /8 segments; IPv4 was officially "exhausted". NAT has been a stopgap extending its life for over a decade. IPv6 (detailed in 2.13) has 128-bit addresses; theoretically, every grain of sand can have an IP, eliminating the need for NAT.

🚧 Mini-Theater: "Why is my home IP the same 192.168.1.100 as my neighbor's?"

All home routers default to the 192.168.1.x segment. Your 192.168.1.100 and your neighbor's 192.168.1.100 do not interfere with each other in your respective homes — because they are behind NAT, and the public internet only sees the complex's public IP.

💡 Memory Mnemonic"Public is globally unique, Private is for complex use, Going out relies on NAT" — Hundreds of devices at home can reuse IPs because the public internet only sees the complex gate.

2.12 HTTP/2 and HTTP/3 Evolution: Why upgrade protocols

📌 30-Second ConclusionHTTP/2 fixes the waste of "one request per TCP connection" by using multiplexing, allowing multiple concurrent requests over one connection. HTTP/3 goes further, abandoning TCP for QUIC ("TCP-like" over UDP), eliminating TCP head-of-line blocking. By 2026, mainstream CDNs like Cloudflare have enabled HTTP/3 by default.

What exactly is it: Where HTTP/1.1 hurts

Browsers commonly limit HTTP/1.1 connections per origin to six; the implementation decides. This did not universally become unlimited. HTTP/2 multiplexes streams on a connection.

HTTP/2's Three Big Moves

  • Multiplexing — One TCP connection handles multiple concurrent requests; resources arrive in parallel
  • Header Compression (HPACK) — Repeated headers are not re-transmitted, saving bandwidth
  • Binary Framing — Switches from text to binary transmission for faster parsing

HTTP/3 Revolution: Based on QUIC

HTTP/2 couldn't solve the head-of-line blocking inherent to TCP itself — if one packet drops, all subsequent packets must wait. HTTP/3 directly abandons TCP and switches to QUIC (based on UDP):

HTTP/1.1: Multiple requests queue → TCP blocks → Whole queue waits
HTTP/2:   Multiplexing          → TCP may still block → Partially solved
HTTP/3:   QUIC (UDP)            → Packet loss doesn't affect other streams → Fully solved

Additional HTTP/3 Advantages

  • 0-RTT Handshake — Second visits open almost instantly (QUIC built-in encryption)
  • Connection Migration — Switching from WiFi to 4G doesn't require reconnecting
  • Built-in Encryption — TLS 1.3 by default, no plaintext allowed

2026.8 Deployment Status (Partially unverified)

  • Cloudflare: HTTP/3 enabled by default (since 2019)
  • Google: HTTP/3 default across entire site
  • Domestic CDNs: Alibaba Cloud / Tencent Cloud CDNs already support HTTP/3
  • Global HTTP/3 adoption rate: Exact figures not verified word-for-word here; please refer to the latest 2026.8 Cloudflare Radar reports

"Why is it fine if I still use HTTP/1.1?"

For small to medium projects, HTTP/1.1 + static resource CDNs are perfectly adequate. The cost of upgrading to HTTP/2/HTTP/3 lies in upgrading Nginx/Node services, with benefits mostly seen in "high concurrency + global users" scenarios. Solo developers' v1 projects don't need to chase the bleeding edge.

💡 Memory Mnemonic"H2 multiplexes, H3 kills TCP" — Each generation solves a specific class of problems.

2.13 IPv6 Primer: 128-bit addresses, enough for every grain of sand

📌 30-Second ConclusionIPv6 uses 128-bit addresses; theoretically enough to give every grain of sand on Earth an IP. The biggest advantage is end-to-end reachability, eliminating the need for NAT. By 2026.8, global deployment continues to rise (exact percentages unverified here, refer to Google/APNIC data), and major domestic ISPs largely support it, though outbound traffic often still routes via v4.

What exactly is it: Why IPv4 isn't enough

IPv4 uses 32-bit addresses. Global and regional address pools exhausted at different times. IPv6 uses 128 bits; migration still requires DNS, firewall, and service compatibility planning.

Address Format

IPv4: 192.168.1.100                  (4 segments, each 0-255)
IPv6: 2001:0db8:85a3:0000:0000:8a2e:0370:7334
      ┗──── 8 segments, each 4 hex digits (0-ffff) ────┛

Simplification rules:
  → Leading zeros can be omitted: 2001:db8:85a3:0:0:8a2e:370:7334
  → Consecutive zero blocks can be merged: 2001:db8:85a3::8a2e:370:7334
  → But :: can only appear once

Three Major Advantages

  • Massive address space — 128 bits, 2^128 ≈ 3.4 × 10^38 addresses
  • End-to-end reachability — No more NAT, every device gets a public IP
  • Built-in IPsec — The protocol stack comes with native encryption options

2026.8 Deployment Status (Partially unverified)

  • Google IPv6 Statistics: Global deployment continues to rise; for exact percentages, refer to google.com/intl/en/ipv6/statistics.html for the latest 2026-08 data
  • APNIC Measurements: Visit stats.labs.apnic.net/ipv6 to see deployment rates by country
  • Top 3 Domestic ISPs: Most already support IPv6, but outbound traffic might still default to v4

Should you adopt IPv6?

It depends on your target users:

  • Primarily domestic users → Mostly usable now, but CDNs are still v4-heavy; can postpone
  • Primarily overseas users → Enabling v6 offers performance advantages
  • Future-proofing → Early adoption brings early benefits; dual-stack v4/v6 cost is practically zero

Verification

🚧 Mini-Theater: "Why is IPv4 still prioritized when my v6 service is on?"

Many clients default to v4 (since v4 networks are mature with fewer drops/firewalls) and only fallback to v4 if v6 negotiation fails. To force v6, clients need explicit configuration.

3.2 systemd Process Hosting: Stop Node from dying when SSH closes

Running ssh my-vps && node server.js & directly has two fatal flaws: (1) SSH disconnect = process killed; (2) Server restart = service gone. systemd is Linux's built-in "process manager" that solves both of these problems.

Complete service file template (Ready to use)

Write to /etc/systemd/system/myapp.service:

[Unit]
Description=My Node App
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/var/www/myapp
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5
EnvironmentFile=/var/www/myapp/.env
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

Usage Commands

systemctl daemon-reload                 # Reload config
systemctl enable myapp                  # Start on boot
systemctl start myapp                   # Start service
systemctl status myapp                  # Check status
systemctl restart myapp                 # Restart (common for deployment)
journalctl -u myapp -f                  # Real-time logs
journalctl -u myapp --since "1 hour ago"# Logs from the last hour
Do not run services as rootIn production, always use a dedicated user (www-data or create a new deploy user) so that if the service is compromised, they don't immediately gain root access.

3.3 Nginx Reverse Proxy Practical Configuration Template

Write to /etc/nginx/sites-available/yourdomain.dev (Proxies HTTPS to local Node port 3000):

server {
    listen 80;
    server_name yourdomain.dev www.yourdomain.dev;
    return 301 https://$host$request_uri;  # Force HTTP to HTTPS
}

server {
    listen 443 ssl http2;
    server_name yourdomain.dev www.yourdomain.dev;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.dev/privkey.pem;

    # Reverse proxy to Node
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Static resources returned directly by Nginx (Optional)
    location /static/ {
        alias /var/www/myapp/public/;
        expires 30d;
    }
}

Enable Configuration

ln -s /etc/nginx/sites-available/yourdomain.dev /etc/nginx/sites-enabled/
nginx -t                  # Test config syntax
systemctl reload nginx    # Reload (zero downtime)

Docker solves the age-old "It works on my machine" problem — packaging your app + dependencies into an image so any machine with Docker installed can run it with identical results.

Why Solo Developers Need Docker

        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /var/www/myapp
            git pull origin main
            systemctl restart myapp
            sleep 3
            systemctl status myapp

GitHub Secrets Configuration

Repository → Settings → Secrets and variables → Actions → New repository secret:

  • VPS_HOST: VPS Public IP
  • VPS_USER: deploy (The dedicated deployment user you created)
  • VPS_SSH_KEY: The contents of the ~/.ssh/id_ed25519 private key on your VPS

After this one-time setup, every git push main will automatically deploy your app.

3.6 Environment Variables / Secrets Management / The right way to use .env

Secrets should never appear in your codebase. They live in only two places: (1) Your local .env file; (2) GitHub Secrets / CI Environment Variables.

Node reading .env

# npm install dotenv
require('dotenv').config()
const dbUrl = process.env.DATABASE_URL

.gitignore must include .env

# .gitignore
.env
.env.local
node_modules/

Secure approach for production .env

  1. On the VPS, run vim /var/www/myapp/.env and enter your secrets
  2. Run chmod 600 .env (so only the owner can read it)
  3. Load it in the systemd service file using EnvironmentFile=/var/www/myapp/.env (see 3.2)
  4. Use GitHub Secrets for CI deployment
Secret Leak EmergencyIf a secret is accidentally pushed to GitHub: (1) Immediately rotate the secret at the corresponding service (DB/Payments); (2) Use BFG Repo-Cleaner to clear history; (3) Delete and push the repository from scratch (cleanest). A secret leak is not Game Over, but it must be handled instantly.

5 Types of Failures 30-Second Remedy Table

Don't panic when a failure occurs. First look at the "Symptom", then run the "30-Second Command", and finally fix the "Root Cause". of failures are variations of these 5 types.

Symptom 1 · 502 Bad Gateway

30-Second Command: systemctl status myapp && journalctl -u myapp -n 50

Common causes: inspect evidence before acting; do not terminate unknown processes.: (a) App process crashed → Check journalctl errors and restart; (b) Reverse proxy upstream port is wrong → Verify the port in proxy_pass http://127.0.0.1:3000

Deep Dive: §3.2, §3.3

Symptom 2 · SSH Unreachable

30-Second Command: Run ssh -v root@IP locally for verbose logs; use VPS web console VNC/serial access

Common causes: inspect evidence before acting; do not terminate unknown processes.: (a) Port blocked by firewall (Default 22 is often blocked in China, change to 22222); (b) Key permissions not set to 600; (c) Cloud provider security group hasn't allowed port 22

Lifesaver: VPS Console → Instances → "VNC Login" or "Rescue Mode" to enter the system bypassing SSH

Symptom 3 · Disk Full

30-Second Command: df -h && du -sh /* | sort -h | tail -10

Common causes: inspect evidence before acting; do not terminate unknown processes.: (a) Logs not rotated (/var/log/nginx taking tens of GBs); (b) Temp files not cleared (/tmp); (c) Database bloated

Remedy: journalctl --vacuum-size=500M to trim logs; find /var/log -type f -size +100M to find large files

Symptom 4 · Service Memory Leak OOM

30-Second Command: dmesg | grep -i "out of memory" | tail -5 (Check OOM Killer records)

Common causes: inspect evidence before acting; do not terminate unknown processes.: (a) App code leak (Global Map/Array constantly pushed); (b) Configured cache too large; (c) Traffic spike

Temporary: Add swap fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile; Permanent: Restart service + debug memory leak code

Symptom 5 · SSL Certificate Expired

30-Second Command: certbot certificates && certbot renew --dry-run

Common causes: inspect evidence before acting; do not terminate unknown processes.: (a) certbot auto-renew cron/timer crashed; Immediate Renewal: certbot renew --force-renewal + systemctl reload nginx

Prevention: systemctl list-timers | grep certbot to ensure the timer is running
