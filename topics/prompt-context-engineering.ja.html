概念 00

全体像：プロンプトエンジニアリングからコンテキストエンジニアリングへ

2023年に広く語られた「プロンプトエンジニアリング（どう問いかけるか）」は、2026年には コンテキストエンジニアリング（モデルに見せるすべての情報をどう設計・管理するか） へと進化しました。単発の質問への回答から「自律的なタスク遂行」へとAIの役割が変化したためです。

項目プロンプトエンジニアリング（単発型）コンテキストエンジニアリング（エージェント時代）
最適化対象単一の指示文の表現コンテキストウィンドウ全体に何を・いつ投入し・いつ破棄するか
主要制約指示の明確さAttention（注意）予算の有限性：トークン過多による注意散漫
代表的アクション例文の追加、フォーマットの指定システムプロンプトの階層化、ツールセットの絞り込み、要約・圧縮
公式定義最小限の高シグナルトークンセットによって、目的の成果物が得られる確率を最大化する（Anthropic Context Engineering 論文より）
マインドセットとエンジニアリングの役割分担AI 活用効率マップ & マインドセット が「AIで何ができるか・どう向き合うか（原則）」を扱うのに対し、本ページは「具体的にどう記述し・どう情報を渡すか（実装）」を解説する実践マニュアルです。
技法 01

7大基本技法（❌/✅ 対比）

1. 明確性と具体性 (Be Clear & Direct)

❌ 曖昧な指示「コードをリファクタリングして綺麗にして」
✅ 具体的指示「`calculateTotal` 関数内の多重ネストされた if 文を早期リターン（ガード節）に書き換え、計算ロジックを純粋関数として抽出してください」

2. Few-shot（具体例の提示）

❌ 抽象的なルール指示のみ「ユーザーのフィードバックを感情分析してポジティブ/ネガティブに分類して」
✅ 2〜3件の入出力例を併記「入力: '動作は軽快だがUIが分かりにくい' → 出力: `{"sentiment": "mixed", "aspects": {"performance": "+", "ui": "-"}}` のように形式を例示」

3. 思考プロセスの明示 (Chain of Thought / CoT)

❌ 即座に答えを求める「このアルゴリズムの計算量を求めて」
✅ 思考ステップを指定「まず各ループの実行回数を数式化し、次に最悪ケースを特定した上で、最終的なビッグオー記法を導出してください」

4. 構造化タグによるコンテキスト分離 (XML/Markdown Tags)

❌ 指示と参考文書の混在「次の記事を要約して。記事内容：...」
✅ タグで領域を明確化「`<document>...</document>` 内の資料に基づき、`<instructions>...</instructions>` に従って要約してください」

5. 役割とトーンの定義 (Role & Persona)

❌ 一般論としての回答「このセキュリティ設計を評価して」
✅ 専門家の視点を付与「あなたは金融系システムのシニアセキュリティアーキテクトです。OAuth 2.0 PKCE フローのトークン漏洩リスクに焦点を当ててレビューしてください」

6. ネガティブ制約（禁止事項の明確化）

❌ ポジティブ指示のみ「React コンポーネントを書いて」
✅ 禁止事項を併記「外部ライブラリは新規追加せず、CSS-in-JS は使用せず、必ず CSS Modules を用いてください」

7. 出力フォーマットの厳格指定

❌ 自然言語のまま出力「変更点の一覧を出して」
✅ スキーマやマークダウン表を指定「`ファイルパス | 変更種別 | 変更理由` の3列 Markdown テーブル形式で出力してください」
技法 02

構造化出力 & フォーマット制御

プログラムによる自動処理を行う場合、JSON Mode や Structured Outputs（Pydantic スキーマ等）を活用し、パースエラーの発生率を物理的にゼロに近づけます。

# Pydantic スキーマによる確実な構造化出力
class CodeAuditResult(BaseModel):
    has_vulnerability: bool
    severity: Literal["LOW", "MEDIUM", "HIGH", "CRITICAL"]
    cve_id: str | None = None
    remediation_steps: list[str]
技法 03

マルチモーダルプロンプトの極意

  • UI スクリーンショット： 解像度を適切に保ちつつ、注目すべき領域を赤枠やアノテーションで強調。
  • 設計書・PDF： ページ数が多い場合は、該当章を特定して抽出投入し、Attention 散漫を防ぐ。
  • OCR テキストとの併用： 画像だけでなく、抽出可能なテキストデータを併せて渡すことで認識精度が飛躍的に向上。

モデル別の指示調整

推論、ツール、構造化出力、複数モダリティの公式説明を確認します。古いモデルのコツを一般化せず、条件をそろえて比較します。

RAG シナリオにおけるプロンプト設計

RAG（検索拡張生成）では、検索されたコンテキストをモデルが「事実」として優先するようプロンプトで制御します：

<system>
以下の <sources> に記載されている情報のみに基づいて回答してください。
資料内に回答が存在しない場合は、一般的な推測を行わず「提供された資料には記載がありません」と明答してください。
すべての主張には [1] のような出典番号を付与してください。
</system>
エンジニアリング 06

コンテキストエンジニアリングの核心

「コンテキストウィンドウが大きいからといって、何でも詰め込んでよいわけではない」——これが現代の鉄則です。コンテキスト内の情報量が増えるほど、トークンあたりの Attention 強度は低下 します。

  • 高シグナル・低ノイズ： 不要な依存関係ファイルやビルド成果物は除外して投入。
  • 位置バイアス（Lost in the Middle）： 重要な指示やルールは、コンテキストの最前部または最後尾に配置。
  • Context Caching の活用： 静的な仕様書やリポジトリ定義はキャッシュし、コストとレイテンシを削減。
エンジニアリング 07

自律型エージェント（Agentic）のコンテキスト管理

長期にわたるタスクをエージェントに任せる場合、コンテキストの肥大化と迷走を防ぐための設計が必要です：

  • サブエージェント分割： 調査（Research）、設計（Plan）、実装（Coder）で独立したコンテキストを持たせる。
  • 中間成果物の永続化： 思考過程をディスク上の Markdown（implementation_plan.md 等）に書き出し、記憶を外部化。
  • コンテキストの定期リフレッシュ： 単一セッションで何十回もやり直さず、キリの良いところで新しい対話を開始。
エンジニアリング 08

Token 経済学とコスト管理

💡 コスト最適化のベストプラクティス ・静的な共通プロンプトを先頭に固定して Prompt Caching を最大化。
・日常のルーティングや軽微な整形には軽量モデル（Flash / Mini）を割り当て。
・過度な会話ログを適宜要約・クリア。
💸 コストが跳ね上がるアンチパターン ・毎回プロンプトの先頭に動的なタイムスタンプを入れ、キャッシュを無効化。
・全タスクに最高額の推論モデルを画一的に使用。

モデルルーティングは評価から

品質による選択、負荷分散、障害時切替を区別し、代表課題で評価します。古い issue や検索結果の不足で機能の不存在を断定しません。

エンジニアリング 10

Prompt インジェクション & セキュリティ防御

  • 間接的インジェクション対策: 外部 Web ページやユーザー入力テキストを処理する際、プロンプト指示とデータ領域を明確に分離。
  • 実行権限のガードレール: コマンド実行やファイル削除を行う前に、インターセプターミドルウェアで危険なパターンを検知・遮断。

実践 14

アンチパターン図鑑

  • 万能プロンプト病: 1つの巨大プロンプトにあらゆる要件を詰め込み、モデルの注意を飽和させる。
  • 感情的懇願: 「お願いだから間違えないで」と懇願し、型スキーマや具体的制約を与えない。
  • コンテキスト汚染: 過去のエラーログや迷走した会話履歴をクリアせずに引きずり続ける。
