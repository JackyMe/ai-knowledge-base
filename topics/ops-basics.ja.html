なぜ学ぶ必要があるのか

こんな経験はありませんか？ Vercel にデプロイした個人開発アプリが突然 DDoS を受けて高額請求に怯えたり、Cloudflare Pages の帯域制限やリージョン制限に悩まされたり、深夜に Supabase の接続数上限に達して立ち往生したり……。

SaaS プラットフォームは極めて便利ですが、プラットフォームの制約や料金の壁に直面した瞬間、その恩恵は足かせに変わります。そこから一歩踏み出そうとしたとき、SSH、systemd、リバースプロキシ、DNS レコード、TLS ハンドシェイクといったインフラ用語の山に圧倒されてしまう開発者は少なくありません。

このドキュメントが提供するものと提供しないもの提供するもの： 5段階ロードマップ ＋ サーバー・ネットワーク・デプロイの 必要最小限のコア知識 ＋ 5大障害の30秒処方箋。読了後に中規模プロジェクトのサーバーを自力で管理・運用できるようになります。
提供しないもの： Kubernetes クラスタの大規模運用、GPU 分散推論クラスタ、99.999% の極限チューニングなどは対象外です。

対象読者

  • Next.js / Node / Python / Go 等でフルスタックアプリを構築した経験があり、普段は Vercel / Netlify / Cloudflare / Supabase / Railway に頼っている方。
  • ドメインを購入したことはあるが、DNS 解決や TLS 証明書の背後で何が起きているか正確に把握していない方。
  • 本番障害が起きたときに自力でログを追えず、他人に助けを求めるしかなかった経験がある方。
  • SRE や専門インフラエンジニアを目指すわけではないが、自前でサーバーを安定運用できるスキルを身につけたい方。

5段階ロードマップ

学習プロセスを5つの段階に分割しています。各段階には 検証可能な具体的成果物 が設定されており、着実にステップアップできます。

ロードマップ R1

R1 · 現状の棚卸し

いきなり VPS を契約する前に、現在開発・運用しているプロジェクトの構成を書き出します。これにより、SaaS の継続が適しているか、自前運用に切り替えるべきかが明確になります。

実践：プロジェクトデプロイ一覧の作成

稼働中のアプリごとに以下の4項目を整理します：

  1. 実行環境: Vercel / Netlify / Cloudflare Pages / Supabase / VPS / その他
  2. 月額コスト: Free Tier / Pro / 推定月額費用
  3. 現在のボトルネック: レスポンス遅延 / タイムアウト / 予期せぬ従量課金 / リージョン制限など
  4. 自前運用の価値: 静的フロントエンド中心なら SaaS 維持が有利。長時間バックグラウンド処理、WebSocket 常時接続、独自ランタイムが必要なら自前運用の費用対効果が高い。
判断の目安プロジェクトの80%が 静的サイト ＋ 外部SaaS DB であれば、無理に移行する必要はありません。常時起動タスク、大量の画像処理、ローカルLLM連携、リージョン制限の回避 が必要なサービスから自前運用を導入するのが賢明です。
ロードマップ R2

R2 · Linuxの基礎

1コア 1GB メモリ程度の安価な VPS（月額 $3〜$5 程度）を契約し、Ubuntu 24.04 LTS をセットアップします。SSH 鍵認証でログインし、Nginx を起動してブラウザから接続確認を行います。

実践ステップ

  1. VPS の選定: DigitalOcean, Vultr, AWS, Linode, さくらのVPS などからユーザーに近いリージョンを選択。OS は最も情報量の多い Ubuntu 24.04 LTS を推奨。
  2. ローカルで SSH 鍵を生成: ssh-keygen -t ed25519 -C "your@email" を実行し、~/.ssh/id_ed25519.pub の内容を VPS 管理画面の SSH 鍵登録欄に貼り付け。
  3. VPS への接続: ターミナルから ssh root@YOUR_VPS_IP で接続。初回接続時のフィンガープリント確認には "yes" と入力。
  4. Nginx のインストール: apt update && apt install -y nginx を実行後、systemctl status nginx で active (running) を確認。
  5. ブラウザ確認: http://YOUR_VPS_IP にアクセスし、Nginx の Welcome 画面が表示されれば R2 は完了です。
ロードマップ R3

R3 · ネットワーク基幹

IP アドレス直接アクセスから、独自ドメイン ＋ HTTPS（SSL証明書）による安全な接続へと昇格させます。DNS、Certbot、Nginx のリバースプロキシ連携を一気に形にします。

実践ステップ

  1. ドメインの取得: Cloudflare Registrar、Namecheap、お名前.com 等でドメインを取得。
  2. DNS レコードの設定: 管理画面で A レコードを作成し、ドメインを VPS のパブリック IP に紐付け。dig yourdomain.dev で反映を確認。
  3. SSL 証明書の発行: apt install -y certbot python3-certbot-nginx を実行後、certbot --nginx -d yourdomain.dev で無料の Let's Encrypt 証明書を自動取得・設定。
  4. リバースプロキシの設定: Nginx 経由でポート 443（HTTPS）の通信をローカルの Node/Python アプリ（例: ポート 3000）へ転送。
  5. ブラウザ接続: https://yourdomain.dev で鍵マーク付きで自作アプリが表示されれば R3 完了です。
ロードマップ R4

R4 · デプロイパイプライン

手動でのファイル転送や SSH 直接ログインでの更新から卒業し、git push をトリガーとする自動デプロイ環境を構築します。

実践ステップ

  1. systemd サービス定義: /etc/systemd/system/myapp.service を作成し、SSH 切断後もアプリがバックグラウンドで永続稼働しクラッシュ時に自動再起動するよう設定。
  2. GitHub Actions ワークフローの作成: .github/workflows/deploy.yml を設定し、main ブランチへの push を契機に VPS へ自動 SSH 接続・コード取得・再起動を実行。
  3. シークレットの安全な管理: SSH 秘密鍵を GitHub の Repository Secrets に登録。環境変数はサーバー上の .env ファイルに集約。
  4. 本番テスト: README などを1行変更して push し、GitHub Actions がグリーンになり30秒で本番に反映されることを確認。
ロードマップ R5

R5 · 障害調査とトラブルシューティング

本番運用における最大の武器は、「障害を起こさないこと」ではなく「障害が起きた際に30秒以内に適切な切り分けができること」です。

実践：代表的な5大障害の再現と復旧

  1. 502 Bad Gateway: systemctl stop myapp でアプリを停止させ、Nginx のエラー挙動を確認した後に再起動で復旧。
  2. SSH 接続不能: ポート設定の誤りやファイアウォール遮断のパターンを把握し、コンソール経由での復旧手順を確認。
  3. ディスク容量枯渇: df -h で空き容量を確認し、肥大化したログファイルや Docker イメージのクリーンアップを実践。
  4. OOM（メモリ不足）: メモリリーク発生時の OOM Killer のログを dmesg -T で確認し、スワップ設定やプロセス制限を適用。
  5. SSL 証明書の更新エラー: certbot renew --dry-run で自動更新のシミュレーションを実行。
モジュール 1 · Linux

1.1 サーバーとは何か

「サーバー」という言葉に身構える必要はありません。サーバーの本質は、24時間365日電源が入ったままネットワークに繋がっているコンピュータ に過ぎません。手元のPCとハードウェア構造はほぼ同じであり、ディスプレイやキーボードを持たず、データセンターのラックに収められ、SSH 経由でリモート操作する点が異なるだけです。

手元のPCとクラウドサーバーの違い

項目手元の PC / ラップトップクラウドサーバー (VPS)
OSmacOS / WindowsUbuntu / Debian 等の Linux が主流
操作形態GUI（画面・マウス・キーボード）SSH（コマンドラインのみ）
稼働時間作業時のみ起動24時間常時稼働
パブリック IP通常は家庭内プライベート IP固有のグローバル IP を保持
重視される特性操作の快適さ・デザイン高可用性・安定性・リソース効率
なぜサーバーOSは Linux なのかNginx、Node.js、Python、PostgreSQL、Docker、systemd など、現代のWebインフラを支える主要ソフトウェアは Linux ファーストで最適化されています。バックエンドやインフラを学ぶことは、実質的に Linux の基本を習得することと同義です。
モジュール 1 · Linux

1.2 3つの抽象概念：ファイルシステム、プロセス、ポート

Linux サーバーを「アパート」に例えてみましょう。各部屋の住人が プロセス、部屋番号が ポート、契約や鍵が 権限 に相当します。日々のサーバー運用の8割は、どのプロセスが動いているか、どのポートを使用しているか、どの権限で動いているかの確認です。

ファイルシステム：すべてはファイルである

Linux の根幹哲学は「Everything is a File（すべてはファイルである）」です。ストレージだけでなく、ハードウェアデバイス、ネットワークソケット、プロセスの情報まで、すべて /（ルートディレクトリ）以下の階層に配置されたファイルとして扱われます。

ls /                  # ルートディレクトリの確認
ls /etc/nginx/         # Nginx の設定ファイル群
ls /var/log/           # システムおよび各サービスのログ
cat /proc/cpuinfo      # CPU 情報（メモリ上の仮想ファイル）

プロセス：実行中のプログラム

node server.js を実行すると、固有の PID（プロセスID）を持つプロセスが生成されます。運用で頻出するコマンド：

ps aux | grep node     # Node プロセスの稼働状況を確認
top                    # リアルタイムの CPU / メモリ消費量を確認（q で終了）
htop                   # より見やすいリソースモニター（apt install htop）
kill -9 1234           # PID 1234 のプロセスを強制終了
systemctl status myapp # systemd 管理下のサービス状態を確認

ポート：通信の部屋番号 (0〜65535)

1台のサーバー上で複数のネットワークサービスを同時に稼働させるため、通信ごとに「ポート番号」で識別します。

ポート番号主な用途
22SSH（リモート接続）
80HTTP（暗号化なしWeb通信）
443HTTPS（SSL/TLS暗号化Web通信）
3000 / 8080アプリのローカル開発用ポート（Node/Next.js 等）
3306 / 5432MySQL / PostgreSQL
6379Redis
ss -tlnp               # リッスン中のポート一覧を確認
lsof -i :3000          # ポート 3000 を使用しているプロセスを特定
ポート衝突（Address already in use）初学者が最も頻繁に遭遇するエラーです。lsof -i :対象ポート で占有しているプロセスを特定し、不要なものを終了させるか設定ポートを変更します。
モジュール 1 · Linux

1.3 SSH は単なるログインではない

SSH（Secure Shell）は暗号化された安全な通信路を提供するプロトコルです。端末操作だけでなく、ポートフォワーディング、ファイル転送（SFTP/rsync）、Git 連携の基盤として機能します。

パスワード認証の廃止と公開鍵認証の徹底

パスワード認証はブルートフォース攻撃（総当たり攻撃）のリスクに常に晒されます。公開鍵暗号（Ed25519）を用いた鍵認証に切り替えることで、秘密鍵を持たない外部からの不正アクセスを物理的に遮断できます。

# /etc/ssh/sshd_config の推奨セキュリティ設定
PasswordAuthentication no
PermitRootLogin prohibit-password
PubkeyAuthentication yes

~/.ssh/config による接続設定の簡素化

ローカル PC の ~/.ssh/config に設定を記述しておくことで、ssh myserver の一撃で接続できるようになります：

Host myserver
    HostName 203.0.113.195
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519
    Port 22

1.4 パッケージマネージャー速引

Linux ではソフトウェアのインストールや更新をパッケージマネージャー（Ubuntu/Debian では apt）を通じて一元管理します。

apt update             # パッケージリストの最新化
apt upgrade -y         # インストール済みパッケージの一括更新

apt remove --purge -y nginx # 設定ファイルを含めた完全削除
モジュール 1 · Linux

1.5 権限とユーザー管理

最高権限を持つ root での常時作業は、誤操作によるシステム破壊リスクを伴います。日常作業用の一般ユーザーを作成し、必要なときのみ sudo で昇格する運用が鉄則です。

adduser deployer                 # 新規ユーザー作成
usermod -aG sudo deployer        # sudo 権限を付与
chmod 600 ~/.ssh/authorized_keys # 鍵ファイルの権限を所有者のみに制限
chown -R deployer:deployer /var/www # ディレクトリ所有者を変更
モジュール 2a · 概念基礎

2.1 HTTP → TCP → IP 階層構造

Web の通信はカプセル化されたレイヤー構造で成り立っています：

  • アプリケーション層 (HTTP/HTTPS): クライアントとサーバーがやり取りする要求（GET /api/users）と応答。
  • トランスポート層 (TCP): パケットの順序保証、再送制御、コネクション確立（3-Way Handshake）。
  • ネットワーク層 (IP): 送信元と宛先の IP アドレスに基づいたパケットのルーティング。
モジュール 2a · 概念基礎

2.2 DNS（ドメインネームシステム）

人間が理解しやすいドメイン名（例: example.com）をコンピュータが通信に使用する IP アドレス（例: 203.0.113.195）に変換する分散型名前解決システムです。

レコード種別用途設定例
Aドメインを IPv4 アドレスに紐付け@ -> 203.0.113.195
AAAAドメインを IPv6 アドレスに紐付け@ -> 2001:db8::1
CNAME別のドメインへのエイリアス（別名）www -> example.com
TXTドメイン所有権確認や SPF / DKIM メール認証v=spf1 include:...
モジュール 2a · 概念基礎

2.3 HTTPS / TLS 暗号化と証明書管理

HTTPS は HTTP 通信を TLS（Transport Layer Security）で暗号化し、盗聴や改ざん、なりすましを防ぐ仕組みです。現代のWeb標準において、HTTPS化は必須要件です。

Let's Encrypt と Certbot非営利の認証局 Let's Encrypt により、無料で正規の SSL/TLS 証明書を取得できます。Certbot を利用すれば、証明書の発行から Nginx 設定の自動書き換え、90日ごとの自動更新 Cron まで全自動で完結します。
モジュール 2a · 概念基礎

2.4 リバースプロキシ（Reverse Proxy）の役割

クライアントからのリクエストを最前線で受け付け、背後にある適切なアプリケーションサーバー（Node.js, Python, Go 等）へ中継するサーバーです（代表例: Nginx, Caddy）。

  • SSL 終端（SSL Termination）: 重い暗号化・復号処理をプロキシ側で一括処理。
  • ルーティングと負荷分散: /api はバックエンドへ、静的ファイルはディスクから直接配信。
  • セキュリティ防壁: バックエンドの実際の稼働ポートをインターネットに直接公開しない。
モジュール 2a · 概念基礎

2.5 ファイアウォールとアクセス制御

不要なポートへの外部アクセスを遮断し、必要な通信（22, 80, 443）のみを許可します。Ubuntu では ufw（Uncomplicated Firewall）を使用するのが最も直感的です。

ufw default deny incoming  # 受信通信をデフォルト遮断
ufw default allow outgoing  # 送信通信を許可
ufw allow 22/tcp            # SSH を許可（忘れると締め出されます）
ufw allow 80/tcp            # HTTP を許可
ufw allow 443/tcp           # HTTPS を許可
ufw enable                  # ファイアウォール有効化
モジュール 2a · 概念基礎

2.6 アタックサーフェス（攻撃面）の最小化

サーバーを公開した瞬間から、ボットによる自動スキャンが始まります。攻撃対象となる隙（アタックサーフェス）を最小化するための基本方針：

❌ 危険な運用データベース（MySQL 3306, Redis 6379）のポートを 0.0.0.0 で世界中に公開し、パスワード認証のみに依存する。
✅ 安全な設計DB は 127.0.0.1（ローカルループバック）にのみバインドし、外部からは SSH トンネルやプライベートネットワーク経由でのみアクセスする。

2.8 127.0.0.1 vs 0.0.0.0 バインドの違い

アプリケーション起動時のバインドアドレスの選択は、セキュリティ上極めて重要です：

  • 127.0.0.1 (localhost): サーバー内部の同一マシンからのみアクセス可能。外部からの直接通信は完全に遮断される。
  • 0.0.0.0: サーバーが持つすべてのネットワークインターフェース（パブリックIP含む）からの接続を受け付ける。

3.1 本番デプロイ 7ステップ パイプライン

  1. コードチェックアウト: サーバー上で git pull または CI/CD 上でビルド。
  2. 依存関係のインストール: npm ci や pip install -r requirements.txt。
  3. アセットのビルド: npm run build による最適化。
  4. DB マイグレーション: prisma migrate deploy 等によるスキーマ反映。

3.2 systemd によるプロセスのデーモン化と自動再起動

ターミナルを閉じてもプロセスを稼働させ続け、サーバー再起動時やクラッシュ時に自動復旧させるため、systemd ユニットファイルを作成します。

# /etc/systemd/system/myapp.service
[Unit]
Description=My Fullstack Web Application
After=network.target

[Service]
Type=simple
User=deployer
WorkingDirectory=/var/www/myapp
EnvironmentFile=/var/www/myapp/.env
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5s

[Install]
WantedBy=multi-user.target
systemctl daemon-reload
systemctl enable --now myapp   # 自動起動有効化 & 即時起動
systemctl status myapp         # 状態確認
journalctl -u myapp -f         # アプリのリアルタイムログ出力

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

3.6 シークレットと環境変数（.env）の安全管理
