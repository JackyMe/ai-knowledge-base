认识 00

Codex 全景与选型三棱镜

Codex 是 OpenAI 推出的代理式（Agentic）智能编码体系：它不仅仅是“会写代码的聊天机器人”，而是一个具备项目理解、工具调用、OS 级沙箱隔离、代码修补验证与跨平台执行能力的自主研发助手。理解 Codex 的第一步，是建立清晰的选型心智模型。

三、选型三棱镜 ②：App vs CLI vs IDE vs Cloud 怎么搭配

✅ 黄金组合推荐（大厂高效实践）
  • 需求与方案规划：在桌面 App 或 CLI 运行 /plan 摸清架构与影响面；
  • 核心代码开发：在 IDE 扩展或 CLI 交互式开发，即时看 diff；
  • 耗时长的大重构/多文件迁移：派发给 codex cloud exec --attempts 3，本地继续做其他事；
  • PR 提交前防守：触发 @codex review 自动化双审。
❌ 典型反模式（易导致低效与翻车）
  • 在普通 Web Chat 里让模型写长代码，然后人工手动一段段复制粘贴；
  • 在本地 CLI 阻塞等待一个耗时 30 分钟的大迁移任务，导致终端无法做其他工作；
  • 在没有 Git 干净工作树的情况下直接在 IDE 允许大范围全自动替换；
  • 把依赖真实浏览器验证的前端交互任务丢给无头环境纯猜。

4 条目标导向学习路线

不需要盲目从头读完所有文档。根据你当前的技术背景与核心目标，选择对应的成长路径：

🌱路线 01：零基础入门（建立安全感与闭环）TRACK 01

适合：第一次接触 Codex，或还没有独立完成过真实可回滚任务的用户。

  1. 环境就绪：完成安装，通过 codex login 登录 ChatGPT 账号；
  2. 建立安全底线：确认处于一个独立的 Git 测试分支，运行 git status 确保无脏改动；
  3. 只读探测：启动 codex --sandbox read-only，让 Codex 梳理项目结构与 README，不产生任何文件改动；
  4. 完成第一个最小可回滚任务：提出一个 15 分钟内可验证的小任务（如修复一行类型错误、加一段注释），执行后通过 /diff 审阅，本地跑测试通过后提交。
⚡路线 02：专业开发者实战（高质交付与 TDD 闭环）TRACK 02

适合：熟练掌握 Git 与至少一门后端/前端语言，追求极致开发效率的工程师。

  1. 项目记忆初始化：在仓库根目录运行 /init 生成精简 AGENTS.md，固化构建与测试命令；
  2. TDD 失败测试先行：遇到 Bug 先要求 Codex 编写复现失败的自动化测试，再执行修复至绿灯；
  3. 长任务四权分立：运用讨论（Plan）→ 执行（Exec）→ 审查（Review）→ 记忆收尾（Closeout）四步法推进复杂模块；
  4. GitHub Issue 到 PR 闭环：打通云端自动化与 @codex review 自动化评审。
🛠️路线 03：能力扩展与自动化（打造专属 AI 工具箱）TRACK 03

适合：希望把团队重复性繁重工作固化为自动化能力的研发骨干或 DevOps 工程师。

  1. Skill 开发工程化：按开放 Agent Skills 标准开发包含 SKILL.md、scripts/、references/ 的定制技能；
  2. MCP 协议双向互联：接入数据库/Sentry/Figma MCP 服务，并通过 codex mcp-server 暴露给外部代理；
  3. E2E 浏览器与登录态验收：利用内置浏览器和 CDP 协议跑通上线前的视觉与业务流截图验收；
  4. CI/CD 与脚本化调用：用 codex exec --json 接入定时任务与自动化测试流水线。
📑路线 04：非程序员/站长/PM 工作流（安全内容与数据维护）TRACK 04

适合：维护文档站、知识库、多媒体资产或数据报表的站长、PM、内容运营者。

  1. 安全受控操作：在桌面 App 或沙箱限制下操作文件，永远在备份或 Git 分支下工作；
  2. 批量多媒体/图片转换：使用成熟 Skill 批量处理图片压缩、格式转换、音视频转码与字幕校对；
  3. 结构化知识沉淀：利用 Notion 插件或 Markdown 记忆系统，将调研与业务事实直接输出为结构化数据库；
  4. 验收确认与发布：严格核对 diff 报告与渲染效果，杜绝幻觉扩散。

心法 05

核心方法论与新手避坑指南

一、真实任务的四要素法则（Goal-Context-Constraints-Done）

任务失控 90% 源于初始输入过于空泛。高质量 Prompt 必须包含四个锚点：

  • Goal (目标)：用一句话清晰定义要交付的具体结果，拒绝“帮我看看这个模块”；
  • Context (上下文)：指定核心关联文件与相关 Issue/API 文档（善用 /mention）；
  • Constraints (边界约束)：声明禁止修改的文件、不可引入的第三方库或向后兼容要求；
  • Done-when (验收标准)：给出可量化验收条件（如：某个特定单测全绿、返回特定 JSON 字段）。

二、新手最容易让任务失控的 8 大误区

协同 06

长任务工作流与多会话工程

处理耗时半小时以上的大型重构或复杂模块时，单会话从头滚到底必然导致注意力稀释与幻觉失控。Codex 的高阶打法是“四权分立”与会话分流。

一、长任务“四权分立”工作流

  1. 讨论与规划阶段 (Discuss / Plan)：在 read-only 沙箱下运行 /plan，只读分析仓库，产出详细修改方案、文件清单与风险评估。不写代码。
  2. 隔离执行阶段 (Execute)：开启新会话或子线程，挂载已确认的 Plan，给足 workspace-write 权限，按模块逐个攻克，每一步要求运行最小验证。
  3. 独立审查阶段 (Review)：另起全新会话或调用 /review，从“未参与编写的第三者”视角做健壮性、边界与安全审查。
  4. 收尾与交接阶段 (Closeout & Handover)：提取测试证据与截图，更新 DECISIONS.md 与 AGENTS.md，生成结构化 PR 描述。

二、多会话分流与协同工具箱

  • 临时侧对话 /side (/btw)：遇到疑问（如“这个库的版本号为什么锁在 2.1”）时调起侧对话，探查完毕后带着结论回到主线，主会话不增加任何中间探讨的 token 垃圾。
  • 会话分叉 codex fork：针对同一个复杂方案想尝试 A 方案（重构）与 B 方案（热修），直接从主分支分叉为两个独立线程并行验证。
  • 双机远程控制 (Remote Control)：轻薄本（MacBook Air）通过 --remote ws://... 连接常开的高配台式机/云服务器上的 Codex app-server，享受本地键盘输入与远端庞大算力。

> 【目标】为 src/auth/jwt.ts 增加 Refresh Token 滑动窗口续期逻辑。
  【上下文】请阅读 docs/auth-flow.md 和当前的 jwt.ts 代码。
  【约束】
  1. 只能修改 jwt.ts 和对应的测试文件，不可碰 routes 模块。

  【验收】
  先在 tests/auth/jwt.test.ts 写 3 个测试用例（包括并发刷新测试）。
  执行测试，直到看到全绿通过。最后做一次 /diff 给我看。

二、四大高阶场景与“绝杀”命令组合

场景最佳命令串与操作姿势为什么最优？

然后在 Codex 中输入：读取 build-error.log 并修复报错		 绝不要直接把几万行的报错粘贴到终端对话框里！这会瞬间耗尽上下文 Token，引发模型遗忘。重定向到文件让它自己读取，消耗极低且精准。

2026 极限压榨指南：OpenAI 全家桶高阶玩法与 API 兜底

如果您每年向 OpenAI 支付上千美元订阅 ChatGPT Pro (5x/20x)，却只把它当成代码补全工具，那您至少浪费了 80% 的价值。2026 年的 OpenAI 生态已经彻底分离了各个底层产品线。这篇长文汇集了海外顶尖极客博客（如 The Rundown AI、Dev.to 等）的最强实战策略，教您如何真正榨干每一分钱。

🛑 1. 揭开官方不说的隐藏限流规则

OpenAI 表面上说“按需分配”，但在系统底层，额度被严格划分为三个独立的算力池：

  • 终端代码生成池 (Codex/Cursor/Antigravity)：采用严苛的 5 小时滚动窗口。处理 1M Token 的大文件时，极其容易在 2 小时内被降级到 gpt-5.6-luna。
  • 深度研究池 (Deep Research)：拥有绝对独立的配额。Plus 每月约 25 次，Pro 每月 250+ 次。这个池子专为解决“多步搜索与千页资料整合”而生。
  • o3/Astra 思考模型池 (Thinking Mode)：限制最死。哪怕您是 Pro 用户，每天能让模型“深度思考超过 5 分钟”的次数也屈指可数。

🛠 2. 顶级工作流 SOP：AST 语法树分离与 API 兜底

这是硅谷高阶工程师每天都在使用的工作流，彻底解决“改一行代码却烧光整个工程算力”的痛点：

第一步：不要让终端读源码，让它读 AST 语法树

把几百个 .ts 文件扔给终端，是新手最容易踩的坑。最佳实践是利用 Python 或 Node 脚本，一键提取出整个工程的 AST（抽象语法树）骨架，只保留类名、函数签名和类型定义，剥离所有的具体实现代码。然后把这份 20KB 的骨架文件上传给 Web 端的 Work Projects (工作区)。这能将上下文占用降低 95%。

第二步：Web 端 Deep Research 负责“破荒”

在迁移旧工程或引入完全没用过的框架（如 Next.js 16）时：
不要： 在本地瞎试报错。
最佳做法： 在网页端触发 /Deepresearch。使用以下高阶 Prompt：
"启动深度研究：爬取官方文档的最新版本。要求输出一个严格遵循以下 JSON Schema 的迁移指南：{ 'components': [...], 'deprecated_hooks': [...] }。不要输出废话。"
拿到这绝对精准的 JSON 后，再交给本地 Codex 执行重构，确保零幻觉。

第三步：配置 API Fallback（无缝兜底防挂机）

当 Codex 触发 5 小时滚动限流时，普通人只能去喝咖啡。高手会配置 API Key 作为备用通道（Fallback）。
在 ~/.codex/config.json 中：

{
  "fallback_strategy": "api_key",
  "api_model": "gpt-5.6-turbo",
  "max_fallback_spend": 5.0
}

当订阅额度耗尽时，系统自动切到 API 计费，花几毛钱保证灵感不中断。

🎨 3. 视觉管线极限压缩（Image 2.5 转代码）

在 UI 还原时，直接把截图发给终端改 10 次，会立刻耗尽视觉解析算力。
最佳实践 (Dimensional Reduction)：在 Web 端的 GPT-6 中上传截图，输入："以资深前端架构师视角，描述这张图的所有 CSS 细节（包括 flex 关系、色号、阴影），并直接输出 Tailwind 骨架树。纯文本返回。"
随后，将生成的纯文本喂给 Codex。文本的处理速度不仅是图片的 100 倍，且几乎没有限流惩罚。
